# Как устроен набор упражнений к уроку

Спецификация для того, кто добавляет новый урок. Держись её буквально —
инструменты (`watch.sh`, `compare.py`, `make_template.py`, скилл
`/check-code`) рассчитывают именно на эту раскладку.

## Каталог

```text
learning-exercises/pNN-lNN-<slug>/
  solution.py           пишешь руками: docstring + реализация
  test_exercise.py      пишешь руками
  bench.py              пишешь руками: BENCH = {имя функции: кортеж аргументов}
  pytest.ini            копия одной строкой, см. ниже
  exercise.template.py  НЕ пишешь — генерится из solution.py
  exercise.py           НЕ коммитится — личный файл учащегося
```

`<slug>` совпадает с именем каталога урока в `phases/`. Например
`phases/01-math-foundations/06-probability-and-distributions/` даёт
`p01-l06-probability-and-distributions`.

## solution.py

Первая непустая строка docstring модуля — чистый заголовок урока
по-русски, дальше через тире слово «эталон». `make_template.py` режет
именно по этому суффиксу.

```python
"""
Вероятность и распределения — эталон.

Открывай ПОСЛЕ своих зелёных тестов.
"""
```

Обычно дальше идут 5–8 учебных функций или методов. Для сложного урока их
может быть больше, если каждая добавляет отдельный проверяемый навык. У каждой
— docstring, который целиком уедет в заготовку, поэтому он пишется для того,
кто ещё НЕ решил задачу:

- одна строка что функция делает;
- 2–3 примера `вызов  ->  результат` с реальными числами;
- где уместно — подсказка про ловушку (переполнение, деление на ноль,
  порядок аргументов), но **не решение**;
- где уместно — одна строка зачем это в AI.

Тело функции — рабочий код с комментариями «почему так, а не иначе»:
что ради скорости, что ради читаемости, какая сложность. Эти комментарии в
заготовку не попадают, их учащийся увидит только когда откроет эталон.

Только стандартная библиотека — `math`, `random`, `itertools`. Никаких
numpy: смысл упражнений в том, чтобы собрать руками.

Функции упорядочены по нарастанию, поздние опираются на ранние и вызывают
их, а не копируют формулу заново.

Константы уровня модуля (`GRID = 5`, `ACTIONS = (...)`) переносятся в
заготовку целиком — их можно импортировать из `exercise` в тестах. Раньше
`make_template.py` их терял, и заготовка падала на коллекции с `NameError`
вместо `NotImplementedError`: проверка «N failed == N passed» при этом
показывает совпадающие числа, ничего не проверяя. Если правишь генератор —
не потеряй это снова.

## test_exercise.py

```python
"""Тесты к уроку «<название>». Правь exercise.py."""

import pytest

from exercise import fn_a, fn_b   # импорт из exercise, НЕ из solution

APPROX = lambda x: pytest.approx(x, abs=1e-9)
```

Правила:

- 3–6 тестов на функцию; обычно 15–35 на урок, больше — когда набор содержит
  много независимых функций или методов;
- **имя теста называет проверяемое свойство**
  (`test_projection_residual_is_perpendicular`), потому что имя — первая
  подсказка учащемуся, когда тест краснеет;
- проверяй не только арифметику, но и смысловые свойства: что косинус не
  зависит от длины, что матрица ранга 1 склеивает два разных входа, что
  остаток проекции перпендикулярен;
- каждая ловушка из docstring должна иметь свой тест;
- `pytest.approx` **не умеет вложенные списки**. Матрицы сравнивай через
  локальный хелпер `flat(M)`, разворачивающий их в плоский список;
- у углов и всего, что идёт через `acos`, допуск не жёстче `1e-5`.

### Три ловушки, которые дают ложный зелёный

Все три тихие: набор выглядит готовым, а проверка «заготовка красная» на
самом деле не выполняется.

**1. `NotImplementedError` наследуется от `RuntimeError`.** Тест вида
`pytest.raises(RuntimeError)` пройдёт зелёным на пустой заготовке. Всегда
проверяй конкретный тип, а не родительский.

**2. Абстрактный базовый класс бросает `NotImplementedError` по замыслу.**
Тест «база отказывается считать» неотличим от заготовки, где ещё ничего не
написано. Лечится проверкой контраста: база бросает, а рабочий подкласс
считает — вторая половина краснеет на заготовке.

```python
def test_layer_forward_is_not_implemented():
    with pytest.raises(NotImplementedError):
        Layer().forward([1.0])
    assert ReLU().forward([-1.0, 2.0]) == [0.0, 2.0]   # <- без этой строки
                                                        #    тест бесполезен
```

**3. Тест проверяет только константы уровня модуля.** Константы переносятся
в заготовку целиком (см. раздел «solution.py»), поэтому тест вида
`assert DEPTH_CEILING == 2` зелёный ещё до того, как учащийся написал первую
строку. Каждый тест обязан вызвать хотя бы одну функцию. Смысл проверки при
этом сохраняется — константу не выкидывай, а привяжи к поведению:

```python
def test_the_default_ceiling_is_the_lesson_value():
    assert too_deep(DEEP, "top") == too_deep(DEEP, "top", ceiling=DEPTH_CEILING)
    assert too_deep(DEEP, "top") != too_deep(DEEP, "top", ceiling=DEPTH_CEILING + 1)
```

Эта ловушка самая частая: при авторинге фаз 16–17 она сработала пять раз в
одном заходе, включая наборы, авторы которых считали их готовыми.

## bench.py

```python
"""Входные данные для замера скорости."""

import random

random.seed(0)          # обязательно: замер должен быть воспроизводим

_data = [...]

BENCH = {"fn_a": (_data,), "fn_b": (_data, 3)}
```

Размер данных подбирается так, чтобы наивная квадратичная реализация была
заметно медленнее хорошей, но один вызов укладывался в десятки
миллисекунд. Аргументы — всегда кортеж, даже для одного.

## pytest.ini

```ini
[pytest]
addopts = -q --no-header
testpaths = .
```

## Обязательная проверка перед сдачей

```bash
cd learning-exercises/<slug>
cp solution.py exercise.py
python3 -m pytest                         # обязано быть 100% зелёным
cd ../.. && python3 learning-exercises/make_template.py <slug>
cp learning-exercises/<slug>/exercise.template.py \
   learning-exercises/<slug>/exercise.py
cd learning-exercises/<slug> && python3 -m pytest --tb=line   # обязано быть красным
```

Флаг `-q` не добавляй: он уже есть в `addopts` внутри `pytest.ini`, второй
даёт `-qq`, а тот глушит итоговую строку `N passed` — ровно ту, по которой
эта проверка и сверяется.

Оба прогона обязательны, и первый не менее важен второго. Зелёный на
эталоне доказывает, что задача решаема; красный на заготовке — что
учащемуся есть что делать. Набор, не прошедший обе проверки, не готов.
Тест, красный на самом эталоне, — это сломанный набор, а не недоделанный:
такие уже уезжали в репозиторий, потому что автор прогонял только вторую
половину.

**Числа обязаны совпасть.** `N passed` на эталоне и `N failed` на
заготовке — одно и то же N. Если на заготовке хоть один тест зелёный, он
ничего не проверяет: см. «Три ловушки» выше.

**Смотри причину падений, а не счётчики.** Заготовка, падающая на сборе
(`NameError`, `ImportError`), даёт те же совпадающие числа и при этом не
проверяет ничего. В выводе `--tb=line` каждая строка обязана заканчиваться
на `NotImplementedError`:

```bash
python3 -m pytest --tb=line | grep -E '^/.*Error' | grep -v NotImplementedError
# пусто = проверка настоящая
```

Регенерация шаблонов идемпотентна: `make_template.py` без аргумента
пересобирает все уроки, и диффа быть не должно. Если у какого-то урока
после этого шаблон изменился — значит его `solution.py` отклоняется от
соглашения, и чинить надо эталон, а не шаблон руками.
