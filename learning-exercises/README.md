# Практика: ты пишешь код, тесты его проверяют

Тесты пишу я, реализацию — ты. Красный тест говорит, что именно сломано;
зелёный — что понял.

## Быстрый путь: одна команда в чате

```text
/check-code                                   # текущий урок из LEARNING.md
/check-code p01-l01-linear-algebra-intuition  # конкретный
/check-code p01-l01                           # хватит и префикса
```

Гоняет тесты. Красные — объясняю что сломано и подсказываю направление,
дальше не иду. Все зелёные — запускаю сравнение с эталоном и разбираю твой
код словами.

Ниже — то же самое руками, если хочется держать в соседнем терминале.

## Запуск

```bash
./learning-exercises/watch.sh                                   # последний урок
./learning-exercises/watch.sh p01-l01-linear-algebra-intuition  # конкретный
```

Открой рядом `learning-exercises/p01-l01-linear-algebra-intuition/exercise.py`.
Сохранил файл — тесты перезапустились сами. Выход: `Ctrl-C`.

Разовый прогон без слежения:

```bash
cd learning-exercises/p01-l01-linear-algebra-intuition && python3 -m pytest
```

## Что где

Директория урока называется `p<фаза>-l<урок>-<slug>`: `p01-l01-...` — первый
урок первой фазы, ровно тот же номер, что в `phases/`.

```text
learning-exercises/
  watch.sh              запускалка
  p01-l01-linear-algebra-intuition/
    exercise.py         ← пишешь сюда, заглушки бросают NotImplementedError
    test_exercise.py    ← мои тесты, не трогай
    solution.py         ← эталон, открывать после своих зелёных
```

`solution.py` — не ответ, а вариант для сравнения. В нём к каждой функции
подписано, почему написано именно так: что ради скорости, что ради
читаемости, где какая сложность. Смотри туда, когда свой вариант уже
работает.

## Как читать провалившийся тест

```console
FAILED test_exercise.py::test_dot_basic
    assert dot([1, 2, 3], [4, 5, 6]) == APPROX(32)
E   assert 0 == 32 ± 1.0e-09
```

Три строки: **какой** тест упал, **что** он проверял, **что получилось против
чего ожидалось**. Имя теста — уже подсказка, что именно сломано.

## Порядок

Иди сверху вниз по `exercise.py` — функции выстроены по нарастанию, и
поздние опираются на ранние (`cosine_similarity` использует `dot` и
`magnitude`). Делай по одной, добивайся зелёного, переходи к следующей.

Застрял — спроси в чате. Подскажу направление, решение не дам.

## Сравнение с эталоном

```bash
python3 learning-exercises/compare.py p01-l01-linear-algebra-intuition
```

Показывает по каждой функции: строк, циклов, вложенность и **реальное время
работы** — твоё против эталонного, плюс прогон линтером `ruff`.

```console
функция                строк     циклов    вложен.            мкс
                 ты / эталон  ты/эталон  ты/эталон    ты / эталон
magnitude              4 / 1      1 / 1      1 / 0   19.68 / 8.92  ×2.2
dot                    4 / 1      1 / 1      1 / 0  10.04 / 11.72  ок
most_similar_pair     10 / 7      2 / 2      4 / 3    8597 / 5358  ×1.6

PERF401 Use a list comprehension to create a transformed list
SIM103  Return the condition `abs(det) > 1e-09` directly
```

Читается так: `ок` — вровень с эталоном, жёлтое `×1.7` — заметно медленнее,
красное `×2.2` — есть что чинить. Числа врут только в одну сторону: если у
тебя короче и быстрее эталона — значит правда лучше.

Метрики не приговор. Вариант на строку длиннее, но понятнее — лучше. А вот
вдвое медленнее или на два уровня глубже вложенность — повод разобраться.

## Зелёные тесты — это половина

Когда всё позеленело, скажи в чате — я прочитаю твой `exercise.py` и разберу
**как** он написан. Тесты ловят только правильность. Отдельно смотрю на:

- лишние проходы по данным — два цикла там, где хватает одного;
- вычисление внутри цикла того, что не меняется от итерации;
- `range(len(x))` там, где можно идти прямо по элементам;
- ручной накопитель вместо генератора — длиннее и легче сломать;
- квадратичная работа, спрятанная во вложенном цикле;
- повтор логики, которую ты уже написал функцией выше — вызови её.

Код, проходящий тесты, но неоптимальный — это замечание, а не успех.
