# Capstone 09 — Агент миграции кода (обновление языка или рантайма в масштабе репозитория)

> MigrationBench от Amazon (Java 8 в Java 17) и мигратор Google App Engine с Py2 на Py3 задают планку 2026 года. OpenRewrite от Moderne делает детерминированные переписывания по AST в промышленном масштабе. Grit решает ту же задачу через DSL в стиле codemod. Продакшен-схема совмещает оба подхода: детерминированная основа для безопасных правок плюс слой агента для неоднозначных случаев, песочница для сборки каждой ветки и тестовый прогон, который должен позеленеть до открытия PR. Задача капстоуна — мигрировать 50 реальных репозиториев и опубликовать долю успеха вместе с таксономией отказов.

**Type:** Capstone
**Languages:** Python (agent), Java / Python (targets), TypeScript (dashboard)
**Prerequisites:** Phase 5 (NLP), Phase 7 (transformers), Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 15 (autonomous), Phase 17 (infrastructure)
**Phases exercised:** фазы P5 · P7 · P11 · P13 · P14 · P15 · P17
**Time:** 30 hours

> 🎒 **На пальцах.** Здесь есть роскошь, которой нет у большинства AI-задач: правильный ответ проверяется машиной. Тесты позеленели — миграция удалась, не позеленели — нет, спорить не о чем. Это как задача по арифметике с ответом в конце учебника, только ответ считает CI.

## Problem

Массовая миграция кода — одно из самых чистых продакшен-применений кодовых агентов 2026 года. Истина здесь очевидна (проходит ли набор тестов после миграции?), выгода реальна (миграция парка сервисов с Java 8 — проект масштаба целого отдела), а бенчмарки публичны (подмножество MigrationBench из 50 репозиториев). OpenRewrite от Moderne закрывает детерминированную часть. Слой агента берёт всё, что рецептам OpenRewrite не по зубам: неоднозначные переписывания, расхождения в системе сборки, длинный хвост синтаксиса, поломки транзитивных зависимостей.

> 🎒 **На пальцах.** Разделение труда тут как в ремонте: типовые розетки меняет по инструкции подмастерье, а с проводкой, которая идёт непонятно куда, разбирается мастер. Рецепты дешёвые, детерминированные и всегда одинаковые; агент дорогой, но справляется с тем, чего в инструкции нет. Экономика проекта держится на том, чтобы мастера звали как можно реже.

Вы построите агента, который берёт репозиторий на Java 8 (или на Python 2) и выдаёт мигрированную ветку с зелёным CI. Вы измерите долю успеха, сохранность покрытия тестами, стоимость на репозиторий и соберёте таксономию отказов. Сравнение бок о бок с базовой линией «только детерминированные рецепты» покажет, где именно живёт ценность агента.

> 🎒 **На пальцах.** Базовая линия здесь обязательна: без неё вы не отличите работу агента от работы рецептов. Если рецепты сами дают 60% успеха, а полный пайплайн — 78%, то вклад агента ровно 18 процентных пунктов, и за них вы платите деньгами и временем. Без такого замера легко купить дорогую LLM ради того, что и так делал бесплатный инструмент.

## Concept

В пайплайне два слоя. **Детерминированная основа** (OpenRewrite для Java, libcst для Python) безопасно выполняет основную массу механических переписываний: импорты, сигнатуры методов, правки на null-безопасность, try-with-resources, замену устаревших API. Она быстрая и даёт диффы, которые можно проверить глазами. **Слой агента** (OpenAI Agents SDK или LangGraph поверх Claude Opus 4.7 и GPT-5.4-Codex) разбирается с тем, чего рецепты не умеют: обновления файлов сборки (Maven/Gradle/pyproject), конфликты транзитивных зависимостей, нестабильные тесты, самописные аннотации.

> 🎒 **На пальцах.** Детерминированный слой правит дерево кода (AST), а не текст, поэтому он не может случайно испортить строку внутри комментария. Как замена детали по чертежу: результат предсказуем и повторяем на любом репозитории. Агент же работает догадками — мощно, но проверять за ним надо всегда.

Каждый репозиторий получает песочницу Daytona с уже установленным целевым рантаймом. Агент крутит цикл: собрать, классифицировать ошибки, применить правку, пересобрать. Жёсткие лимиты: 30 минут на репозиторий, 8 долларов на репозиторий, 20 ходов агента. Если все тесты проходят и покрытие не упало, ветка отправляется в PR. Если нет — репозиторий попадает в класс отказа вместе с доказательствами.

> 🎒 **На пальцах.** Считайте потолок расходов: 50 репозиториев по 8 долларов — это максимум 400 долларов за весь прогон, и вы знаете это заранее. Лимит в 20 ходов нужен ещё и потому, что агент, который не справился за 20 попыток, на 21-й обычно тоже не справляется — он просто ходит по кругу. Как таймер у духовки: не готово за час — доставайте и разбирайтесь, а не ждите вечно.

Таксономия отказов — вот главный результат. Что сломалось на 50 репозиториях? Транзитивные зависимости? Самописные аннотации? Версия сборщика? Нестабильные тесты, не связанные с миграцией? У каждого класса есть счётчик и показательный дифф. Авторы будущих рецептов смогут прицелиться в первую тройку.

> 🎒 **На пальцах.** Таксономия превращает 50 отдельных провалов в 5-6 понятных причин с числами: например, «конфликты зависимостей — 12 репозиториев, самописные аннотации — 7». Написать один рецепт на 12 случаев дешевле, чем чинить 12 репозиториев руками. Это как разбор жалоб в сервисе: чинят не каждую жалобу отдельно, а главную причину.

## Architecture

```
target repo
      |
      v
OpenRewrite / libcst deterministic recipes
   (safe, fast, auditable, ~70-80% of fixes)
      |
      v
Daytona sandbox per branch
      |
      v
agent loop (Claude Opus 4.7 / GPT-5.4-Codex):
   - run build -> capture failures
   - classify failures (build, test, lint)
   - apply fix (patch or retry recipe)
   - rerun
   - budget: 30 min, $8, 20 turns
      |
      v
test + coverage delta gate
      |
      v (passed)
open PR
      |
      v (failed)
file under failure class + attach repro
```

> 🎒 **На пальцах.** Схема ветвится в конце: зелёная ветка идёт в PR, красная — в класс отказа с приложенным способом воспроизведения. Никакого третьего пути вроде «почти получилось» нет, и это принципиально. Именно поэтому 70-80% правок отдают рецептам ещё до входа в цикл агента — чем меньше остаётся агенту, тем чаще ветка зелёная.

## Stack

- Deterministic substrate: OpenRewrite (Java) или libcst (Python)
- Agent: OpenAI Agents SDK или LangGraph поверх Claude Opus 4.7 + GPT-5.4-Codex
- Sandbox: devcontainer Daytona на каждую ветку, целевой рантайм уже установлен (Java 17 / Python 3.12)
- Build systems: Maven, Gradle, uv (Python)
- Benchmarks: подмножество Amazon MigrationBench из 50 репозиториев (Java 8 в 17), репозитории Google App Engine с Py2 на Py3
- Test harness: параллельный раннер, покрытие через Jacoco (Java) или coverage.py (Python)
- Observability: Langfuse плюс пакет трейсов на каждый репозиторий со всеми кусками диффа
- Dashboard: дашборд таксономии отказов со счётчиками по классам и показательными диффами

```figure
ce-migration-funnel
```

> 🎒 **На пальцах.** Отдельная песочница на ветку нужна затем, чтобы Java 17 из одного репозитория не встретилась с Java 8 из соседнего. Как отдельная разделочная доска для рыбы и для овощей: дешевле завести вторую, чем потом объяснять вкус. Плюс упавшая сборка не может испортить машину — песочницу просто выкидывают.

## Build It

1. **Recipe pass.** Сначала прогоните рецепты OpenRewrite (Java) или libcst (Python). Они забирают те 70-80% миграций, которые чисто механические. Зафиксируйте это отдельным коммитом «recipe».

2. **Build trial.** Песочница Daytona: ставим целевой рантайм, запускаем сборку. Зелёная — сразу к тестам. Красная — передаём агенту.

3. **Agent loop.** LangGraph с инструментами: `run_build`, `read_file`, `edit_file`, `run_test`, `git_diff`. Агент классифицирует ошибку (зависимость, синтаксис, тест, сборщик) и применяет точечную правку. Пересборка.

4. **Budget caps.** 30 минут реального времени на репозиторий, 8 долларов, 20 ходов агента. Любое превышение останавливает работу и заводит запись «budget_exhausted» с текущим диффом.

5. **Test + coverage gate.** Когда сборка позеленела, прогоните набор тестов. Сравните покрытие с исходным репозиторием. Если покрытие упало больше чем на 2%, заводите «coverage_regression».

6. **PR open.** При успехе запушьте ветку и откройте PR с диффом и кратким описанием: какие рецепты сработали и какие коммиты написал агент.

7. **Failure taxonomy.** Каждому упавшему репозиторию присвойте класс: `dep_upgrade_required`, `build_tool_drift`, `custom_annotation`, `test_flake`, `syntax_edge_case`, `budget_exhausted`. Соберите дашборд.

8. **50-repo run.** Прогоните всё подмножество MigrationBench. Отчитайтесь по доле успеха в разрезе классов, стоимости на репозиторий, сохранности покрытия и сравнению с базовой линией «только детерминированные рецепты».

> 🎒 **На пальцах.** Шаг 5 ловит хитрый вид жульничества: тесты можно «починить», просто удалив те, что мешают. Порог в 2% на падение покрытия закрывает эту лазейку — если из 412 тестов агент тихо выкинул десяток, покрытие просядет и гейт не пропустит ветку. Зелёный CI без покрытия — это как пустая ведомость с одними пятёрками.

## Use It

```
$ migrate legacy-java-service --target java17
[recipe]   27 rewrites applied (JUnit 4->5, HashMap initializer, try-with-resources)
[build]    FAIL: cannot find symbol sun.misc.BASE64Encoder
[agent]    turn 1 classify: removed_jdk_api
[agent]    turn 2 apply: sun.misc.BASE64Encoder -> java.util.Base64
[build]    OK
[tests]    412/412 passing; coverage 84.1% -> 84.3%
[pr]       opened #1841  cost=$3.20  turns=4
```

> 🎒 **На пальцах.** Разберите лог: 27 правок сделали рецепты бесплатно, а агенту досталась ровно одна проблема — исчезнувший из JDK класс `sun.misc.BASE64Encoder`, и он закрыл её за 2 хода из 20 разрешённых. Итог: 412 из 412 тестов зелёные, покрытие даже выросло с 84,1% до 84,3%, счёт — 3,20 доллара при лимите в 8. Так и выглядит здоровый прогон: дорогой агент включился на минуту, а не на полчаса.

## Ship It

`outputs/skill-migration-agent.md` — это и есть результат. Получив репозиторий, он выполняет детерминированные рецепты, затем цикл агента и выдаёт зелёную мигрированную ветку — либо заводит репозиторий в класс таксономии.

| Weight | Criterion | How it is measured |
|:-:|---|---|
| 25 | MigrationBench pass rate | pass@1 на подмножестве из 50 репозиториев |
| 20 | Test-coverage preservation | Среднее изменение покрытия относительно исходного репозитория |
| 20 | Cost per migrated repo | $/репозиторий на успешных прогонах |
| 20 | Agent / deterministic-tool integration | Доля правок, сделанных OpenRewrite, против написанных агентом |
| 15 | Failure analysis write-up | Полнота таксономии с показательными примерами |
| **100** | | |

> 🎒 **На пальцах.** Обратите внимание на четвёртый критерий: 20 очков дают за долю правок, сделанных детерминированным инструментом. То есть система, где агент делает всё сам, оценивается хуже, чем та, где он делает только сложное. Дешёвый и предсказуемый инструмент выигрывает у умного везде, где задача типовая.

## Exercises

1. Прогоните пайплайн миграции только на OpenRewrite, без агента. Сравните долю успеха с полным пайплайном. Найдите случаи, где разницу делает исключительно агент.

2. Реализуйте проверку «lint-clean»: после миграции запускайте стилевой линтер (spotless для Java, ruff для Python). Валите PR, если появились новые замечания. Измерьте, как часто покрытие сохраняется, а стиль деградирует.

3. Добавьте оптимизатор «minimal-diff»: после того как ветка агента прошла тесты, вторым проходом уберите лишние изменения. Отчитайтесь, насколько уменьшился дифф.

4. Расширьте на третью миграцию: Node 18 в Node 22. Переиспользуйте обвязку песочницы; замените слой рецептов на свой codemod.

5. Измерьте время до первой зелёной сборки (TTFGB) как UX-метрику. Цель: p50 меньше 10 минут.

> 🎒 **На пальцах.** Упражнение 3 про размер диффа — это про людей, а не про машины. Дифф на 40 строк ревьюер прочитает за пять минут, дифф на 400 строк с лишними переформатированиями отложит на завтра. Агент, который трогает только нужное, реально ускоряет миграцию, даже если тесты в обоих случаях зелёные.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Deterministic substrate | «Движок рецептов» | OpenRewrite / libcst: декларативные переписывания AST с гарантиями безопасности |
| Codemod | «Программа, меняющая код» | Правило переписывания, которое механически меняет исходный код |
| Build drift | «Расхождение версий инструментов» | Незаметные изменения поведения Maven / Gradle / uv между мажорными версиями |
| Failure class | «Корзина таксономии» | Помеченная причина, по которой репозиторий не мигрировал: зависимость, синтаксис, тест, сборщик, бюджет |
| Coverage delta | «Сохранность покрытия» | Изменение процента покрытия тестами от исходной ветки к мигрированной |
| Agent turn | «Раунд вызова инструментов» | Один цикл план -> действие -> наблюдение внутри агентного цикла |
| Budget exhaustion | «Упёрлись в потолок» | Репозиторий исчерпал свои 30 минут / 8 долларов / 20 ходов и не прошёл |

> 🎒 **На пальцах.** Один ход агента (agent turn) — это план, действие и наблюдение: например, «запустить сборку», прочитать ошибку, решить, что делать дальше. В логе выше их было 4 при лимите 20, то есть агент уложился в пятую часть бюджета. Считайте ходы так же, как минуты в разговоре: чем меньше их нужно на понятную проблему, тем лучше устроен агент.
