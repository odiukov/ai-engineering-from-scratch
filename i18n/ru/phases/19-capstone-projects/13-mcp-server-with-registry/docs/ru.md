# Capstone 13 — MCP-сервер с реестром и governance

> Model Context Protocol перестал быть будущим и стал стандартной спецификацией использования инструментов в 2026 году. Anthropic, OpenAI, Google и все крупные IDE поставляют MCP-клиентов. Pinterest опубликовал свою внутреннюю экосистему MCP-серверов. Реестр AAIF формализовал метаданные о возможностях по адресу `.well-known`. AWS ECS выпустил эталонный stateless-деплой. goose-agent от Block положил тот же протокол внутрь хостируемого ассистента. Продакшен-форма 2026 года выглядит так: транспорт StreamableHTTP, скоупы OAuth 2.1, воротца политик на OPA и реестр, который позволяет платформенным командам находить, валидировать и включать серверы. Соберите это от начала до конца.

**Type:** Capstone
**Languages:** Python (server, via FastMCP) or TypeScript (@modelcontextprotocol/sdk), Go (registry service)
**Prerequisites:** Phase 11 (LLM engineering), Phase 13 (tools and MCP), Phase 14 (agents), Phase 17 (infrastructure), Phase 18 (safety)
**Phases exercised:** фазы P11 · P13 · P14 · P17 · P18
**Time:** 25 hours

> 🎒 **На пальцах.** MCP — это USB-C для инструментов: один разъём, и в него втыкается что угодно. В этом проекте вы делаете не один инструмент, а целую розетку на 10 гнёзд плюс каталог, по которому платформенная команда понимает, что вообще воткнуто.

## Problem

MCP стал общим языком для вызова инструментов. Claude Code, Cursor 3, Amp, OpenCode, Gemini CLI и любой управляемый агент теперь потребляют MCP-серверы. Продакшен-сложность не в том, чтобы написать сервер (с FastMCP это просто), а в том, чтобы развернуть его на масштабе с корпоративными требованиями: скоупы OAuth на каждого арендатора, политика OPA на разрушительные инструменты, stateless-масштабирование через StreamableHTTP, реестр для поиска, аудит-логи на каждый вызов инструмента. Внутренняя экосистема MCP в Pinterest и спецификация реестра AAIF задают планку 2026 года.

> 🎒 **На пальцах.** Написать сервер и эксплуатировать сервер — это как испечь пирог и открыть пекарню. Пирог у вас выйдет за вечер на FastMCP. Пекарня требует пропусков, журнала, кто что взял, и полки, на которой видно весь ассортимент.

Вы соберёте MCP-сервер с 10 внутренними инструментами (read-only Postgres, листинг S3, Jira, Linear, Datadog и так далее), UI реестра для платформенного поиска и воротца с человеческим подтверждением для разрушительных инструментов. Нагрузочный тест демонстрирует горизонтальное масштабирование StreamableHTTP. Аудит-след проходит корпоративное ревью безопасности.

## Concept

MCP-ревизия 2026 года предписывает StreamableHTTP как транспорт по умолчанию. В отличие от прежней формы со stdio и SSE, StreamableHTTP по умолчанию stateless: единственный HTTP-эндпоинт принимает JSON-RPC-запросы, стримит ответы и поддерживает долгоживущие соединения для уведомлений. Stateless означает горизонтальную масштабируемость за балансировщиком.

> 🎒 **На пальцах.** Stateless — это гардероб без номерков: любой сотрудник обслужит вас одинаково, потому что всё нужное вы приносите с собой в запросе. Поэтому реплику номер два можно поднять за минуту и балансировщик просто начнёт слать ей половину трафика — переучивать её не нужно.

Авторизация — OAuth 2.1 со скоупами на каждый инструмент. Токен несёт скоупы вроде `jira:read`, `s3:list`, `postgres:query:readonly`. MCP-сервер проверяет скоупы в момент вызова инструмента, а не только на старте сессии. Для инструментов повышенного риска сервер отклоняет любой вызов, чей скоуп не был поднят до `approved:by:human` за последние N минут — это повышение приходит из карточки ревью в Slack.

> 🎒 **На пальцах.** Скоуп — это отметка в пропуске: `postgres:query:readonly` пускает читать и не пускает писать. А `approved:by:human` — как разовый пропуск с истекающим сроком: подписали в Slack, и 15 минут дверь открыта, потом снова закрыта.

Реестр — отдельный сервис. Каждый MCP-сервер отдаёт документ `.well-known/mcp-capabilities` со своим манифестом инструментов, URL транспорта и требованиями к авторизации. Реестр опрашивает серверы, валидирует и индексирует. Платформенные команды через UI реестра видят, какие инструменты доступны, какие скоупы им нужны и какие команды ими владеют.

> 🎒 **На пальцах.** `.well-known/mcp-capabilities` — это меню на двери кафе: не заходя внутрь, видно, что подают и по какой цене. Реестр обходит все двери по расписанию, переписывает меню к себе и даёт по ним поиск.

## Architecture

```
MCP client (Claude Code, Cursor 3, ...)
          |
          v
StreamableHTTP over HTTPS (JSON-RPC + streaming)
          |
          v
MCP server (FastMCP) behind load balancer
          |
   +------+------+---------+----------+------------+
   v             v         v          v            v
Postgres    S3 listing  Jira       Linear     Datadog
(read-only) (paged)     (read)     (read)     (query)
          |
   +------+-------------+
   v                    v
 OPA policy gate   destructive tool MCP (separate server)
                        |
                        v
                   human approval via Slack
                        |
                        v
                   audit log (append-only, per-tenant)

  registry service
     |
     v  GET /.well-known/mcp-capabilities from each server
     v
     UI: search / validate / enable-disable / ownership
```

> 🎒 **На пальцах.** Проследите на схеме путь разрушительного вызова: он не идёт вместе с остальными пятью, а сворачивает на отдельный MCP-сервер, оттуда в Slack к человеку и только потом в append-only аудит. Пять читающих инструментов идут прямо — их никто не подписывает.

## Stack

- Фреймворк сервера: FastMCP (Python) или `@modelcontextprotocol/sdk` (TypeScript)
- Транспорт: StreamableHTTP поверх HTTPS (stateless)
- Авторизация: OAuth 2.1 с workload identity через SPIFFE / SPIRE
- Политики: правила OPA / Rego на каждый инструмент; сервис принятия решений на каждый запрос
- Реестр: собственный хостинг, потребляет манифесты `.well-known/mcp-capabilities`
- Человеческое подтверждение: интерактивное сообщение в Slack для разрушительных инструментов
- Деплой: AWS ECS Fargate или Fly.io, по серверу на арендатора либо общий сервер со скоупингом по арендатору
- Аудит: структурированный JSONL в бакет на каждого арендатора, с происхождением каждого вызова

> 🎒 **На пальцах.** SPIFFE / SPIRE выдают паспорт не человеку, а процессу: контейнер доказывает, кто он, и уже под это получает OAuth-токен. Пароля в переменной окружения при этом нет вообще — красть нечего.

## Build It

1. **Tool surface.** Выставьте 10 внутренних инструментов: read-only запрос в Postgres, листинг объектов S3, поиск и чтение в Jira, поиск и чтение в Linear, запрос метрик Datadog, поиск дежурного в PagerDuty, read-only GitHub, поиск в Notion, поиск в Slack, чтение Salesforce. У каждого инструмента типизированная схема и метка скоупа.

2. **FastMCP server.** Смонтируйте инструменты. Настройте транспорт StreamableHTTP. Добавьте middleware для интроспекции OAuth-токена и проверки скоупов.

> 🎒 **На пальцах.** Десять инструментов — это десять схем и десять меток скоупа, то есть 20 штук, которые нужно держать в порядке. Заведите их одним списком в коде: забыли метку у одного — и он поедет наружу вообще без ограничений.

3. **OPA policy.** Политика Rego на каждый инструмент: какие скоупы разрешают вызов, какая редакция PII применяется, какие ограничения на размер полезной нагрузки. Сервис решений вызывается на каждом обращении к инструменту.

4. **Registry service.** Отдельный сервис на Go или TS, который опрашивает `.well-known/mcp-capabilities` у зарегистрированных серверов, валидирует их по JSON Schema и отдаёт UI со списком, поиском, валидацией и включением-выключением.

5. **Capability manifest.** Каждый сервер отдаёт `.well-known/mcp-capabilities` со списком инструментов, требованиями к авторизации, URL транспорта, командой-владельцем и SLO.

> 🎒 **На пальцах.** OPA — это охранник, который держит правила отдельно от кода сервера. Хотите завтра запретить запросы больше 1 МБ — правите файл Rego, а не пересобираете сервер и не выкатываете новую версию всех десяти инструментов.

6. **Destructive tool separation.** Инструменты, меняющие состояние (создание задачи в Jira, создание задачи в Linear, запись в Postgres), живут на втором MCP-сервере со строгим потоком авторизации: у токена должен быть скоуп `approved:by:human`, поднятый через карточку в Slack не более 15 минут назад.

7. **Audit log.** Append-only JSONL на каждого арендатора: `{timestamp, user, tool, args_redacted, response_redacted, outcome}`. Редакция PII через Presidio перед записью.

> 🎒 **На пальцах.** В аудит-записи ровно шесть полей, и два из них — с суффиксом `_redacted`: аргументы и ответ пишутся уже без персональных данных. То есть даже если журнал утечёт целиком, оттуда нельзя вытащить ни email, ни телефон — только кто, что и чем закончилось.

8. **Load test.** 100 одновременных клиентов на StreamableHTTP. Продемонстрируйте горизонтальное масштабирование, добавив вторую реплику; покажите, как балансировщик перераспределяет нагрузку без прилипания сессий.

9. **Conformance tests.** Прогоните официальный набор conformance-тестов MCP против обоих серверов. Пройдите все обязательные разделы.

> 🎒 **На пальцах.** 100 клиентов на одну реплику — это 100 клиентов; добавили вторую — стало по 50 на каждую, и задержка должна упасть примерно вдвое. Если не упала, значит где-то живёт состояние и балансировщик на самом деле возвращает клиента на тот же сервер.

## Use It

```
$ curl -H "Authorization: Bearer eyJhbGc..." \
       -X POST https://mcp.internal.example.com/ \
       -d '{"jsonrpc":"2.0","method":"tools/call",
            "params":{"name":"postgres.readonly","arguments":{"sql":"SELECT 1"}}}'
[registry]   capability validated: postgres.readonly v1.2
[policy]    scope postgres:query:readonly present; allowed
[audit]     logged: user=u42 tool=postgres.readonly outcome=ok
response:    { "result": { "rows": [[1]] } }
```

> 🎒 **На пальцах.** Прочитайте четыре строки лога как четыре поста охраны: реестр подтвердил, что такой инструмент версии 1.2 вообще существует, политика нашла нужный скоуп, аудит записал факт вызова, и только после этого пришёл ответ. Уберите любую из трёх строк — и корпоративное ревью безопасности вы не пройдёте.

| Weight | Criterion | How it is measured |
|:-:|---|---|
| 25 | Соответствие спецификации | StreamableHTTP и манифест возможностей проходят conformance-тесты MCP |
| 20 | Безопасность | Проверка скоупов, покрытие OPA на каждом инструменте, гигиена секретов |
| 20 | Наблюдаемость | Аудит-лог на каждый вызов инструмента с редакцией PII |
| 20 | Масштаб | Демонстрация горизонтального масштабирования под нагрузкой в 100 клиентов |
| 15 | UX реестра | Сценарий «найти / провалидировать / включить-выключить» |
| **100** | | |

> 🎒 **На пальцах.** Сложите веса: 25 + 20 + 20 + 20 + 15 = 100, и заметьте, что на «работает вообще» приходится только 25. Остальные 75 баллов — за то, что вокруг работающего сервера: безопасность, аудит, масштаб и удобство поиска.

## Exercises

1. Добавьте новый инструмент (поиск в Confluence). Проведите его через поток валидации реестра, не трогая основной сервер.

2. Напишите политику OPA, которая скрывает результаты запросов к Postgres, содержащие колонки с именами `email`, `ssn` или `phone`. Проверьте пробным запросом.

3. Сравните задержку StreamableHTTP и stdio локально. Отчитайтесь по p50/p95 на вызов.

4. Реализуйте квоту на арендатора: максимум N вызовов в минуту на инструмент на арендатора. Обеспечьте вторым правилом OPA.

5. Прогоните conformance-набор MCP из [mcp-conformance-tests](https://github.com/modelcontextprotocol/conformance) и исправьте каждый провал.

> 🎒 **На пальцах.** Первое упражнение — главная проверка всей затеи: если ради одиннадцатого инструмента приходится пересобирать сервер, реестр вы построили зря. Хорошая архитектура здесь означает «добавили манифест, реестр подхватил, платформа увидела».

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| StreamableHTTP | «транспорт MCP 2026 года» | Stateless HTTP плюс стриминг; заменяет SSE и stdio для сетевых серверов |
| Capability manifest | «well-known-документ» | `.well-known/mcp-capabilities` со списком инструментов, авторизацией, URL транспорта |
| OPA / Rego | «движок политик» | Open Policy Agent для авторизации вызовов инструментов по внешним правилам |
| Scope elevation | «подтверждено человеком» | Короткоживущий скоуп, выданный через подтверждение в Slack; обязателен для разрушительных инструментов |
| Registry | «поиск инструментов» | Сервис, индексирующий MCP-серверы по их манифестам возможностей |
| Workload identity | «SPIFFE / SPIRE» | Криптографическая идентичность сервиса для выпуска OAuth-токенов |
| Conformance suite | «тесты по спеке» | Официальный набор тестов MCP на корректность StreamableHTTP и манифеста инструментов |

> 🎒 **На пальцах.** Обратите внимание на разрыв между колонками: в разговоре говорят «well-known-документ», а на деле это конкретный URL `.well-known/mcp-capabilities`, который реестр обходит по расписанию. Знать точный путь важнее, чем знать жаргон, — по нему вы отладите реестр curl-ом за минуту.
