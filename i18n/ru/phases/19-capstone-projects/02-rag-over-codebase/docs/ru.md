# Капстоун 02 — RAG по кодовой базе (семантический поиск через репозитории)

> В 2026 году любая серьёзная инженерная организация держит внутренний поиск по коду, который понимает смысл, а не только строки. Sourcegraph Amp, ответы по кодовой базе в Cursor, корпоративный граф Augment, repomap в Aider, внутренний MCP в Pinterest — форма у всех одна. Затянуть много репозиториев, разобрать их через tree-sitter, посчитать embedding для чанков уровня функций и классов, искать гибридно, переранжировать, ответить со ссылками. Этот капстоун просит собрать такую систему на 2 миллиона строк кода в 10 репозиториях так, чтобы она переживала инкрементальную переиндексацию на каждый git push.

**Type:** Capstone
**Languages:** Python (ingestion), TypeScript (API + UI)
**Prerequisites:** Phase 5 (NLP foundations), Phase 7 (transformers), Phase 11 (LLM engineering), Phase 13 (tools), Phase 17 (infrastructure)
**Phases exercised:** фазы P5 · P7 · P11 · P13 · P17
**Time:** 30 hours

## Problem

К 2026 году каждый фронтирный кодовый агент везёт с собой слой retrieval по кодовой базе, потому что одними контекстными окнами вопросы «через несколько репозиториев» не решаются. Контекст на миллион токенов у Claude помогает, но не отменяет ранжированный поиск. Наивный косинусный поиск по сырым чанкам отравляет выдачу на сгенерированном коде, на дублях внутри монорепозитория и на длинном хвосте редко импортируемых символов. Продакшен-ответ — гибридный поиск (dense + BM25) по чанкам, нарезанным с оглядкой на AST, с реранкером и графом ссылок между символами за спиной.

> 🎒 **На пальцах.** Наивный косинусный поиск похож на поиск книги по общему настроению обложки: сгенерированный boilerplate «выглядит» релевантным почти для любого запроса. Отсюда и связка dense + BM25: векторы ловят смысл, а BM25 — точное имя `AbortMultipartOnFail`, которое ни в какой embedding толком не помещается.

Учатся этому, индексируя настоящий парк репозиториев — не один туториальный, — и меряя MRR@10, верность цитат и свежесть после инкрементального обновления. Отказы здесь инфраструктурные: монорепозиторий на 100 тысяч файлов, пуш, который трогает половину файлов, запрос, для правильного ответа на который надо пройти через четыре репозитория.

> 🎒 **На пальцах.** Прикиньте масштаб: 100 тысяч файлов, в среднем по 5 функций на файл — это полмиллиона чанков. Полная переиндексация на каждый пуш означает полмиллиона вызовов embedding; при 100 чанках в секунду это почти полтора часа. Отсюда всё требование инкрементальности: пересчитывать надо десятки чанков, а не сотни тысяч.

## Concept

Конвейер загрузки с оглядкой на AST разбирает каждый файл через tree-sitter, вытаскивает узлы функций и классов и режет по границам узлов, а не по фиксированным окнам токенов. У каждого чанка три представления: плотный embedding (Voyage-code-3 или nomic-embed-code), разреженные термы BM25 и короткая сводка на естественном языке. Сводка добавляет третью модальность для поиска — пользователь спрашивает «как здесь устроена авторизация», и сводка упоминает «authz», даже если в коде есть только `check_permission`.

> 🎒 **На пальцах.** Резать по границам узлов AST — это как резать пирог по кускам начинки, а не по линейке: функция целиком остаётся в одном чанке, а не разваливается посреди тела. Третье представление, сводка, чинит разрыв словаря: слова «авторизация» в коде нет вообще, но оно есть в предложении, которое Haiku написал про эту функцию.

Retrieval гибридный. Запрос запускает и плотный поиск, и BM25, объединяет top-k и отдаёт объединение кросс-энкодерному реранкеру (Cohere rerank-3 или bge-reranker-v2-gemma-2b). Переранжированный список уходит в синтезатор с длинным контекстом (Claude Sonnet 4.7 с prompt caching или Llama 3.3 70B на своих серверах) с инструкцией подкреплять каждое утверждение ссылкой на файл и диапазон строк. Ответы без ссылок отбрасывает пост-фильтр.

> 🎒 **На пальцах.** Реранкер работает как второй тур собеседования: первый этап дёшево отбирает 50 кандидатов из полумиллиона, второй дорого и внимательно смотрит на каждую пару «запрос — кандидат» и оставляет 10. Гонять кросс-энкодер сразу по всей базе нельзя — это 500 тысяч прогонов модели на один вопрос вместо пятидесяти.

Инкрементальная свежесть — вот где начинается инфраструктурная задача. Git push запускает разбор диффа: какие файлы изменились, какие символы изменились. Пересчитываются embedding только у затронутых чанков. Пересчитываются затронутые межфайловые рёбра символов (импорты, вызовы методов). Индекс остаётся согласованным без перемалывания 2 миллионов строк на каждый коммит.

> 🎒 **На пальцах.** Разница как между «перепечатать весь телефонный справочник» и «заклеить одну строчку». Пуш на 50 файлов трогает, скажем, 200 функций — это 200 embedding вместо полумиллиона, то есть в 2500 раз меньше работы, и целевые 60 секунд из шага 8 становятся достижимыми.

## Architecture

```
git push --> webhook --> ingest worker (LlamaIndex Workflow)
                           |
                           v
             tree-sitter parse + AST chunk
                           |
            +--------------+----------------+
            v              v                v
          dense        BM25 index       summary (LLM)
        (Voyage / bge)  (Tantivy)        (Haiku 4.5)
            |              |                |
            +------> Qdrant / pgvector <----+
                            |
                            v
                      symbol graph (Neo4j / kuzu)
                            |
  query --> LangGraph agent (retrieve -> rerank -> synth)
                            |
                            v
                 Claude Sonnet 4.7 1M context
                            |
                            v
                 answer + file:line citations
```

> 🎒 **На пальцах.** Схема делится на две половины: всё до Qdrant происходит по пушу и офлайн, всё от `query` — вживую и за секунды. Заметьте развилку на три ветки после парсинга: один и тот же чанк идёт в векторы, в BM25 и в LLM за сводкой, то есть хранится трижды в трёх разных видах. Граф символов стоит сбоку и нужен, чтобы дотянуться из одного репозитория в другой.

## Stack

- Парсинг: tree-sitter с грамматиками 17 языков (Python, TS, Rust, Go, Java, C++ и другие)
- Плотные embedding: Voyage-code-3 (хостится) или nomic-embed-code-v1.5 (на своих серверах), bge-code-v1 как запасной
- Разреженный индекс: Tantivy (Rust) с BM25F, вес поля у имени символа выше, чем у тела
- Векторная база: Qdrant 1.12 с гибридным поиском либо pgvector + pgvectorscale для команд с объёмом до 50 млн векторов
- Модель для сводок чанков: Claude Haiku 4.5 или Gemini 2.5 Flash, с кешированием промпта
- Реранкер: Cohere rerank-3 или bge-reranker-v2-gemma-2b на своих серверах
- Оркестрация: LlamaIndex Workflows на загрузке, LangGraph на агенте запросов
- Синтезатор: Claude Sonnet 4.7 (контекст 1M) с кешированием промпта
- Граф символов: Neo4j (управляемый) или kuzu (встроенный) для рёбер импортов и вызовов
- Наблюдаемость: спаны Langfuse на каждый шаг retrieval и синтеза

> 🎒 **На пальцах.** Обратите внимание, что в стеке три разные модели и каждая на своём месте по цене: Haiku пишет полмиллиона сводок (дёшево и много), реранкер обрабатывает 50 кандидатов на запрос, Sonnet вызывается один раз за ответ. Поставьте Sonnet писать сводки — и счёт вырастет в десятки раз без единого лишнего процента качества.

## Build It

1. **Ingestion walker.** Обходите историю git на каждый хук пуша. Собирайте изменённые файлы. Каждый файл разбирайте через tree-sitter, вытаскивайте узлы функций и классов вместе с полным диапазоном исходника. Выдавайте записи чанков `{repo, path, start_line, end_line, symbol, body}`.

2. **Chunk summarizer.** Пакуйте чанки в пачки и шлите в Haiku 4.5 с кешированием промпта на системной преамбуле. Промпт: «Summarize this function in one sentence, naming its public contract and side effects». Сводку храните рядом с чанком.

3. **Embedding pool.** Две параллельные очереди: плотная (Voyage-code-3, пачками по 128) и по сводкам (та же модель, но на строке сводки). Пишите векторы в Qdrant с полезной нагрузкой `{repo, path, start_line, end_line, symbol, kind}`.

4. **BM25 index.** Индекс Tantivy со взвешенными полями: имя символа вес 4, тело символа вес 1, сводка вес 2. Это даёт работать и запросам «найди функцию с именем X», и запросам «найди функцию, которая делает X».

5. **Symbol graph.** Для каждого чанка записывайте рёбра: импорты (этот файл использует символ Y из репозитория Z), вызовы (эта функция вызывает метод M у класса C), наследование. Кладите в kuzu. На запросах граф нужен, чтобы расширять retrieval за границы одного репозитория.

6. **Query agent.** LangGraph из трёх узлов. `retrieve` запускает dense и BM25 параллельно и убирает дубли по (repo, path, symbol). `rerank` гоняет кросс-энкодер по top-50 и оставляет top-10. `synth` вызывает Claude Sonnet 4.7 с переранжированными чанками в контексте, кеширует системный промпт и требует ссылок вида file:line.

7. **Citation enforcement.** Разбирайте вывод модели; любое утверждение без якоря `(repo/path:start-end)` помечайте на переспрос или выбрасывайте. Пользователю возвращайте только подкреплённый ответ.

8. **Incremental re-index.** На каждый вебхук считайте дифф на уровне символов. Пересчитывайте embedding только у чанков, чей текст изменился. Пересчитывайте рёбра символов у чанков, чьи импорты изменились. Замер: пуш на 50 файлов переиндексируется меньше чем за 60 секунд на парке в 2 млн строк.

9. **Eval.** Разметьте 100 вопросов через репозитории с эталонными ответами file:line. Меряйте MRR@10, nDCG@10, верность цитат (доля утверждений с проверяемыми якорями) и задержку p50/p99.

> 🎒 **На пальцах.** Присмотритесь к весам полей в шаге 4: имя символа весит 4, тело — 1, то есть совпадение по имени функции в четыре раза важнее, чем то же слово где-то в теле. Именно это отличает запрос «найди функцию с именем retry_budget» от «найди, где считается бюджет ретраев», хотя слова в них почти одинаковые. Шаг 7 — самый недооценённый: он превращает красивый абзац от модели в проверяемый ответ.

## Use It

```
$ code-rag ask "how is S3 multipart abort wired into our retry budget?"
[retrieve]  12 chunks dense + 7 chunks bm25, 16 unique after dedup
[rerank]    top-5 kept (cohere rerank-3)
[synth]     claude-sonnet-4.7, cache hit rate 68%, 2.1s
answer:
  Multipart aborts are triggered by `AbortMultipartOnFail` in
  services/uploader/retry.go:122-148, which decrements the per-bucket
  retry budget defined in config/budgets.yaml:34-51 ...
  citations: [services/uploader/retry.go:122-148, config/budgets.yaml:34-51,
              libs/s3client/multipart.ts:44-61]
```

> 🎒 **На пальцах.** Считаем по строкам лога: 12 плотных плюс 7 из BM25 — это 19 попаданий, а после дедупликации осталось 16, значит три чанка нашли оба метода сразу. Такие пересечения — хороший знак, но именно ради оставшихся 13 и держат два поиска. И заметьте `cache hit rate 68%`: две трети токенов промпта оплачены по льготной ставке, потому что системная часть не менялась.

## Ship It

Поставляемый навык — `outputs/skill-codebase-rag.md`. Получив корпус репозиториев, он поднимает конвейер загрузки, гибридный индекс и агента запросов и возвращает ответ со ссылками на любой вопрос через репозитории. Критерии оценки:

> 🎒 **На пальцах.** Обратите внимание, что поставляется не индекс, а способ его построить. Разница практическая: индекс протухает к завтрашнему утру, а конвейер, который переиндексирует 50-файловый пуш за минуту, живёт годами.

| Weight | Criterion | How it is measured |
|:-:|---|---|
| 25 | Качество retrieval | MRR@10 и nDCG@10 на отложенном наборе из 100 вопросов |
| 20 | Верность цитат | Доля утверждений в ответе с проверяемыми якорями file:line |
| 20 | Задержка и масштаб | Задержка запроса p95 при 10k QPS на корпусе того размера, что вы проиндексировали |
| 20 | Корректность инкрементальной индексации | Время от git push до появления в поиске на коммите из 50 файлов |
| 15 | UX и оформление ответа | Кликабельность ссылок, предпросмотр фрагментов, удобство задать уточняющий вопрос |
| **100** | | |

> 🎒 **На пальцах.** Сложите первые две строки: 45 баллов из 100 уходят на то, нашли ли вы правильный кусок кода и можно ли это проверить. Красивая вёрстка стоит 15. Порядок весов подсказывает и порядок работы: сначала доведите MRR@10, потом занимайтесь интерфейсом.

## Exercises

1. Замените Voyage-code-3 на nomic-embed-code на своих серверах. Померьте разницу в MRR@10. Скажите, закрывается ли разрыв, когда включён реранкер.

2. Влейте в корпус 20% сгенерированного кода (boilerplate от LLM) и переоцените систему. Понаблюдайте за отравлением retrieval. Добавьте в полезную нагрузку флаг «generated» и понижайте вес таких попаданий.

3. Сравните гибридный поиск Qdrant с pgvector + pgvectorscale на вашем размере корпуса. Приведите p99 при размере пачки 1.

4. Добавьте проверку дрейфа по выборке: раз в неделю переигрывайте оценку на 100 вопросах. Поднимайте алерт при падении MRR@10 больше чем на 5%.

5. Расширьтесь до разрешения символов между языками: питоновская функция вызывает Go-сервис по gRPC. Свяжите их через граф символов.

> 🎒 **На пальцах.** Второе задание даёт самый наглядный эффект: сгенерированный boilerplate выглядит гладко и похоже на всё сразу, поэтому 20% мусора способны выбить из top-10 половину правильных попаданий. Понижение веса по флагу — это одна строка в запросе, а прирост MRR@10 обычно измеряется в единицах процентов; редко где так дёшево.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| AST-aware chunking | «Резать по функциям» | Нарезка кода по границам узлов tree-sitter вместо фиксированных окон токенов |
| Hybrid search | «Плотный плюс разреженный» | Запустить BM25 и векторный поиск параллельно, объединить top-k, переранжировать |
| Cross-encoder rerank | «Ранжирование вторым этапом» | Модель, которая оценивает пару (запрос, кандидат) целиком; точнее косинуса |
| Prompt caching | «Кешированный системный промпт» | Возможность Claude и OpenAI 2026 года: повторяющийся префикс токенов дешевле на величину до 90% |
| Symbol graph | «Граф кода» | Рёбра импортов, вызовов и наследования между файлами и репозиториями |
| Citation faithfulness | «Доля заземлённых ответов» | Доля утверждений, которые пользователь может проверить, кликнув по якорю и прочитав указанный фрагмент |
| Incremental re-index | «Время от пуша до поиска» | Время по часам от git push до момента, когда изменённые символы можно найти |

> 🎒 **На пальцах.** Сравните строки Prompt caching и Incremental re-index — обе про то, чтобы не платить дважды за неизменившееся. Кеш промпта экономит до 90% токенов на повторяющейся системной части, инкрементальная индексация экономит те же 99% работы на неизменившихся файлах. Одна идея, два разных слоя системы.
