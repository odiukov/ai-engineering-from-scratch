# Capstone 16 — автономный агент «issue → PR» на GitHub

> Повесил метку на issue — получил PR. В 2026 году это и есть продуктовая форма автономных кодовых агентов: агент поднимается в облачной песочнице, убеждается, что тесты зелёные, и открывает готовый к ревью PR с обоснованием. AWS Remote SWE Agents, Cursor Background Agents, OpenAI Codex cloud и Google Jules — все выпустили именно это. Трудное здесь другое: автоматически воспроизвести окружение сборки репозитория, не дать утечь кредам, удержать бюджет на репозиторий и не позволить агенту сделать force-push. В этом capstone вы собираете self-hosted версию и сравниваете её с хостед-альтернативами по цене и доле решённых задач.

**Type:** Capstone
**Languages:** Python (agent), TypeScript (GitHub App), YAML (Actions)
**Prerequisites:** Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 15 (autonomous), Phase 17 (infrastructure)
**Phases exercised:** фазы P11 · P13 · P14 · P15 · P17
**Time:** 30 hours

## Problem

Асинхронный облачный кодовый агент — это отдельная продуктовая категория, не то же самое, что интерактивный кодовый агент из capstone 01. Весь интерфейс здесь — метка на GitHub. Вы вешаете на issue метку `@agent fix this`, воркер поднимается в облачной песочнице, клонирует репозиторий, запускает тесты, правит файлы, проверяет результат и открывает PR, в теле которого лежит рассуждение агента. Никакого интерактивного цикла, никакого терминала. AWS Remote SWE Agents, Cursor Background Agents, OpenAI Codex cloud, Google Jules и Factory Droids сошлись на одной и той же форме.

> 🎒 **На пальцах.** Разница с capstone 01 — как между разговором с мастером в сервисе и запиской, которую вы оставили на бампере: во втором случае вы не стоите рядом и не подсказываете. Отсюда все сложности: агент не может переспросить, поэтому всё, что он должен знать, обязано быть в issue и в репозитории.

Инженерные трудности вполне конкретные: воспроизведение окружения (агенту нужно собрать репозиторий с нуля, без заранее прогретого dev-образа), нестабильные тесты (их надо перезапускать или изолировать), ограничение прав кредов (GitHub App с минимальными fine-grained правами), удержание бюджета на репозиторий в сутки и политика «никакого force-push». Capstone измеряет долю решённых задач, цену и безопасность в сравнении с хостед-альтернативами.

> 🎒 **На пальцах.** Пять трудностей — это пять мест, где ваш агент сломается первым, и ни одна из них не про «модель плохо пишет код». Как в походе: маршрут вы пройдёте, а вот еда, вода, погода, обувь и деньги — вот что решает исход.

## Concept

Триггером служит вебхук GitHub (метка на issue или комментарий в PR). Диспетчер ставит работу в очередь на ECS Fargate или Lambda. Воркер разворачивает репозиторий в песочнице Daytona или E2B с обобщённым Dockerfile, выведенным из самого репозитория (язык, фреймворк). Агент крутит цикл mini-swe-agent или SWE-agent v2 поверх Claude Opus 4.7 либо GPT-5.4-Codex. Итерация одна и та же: прочитать код, предложить починку, применить патч, прогнать тесты.

> 🎒 **На пальцах.** Заметьте, что в цикле четыре шага и они замкнуты: тесты дают агенту обратную связь, и следующий проход начинается уже с их результата. Это как решать уравнение подстановкой: подставил, проверил, поправил — а не «написал ответ и ушёл».

Проверка — это тот самый шлагбаум. Полный CI обязан пройти внутри песочницы до того, как откроется PR. Считается дельта покрытия; если она ушла в минус сильнее порога, PR всё равно открывается, но получает метку `needs-review`. Обоснование агент кладёт в описание PR и заводит тред `@agent`, куда ревьюер может написать с уточнениями.

> 🎒 **На пальцах.** Порог по покрытию делает вердикт трёхзначным вместо двухзначного: CI красный — PR не открывается вовсе, покрытие просело — PR открывается с меткой, всё хорошо — PR открывается чистым. Как с сочинением: одна ошибка — правка, десять — переписать, ноль — сдал.

Безопасность разведена по двум разным поверхностям GitHub: App выдаёт короткоживущий installation-токен с правом `workflows: read` и узкими правами на содержимое репозитория и PR; а вот «никаких прямых записей в `main`» и «никакого force-push» обеспечивает branch protection, а не права приложения — приложение никогда не добавляют в bypass-список. Доступ только на чтение к `.github/workflows` по путям — не настоящий примитив GitHub App, поэтому allow-list на правку файлов приходится проверять на стороне воркера. Потолки бюджета на репозиторий в сутки держит диспетчер (например, максимум 5 PR на репозиторий в день и $20 на PR).

> 🎒 **На пальцах.** Пять PR по двадцать долларов — это потолок в сто долларов на репозиторий в день, и такой предел легко посчитать заранее. Ключевая мысль в другом: запрет на force-push живёт не в правах агента, а в защите ветки, потому что права можно случайно расширить, а branch protection действует на всех сразу.

## Architecture

```
GitHub issue labeled `@agent fix` or PR comment
            |
            v
    GitHub App webhook -> AWS Lambda dispatcher
            |
            v
    ECS Fargate task (or GitHub Actions self-hosted runner)
       - pull repo
       - infer Dockerfile (language, package manager)
       - Daytona / E2B sandbox with target runtime
       - clone -> git worktree -> agent branch
            |
            v
    mini-swe-agent / SWE-agent v2 loop
       Claude Opus 4.7 or GPT-5.4-Codex
       tools: ripgrep, tree-sitter, read/edit, run_tests, git
            |
            v
    verify CI passes in-sandbox + coverage delta check
            |
            v (verified)
    git push + open PR via GitHub App
       PR body = rationale + diff summary + trace URL
       label: needs-review
            |
            v
    operator reviews; can @-mention agent for follow-ups
```

> 🎒 **На пальцах.** Пройдите схему сверху вниз и посчитайте: от метки до открытого PR ровно пять переходов, и проверка стоит четвёртой, прямо перед пушем. Ни одна стрелка не идёт назад к `main` в обход PR — это не украшение диаграммы, а буквально то, что обеспечивает branch protection.

## Stack

- Trigger: GitHub App с fine-grained токеном; приёмник вебхуков на Lambda или Fly.io
- Worker: задача ECS Fargate (или self-hosted runner GitHub Actions)
- Sandbox: devcontainer Daytona или песочница E2B на каждую задачу
- Agent loop: базовый mini-swe-agent или SWE-agent v2 поверх Claude Opus 4.7 / GPT-5.4-Codex
- Retrieval: карта репозитория на tree-sitter плюс ripgrep
- Verification: полный CI внутри песочницы плюс гейт по дельте покрытия
- Observability: Langfuse, архив трассы на каждый PR со ссылкой из тела PR
- Budget: дневной денежный потолок на репозиторий; максимум PR на репозиторий в день

> 🎒 **На пальцах.** Восемь строк стека — это восемь коробок, которые надо закрыть, и ни одна из них не про выбор модели. Модель упомянута ровно в одной строке из восьми; остальные семь — обычная инфраструктура, и именно на них уходит большая часть из тридцати часов.

## Build It

1. **GitHub App.** Fine-grained installation-токен: issues на чтение и запись, pull_requests на запись, contents на чтение и запись, workflows на чтение. Branch protection (единственная поверхность, которая на это способна) обеспечивает «никаких прямых пушей в `main`» и «никакого force-push»; приложения нет в bypass-списке. Правило «не писать внутрь `.github/workflows`» воркер проверяет сам, как allow-list по предложенному дифу, потому что права GitHub App не умеют ограничиваться путями.

2. **Webhook receiver.** Функция Lambda принимает вебхуки о метках на issue и комментариях в PR. Фильтрует по метке `@agent fix this`. Кладёт задачу в SQS.

3. **Dispatcher.** Забирает задачи из SQS. Следит за дневным бюджетом на репозиторий. Поднимает задачу ECS Fargate с URL репозитория, телом issue и свежей песочницей Daytona.

4. **Environment inference.** Определить язык (Python, Node, Go, Rust) и пакетный менеджер (uv, pnpm, go mod, cargo). Сгенерировать Dockerfile на лету, если его нет.

5. **Agent loop.** mini-swe-agent или SWE-agent v2 с Claude Opus 4.7. Инструменты: ripgrep, карта репозитория на tree-sitter, read_file, edit_file, run_tests, git. Жёсткие лимиты: $20 стоимости, 30 минут по часам, 30 ходов агента.

> 🎒 **На пальцах.** Три лимита из шага 5 держат друг друга: даже если модель зациклится, её остановит либо счётчик ходов, либо секундомер, либо кошелёк — что сработает раньше. Двадцать долларов на тридцать ходов — это меньше семидесяти центов на ход, и такой бюджет заставляет писать узкие инструменты, а не вываливать агенту весь репозиторий.

6. **Verification.** Когда цикл закончился, прогнать полный набор тестов внутри песочницы. Посчитать дельту покрытия через jacoco или coverage.py. Если CI красный — остановиться и не открывать PR. Если покрытие упало больше чем на 2% — открыть PR с меткой `needs-review`.

7. **PR posting.** Запушить ветку агента. Открыть PR через GitHub API, указав заголовок, обоснование, сводку по дифу, ссылку на трассу, стоимость и число ходов.

> 🎒 **На пальцах.** Порог в 2% выбран не наугад: одна ненаписанная проверка в среднем проекте стоит десятые доли процента, а вот удалённый тестовый файл сразу даёт минус несколько процентов. То есть гейт ловит именно «агент выкинул мешающие тесты», а не мелкий шум округления.

8. **Credential hygiene.** Воркер работает с короткоживущим installation-токеном GitHub App. Логи перед архивацией чистятся от секретов.

9. **Eval.** 30 заранее подобранных внутренних issue разной сложности. Померить долю решённых, качество PR (размер дифа, стиль, покрытие), стоимость, задержку. Сравнить с Cursor Background Agents и AWS Remote SWE Agents на тех же самых issue.

> 🎒 **На пальцах.** Тридцать issue — это минимум, при котором проценты вообще что-то значат: одна задача весит примерно 3,3 процентных пункта, так что разница «18 из 30 против 20 из 30» ещё в пределах шума. Сравнивать надо строго на одних и тех же issue, иначе вы сравниваете сложность задач, а не агентов.

## Use It

```
# on github.com
  - user labels issue #842 with `@agent fix this`
  - PR #1903 appears 14 minutes later
  - body:
    > Fixed NPE in widget.dedupe() caused by null comparator entry.
    > Added regression test widget_test.go::TestDedupeNullComparator.
    > Coverage delta: +0.12%
    > Turns: 7  Cost: $1.80  Trace: langfuse:...
    > Label: needs-review
```

> 🎒 **На пальцах.** Прочитайте тело PR как чек: 7 ходов, $1,80, +0,12% покрытия, 14 минут от метки до PR. Меньше двух долларов за починку NPE с регрессионным тестом — вот та экономика, ради которой всё и строится; и заметьте, что метка `needs-review` тут всё равно стоит, потому что финальное слово за человеком.

## Ship It

`outputs/skill-issue-to-pr.md` — итоговый артефакт. GitHub App плюс асинхронный облачный воркер, который превращает помеченные issue в готовые к ревью PR при ограниченной стоимости и урезанных правах.

| Weight | Criterion | How it is measured |
|:-:|---|---|
| 25 | Доля решённых на 30 issue | Успех от начала до конца (CI зелёный и покрытие в порядке) |
| 20 | Качество PR | Размер дифа, дельта покрытия, соответствие стилю |
| 20 | Стоимость и задержка на решённую issue | Доллары и время по часам на один PR |
| 20 | Безопасность | Урезанный токен, бюджет на репозиторий, отсутствие force-push, гигиена кредов |
| 15 | Удобство для оператора | Комментарии с обоснованием, возможность перезапуска, дообщение через @-упоминание |
| **100** | | |

> 🎒 **На пальцах.** Сложите веса: безопасность и стоимость дают 40 из 100, а сама доля решённых — только 25. То есть агент, который чинит все тридцать issue, но ходит с широкими правами и жжёт деньги, наберёт меньше аккуратного агента с долей решённых в две трети.

## Exercises

1. Добавьте режим «починить нестабильный тест»: метка `@agent stabilize-flake TestX` запускает тест 50 раз внутри песочницы и предлагает минимальное изменение, которое его стабилизирует.

2. Сравните стоимость с Cursor Background Agents на трёх общих issue. Опишите, какой инструмент где выигрывает.

3. Сделайте дашборд бюджета: стоимость по репозиториям за день и по пользователям. Оповещение при аномалии.

4. Соберите режим «сухого прогона», который открывает черновой PR без запуска CI, чтобы ревьюеры могли дёшево посмотреть на план.

5. Добавьте политику хранения: ветки PR старше 7 дней без мержа удаляются автоматически.

> 🎒 **На пальцах.** Первое задание сильнее, чем кажется: 50 прогонов теста — это статистика, а не догадка, и она сразу отличает «упал 1 раз из 50» от «упал 20 раз из 50». Начните лучше с четвёртого — сухой прогон снимает CI из цикла и делает отладку всего остального в разы дешевле.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| GitHub App | «Бот с урезанными правами» | Приложение с fine-grained правами и короткоживущим installation-токеном |
| Async cloud agent | «Фоновый агент» | Неинтерактивный воркер, который живёт в облачной песочнице, а не в терминале |
| Environment inference | «Синтез Dockerfile» | Определить язык и пакетный менеджер, сгенерировать Dockerfile, если его нет |
| Verification | «CI внутри песочницы» | Прогнать полный набор тестов внутри воркера до открытия PR |
| Coverage delta | «Сохранение покрытия» | Изменение процента покрытия тестами между базой и веткой агента |
| Per-repo budget | «Дневной потолок» | Ограничение по деньгам и по числу PR, которое держит диспетчер |
| Rationale | «Пояснение в теле PR» | Сводка агента о том, что изменено и зачем; обязательна в теле PR |

> 🎒 **На пальцах.** Обратите внимание, что четыре из семи терминов — про ограничения, а не про способности: права, бюджет, проверка, покрытие. Так и выглядит взрослый агент; «умеет писать код» здесь просто предпосылка, а не достижение.
