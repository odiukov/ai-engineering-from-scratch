# Численная устойчивость

> Числа с плавающей точкой — дырявая абстракция. Она укусит вас во время обучения, и вы не увидите этого заранее.

**Type:** Build
**Language:** Python
**Prerequisites:** Phase 1, Lessons 01-04
**Time:** ~120 minutes

## Learning Objectives

- Реализовать численно устойчивые softmax и log-sum-exp через приём вычитания максимума
- Распознавать переполнение, исчезновение порядка и катастрофическую потерю значимости в вычислениях с плавающей точкой
- Проверять аналитические градиенты численными через центральные конечные разности
- Объяснить, почему bfloat16 предпочтительнее float16 для обучения и как масштабирование потерь спасает градиенты от исчезновения

> 🎒 **На пальцах.** Компьютер не умеет считать точно. У него ограниченное число цифр, как у калькулятора с маленьким экраном. Обычно это неважно, но в нейросетях миллионы операций подряд — и мелкие ошибки складываются в катастрофу.

## The Problem

Ваша модель учится три часа, потом потери становятся NaN. Вы добавляете print. На шаге 9000 логиты в порядке. На шаге 9001 они `inf`. К шагу 9002 каждый градиент — `nan`, и обучение мертво.

Или: модель доучилась, но точность на 2% хуже, чем в статье. Вы проверяете всё. Архитектура совпадает. Гиперпараметры совпадают. Данные совпадают. Проблема в том, что в статье использовали float32, а вы float16 без правильного масштабирования. Тридцать два бита накопленной ошибки округления тихо съели вашу точность.

Или: вы пишете cross-entropy loss с нуля. На маленьких логитах работает. Когда логиты превышают 100, возвращается `inf`. Softmax переполнился, потому что `exp(100)` больше, чем может представить float32. Каждый ML-фреймворк решает это двумя строками. Вы не знали, что такой приём существует.

Численная устойчивость — не теоретическая забота. Это разница между успешным прогоном обучения и тихо проваленным. Любой серьёзный ML-баг, который вам придётся отлаживать, в итоге упирается в числа с плавающей точкой.

## The Concept

### IEEE 754: How Computers Store Real Numbers

Компьютеры хранят вещественные числа как значения с плавающей точкой по стандарту IEEE 754. У числа три части: знаковый бит, экспонента и мантисса.

```
Float32 layout (32 bits total):
[1 sign] [8 exponent] [23 mantissa]

Value = (-1)^sign * 2^(exponent - 127) * 1.mantissa
```

Мантисса определяет точность (сколько значащих цифр). Экспонента определяет диапазон (насколько большим или маленьким может быть число).

```
Format     Bits   Exponent  Mantissa  Decimal digits  Range (approx)
float64    64     11        52        ~15-16          +/- 1.8e308
float32    32     8         23        ~7-8            +/- 3.4e38
float16    16     5         10        ~3-4            +/- 65,504
bfloat16   16     8         7         ~2-3            +/- 3.4e38
```

float32 даёт примерно 7 десятичных знаков точности. То есть он различит 1.0000001 и 1.0000002, но не 1.00000001 и 1.00000002. После седьмой цифры всё — шум округления.

float16 даёт около 3 цифр. Наибольшее представимое число — 65 504. Тревожно мало для ML, где логиты, градиенты и активации регулярно это превышают.

bfloat16 — ответ Google на проблему диапазона float16. У него та же 8-битная экспонента, что у float32 (тот же диапазон, до 3.4e38), но всего 7 бит мантиссы (точность ниже, чем у float16). Для обучения нейросетей диапазон важнее точности, поэтому bfloat16 обычно выигрывает.

> 🎒 **На пальцах.** Экспонента — «насколько большое число», мантисса — «сколько цифр в нём точны». Как в записи 3.14 × 10⁵: степень десятки задаёт масштаб, а 3.14 — подробность. Урезали цифры после запятой — потеряли подробность. Урезали степень — вообще не смогли записать большое число.

### Why 0.1 + 0.2 != 0.3

Число 0.1 нельзя представить точно в двоичной плавающей точке. В основании 2 это периодическая дробь:

```
0.1 in binary = 0.0001100110011001100110011... (repeating forever)
```

Float32 обрезает её до 23 бит мантиссы. Хранится примерно 0.100000001490116. Аналогично 0.2 хранится как примерно 0.200000002980232. Их сумма — 0.300000004470348, а не 0.3.

```
In Python:
>>> 0.1 + 0.2
0.30000000000000004

>>> 0.1 + 0.2 == 0.3
False
```

Для ML это важно, потому что:

1. Сравнения вроде `if loss < threshold` могут дать неверный ответ
2. Накопление множества мелких значений (обновления градиентов за тысячи шагов) уплывает от истинной суммы
3. Контрольные суммы и тесты воспроизводимости падают, если сравнивать числа через `==`

Лечение: никогда не сравнивайте числа с плавающей точкой через `==`. Используйте `abs(a - b) < epsilon` или `math.isclose()`.

> 🎒 **На пальцах.** Точно так же 1/3 нельзя записать десятичной дробью: 0.3333... Сколько цифр ни пиши, точного значения не получишь, а 0.3333 × 3 = 0.9999, а не 1. У компьютера основание 2, и в нём «неудобной» дробью оказывается уже 0.1. Отсюда и знаменитая шутка про 0.1 + 0.2.

### Catastrophic Cancellation

Когда вы вычитаете два почти равных числа с плавающей точкой, значащие цифры взаимно уничтожаются, и на первое место выходит шум округления.

```
a = 1.0000001    (stored as 1.00000011920929 in float32)
b = 1.0000000    (stored as 1.00000000000000 in float32)

True difference:  0.0000001
Computed:         0.00000011920929

Relative error: 19.2%
```

19% относительной ошибки от одного вычитания. В ML это происходит всякий раз, когда вы:

- Считаете дисперсию данных с большим средним: `E[x^2] - E[x]^2` при большом E[x]
- Вычитаете почти равные логарифмы вероятностей
- Считаете градиенты конечными разностями со слишком маленьким epsilon

Лечение: переписать формулу так, чтобы не вычитать большие почти равные числа. Для дисперсии — алгоритм Уэлфорда или предварительное центрирование. Для логарифмов вероятностей — работать в логарифмах насквозь.

> 🎒 **На пальцах.** Измерьте рост двух друзей рулеткой с точностью до сантиметра: 180 и 181. Разница — 1 см, но ваша погрешность тоже около сантиметра. То есть разница целиком состоит из погрешности. Вычитание близких чисел всегда так работает: сами числа точны, а их разность — мусор.

### Overflow and Underflow

Переполнение происходит, когда результат слишком велик для представления. Исчезновение порядка — когда слишком мал (ближе к нулю, чем наименьшее представимое положительное число).

```
Float32 boundaries:
  Maximum:  3.4028235e+38
  Minimum positive (normal): 1.175e-38
  Minimum positive (denorm): 1.401e-45
  Overflow:  anything > 3.4e38 becomes inf
  Underflow: anything < 1.4e-45 becomes 0.0
```

Функция `exp()` — главный источник переполнения в ML:

```
exp(88.7)  = 3.40e+38   (barely fits in float32)
exp(89.0)  = inf         (overflow)
exp(-87.3) = 1.18e-38   (barely above underflow)
exp(-104)  = 0.0         (underflow to zero)
```

Функция `log()` бьёт с другой стороны:

```
log(0.0)   = -inf
log(-1.0)  = nan
log(1e-45) = -103.3      (fine)
log(1e-46) = -inf        (input underflowed to 0, then log(0) = -inf)
```

В ML `exp()` появляется в softmax, sigmoid и вычислениях вероятностей. `log()` — в cross-entropy, логарифмах правдоподобия и KL divergence. Комбинация `log(exp(x))` — минное поле без правильных приёмов.

> 🎒 **На пальцах.** Запомните число 88. Это граница: `exp(88)` ещё влезает во float32, `exp(89)` уже бесконечность. То есть достаточно логиту дорасти до 89 — и всё обучение умирает. А логиты растут сами собой по мере обучения.

### The Log-Sum-Exp Trick

Вычислять `log(sum(exp(x_i)))` в лоб численно опасно. Если какое-то `x_i` велико, `exp(x_i)` переполнится. Если все `x_i` сильно отрицательны, каждый `exp(x_i)` исчезнет в ноль, и `log(0)` даст `-inf`.

Приём: вычесть максимум перед экспонированием.

```
log(sum(exp(x_i))) = max(x) + log(sum(exp(x_i - max(x))))
```

Почему работает: после вычитания `max(x)` наибольший показатель — `exp(0) = 1`. Переполнение невозможно. Хотя бы одно слагаемое равно 1, значит сумма не меньше 1, и `log(1) = 0`. Исчезновение в `-inf` тоже невозможно.

Доказательство:

```
log(sum(exp(x_i)))
= log(sum(exp(x_i - c + c)))                    (add and subtract c)
= log(sum(exp(x_i - c) * exp(c)))               (exp(a+b) = exp(a)*exp(b))
= log(exp(c) * sum(exp(x_i - c)))               (factor out exp(c))
= c + log(sum(exp(x_i - c)))                    (log(a*b) = log(a) + log(b))
```

Положите `c = max(x)`, и переполнение исчезает.

Этот приём встречается в ML повсюду:
- Нормировка softmax
- Вычисление cross-entropy loss
- Суммирование логарифмов вероятностей в моделях последовательностей
- Смеси гауссиан
- Вариационный вывод

> 🎒 **На пальцах.** Смотрите на доказательство внимательно: это школьное правило «прибавили и отняли одно и то же». Ничего не изменилось математически — ответ ровно тот же. Изменилось только то, какие числа компьютер держит в руках по дороге: вместо гигантских — маленькие и удобные.

### Why Softmax Needs the Max-Subtraction Trick

Softmax превращает логиты в вероятности:

```
softmax(x_i) = exp(x_i) / sum(exp(x_j))
```

Без приёма логиты [100, 101, 102] вызывают переполнение:

```
exp(100) = 2.69e43
exp(101) = 7.31e43
exp(102) = 1.99e44
sum      = 2.99e44

These overflow float32 (max ~3.4e38)? No, 2.69e43 < 3.4e38? Actually:
exp(88.7) is already at the float32 limit.
exp(100) = inf in float32.
```

С приёмом вычитаем max(x) = 102:

```
exp(100 - 102) = exp(-2) = 0.135
exp(101 - 102) = exp(-1) = 0.368
exp(102 - 102) = exp(0)  = 1.000
sum = 1.503

softmax = [0.090, 0.245, 0.665]
```

Вероятности идентичны. Вычисление безопасно. Это не оптимизация. Это требование корректности.

> 🎒 **На пальцах.** Разница между учениками с баллами 100, 101 и 102 та же, что между 0, 1 и 2 — просто отсчёт от другой точки. Softmax смотрит только на разницу, а не на абсолютные значения. Поэтому вычитание максимума ничего не портит, а от переполнения спасает — и вся правка это одна строка `max_logit = max(logits)` и один минус.

### NaN and Inf: Detection and Prevention

`nan` (Not a Number) и `inf` (бесконечность) расползаются по вычислениям как вирус. Один `nan` в обновлении градиента делает вес `nan`, что делает `nan` каждый последующий выход. Обучение мертво за один шаг.

Как появляется `inf`:
- `exp()` большого положительного числа
- Деление на ноль: `1.0 / 0.0`
- Переполнение `float32` при накоплении

Как появляется `nan`:
- `0.0 / 0.0`
- `inf - inf`
- `inf * 0`
- `sqrt()` отрицательного числа
- `log()` отрицательного числа
- Любая арифметика с уже существующим `nan`

Обнаружение:

```python
import math

math.isnan(x)       # True if x is nan
math.isinf(x)       # True if x is +inf or -inf
math.isfinite(x)    # True if x is neither nan nor inf
```

Стратегии профилактики:

1. Ограничивать вход `exp()`: `exp(clamp(x, -80, 80))`
2. Добавлять epsilon в знаменатели: `x / (y + 1e-8)`
3. Добавлять epsilon внутрь `log()`: `log(x + 1e-8)`
4. Использовать устойчивые реализации (log-sum-exp, стабильный softmax)
5. Обрезать градиенты, чтобы веса не взрывались
6. Проверять на `nan`/`inf` после каждого прямого прохода при отладке

> 🎒 **На пальцах.** NaN ведёт себя как капля чернил в стакане воды: одна капля — и вся вода испорчена, обратно её не выловить. Поэтому важно поймать самый первый `nan`, а не разбираться потом, почему всё сломалось.

### Numerical Gradient Checking

У аналитических градиентов (из обратного распространения) бывают баги. Численная проверка градиентов подтверждает их, вычисляя градиенты конечными разностями.

Формула центральной разности:

```
df/dx ~= (f(x + h) - f(x - h)) / (2h)
```

Её точность O(h^2), намного лучше правой разности `(f(x+h) - f(x)) / h`, у которой только O(h).

Выбор h: слишком большое — приближение неверно. Слишком маленькое — катастрофическая потеря значимости уничтожает ответ. Обычно берут `h = 1e-5` до `1e-7`.

Проверка: посчитать относительную разницу между аналитическим и численным градиентом.

```
relative_error = |grad_analytical - grad_numerical| / max(|grad_analytical|, |grad_numerical|, 1e-8)
```

Практические ориентиры:
- relative_error < 1e-7: идеально, градиент верен
- relative_error < 1e-5: приемлемо, скорее всего верен
- relative_error > 1e-3: что-то не так
- relative_error > 1: градиент совершенно неверен

Всегда проверяйте градиенты при реализации нового слоя или функции потерь. В PyTorch для этого есть `torch.autograd.gradcheck()`.

> 🎒 **На пальцах.** Обратите внимание на компромисс с h: слишком большое — меряете не наклон в точке, а наклон «в среднем по округе». Слишком маленькое — вычитаете два почти равных числа и получаете тот самый мусор из раздела про потерю значимости. Золотая середина где-то около 1e-6.

### Mixed Precision Training

У современных GPU есть специальное железо (Tensor Cores), считающее умножение матриц в float16 в 2-8 раз быстрее, чем в float32. Обучение в смешанной точности этим пользуется:

```
1. Maintain float32 master copy of weights
2. Forward pass in float16 (fast)
3. Compute loss in float32 (prevents overflow)
4. Backward pass in float16 (fast)
5. Scale gradients to float32
6. Update float32 master weights
```

Проблема чистого float16-обучения: градиенты часто очень малы (1e-8 и меньше). Float16 обнуляет всё, что ниже примерно 6e-8. Модель перестаёт учиться, потому что все обновления нулевые.

Лечение — масштабирование потерь:

```
1. Multiply loss by a large scale factor (e.g., 1024)
2. Backward pass computes gradients of (loss * 1024)
3. All gradients are 1024x larger (pushed above float16 underflow)
4. Divide gradients by 1024 before updating weights
5. Net effect: same update, but no underflow
```

Динамическое масштабирование подбирает коэффициент автоматически. Начинают с большого значения (65536). Если градиенты переполнились в `inf` — уменьшают вдвое. Если N шагов прошло без переполнения — увеличивают вдвое.

> 🎒 **На пальцах.** Вам нужно взвесить пёрышко на весах, которые показывают только целые граммы. Пёрышко весит 0.3 грамма — весы покажут ноль. Решение: взвесить сразу тысячу пёрышек, получить 300 граммов, поделить на тысячу. Масштабирование потерь — ровно этот трюк.

### bfloat16 vs float16: Why bfloat16 Wins for Training

```
float16:   [1 sign] [5 exponent]  [10 mantissa]
bfloat16:  [1 sign] [8 exponent]  [7 mantissa]
```

У float16 больше точности (10 бит мантиссы против 7), но ограниченный диапазон (максимум около 65 504). У bfloat16 меньше точности, но диапазон такой же, как у float32 (максимум около 3.4e38).

Для обучения нейросетей:

- Активации и логиты регулярно превышают 65 504 на всплесках во время обучения. float16 переполняется, bfloat16 справляется.
- С float16 масштабирование потерь обязательно, с bfloat16 обычно не нужно, потому что его диапазон покрывает весь спектр величин градиентов.
- bfloat16 — простое обрезание float32: выбросить нижние 16 бит мантиссы. Преобразование тривиально и не трогает экспоненту.

float16 предпочтителен для инференса, где значения ограничены и точность важнее. bfloat16 предпочтителен для обучения, где важнее диапазон. Поэтому TPU и современные GPU NVIDIA (A100, H100) имеют встроенную поддержку bfloat16.

> 🎒 **На пальцах.** Выбор между «линейкой с миллиметрами длиной 30 см» и «рулеткой с сантиметрами длиной 50 метров». Для черчения нужна первая. Для измерения дома — вторая, даже если она грубее. Обучение нейросети — это измерение дома: важнее дотянуться, чем поймать миллиметр.

### Gradient Clipping

Взрывающиеся градиенты возникают, когда градиенты растут экспоненциально через множество слоёв (обычное дело в RNN, глубоких сетях и трансформерах). Один большой градиент может испортить все веса за один шаг.

Два вида обрезания:

**Clip by value:** ограничить каждый элемент градиента независимо.

```
grad = clamp(grad, -max_val, max_val)
```

Просто, но может изменить направление вектора градиента.

**Clip by norm:** масштабировать весь вектор градиента так, чтобы его норма не превышала порог.

```
if ||grad|| > max_norm:
    grad = grad * (max_norm / ||grad||)
```

Сохраняет направление градиента. Именно это делает `torch.nn.utils.clip_grad_norm_()`. Стандартный выбор.

Типичные значения: `max_norm=1.0` для трансформеров, `max_norm=0.5` для RL, `max_norm=5.0` для более простых сетей.

Обрезание градиентов — не костыль. Это предохранитель. Без него один выбросовый батч способен породить градиент, достаточный, чтобы угробить недели обучения.

> 🎒 **На пальцах.** Разница между двумя способами: обрезание по значению — как подрезать каждому в классе рост до 180 см (пропорции класса поехали). Обрезание по норме — как уменьшить всех одинаково, сохранив, кто выше кого. Второе честнее, поэтому им и пользуются.

### Normalization Layers as Numerical Stabilizers

Batch normalization, layer normalization и RMS normalization обычно подают как регуляризаторы, помогающие сходимости. Они ещё и численные стабилизаторы.

Без нормализации активации могут экспоненциально расти или таять через слои:

```
Layer 1: values in [0, 1]
Layer 5: values in [0, 100]
Layer 10: values in [0, 10,000]
Layer 50: values in [0, inf]
```

Нормализация переносит и перемасштабирует активации на каждом слое:

```
LayerNorm(x) = (x - mean(x)) / (std(x) + epsilon) * gamma + beta
```

`epsilon` (обычно 1e-5) не даёт делить на ноль, когда все активации одинаковы. Обучаемые параметры `gamma` и `beta` позволяют сети восстановить любой нужный масштаб.

Это удерживает значения в численно безопасном диапазоне по всей сети, предотвращая и переполнение на прямом проходе, и взрыв градиентов на обратном.

> 🎒 **На пальцах.** Посмотрите на табличку с ростом значений: 1 → 100 → 10 000 → бесконечность. Каждый слой умножает примерно на одно и то же, и через 50 слоёв получается катастрофа. Нормализация — как приводить оценки к пятибалльной шкале после каждой контрольной: сколько бы баллов ни было сырых, на выходе всегда от 1 до 5.

### Common ML Numerical Bugs

**Bug: Loss is NaN after a few epochs.**
Причина: логиты выросли слишком сильно, softmax переполнился. Либо learning rate велик и веса разошлись.
Лечение: стабильный softmax (вычитание максимума), уменьшить learning rate, добавить обрезание градиентов.

**Bug: Loss is stuck at log(num_classes).**
Причина: модель выдаёт почти равномерные вероятности. Часто означает затухание градиентов или что модель вообще не учится.
Лечение: проверить корректность меток, проверить функцию потерь, поискать мёртвые ReLU.

**Bug: Validation accuracy is lower than expected by 1-3%.**
Причина: смешанная точность без правильного масштабирования потерь. Исчезновение градиентов молча обнуляет мелкие обновления.
Лечение: включить динамическое масштабирование потерь или перейти на bfloat16.

**Bug: Gradient norms are 0.0 for some layers.**
Причина: мёртвые ReLU-нейроны (все входы отрицательны) или исчезновение порядка во float16.
Лечение: использовать LeakyReLU или GELU, масштабировать градиенты, проверить инициализацию весов.

**Bug: Model works on one GPU but gives different results on another.**
Причина: недетерминированный порядок накопления чисел с плавающей точкой. Параллельные свёртки на GPU суммируют в разном порядке на разном железе, а сложение с плавающей точкой не ассоциативно.
Лечение: принять малые расхождения (1e-6) или включить `torch.use_deterministic_algorithms(True)` и смириться с потерей скорости.

**Bug: `exp()` returns `inf` in loss computation.**
Причина: сырые логиты переданы в `exp()` без приёма вычитания максимума.
Лечение: использовать `torch.nn.functional.log_softmax()`, где log-sum-exp реализован внутри.

**Bug: Training diverges after switching from float32 to float16.**
Причина: float16 не представляет градиенты меньше 6e-8 и активации больше 65 504.
Лечение: смешанная точность с масштабированием потерь (AMP) или переход на bfloat16.

> 🎒 **На пальцах.** Второй баг стоит запомнить отдельно. `log(num_classes)` — это потери «идеально ничего не знающей» модели: при 10 классах примерно 2.3. Увидели, что loss замер на 2.3 и не двигается? Модель не учится вообще, она просто угадывает наугад. Одно число экономит часы отладки.

### Step 2: Implement naive vs stable softmax

```python
import math

def softmax_naive(logits):
    exps = [math.exp(z) for z in logits]
    total = sum(exps)
    return [e / total for e in exps]

def softmax_stable(logits):
    max_logit = max(logits)
    exps = [math.exp(z - max_logit) for z in logits]
    total = sum(exps)
    return [e / total for e in exps]

safe_logits = [2.0, 1.0, 0.1]
print(f"Naive:  {softmax_naive(safe_logits)}")
print(f"Stable: {softmax_stable(safe_logits)}")

dangerous_logits = [100.0, 101.0, 102.0]
print(f"Stable: {softmax_stable(dangerous_logits)}")
# softmax_naive(dangerous_logits) would return [nan, nan, nan]
```

### Step 3: Implement stable log-sum-exp

```python
def logsumexp_naive(values):
    return math.log(sum(math.exp(v) for v in values))

def logsumexp_stable(values):
    c = max(values)
    return c + math.log(sum(math.exp(v - c) for v in values))

safe = [1.0, 2.0, 3.0]
print(f"Naive:  {logsumexp_naive(safe):.6f}")
print(f"Stable: {logsumexp_stable(safe):.6f}")

large = [500.0, 501.0, 502.0]
print(f"Stable: {logsumexp_stable(large):.6f}")
# logsumexp_naive(large) returns inf
```

### Step 4: Implement stable cross-entropy

```python
def cross_entropy_naive(true_class, logits):
    probs = softmax_naive(logits)
    return -math.log(probs[true_class])

def cross_entropy_stable(true_class, logits):
    max_logit = max(logits)
    shifted = [z - max_logit for z in logits]
    log_sum_exp = math.log(sum(math.exp(s) for s in shifted))
    log_prob = shifted[true_class] - log_sum_exp
    return -log_prob

logits = [2.0, 5.0, 1.0]
true_class = 1
print(f"Naive:  {cross_entropy_naive(true_class, logits):.6f}")
print(f"Stable: {cross_entropy_stable(true_class, logits):.6f}")
```

### Step 5: Gradient checking

```python
def numerical_gradient(f, x, h=1e-5):
    grad = []
    for i in range(len(x)):
        x_plus = x[:]
        x_minus = x[:]
        x_plus[i] += h
        x_minus[i] -= h
        grad.append((f(x_plus) - f(x_minus)) / (2 * h))
    return grad

def check_gradient(analytical, numerical, tolerance=1e-5):
    for i, (a, n) in enumerate(zip(analytical, numerical)):
        denom = max(abs(a), abs(n), 1e-8)
        rel_error = abs(a - n) / denom
        status = "OK" if rel_error < tolerance else "FAIL"
        print(f"  param {i}: analytical={a:.8f} numerical={n:.8f} "
              f"rel_error={rel_error:.2e} [{status}]")

def f(params):
    x, y = params
    return x**2 + 3*x*y + y**3

def f_grad(params):
    x, y = params
    return [2*x + 3*y, 3*x + 3*y**2]

point = [2.0, 1.0]
analytical = f_grad(point)
numerical = numerical_gradient(f, point)
check_gradient(analytical, numerical)
```

> 🎒 **На пальцах.** Проверьте аналитическую формулу сами: для f = x² + 3xy + y³ производная по x равна 2x + 3y, в точке (2, 1) это 4 + 3 = 7. По y: 3x + 3y² = 6 + 3 = 9. Программа должна напечатать примерно 7 и 9 обоими способами. Если численный и аналитический разошлись — ошибка в формуле, и вы её только что поймали.

def float32_to_float16_round(x):
    packed = struct.pack('f', x)

### Gradient clipping

```python
def clip_by_norm(gradients, max_norm):
    total_norm = math.sqrt(sum(g**2 for g in gradients))
    if total_norm > max_norm:
        scale = max_norm / total_norm
        return [g * scale for g in gradients]
    return gradients

grads = [10.0, 20.0, 30.0]
clipped = clip_by_norm(grads, max_norm=5.0)
print(f"Original norm: {math.sqrt(sum(g**2 for g in grads)):.2f}")
print(f"Clipped norm:  {math.sqrt(sum(g**2 for g in clipped)):.2f}")
print(f"Direction preserved: {[c/clipped[0] for c in clipped]} == {[g/grads[0] for g in grads]}")
```

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|----------------------|
| IEEE 754 | «Стандарт чисел с плавающей точкой» | Международный стандарт, задающий двоичные форматы, правила округления и особые значения (inf, nan). Реализован в каждом современном процессоре и GPU. |
| Machine epsilon | «Предел точности» | Наименьшее e такое, что 1.0 + e != 1.0 в данном формате. Для float32 это около 1.19e-7. |
| Catastrophic cancellation | «Потеря точности при вычитании» | При вычитании почти равных чисел значащие цифры взаимно уничтожаются, и результатом правит шум округления. |
| Overflow | «Число слишком большое» | Результат превышает максимальное представимое значение и становится inf. exp(89) переполняет float32. |
| Underflow | «Число слишком маленькое» | Результат ближе к нулю, чем наименьшее представимое положительное число, и становится 0.0. exp(-104) исчезает во float32. |
| Log-sum-exp trick | «Сначала вычесть максимум» | Вычисление log(sum(exp(x))) с выносом exp(max(x)) для защиты от переполнения и исчезновения. Используется в softmax, cross-entropy и арифметике логарифмов вероятностей. |
| Stable softmax | «Softmax, который не взрывается» | Вычитание max(logits) перед экспонированием. Численно тот же результат, переполнение невозможно. |
| Gradient checking | «Проверить свой backprop» | Сравнение аналитических градиентов из обратного распространения с численными из конечных разностей для поимки багов реализации. |
| Mixed precision | «Float16 вперёд, float32 назад» | Использование чисел меньшей точности для критичных к скорости операций и большей точности для численно чувствительных. Типичное ускорение 2-3 раза. |
| Loss scaling | «Спасти градиенты от исчезновения» | Умножение потерь на большую константу перед обратным проходом, чтобы градиенты остались в представимом диапазоне float16, с обратным делением перед обновлением весов. |
| bfloat16 | «Brain floating point» | 16-битный формат от Google с 8 битами экспоненты (диапазон как у float32) и 7 битами мантиссы (точность ниже float16). Предпочтителен для обучения. |
| Gradient clipping | «Ограничить норму градиента» | Масштабирование вектора градиента так, чтобы его норма не превышала порог. Не даёт взрывающимся градиентам испортить веса. |
| NaN | «Not a Number» | Особое значение из неопределённых операций (0/0, inf-inf, sqrt(-1)). Распространяется по всей последующей арифметике. |
| Inf | «Бесконечность» | Особое значение из переполнения или деления на ноль. В комбинациях порождает NaN (inf - inf, inf * 0). |
| Numerical gradient | «Производная в лоб» | Приближение производной вычислением f(x+h) и f(x-h) с делением на 2h. Медленно, но надёжно для проверки. |
