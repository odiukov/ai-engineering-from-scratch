# Долгоживущие фоновые агенты: надёжное выполнение (durable execution)

> Продакшен-агенты с длинным горизонтом не живут в `while True`. Каждый вызов модели становится activity с чекпоинтом, повтором и воспроизведением. Интеграция Temporal с OpenAI Agents SDK вышла в GA в марте 2026. Claude Code Routines (Anthropic) запускает Claude Code по расписанию без постоянного локального процесса. Сессии встают на паузу в ожидании человека, переживают деплои и продолжаются с последнего чекпоинта по ключу `thread_id`. За новой эргономикой стоит старый паттерн — оркестрация workflow — с одним новым входом: вызовы модели как недетерминированные activity, которые при восстановлении надо детерминированно воспроизвести.

**Type:** Learn
**Languages:** Python (stdlib, minimal durable-execution state machine)
**Prerequisites:** Phase 15 · 10 (Permission modes), Phase 15 · 01 (Long-horizon agents)
**Time:** ~60 minutes

## The Problem

Представьте агента, который работает четыре часа. Он вызывает три инструмента, дважды спрашивает пользователя и делает сорок вызовов модели. На середине машина, на которой он крутится, перезагружается. Что происходит?

> 🎒 **На пальцах.** Задержитесь на числах: четыре часа, три инструмента, два вопроса человеку, сорок вызовов модели. Это не экзотика, а обычный ночной прогон. И перезагрузка машины на середине — событие, которое случается не «если», а «когда».

- В наивном цикле `while True`: потеряно всё. Прогон стартует с нуля. Три вызова инструментов (с настоящими побочными эффектами) выполняются снова. Пользователя снова спрашивают про то, что он уже одобрил. Сорок вызовов модели оплачиваются заново.
- С durable execution: прогон продолжается с самого свежего чекпоинта. Уже завершённые activity не выполняются повторно; их результаты воспроизводятся из durable-журнала. Пользователь не одобряет заново то, что уже одобрил. Уже сделанные вызовы модели не оплачиваются второй раз.

> 🎒 **На пальцах.** Сравните две строки по деньгам: если один вызов модели стоит 2 цента, наивный перезапуск дарит провайдеру 80 центов на пустом месте, и это только за один сбой. Но хуже денег — три повторных вызова инструментов: письмо отправлено дважды, файл удалён дважды, платёж прошёл дважды. Побочные эффекты нельзя «оплатить заново», их приходится разгребать.

Это тот же паттерн, который движки workflow поставляют уже десять лет (Temporal, Cadence, Cherami в Uber). Новое здесь то, что вызовы модели теперь тоже разновидность activity — недетерминированные, дорогие, с побочными эффектами, — и они ложатся в этот паттерн чисто.

Сквозная тема урока: надёжность на длинном горизонте деградирует (METR наблюдает «деградацию после 35 минут» — доля успеха падает примерно квадратично с ростом горизонта). Durable execution позволяет делать прогоны длиннее, чем позволяет профиль надёжности, а это новый способ падать безопасно при правильном проекте и небезопасно при неправильном.

> 🎒 **На пальцах.** Последняя фраза — предупреждение, а не реклама. Durable execution не делает агента надёжнее, оно снимает ограничение по времени: теперь прогон может идти шесть часов вместо тридцати минут. Если качество падает квадратично, то шестичасовой прогон — это очень много плохих шагов, аккуратно сохранённых в журнал.

## The Concept

### Activities, workflows, and replay

- **Workflow**: детерминированный код оркестрации. Задаёт последовательность activity, ветвления, ожидания. Обязан быть детерминированным, чтобы его можно было воспроизвести из журнала событий без неожиданных расхождений.
- **Activity**: недетерминированная единица работы, которая может упасть. Вызов модели, вызов инструмента, запись файла, HTTP-запрос. Каждая activity пишется в журнал вместе со входами и (после завершения) с выходами.
- **Event log**: durable-хранилище под всем этим. Записывается каждый старт, завершение, отказ и повтор activity, а также каждое решение workflow.
- **Replay**: при восстановлении код workflow прогоняется с самого начала; каждая уже завершённая activity возвращает записанный результат, не выполняясь снова. По-настоящему выполняются только те activity, которые не успели завершиться.

> 🎒 **На пальцах.** Главное разделение здесь такое: workflow — это сценарий, activity — это поступки. Сценарий можно перечитывать сколько угодно, он всегда даёт тот же порядок; поступки повторять нельзя, поэтому их результаты берутся из журнала. Поэтому в workflow запрещены случайные числа и часы: перечитанный сценарий должен читаться одинаково.

Форма та же, что у React, перерисовывающего виртуальный DOM, или у Git, восстанавливающего рабочее дерево из коммитов. Детерминизм в оркестраторе — вот что делает надёжность дешёвой.

> 🎒 **На пальцах.** Сравнение с Git точное: коммиты — это журнал, рабочее дерево — состояние, и его можно выбросить и собрать заново, потому что журнал полный. Дешёвой надёжность становится именно поэтому: хранить надо только события, а не снимок всей памяти агента после каждого шага.

### Why LLM calls fit the pattern

Вызовы модели:
- Недетерминированные (temperature > 0; даже при temperature 0 результат уплывает между версиями модели).
- Дорогие (деньги и задержка).
- Способные упасть (лимиты частоты, таймауты).
- С побочными эффектами (если вызывают инструменты).

Это ровно профиль activity. Обернув каждый вызов модели в activity, вы получаете повторы с экспоненциальной выдержкой, чекпоинты через перезапуски и воспроизводимый трейс для отладки.

> 🎒 **На пальцах.** Обратите внимание, что все четыре свойства — про ненадёжность и цену, и это не случайно. Вызов модели по повадкам ближе к сетевому запросу в чужой сервис, чем к вызову локальной функции. Как только вы начнёте относиться к нему так, повторы и чекпоинты станут очевидны сами.

### Checkpoints keyed by `thread_id`

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects и Claude Code Routines сошлись на одной форме API: `thread_id` (или его аналог) определяет сессию; каждый переход состояния сохраняется в бэкенд (PostgreSQL по умолчанию, SQLite для разработки, Redis для кеша); продолжение читает последний чекпоинт.

> 🎒 **На пальцах.** `thread_id` — это номерок в гардеробе: по нему находят именно ваше состояние среди тысячи чужих. Четыре независимые команды пришли к одной и той же идее, и это хороший знак: значит, это не мода одного фреймворка, а минимально необходимая вещь.

Выбор бэкенда важен:

- **PostgreSQL**: durable, можно запрашивать, переживает деплои. Значение по умолчанию для LangGraph.
- **SQLite**: только локальная разработка; между хостами данные теряются.
- **Redis**: быстрый, но недолговечный, если не настроены AOF или снимки.
- **Cloudflare Durable Objects**: распределяется прозрачно; область задаётся уникальным ключом; живёт от часов до недель.

> 🎒 **На пальцах.** Проверьте себя на строке про SQLite: почему «только разработка»? Потому что файл лежит на одной машине, а в проде ваши воркеры завтра поднимутся на другой — и чекпоинтов там нет. Тот же прогон в PostgreSQL продолжится с любого хоста, потому что состояние живёт отдельно от процесса.

### Human-input as a first-class state

Схема «сначала предложи, потом исполняй» (урок 15) требует durable-состояния «ждём человека». Workflow встаёт на паузу, внешняя очередь держит ожидающий запрос, а одобрение продолжает работу ровно с этой точки. Без надёжности это работает как получится; с ней ночное одобрение приходит утром, и workflow подхватывает дело.

> 🎒 **На пальцах.** Ключевое слово — «состояние», а не «ожидание в коде». Агент, который держит паузу через `input()` в живом процессе, умрёт вместе с процессом; агент, у которого «ждём человека» записано в журнал, спокойно переживёт ночь и деплой. Вы приходите утром, нажимаете «ок» — и прогон едет дальше с того же шага.

### The 35-minute degradation

METR наблюдает, что все измеренные классы агентов показывают деградацию надёжности после примерно 35 минут непрерывной работы. Удвоение длительности задачи примерно вчетверо повышает частоту отказов. Durable execution это не лечит; оно позволяет делать прогоны длиннее, чем позволяет профиль надёжности. Безопасная схема — сочетать надёжность с чекпоинтами, требующими свежего участия человека при возврате в работу, и с аварийными выключателями по бюджету (урок 13), которые ограничивают общий расход вычислений независимо от времени по часам.

> 🎒 **На пальцах.** Посчитайте «квадратично» на числах: если на 35 минутах отказов 10%, то на 70 минутах их около 40%, а на 140 — задача почти гарантированно провалится. Отсюда вывод: длинную задачу надо резать на куски по полчаса с чекпоинтом и подтверждением между ними, а не запускать одним шестичасовым забегом.

### When durable execution is the wrong answer

- Прогоны короче нескольких минут без участия человека. Накладные расходы больше выгоды.
- Строго read-only извлечение информации.
- Задачи, где для корректности нужно уложиться в одно окно контекста от начала до конца (часть задач на рассуждение; часть однократных генераций).

> 🎒 **На пальцах.** Первый пункт легко посчитать: если прогон длится 20 секунд, а запись чекпоинтов добавляет 5, вы платите четверть времени за страховку от сбоя, который дешевле просто перезапустить. Durable execution окупается там, где повторный прогон дороже записи состояния — то есть на десятках минут, а не на секундах.

## Use It

`code/main.py` реализует минимальный движок durable execution на стандартной библиотеке Python. Он поддерживает:

- Декоратор `@activity`, который пишет входы и выходы в журнал событий в формате JSON.
- Функцию workflow, выстраивающую activity по порядку.
- Функцию `run_or_replay(workflow, event_log)`, которая воспроизводит завершённые activity, не выполняя их снова.

> 🎒 **На пальцах.** Обратите внимание, что весь механизм — это декоратор плюс словарь с результатами. Никакого Temporal для понимания идеи не нужно: «посмотри в журнал, есть результат — верни его, нет — выполни и запиши». Промышленные движки добавляют распределённость и гарантии, а не другую идею.

Драйвер имитирует workflow из трёх activity, падает на середине и показывает: (a) наивный повтор, который выполняет всё заново, против (b) воспроизведение, которое выполняет только пропущенную activity.

> 🎒 **На пальцах.** Считайте выполненные activity: наивный повтор даст 3 + 3 = 6 выполнений, воспроизведение — 3 + 1 = 4. При падении после второго шага разница ещё заметнее в пользу replay. Именно это число — счётчик выполнений — и есть измеримая польза durable execution.

Скилл нужен затем, чтобы эти ошибки нашлись на схеме, а не на четвёртом часу прогона.

## Exercises

1. Запустите `code/main.py`. Посмотрите на разницу в числе выполненных activity между наивным повтором и воспроизведением. Сдвиньте точку падения и покажите, что число при воспроизведении меняется соответственно.

2. Переведите игрушечный движок на явный `thread_id`. Смоделируйте две одновременные сессии, использующие один движок, и убедитесь, что их журналы событий не пересекаются.

3. Возьмите одну activity в игрушечном движке. Внесите недетерминизм (метка времени по часам внутри решения workflow). Покажите расхождение при воспроизведении. Объясните, как с этим справляются настоящие движки (регистрация побочного эффекта, API вида `Workflow.now()`).

4. Прочитайте пост LangChain «Runtime behind production deep agents». Выпишите все состояния, которые сохраняет этот рантайм, и назовите, какой режим отказа закрывает каждое из них.

5. Спроектируйте политику чекпоинтов для шестичасовой автономной задачи по программированию. Где вы ставите чекпоинты? Как выглядит продолжение после падения? Что требует свежего участия человека?

> 🎒 **На пальцах.** Задание 3 стоит того, чтобы его сделать руками: положите в workflow `time.time()`, и при воспроизведении сценарий пойдёт другой веткой, чем в первый раз, потому что часы показывают другое. Журнал при этом «правильный», а поведение разъехалось — и отладить это в проде почти невозможно. Один раз увидев расхождение на игрушке, вы больше никогда не положите часы в workflow.

## Key Terms

| Term | What people say | What it actually means |
|---|---|---|
| Workflow | «Сценарий агента» | Детерминированный код оркестрации; воспроизводим из журнала событий |
| Activity | «Шаг» | Недетерминированная единица (вызов модели, вызов инструмента); пишется в журнал до и после |
| Event log | «Хранилище» | Durable-запись каждого перехода состояния |
| Replay | «Продолжение» | Повторный прогон workflow; завершённые activity возвращают записанный результат без повторного выполнения |
| Checkpoint | «Точка сохранения» | Сохранённое состояние по ключу thread_id; при продолжении берётся последнее |
| thread_id | «Ключ сессии» | Идентификатор, задающий область durable-состояния |
| 35-minute degradation | «Спад надёжности» | METR: доля успеха падает примерно квадратично с ростом горизонта |
| Non-determinism | «Расхождение при повторе» | Часы, случайность, вывод модели; должны регистрироваться как побочный эффект |

> 🎒 **На пальцах.** Прочитайте таблицу как одну цепочку: workflow ведёт activity, activity пишутся в event log, из журнала делается replay, последняя запись — это checkpoint, а область задаётся thread_id. Две нижние строки — про то, что эту цепочку ломает: непредсказуемое время и непредсказуемый вывод модели. Запомните цепочку, и остальное достраивается само.
