# Примитивная модель мультиагентных систем

> Четыре примитива, и больше ничего — агент, handoff, общее состояние, оркестратор — задают четырёхмерное пространство проектирования, и все крупные мультиагентные фреймворки, живые в 2026 году (AutoGen, LangGraph, CrewAI, OpenAI Agents SDK, Microsoft Agent Framework), — это точки внутри него. В этом уроке мы соберём примитивы с нуля, прогоним на всех четырёх игрушечную систему, а потом разложим каждый крупный фреймворк по тем же осям — чтобы любой новый релиз читался за один абзац.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 (Agent Engineering), Phase 16 · 01 (Why Multi-Agent)
**Time:** ~60 minutes

## Problem

Каждые полгода выходит новый мультиагентный фреймворк. AutoGen в 2023-м. CrewAI в 2024-м. LangGraph и OpenAI Swarm в 2024-м. Google ADK в апреле 2025-го. Microsoft Agent Framework RC в феврале 2026-го. И каждый пресс-релиз объявляет себя «той самой правильной абстракцией».

Если учить их по одному, вы выгорите. API выглядят по-разному. Документации спорят даже о том, что такое «агент». Один фреймворк называет общую память «blackboard», другой — «message pool», третий — «StateGraph». И начинает казаться, что отрасль просто толчётся на месте.

Это не так. Под маркетингом лежат четыре стабильных примитива. Выучите их один раз — и любой новый фреймворк читается за один абзац.

> 🎒 **На пальцах.** Это как учить машины: можно запоминать каждую модель отдельно, а можно один раз понять, что везде есть руль, педали, коробка и колёса. Дальше «новая модель» — это не новая наука, а просто другой набор настроек тех же четырёх штук. Считайте: пять фреймворков из абзаца выше, а примитивов всё равно четыре.

## Concept

### The four primitives

1. **Agent** — системный промпт плюс список инструментов. Без состояния: каждый запуск начинается с системного промпта и текущей истории сообщений.
2. **Handoff** — структурированная передача управления от одного агента другому. Механически это вызов инструмента, возвращающий нового агента, или ребро графа, которое срабатывает по условию.
3. **Shared state** — любая структура данных, которую могут читать (иногда и писать) несколько агентов. Message pool, blackboard, key-value store, векторная память.
4. **Orchestrator** — тот, кто решает, кто говорит следующим. Варианты: явный граф (детерминированный), LLM-выбор говорящего (мягкий), handoff-вызов последнего говорившего (OpenAI Swarm) или планировщик над очередью (архитектура swarm).

Вот и всё пространство проектирования. Каждый фреймворк просто выбирает значения по умолчанию на каждой оси; остальное — поверхностный синтаксис.

> 🎒 **На пальцах.** Представьте школьный проект: есть ученики (agent), есть «передай эстафету соседу» (handoff), есть общая тетрадь на столе (shared state) и есть тот, кто говорит «теперь ты» (orchestrator). Четыре роли — и любая групповая работа описывается через них. Всё, что фреймворк добавляет сверху, — это форма записи, а не новая сущность.

### How every 2026 framework maps to it

| Framework | Agent | Handoff | Shared state | Orchestrator |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | инструмент возвращает Agent | забота вызывающего кода | следующий handoff-вызов LLM |
| AutoGen v0.4 / AG2 | `ConversableAgent` | выбор говорящего в GroupChat | message pool | функция-селектор (LLM или round-robin) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | выходы Task, сцепленные в цепочку | LLM-менеджер или фиксированный порядок |
| LangGraph | функция-узел | ребро графа плюс условие | reducer в `StateGraph` | сам граф, детерминированно |
| Microsoft Agent Framework | агент плюс паттерны оркестрации | зависит от паттерна | thread / context | зависит от паттерна |
| Google ADK | агент плюс A2A-карточка | A2A-задача | A2A-артефакты | решает host |

Поверхностные различия выглядят огромными. Внутри — те же четыре ручки.

> 🎒 **На пальцах.** Пробегитесь по таблице по столбцам, а не по строкам: шесть фреймворков, четыре колонки — и в каждой колонке всего два-три реально разных ответа. Например, оркестратор бывает либо графом, либо LLM, либо самим агентом, либо очередью. Так «шесть фреймворков» превращаются в шесть коротких строк, которые можно запомнить.

### Why this matters

Как только вы видите примитивы, сравнение фреймворков превращается в короткий чек-лист:

- Оркестратор доверяет маршрутизацию LLM (Swarm) или прибивает её в коде (LangGraph)?
- Общее состояние — это полная история (GroupChat) или проекция (reducer в StateGraph)?
- Могут ли агенты менять промпты друг другу (менеджер в CrewAI) или только передавать управление (Swarm)?

Эти три вопроса закрывают 80% выбора фреймворка под конкретную задачу. Вы перестаёте искать «лучший мультиагентный фреймворк» и начинаете проектировать под ту ось, которая вам действительно важна.

> 🎒 **На пальцах.** Три вопроса вместо трёх недель чтения документации — это очень хороший обмен. Проверьте на себе: если задача требует аудита каждого шага, первый же вопрос отсекает Swarm и указывает на LangGraph. Дальше читать документацию вы будете уже с ответом в голове, а не в поисках ответа.

### The stateless insight

Все примитивы, кроме общего состояния, не имеют состояния. Agent — функция от (промпт, инструменты). Handoff — вызов функции. Orchestrator — планировщик. **The only stateful thing in the system is shared state.** Именно там живут все интересные баги: отравление памяти (урок 15), порядок сообщений, версионирование, конкуренция на запись.

Фреймворки, которые прячут общее состояние (Swarm), спихивают проблему на вызывающий код. Фреймворки, которые его централизуют (checkpoint в LangGraph, pool в AutoGen), делают его наблюдаемым, но переносят цену координации на реализацию самого общего состояния.

> 🎒 **На пальцах.** Это как класс, где все ученики без памяти, а вся память — в одной общей тетради на столе. Значит, искать причину странного поведения надо не в учениках, а в тетради: кто что туда дописал и в каком порядке. Из четырёх примитивов ровно один хранит состояние — и он даёт почти все баги.

### Anatomy of a single primitive

#### Agent

```
Agent = (system_prompt, tools, model, optional_name)
```

Ни памяти, ни состояния. Два агента с одинаковым системным промптом и одинаковыми инструментами взаимозаменяемы. Всё, что выглядит как состояние отдельного агента, на самом деле лежит в общем состоянии или в протоколе handoff.

> 🎒 **На пальцах.** Агент здесь — как повар по рецепту: дайте двум людям один рецепт и один набор кастрюль, и они выдадут одно и то же блюдо. Формула из четырёх полей выше — это весь агент целиком, и в ней нет слота под «помню, что было вчера». Если вам кажется, что агент что-то помнит, память лежит снаружи него.

#### Handoff

```
Handoff = (from_agent, to_agent, reason, payload)
```

Доминируют три реализации:

- **Function return** — инструмент возвращает следующего агента. Это паттерн OpenAI Swarm. Маршрутизация живёт прямо в схемах инструментов агента.
- **Graph edge** — LangGraph. Рёбра описаны декларативно. LLM выдаёт значение, а условие выбирает следующий узел.
- **Speaker selection** — GroupChat в AutoGen. Функция-селектор (иногда сама по себе вызов LLM) читает pool и решает, кто говорит следующим.

> 🎒 **На пальцах.** Три способа передать эстафету: сам бегун указывает, кому отдать палочку (function return); маршрут нарисован заранее на дорожке (graph edge); судья на вышке выкликает следующего (speaker selection). Разница не в скорости, а в том, кто виноват, если палочка ушла не туда. В первом случае — модель, во втором — ваш код, в третьем — селектор.

#### Shared state

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

Как минимум это список сообщений. Часто больше: структурированные артефакты (выходы Task в CrewAI), типизированный контекст (reducer'ы в LangGraph), внешняя память (MCP, векторная база).

Есть две топологии: **full pool** (каждый агент видит каждое сообщение) и **projected** (агент видит вид, урезанный под свою роль). Полные пулы просты и плохо масштабируются. Проецированные масштабируются, но требуют заранее спроектированной схемы.

> 🎒 **На пальцах.** Full pool — это общий чат класса, где все читают всё: удобно, пока вас пятеро. Посчитайте: 10 агентов по 20 сообщений — и каждый следующий вызов тащит 200 сообщений контекста, хотя нужны ему три. Projected state — это когда каждому приходит только его страница; дороже спроектировать, зато счёт за токены не растёт квадратично.

#### Orchestrator

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

Четыре разновидности:

- **Static** — граф зафиксирован на этапе сборки (детерминированный LangGraph, CrewAI Sequential).
- **LLM-selected** — LLM читает pool и выбирает следующего говорящего (AutoGen, CrewAI Hierarchical).
- **Handoff-driven** — текущий агент решает сам, вызывая инструмент-handoff (Swarm).
- **Queue-driven** — воркеры сами забирают задачи из общей очереди; явного «следующего говорящего» нет (архитектуры swarm, Matrix).

> 🎒 **На пальцах.** Это четыре способа решить, кто говорит на собрании: расписание (static), ведущий (LLM-selected), «передаю слово Пете» от текущего выступающего (handoff-driven) и «кто свободен, тот берёт задачу» (queue-driven). Первый предсказуем и скучен, последний быстр и непредсказуем. Формула выше показывает, почему они взаимозаменяемы: у всех четырёх один и тот же вход и один и тот же выход.

### What changes between frameworks

Когда примитивы зафиксированы, остаются такие решения:

- **Memory strategy** — эфемерная память против долговечных чекпоинтов (checkpointer в LangGraph).
- **Safety boundary** — кто может одобрить handoff (human-in-the-loop).
- **Cost accounting** — токен-бюджеты на каждого агента.
- **Observability** — трассировка handoff'ов, сохранение состояния для повторного проигрывания.

Всё это реализуется поверх примитивов. Ни одно из них новым примитивом не является.

> 🎒 **На пальцах.** Полезный тест на «пятый примитив»: если фичу можно собрать из четырёх имеющихся, это не примитив, а удобство. Токен-бюджет на агента — просто счётчик рядом с agent; трассировка — лог вокруг handoff. Ни то ни другое не добавляет новой оси в пространство проектирования.

## Build It

`code/main.py` реализует четыре примитива примерно в 150 строках на стандартной библиотеке Python. Настоящего LLM нет: каждый агент — скриптованная политика, чтобы внимание оставалось на структуре координации.

Файл экспортирует:

- `Agent` — датакласс с именем, системным промптом, инструментами и функцией-политикой.
- `Handoff` — функция, возвращающая нового агента.
- `SharedState` — потокобезопасный пул сообщений.
- `Orchestrator` — три варианта: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator` (симулированный).

Демо прогоняет один и тот же конвейер из трёх агентов (research → write → review) через все три типа оркестратора и в конце печатает пул сообщений. Видно, что выходы различаются только тем, *кто выбирает следующего*; агенты и общее состояние во всех прогонах одинаковые.

> 🎒 **На пальцах.** Это контролируемый эксперимент: три агента и общее состояние заморожены, меняется ровно одна переменная — оркестратор. Так вы видите чистый вклад одного примитива, а не смесь эффектов. Ровно так же стоит менять и рабочую систему: по одной ручке за раз.

Запустите:

```
python3 code/main.py
```

Ожидаемый вывод: три прогона, по одному на паттерн. Каждый печатает финальный пул сообщений. Handoff-прогон доходит до меньшего числа агентов, если исследователь решит, что работа закончена раньше времени, — это компромисс LLM-маршрутизации в миниатюре.

> 🎒 **На пальцах.** Обратите внимание на последнюю фразу: при handoff-маршрутизации из трёх агентов может отработать один, потому что модель сама решила, что хватит. Static-оркестратор в той же задаче честно пройдёт все три. Дешевле — не всегда правильнее: вы обменяли предсказуемость на скорость.

## Ship It

Прежде чем принимать новый фреймворк, напишите для него раскладку по примитивам. Если не получается — либо документация неполная, либо фреймворк изобретает пятый примитив (редкость: проверьте, не встретился ли вам незнакомый вид общего состояния).

Закрепите раскладку в вашем архитектурном документе. Новому человеку в команде отправляйте сначала раскладку, а потом уже документацию по API. Когда меняется версия фреймворка, сравнивайте раскладки, а не changelog.

> 🎒 **На пальцах.** Раскладка по примитивам — это как схема метро вместо списка всех улиц: одна страница, которая объясняет, куда что ведёт. Диффить её между версиями гораздо продуктивнее, чем читать changelog из двухсот строк: если все четыре оси остались на месте, релиз для вас косметический.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Agent | «LLM с инструментами» | Тройка `(system_prompt, tools, model)`. Без состояния. |
| Handoff | «Передача управления» | Структурированный вызов, который называет следующего агента и необязательную полезную нагрузку. Три реализации: возврат из функции, ребро графа, выбор говорящего. |
| Shared state | «Память» / «контекст» | Единственная часть мультиагентной системы, у которой есть состояние. Пул сообщений или blackboard. |
| Orchestrator | «Координатор» | Тот, кто решает, кто работает следующим. Статический граф, LLM-селектор, handoff-driven или queue-driven. |
| Primitive | «Абстракция» | Одна из четырёх осей, которые параметризует любой фреймворк. Не фича фреймворка. |
| Message pool | «Общая история чата» | Общее состояние с полной историей. Легко рассуждать, плохо масштабируется. |
| Projected state | «Урезанный вид» | Вид на общее состояние под конкретную роль. Масштабируется, требует проектирования схемы. |
| Speaker selection | «Кто говорит следующим» | Паттерн оркестрации, где функция (часто LLM) выбирает следующего агента из группы. |

> 🎒 **На пальцах.** Обратите внимание на строку Primitive: примитив — это ось, а не галочка в списке фич. И сравните две строки про состояние: message pool и projected state — это один и тот же примитив в двух режимах, и выбор между ними определяет, во что вам обойдётся десятый агент.
