# Зачем вообще мультиагентность?

> Один агент упирается в стену. Умный ход — не агент побольше, а агентов побольше.

**Type:** Learn
**Languages:** TypeScript
**Prerequisites:** Phase 14 (Agent Engineering)
**Time:** ~60 minutes

## Learning Objectives

- Различать признаки потолка одного агента (переполнение контекста, смешанные экспертизы, последовательное узкое место) и объяснять, когда разделение на несколько агентов — правильный ход
- Сравнивать паттерны оркестрации (pipeline, параллельный fan-out, supervisor, иерархия) и выбирать подходящий под структуру задачи
- Проектировать мультиагентную систему с чёткими границами ролей, общим состоянием и контрактом на обмен сообщениями
- Разбирать компромиссы мультиагентной сложности (задержка, стоимость, сложность отладки) против простоты одного агента

## The Problem

В фазе 14 вы собрали одного агента. Он работает. Умеет читать файлы, запускать команды, вызывать API и рассуждать о результатах. А потом вы направляете его на настоящую кодовую базу: 200 файлов, три языка, тесты, которым нужна инфраструктура, и требование сперва изучить внешние API, а потом писать код.

Агент захлёбывается. Не потому, что LLM глупая, а потому что задача больше того, что вмещает один агентный цикл. Контекстное окно забивается содержимым файлов. Агент забывает, что читал 40 вызовов инструментов назад. Он пытается быть одновременно исследователем, программистом и ревьюером — и все три роли исполняет плохо.

Это и есть потолок одного агента. Вы бьётесь в него каждый раз, когда задача требует:

- **More context than fits in one window** — чтение 50 файлов вылетает за 200k токенов
- **Different expertise at different stages** — исследование требует других промптов, чем генерация кода
- **Work that can happen in parallel** — зачем читать три файла по очереди, если можно читать их одновременно?

> 🎒 **На пальцах.** Это как один человек, который сам себе и прораб, и сантехник, и электрик: на маленькой кухне справится, а на стройке в 200 квартир нет. Посчитайте: 50 файлов по 4k токенов — это уже 200k, то есть целое окно уходит только на чтение, а на рассуждение не остаётся ничего. Плюс агент за 40 вызовов инструментов честно забывает, что видел на пятом.

## The Concept

### The Single-Agent Ceiling

Один агент — это один цикл, одно контекстное окно, один системный промпт. Представьте себе картинку:

```
┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘
```

Ломаются три вещи:

1. **Context saturation** — результаты инструментов накапливаются. К тридцатому ходу агент съел 150k токенов содержимого файлов, вывода команд и прошлых рассуждений. Важные детали с пятого хода теряются.

2. **Role confusion** — системный промпт со словами «ты исследователь, программист, ревьюер и тестировщик» даёт агента, который наполовину исследует, наполовину кодит и никогда не доводит ревью до конца.

3. **Sequential bottleneck** — агент читает файл A, потом файл B, потом файл C. Три последовательных вызова LLM. Три последовательных запуска инструментов. Никакого параллелизма.

> 🎒 **На пальцах.** Контекст — это рабочий стол: пока на нём три бумажки, всё видно, а когда 150k токенов бумаг, нужный листок теряется под остальными. Обратите внимание на третий пункт: три файла по очереди — это три круга «запрос к модели → ответ», и если каждый круг занимает 5 секунд, вы ждёте 15 вместо 5.

### The Multi-Agent Solution

Разделите работу. Дайте каждому агенту одну задачу, одно контекстное окно и один системный промпт, заточенный под эту задачу:

```
┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘
```

У каждого агента есть:
- Узкий системный промпт («Ты ревьюер кода. Твоя единственная работа — искать баги.»)
- Своё контекстное окно (не загрязнённое работой других агентов)
- Понятный контракт вход/выход (получает заметки исследователя, отдаёт код)

> 🎒 **На пальцах.** Это переход от мастера-универсала к бригаде: исследователь, кодер, ревьюер, тестировщик. Главная выгода не в количестве голов, а в чистоте столов: 50k токенов документации, которые прочитал исследователь, вообще не попадают в окно ревьюера — он видит только код. И промпт ревьюера можно написать жёстко под баги, не размазывая его на четыре роли.

### Real Systems That Do This

**Claude Code subagents** — когда Claude Code запускает субагента через `Task`, он создаёт дочернего агента с ограниченной задачей. Родитель сохраняет свой контекст чистым. Ребёнок делает узкую работу и возвращает выжимку.

**Devin** — держит агента-планировщика, агента-кодера и агента-браузера. Планировщик разбивает работу на шаги. Кодер пишет код. Браузер изучает документацию. У каждого отдельный контекст.

**Multi-agent coding teams (SWE-bench)** — лучшие системы на SWE-bench используют исследователя, который читает кодовую базу, планировщика, который проектирует исправление, и кодера, который его реализует. Одноагентные системы набирают меньше.

**ChatGPT Deep Research** — запускает несколько поисковых агентов параллельно, каждый копает свой угол, потом результаты синтезируются.

> 🎒 **На пальцах.** Все четыре примера про одно: родитель не читает сам, а раздаёт чтение. В Claude Code это видно буквально — субагент прочитает 20 файлов, а родителю вернёт абзац выжимки, то есть вместо 80k токенов в родительский контекст попадёт около 300. Deep Research делает то же самое по ширине: пять углов темы копаются одновременно, а не по очереди.

### The Spectrum

Мультиагентность — не выбор «да или нет». Это спектр:

```
SIMPLE ──────────────────────────────────────────── COMPLEX

 Single        Sub-         Pipeline      Team         Swarm
 Agent         agents

 ┌───┐       ┌───┐        ┌───┐───┐    ┌───┐───┐    ┌─┐┌─┐┌─┐
 │ A │       │ A │        │ A │ B │    │ A │ B │    │ ││ ││ │
 └───┘       └─┬─┘        └───┘─┬─┘    └─┬─┘─┬─┘    └┬┘└┬┘└┬┘
               │                │        │   │       ┌┴──┴──┴┐
             ┌─┴─┐          ┌───┘───┐    │   │       │shared │
             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles
```

**Single agent** — один цикл, один промпт. Годится для простых задач.

**Subagents** — родитель порождает детей под узкие подзадачи. Родитель держит план. Дети докладывают о результате. Именно так работает Claude Code.

**Pipeline** — агенты идут по очереди. Выход агента A становится входом агента B. Годится для стадийных процессов: исследование -> код -> ревью -> тесты.

**Team** — агенты работают параллельно через общую шину сообщений. У каждого своя роль. Оркестратор их координирует. Годится, когда разные навыки нужны одновременно.

**Swarm** — много одинаковых или почти одинаковых агентов с общим состоянием. Постоянного оркестратора нет. Агенты сами берут работу из очереди. Годится для высокопроизводительных параллельных задач.

> 🎒 **На пальцах.** Читайте эту шкалу как рост организации: сам себе бизнес, потом помощники, потом конвейер, потом отдел с ролями, потом рынок исполнителей. Заметьте, где именно исчезает начальник: в swarm его нет вовсе, агенты берут задачи из очереди сами. И чем правее по шкале, тем больше сообщений между агентами, а каждое сообщение — новое место, где что-то может сломаться.

### The Four Multi-Agent Patterns

#### Pattern 1: Pipeline

```
Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)
```

Каждый агент преобразует данные и передаёт их дальше. Про такую систему легко рассуждать. Сбой на одной стадии блокирует все следующие.

> 🎒 **На пальцах.** Pipeline — это заводской конвейер: сварка, покраска, сборка. Плюс в предсказуемости: три стадии — ровно три вызова LLM, и всегда в одном порядке. Минус тоже понятен: если покраска встала, машины на сборку не приезжают вообще, а не «приезжают неокрашенными».

#### Pattern 2: Fan-out / Fan-in

```
                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘
```

Работа разбивается на параллельных агентов, потом результаты сливаются. Годится для задач, которые распадаются на независимые подзадачи.

> 🎒 **На пальцах.** Это как раздать трём людям по главе книги и потом собрать конспект. Считаем время: три агента по 5 секунд последовательно — 15 секунд, параллельно — те же 5. Токенов при этом уходит столько же, экономится только время ожидания, и работает это лишь тогда, когда куски действительно независимы.

#### Pattern 3: Orchestrator-Worker

```
                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘
```

Умный оркестратор решает, что делать, делегирует работу исполнителям и синтезирует результаты. Сам оркестратор — тоже агент, у которого среди инструментов есть порождение исполнителей.

> 🎒 **На пальцах.** Оркестратор — прораб: сам не кладёт кирпичи, но решает, кто и что делает. Ключевая деталь в схеме выше — стрелки идут только от центра к исполнителям: worker A и worker B друг о друге ничего не знают. Поэтому за целостность результата отвечает ровно одно место, и разбирать инцидент проще.

#### Pattern 4: Peer Swarm

```
         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘
```

Центрального оркестратора нет. Агенты общаются напрямую друг с другом. Решения возникают из взаимодействия. Отлаживать сложнее, зато масштабируется на много агентов.

> 🎒 **На пальцах.** Swarm — это стайка птиц: вожака нет, но стая летит связно. На схеме четыре агента и общее состояние в центре, и любой может написать любому: это уже до 12 направленных связей вместо 4 в схеме с прораба. Отсюда и цена: масштабируется отлично, а на вопрос «почему система сделала вот это» единственного ответственного не найти.

### When NOT to Use Multi-Agent

Мультиагентность добавляет сложность. Каждое сообщение между агентами — потенциальная точка сбоя. Отладка превращается из «прочитай один диалог» в «проследи сообщения через пять агентов».

**Stay single-agent when:**
- Задача влезает в одно контекстное окно (меньше ~100k токенов рабочих данных)
- Вам не нужны разные системные промпты на разных стадиях
- Последовательного выполнения достаточно по скорости
- Задача настолько проста, что дробление добавляет больше накладных расходов, чем пользы

**The complexity cost:**
- Каждая граница между агентами — шаг сжатия с потерями: полный контекст агента A ужимается в одно сообщение для агента B
- Логика координации (кто что делает, когда и в каком порядке) сама становится источником багов
- Задержка растёт: N агентов — это минимум N последовательных вызовов LLM, а если им нужно переговариваться, то больше
- Стоимость умножается: каждый агент жжёт токены отдельно

Правило большого пальца: если задача укладывается в 20 вызовов инструментов и в 100k токенов, оставляйте одного агента.

> 🎒 **На пальцах.** Два числа из правила стоит запомнить как порог: 20 вызовов инструментов и 100k токенов. Пока вы под ними, дробление — чистый убыток: пять агентов вместо одного превращают отладку одного лога в сверку пяти. И помните про сжатие с потерями: всё, что агент A понял, но не написал в сообщении, для агента B просто не существует.

## Build It

### Step 1: The Overloaded Single Agent

Вот один агент, который пытается сделать всё. У него один огромный системный промпт и одно контекстное окно, в котором лежат исследование, код и ревью:

```typescript
type AgentResult = {
  content: string;
  tokensUsed: number;
  toolCalls: number;
};

async function singleAgentApproach(task: string): Promise<AgentResult> {
  const systemPrompt = `You are a full-stack developer. You must:
1. Research the requirements
2. Write the code
3. Review the code for bugs
4. Write tests
Do ALL of these in a single conversation.`;

  const contextWindow: string[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const research = await fakeLLMCall(systemPrompt, `Research: ${task}`);
  contextWindow.push(research.output);
  totalTokens += research.tokens;
  totalToolCalls += research.calls;

  const code = await fakeLLMCall(
    systemPrompt,
    `Given this research:\n${contextWindow.join("\n")}\n\nNow write code for: ${task}`
  );
  contextWindow.push(code.output);
  totalTokens += code.tokens;
  totalToolCalls += code.calls;

  const review = await fakeLLMCall(
    systemPrompt,
    `Given all previous context:\n${contextWindow.join("\n")}\n\nReview the code.`
  );
  contextWindow.push(review.output);
  totalTokens += review.tokens;
  totalToolCalls += review.calls;

  return {
    content: contextWindow.join("\n---\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Проблемы этого подхода:
- Контекстное окно растёт с каждой стадией. К шагу ревью в нём лежат и заметки исследования, И код, И прошлые рассуждения.
- Системный промпт общий. Его нельзя заточить под каждую стадию.
- Ничего не выполняется параллельно.

> 🎒 **На пальцах.** Посмотрите, как в коде живёт `contextWindow`: на исследовании там один элемент, на коде два, на ревью три — и весь массив каждый раз целиком склеивается в промпт. То есть заметки исследования оплачиваются токенами трижды. Это как таскать с собой все черновики на каждую встречу, потому что «вдруг понадобится».

### Step 2: Specialist Agents

Теперь разделим. Каждый агент получает одну работу:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."
);

const reviewer = createSpecialist(
  "reviewer",
  "You are a code reviewer. Find bugs, security issues, and logic errors. Be specific. Cite line numbers."
);
```

У каждого специалиста узкий промпт. Каждый получает чистое контекстное окно, где лежит только нужный ему вход.

> 🎒 **На пальцах.** Обратите внимание, какие короткие промпты у специалистов: у ревьюера буквально «найди баги, будь конкретен, указывай номера строк» — ни слова про исследование или тесты. Фабрика `createSpecialist` делает их однотипными, так что четвёртый специалист — это три строки кода, а не новая архитектура. Как найм: вместо «универсального сотрудника» — три вакансии с одним абзацем требований.

### Step 3: Coordinate Through Messages

Соединяем специалистов явной передачей сообщений:

```typescript
type AgentMessage = {
  from: string;
  to: string;
  content: string;
  timestamp: number;
};

async function multiAgentApproach(task: string): Promise<AgentResult> {
  const messages: AgentMessage[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const researchResult = await researcher.run(task);
  messages.push({
    from: "researcher",
    to: "coder",
    content: researchResult.content,
    timestamp: Date.now(),
  });
  totalTokens += researchResult.tokensUsed;
  totalToolCalls += researchResult.toolCalls;

  const coderInput = messages
    .filter((m) => m.to === "coder")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const codeResult = await coder.run(coderInput);
  messages.push({
    from: "coder",
    to: "reviewer",
    content: codeResult.content,
    timestamp: Date.now(),
  });
  totalTokens += codeResult.tokensUsed;
  totalToolCalls += codeResult.toolCalls;

  const reviewerInput = messages
    .filter((m) => m.to === "reviewer")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const reviewResult = await reviewer.run(reviewerInput);
  messages.push({
    from: "reviewer",
    to: "orchestrator",
    content: reviewResult.content,
    timestamp: Date.now(),
  });
  totalTokens += reviewResult.tokensUsed;
  totalToolCalls += reviewResult.toolCalls;

  return {
    content: messages.map((m) => `[${m.from} -> ${m.to}]: ${m.content}`).join("\n\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Каждый агент получает только адресованные ему сообщения. Никакого загрязнения контекста. 50k токенов документации, прочитанной исследователем, никогда не попадают в контекст ревьюера.

> 🎒 **На пальцах.** Главная строчка здесь — фильтр `messages.filter((m) => m.to === "coder")`: это и есть почтовый ящик агента. Ревьюер получает одно сообщение от кодера, а не всю переписку из трёх, поэтому его окно остаётся чистым. Как в офисе: вам приносят письма на ваше имя, а не всю входящую почту компании.

### Step 4: Compare

```typescript
async function compare() {
  const task = "Build a rate limiter middleware for an Express.js API";

  console.log("=== Single Agent ===");
  const single = await singleAgentApproach(task);
  console.log(`Tokens: ${single.tokensUsed}`);
  console.log(`Tool calls: ${single.toolCalls}`);

  console.log("\n=== Multi-Agent ===");
  const multi = await multiAgentApproach(task);
  console.log(`Tokens: ${multi.tokensUsed}`);
  console.log(`Tool calls: ${multi.toolCalls}`);
}
```

Мультиагентная версия расходует больше токенов суммарно (три агента, три отдельных вызова LLM), зато контекст каждого агента остаётся чистым. Качество каждой стадии растёт, потому что системный промпт специализирован.

> 🎒 **На пальцах.** Вот честный итог сравнения: суммарные токены выросли, а качество каждого шага тоже выросло. Три агента платят три раза за короткие промпты вместо одного раза за раздутый — иногда это даже дешевле, потому что общий контекст не тащится в каждый вызов. Запустите `compare()` и сравните два числа сами, а не на веру.

## Exercises

1. Добавьте четвёртого специалиста: агента-тестировщика, который получает код от кодера и замечания от ревьюера, а потом пишет тесты

3. Превратите последовательный pipeline в fan-out: запустите исследователя и агента-аналитика требований параллельно, а потом слейте их выходы перед передачей кодеру

> 🎒 **На пальцах.** Во втором задании важен именно лимит «максимум 2 круга»: без счётчика кодер и ревьюер могут гонять правки бесконечно, и каждый круг — это два новых вызова LLM. Третье задание про то же с другой стороны: два параллельных агента дают тот же расход токенов, но время ожидания сокращается примерно вдвое.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|----------------------|
| Swarm | "A hive mind of AI agents" | Набор равноправных агентов с общим состоянием и без постоянного лидера. Поведение возникает из локальных взаимодействий. |
| Orchestrator | "The boss agent" | Агент, среди инструментов которого есть порождение других агентов и управление ими. Он планирует и делегирует, но сам работу может не делать. |
| Coordinator | "The traffic cop" | Не-агентный компонент (часто просто код, а не LLM), который маршрутизирует сообщения между агентами по правилам. |
| Consensus | "The agents agree" | Протокол, по которому несколько агентов должны договориться, прежде чем двигаться дальше. Нужен, когда надо разрешить противоречивые выходы. |
| Emergent behavior | "The agents figured it out themselves" | Паттерны уровня системы, которые возникли из взаимодействий агентов, но никем не программировались. Бывают полезными и вредными. |
| Fan-out / fan-in | "Map-reduce for agents" | Разбиение задачи на параллельных агентов (fan-out), затем объединение их результатов (fan-in). |
| Message passing | "Agents talk to each other" | Механизм связи между агентами: структурированные данные, которые один агент отправляет другому вместо общего контекстного окна. |

> 🎒 **На пальцах.** Обратите внимание на пару Orchestrator / Coordinator: первый — это LLM, которая думает, второй — обычный код, который просто раскладывает письма по адресам. Путать их дорого: если маршрутизацию по жёстким правилам делает модель, вы платите токенами за работу оператора `if`. А emergent behavior — красивое слово, которое одинаково подходит и к удачной находке, и к незапланированному циклу из трёх агентов.
