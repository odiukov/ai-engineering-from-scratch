# A2A — протокол «агент — агент»

> Google анонсировала A2A в апреле 2025-го; к апрелю 2026-го спецификация живёт по адресу https://a2a-protocol.org/latest/specification/, и её поддерживают 150+ организаций. A2A — горизонтальное дополнение к MCP (Lesson 13): MCP вертикальный (агент ↔ инструменты), A2A — равноправный (агент ↔ агент). Он описывает Agent Card (обнаружение), задачи с артефактами (текст, структурированные данные, видео), непрозрачные жизненные циклы задач и авторизацию. Продакшен-системы всё чаще ставят MCP и A2A рядом. В 2025-2026 годах Google Cloud встроила поддержку A2A в Vertex AI Agent Builder.

**Type:** Learn + Build
**Languages:** Python (stdlib, `http.server`, `json`)
**Prerequisites:** Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## Problem

Вашему агенту нужно позвать другого агента на другой системе. Как? Можно выставить HTTP-эндпоинт, придумать свою JSON-схему и надеяться, что другая сторона её понимает. И тогда каждая пара агентов превращается в отдельную самописную интеграцию.

A2A — это универсальный протокол для такого вызова. Стандартное обнаружение, стандартная модель задачи, стандартный транспорт, стандартные артефакты. Как HTTP+REST, только агенты в нём — полноправные участники.

> 🎒 **На пальцах.** Считайте руками: 4 агента в разных компаниях, каждый хочет звать каждого — 4×3 = 12 самописных контрактов, и каждый со своей схемой JSON. С A2A остаётся 4 карточки агентов и ноль работы на каждую новую пару. Как единый формат телефонного номера: не нужно договариваться о нём отдельно с каждым абонентом.

## Concept

### The four elements

**Agent Card.** JSON-документ по адресу `/.well-known/agent.json`, который описывает агента: имя, skills, эндпоинты, поддерживаемые модальности, требования к авторизации. Обнаружение — это просто чтение карточки.

```
GET https://agent.example.com/.well-known/agent.json
→ {
    "name": "code-review-agent",
    "skills": ["review-python", "review-typescript"],
    "endpoints": {
      "tasks": "https://agent.example.com/tasks"
    },
    "auth": {"type": "bearer"},
    "modalities": ["text", "structured"]
  }
```

**Task.** Единица работы. Асинхронный объект с состоянием и жизненным циклом: `submitted → working → completed / failed / canceled`. Клиент отправляет задачу, а потом опрашивает статус или подписывается на обновления.

**Artifact.** Тип результата, который производит задача. Текст, структурированный JSON, изображение, видео, аудио. Артефакты типизированы, поэтому разные модальности равноправны.

**Opaque lifecycle.** A2A не предписывает, *как* удалённый агент решает задачу. Клиент видит переходы состояний и артефакты, а реализация вправе использовать любой фреймворк.

> 🎒 **На пальцах.** Карточка агента — это визитка на двери: имя, что умеет, куда стучаться. В примере выше skills ровно два — `review-python` и `review-typescript`, а `modalities` обещает `text` и `structured`. Значит видео этому агенту отправлять бессмысленно, и вы узнаёте это до первого запроса, а не по ошибке в ответе.

> 🎒 **На пальцах.** Обратите внимание, что в жизненном цикле три финальных состояния: completed, failed, canceled. Ровно в одном из трёх задача всегда и заканчивается — гадать не надо. А слово «непрозрачный» означает вот что: вам не покажут, какой фреймворк, какая модель и сколько шагов было внутри. Как в ресторане: блюдо выносят, на кухню не пускают.

### The MCP/A2A split

- **MCP** (Lesson 13): агент ↔ инструмент. Агент читает и пишет через JSON-RPC на сервер инструментов. По умолчанию без состояния.
- **A2A**: агент ↔ агент. Протокол равных, где у обеих сторон есть собственные рассуждения.

Продакшен-системы с несколькими агентами используют оба. Участник A2A на своей стороне зовёт инструменты по MCP. Такое разделение держит две задачи чистыми.

> 🎒 **На пальцах.** Простой тест на выбор. «Прочитай строку из Postgres» — это конкретный инструмент, у которого нет своего мнения, берём MCP. «Проверь этот пулреквест и напиши замечания» — это целая задача с непредсказуемым числом шагов, берём A2A. Один и тот же агент обычно снаружи принимает Task по A2A, а внутри дёргает MCP-инструменты.

### Discovery flow

```
Client                     Agent server
  ├──GET /.well-known/agent.json──>
  <──Agent Card JSON─────────────
  ├──POST /tasks {skill, input}──>
  <──201 task_id, state=submitted
  ├──GET /tasks/{id}──────────────>
  <──state=working, 42% done──────
  ├──GET /tasks/{id}──────────────>
  <──state=completed, artifacts──
```

Или в потоковом варианте: подписка по SSE на `/tasks/{id}/events`, чтобы обновления приходили сами.

> 🎒 **На пальцах.** Посчитайте запросы в схеме выше: один на карточку, один на создание задачи и два опроса — итого четыре обращения на одну задачу. Если задача идёт час, а вы опрашиваете раз в 5 секунд, это 720 бесполезных запросов. Ровно за этим и нужен SSE: подписались один раз и ждёте, пока сервер сам скажет «готово».

### Auth

A2A поддерживает три частых схемы:

- **Bearer token** — OAuth2 или непрозрачный токен.
- **mTLS** — взаимный TLS; организации доказывают личность друг другу.
- **Signed requests** — HMAC поверх полезной нагрузки.

Способ авторизации объявлен в Agent Card, и клиенты сами его вычитывают и соблюдают.

> 🎒 **На пальцах.** Ключевая мысль в последней строчке: способ авторизации указан в самой карточке. То есть клиент сначала читает `"auth": {"type": "bearer"}` и только потом собирает запрос — договариваться письмами с другой командой не нужно. Разница между схемами простая: bearer доказывает «я знаю пароль», mTLS — «мы оба показали паспорта», HMAC — «письмо не подменили по дороге».

### 150+ organizations by April 2026

Масштаб A2A вытянуло корпоративное внедрение. Главный итог: A2A стал тем способом, которым корпоративные системы агентов переходят границы доверия. Google Cloud выпустила поддержку A2A в Vertex AI Agent Builder; Microsoft Agent Framework её поддерживает; большинство крупных фреймворков (LangGraph, CrewAI, AutoGen) поставляют адаптеры A2A.

> 🎒 **На пальцах.** Фраза «границы доверия» тут не про красоту. Внутри одной компании агенты могут звать друг друга напрямую — вы контролируете обе стороны. Как только вторая сторона в другой компании, нужны обнаружение, авторизация и типизированные результаты, иначе интеграция превращается в переписку юристов. Год, 150+ организаций и адаптеры в трёх главных фреймворках — это признак того, что стандарт закрепился, а не эксперимент.

### Where A2A wins

- **Cross-organization calls.** Агент компании A зовёт агента компании B. Без A2A каждая пара — это отдельный самописный контракт.
- **Heterogeneous frameworks.** Агент на LangGraph зовёт агента на CrewAI, тот — своего агента на чистом Python. A2A всё это выравнивает.
- **Typed artifacts.** Видео как результат, структурированный JSON, аудио — всё равноправно.
- **Long-running tasks.** Непрозрачный жизненный цикл плюс опрос делают задачи на несколько часов простыми в реализации.

> 🎒 **На пальцах.** Второй пункт — тот, из-за которого A2A вообще существует. Три фреймворка, три модели агента, три формата сообщений: без общего протокола вам придётся писать три переходника, и каждый новый фреймворк добавит ещё несколько. A2A превращает «переходник на каждую пару» в «одна карточка на агента».

### Where A2A struggles

- **Latency-sensitive micro-calls.** Жизненный цикл A2A асинхронный. Обмен «агент — агент» за доли миллисекунды сюда не влезает; берите прямой RPC.
- **Tight-coupled in-process agents.** Если оба агента живут в одном процессе Python, HTTP-раундтрип из A2A — стрельба из пушки по воробьям.
- **Small teams.** Накладные расходы спецификации реальны; внутренним агентам вся эта формальность может быть просто не нужна.

> 🎒 **На пальцах.** Цифры делают выбор очевидным. Вызов функции внутри процесса — это микросекунды, HTTP-запрос по сети — десятки миллисекунд, то есть в тысячи раз дороже. Если оба агента в одном процессе, вы платите эту тысячу ни за что. A2A окупается там, где сама задача идёт минуты или часы и накладные расходы протокола теряются в шуме.

### A2A vs ACP, ANP, NLIP

В 2024-2026 годах появилось несколько родственных спецификаций:

- **ACP** (IBM/Linux Foundation) — предшественник A2A, область применения уже.
- **ANP** (Agent Network Protocol) — упор на обнаружение соседей, ставка на децентрализацию.
- **NLIP** (Ecma Natural Language Interaction Protocol, стандартизован в декабре 2025) — тип содержимого «естественный язык».

На апрель 2026-го A2A — самый внедрённый протокол равных. Сравнение смотрите в arXiv:2505.02279 (Liu et al., «A Survey of Agent Interoperability Protocols»).

```figure
sw-agent-card-discovery
```

> 🎒 **На пальцах.** Четыре протокола на одну задачу — обычная картина для молодой области, вспомните войну видеокассет. Практический вывод простой: пишите на A2A, потому что его выбрали 150+ организаций, а про остальные три достаточно знать, чем они отличались. ACP уже влился в A2A, ANP решает другую задачу (децентрализованный поиск соседей), NLIP описывает не транспорт, а тип содержимого.

## Build It

`code/main.py` реализует минимальный сервер и клиент A2A на `http.server` и JSON. Сервер:

- выставляет `/.well-known/agent.json`,
- принимает `POST /tasks`,
- ведёт состояние задачи,
- возвращает артефакты на `GET /tasks/{id}`.

Клиент:

- забирает Agent Card,
- отправляет задачу,
- опрашивает её до завершения,
- читает артефакт.

Запуск:

```
python3 code/main.py
```

Скрипт стартует сервер в фоновом потоке, а затем прогоняет по нему клиента. Вы видите полный поток: обнаружение, отправка, опрос, артефакт.

> 🎒 **На пальцах.** Обратите внимание, что весь протокол сводится к трём URL: карточка, создание задачи, чтение задачи. Никакой магии — три обработчика в `http.server` и словарь с состояниями задач. Клиент при этом ни строчки не знает про внутренности сервера: он прочитал карточку и дальше работает только по ней.

## Use It

`outputs/skill-a2a-integrator.md` проектирует интеграцию по A2A: содержимое Agent Card, схемы задач, выбор способа авторизации, стриминг против опроса.

> 🎒 **На пальцах.** Четыре решения в этом списке дальше очень трудно менять. Опечатка в `skills` ломает всех вызывающих сразу, а не одного, а переход с опроса на SSE после запуска требует правок и на сервере, и у каждого клиента. Поэтому дешевле сгенерировать всё это разом из описания, чем править потом в пяти местах.

## Ship It

Чек-лист:

- **Pin the spec version.** A2A ещё меняется; Agent Card должна объявлять версию протокола.
- **Idempotent task creation.** Дубли отправки (ретраи по сети) должны давать одну задачу, а не несколько.
- **Artifact schemas.** Объявляйте, какие формы возвращает агент; потребители должны их валидировать.
- **Rate limits + auth.** A2A смотрит в интернет, поэтому применяйте обычную веб-безопасность.
- **Dead-letter for failed tasks.** Складывайте упавшие задачи отдельно и разбирайте, какие типы отказов повторяются.

> 🎒 **На пальцах.** Пункт про идемпотентность спасает деньги буквально. Клиент отправил задачу, ответ потерялся в сети, клиент повторил — и вы посчитали одно и то же дважды, а на платной задаче списали двойную цену. Лечится ключом идемпотентности в запросе: одинаковый ключ = та же самая задача, второй раз работа не выполняется.

## Exercises

1. Запустите `code/main.py`. Убедитесь, что клиент обнаруживает сервер и получает правильный артефакт.
2. Добавьте на сервер второй skill (например, «summarize»). Обновите Agent Card. Напишите клиента, который выбирает skill по типу задачи.
3. Реализуйте потоковый эндпоинт по SSE: `/tasks/{id}/events`, который отдаёт смены состояний. Что клиенту придётся делать иначе?
4. Прочитайте спецификацию A2A (https://a2a-protocol.org/latest/specification/). Найдите три вещи, которые спецификация требует, а это демо не реализует.
5. Сравните A2A (обнаружение через Agent Card) с MCP (перечисление возможностей на стороне сервера через `listTools`). В чём компромисс между самоописывающимися агентами и опросом возможностей?

> 🎒 **На пальцах.** Задание 2 короче, чем кажется, но у него есть подвох. Второй skill — это плюс одна строка в карточке и плюс один обработчик, зато клиент теперь обязан читать `skills` из карточки, а не хардкодить имя. Если он хардкодит, вся идея обнаружения теряется: вы вернулись к самописной интеграции, только с лишним JSON-файлом.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| A2A | «Агент — агент» | Протокол равных, по которому агенты зовут других агентов на других системах. Google, 2025. |
| Agent Card | «Визитка агента» | JSON по адресу `/.well-known/agent.json` с описанием skills, эндпоинтов и авторизации. |
| Task | «Единица работы» | Асинхронный объект с состоянием и жизненным циклом; на завершении рождает артефакты. |
| Artifact | «Результат» | Типизированный выход: текст, структурированный JSON, изображение, видео, аудио. Медиа равноправны. |
| Opaque lifecycle | «Как решает — дело агента» | Клиент видит переходы состояний; сервер сам выбирает фреймворк и инструменты. |
| Discovery | «Как найти агента» | `GET /.well-known/agent.json` возвращает карточку. |
| MCP vs A2A | «Инструменты против равных» | MCP: вертикально, агент ↔ инструмент. A2A: горизонтально, агент ↔ агент. |
| ACP / ANP / NLIP | «Протоколы-родственники» | Соседние спецификации; в 2026-м самый внедрённый — A2A. |

> 🎒 **На пальцах.** Строки Discovery и Opaque lifecycle вместе описывают всю сделку A2A. Наружу агент обязан рассказать ровно две вещи: что он умеет (карточка) и на какой стадии задача (состояние). Всё остальное — модель, промпты, фреймворк — можно не раскрывать. Именно поэтому два конкурента могут связать своих агентов и ничего друг о друге не узнать.
