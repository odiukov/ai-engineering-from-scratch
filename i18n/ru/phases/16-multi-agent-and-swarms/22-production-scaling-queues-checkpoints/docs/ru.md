# Масштабирование в продакшене: очереди, чекпоинты, надёжность

> Масштабирование многоагентных систем до тысяч одновременных прогонов требует **durable execution** — рабочих очередей плюс чекпоинтов, чтобы любой воркер мог продолжить любой прогон после любого сбоя, если на месте аренда (lease), идемпотентные побочные эффекты и детерминированный повтор. Рантайм LangGraph — эталонный пример: он пишет чекпоинт после каждого super-step с ключом `thread_id` (по умолчанию в Postgres); падение воркера освобождает аренду, и работу подхватывает другой воркер. Агенты могут спать бесконечно, ожидая ответа человека. **MegaAgent** (arXiv:2408.09955) держал очередь производитель-потребитель на каждого агента с тремя состояниями (Idle / Processing / Response) и двухслойную координацию (чат внутри группы + админ-чат между группами). **Fiber/async** обыгрывает поток-на-задачу для стриминга LLM: потоки простаивают 99% времени в ожидании токенов, а файберы кооперативно уступают управление на I/O. Контраргумент: Ashpreet Bedi в «Scaling Agentic Software» настаивает на **FastAPI + Postgres + nothing else**, пока нагрузка не докажет обратное — простые архитектуры уезжают дальше, чем принято думать. В этом уроке мы соберём durable-лог чекпоинтов, очередь работ на каждого агента с переходами состояний, демо async против потоков — и закрепим прагматичное правило «начинай просто».

**Type:** Learn + Build
**Languages:** Python (stdlib, `asyncio`, `sqlite3`)
**Prerequisites:** Phase 16 · 09 (Parallel Swarm Networks), Phase 16 · 13 (Shared Memory)
**Time:** ~75 minutes

## Problem

Прототип многоагентной системы работает на одном ноутбуке: три агента в event loop в памяти. Вы переезжаете в продакшен:

- Агенты иногда работают часами (длинное исследование, ожидание человека в цикле).
- Процессы-воркеры падают. Перезапуск теряет состояние.
- Пик нагрузки в 10 раз выше среднего; нужно горизонтальное масштабирование.
- Пользователи платят за прогон агента; для списаний нужна семантика exactly-once.

Event loop в памяти не даёт ничего из этого. Под низом нужен слой durable execution. Канонические варианты на 2026 год:

1. Движок workflow с чекпоинтами (Temporal, рантайм LangGraph).
2. Очередь сообщений плюс хранилище состояния (Postgres + SQS/RabbitMQ).
3. Фреймворки на акторной модели (производитель-потребитель на каждого агента, как у MegaAgent).
4. Самодельный FastAPI + Postgres (аргумент Bedi).

В этом уроке мы собираем миниатюру каждого.

> 🎒 **На пальцах.** Посчитайте четвёртый пункт: если агент работает три часа и берёт с пользователя деньги, то один упавший воркер — это не «перезапустим», а потерянные три часа вычислений и спорное списание. Пик в 10 раз — это тоже конкретика: три агента на ноутбуке превращаются в тридцать одновременных прогонов, и ноутбучный event loop тут просто заканчивается.

## Concept

### Durable execution, the pattern

Движок durable execution сохраняет полное состояние программы после каждого «шага» (super-step на языке LangGraph). При сбое:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

Что нужно, чтобы это работало:

- **Serializable state.** Всё состояние агента должно быть сохраняемым. Замыкания с живыми соединениями к базе такого не переживут.
- **Deterministic resume.** При том же состоянии и тех же входах агент выдаёт те же действия (или для вызовов LLM опирается на внешний детерминированный оракул).
- **Idempotent side effects.** Внешние вызовы (вызовы инструментов, платежи) должны быть идемпотентными или использовать ключ дедупликации.

LangGraph пишет чекпоинт после каждого super-step; Temporal — после каждой activity; Restate ведёт журналы в стиле event sourcing. Все три реализуют один и тот же паттерн.

> 🎒 **На пальцах.** Три требования проще запомнить через переезд: состояние должно влезть в коробку (serializable), сборка на новом месте должна дать ту же мебель (deterministic), и грузчик, занёсший диван дважды, не должен оставить у вас два дивана (idempotent). Ломается обычно третье: агент успел списать деньги, а чекпоинт записать не успел — при повторе списание уходит второй раз.

### A checkpoint-per-step runtime

Рантайм LangGraph — разобранный пример: у каждого агента есть `thread_id`, состояние это типизированный словарь, каждый super-step пишет строку в таблицу чекпоинтов. При продолжении рантайм переигрывает с последнего чекпоинта, а не с нуля. Агенты могут вызвать `interrupt()` в ожидании человека; рантайм сохраняет состояние и отпускает воркера. Когда ответ приходит, продолжить может любой воркер.

Это эталонный продакшен-дизайн на апрель 2026 года.

> 🎒 **На пальцах.** Ключевая фраза здесь — «отпускает воркера»: агент ждёт ответа человека три дня, но при этом не занимает ни одного процесса. Без чекпоинтов вам пришлось бы держать живой процесс все три дня, и один перезапуск сервера убил бы задачу. С чекпоинтами ожидание стоит одну строку в Postgres.

### MegaAgent's per-agent queue

arXiv:2408.09955 описывает эксперимент на масштаб: тысячи одновременных агентов в одном кластере. Архитектура:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

Двухслойная координация позволяет держать плотный разговор внутри группы, оставляя обмен между группами разреженным — именно этот паттерн держит стоимость линейной на тысячах агентов.

> 🎒 **На пальцах.** Это школа: внутри класса дети говорят друг с другом сколько угодно, а между классами общаются только через завучей. Если бы каждый агент писал каждому, при 1000 агентах вышло бы почти полмиллиона пар связей; при делении на группы по 10 внутри группы 45 пар, а между группами общаются 100 «завучей». Отсюда и линейная, а не квадратичная стоимость.

### Async vs thread-per-job

Вызовы LLM ограничены вводом-выводом. Поток, ждущий следующего токена, простаивает 99% времени. Каждый поток стоит около 1 МБ RAM; при 10 000 одновременных вызовов это 10 ГБ только на стеки.

Файберы (Python `asyncio`, горутины Go, `tokio` в Rust) кооперативно уступают управление на I/O. Те же 10 000 вызовов спокойно живут внутри одного процесса. На масштабе агентов на LLM async — это не оптимизация, это архитектура.

Исключение: постобработка, упирающаяся в процессор (эмбеддинги, фокусы с токенизатором), по-прежнему хочет потоков или процессов. Разделяйте слой I/O и слой CPU.

> 🎒 **На пальцах.** Посчитайте вместе с текстом: 10 000 потоков × 1 МБ = 10 ГБ памяти, из которых 99% времени ничего не делается. Это как посадить 10 000 курьеров ждать у 10 000 дверей вместо одного диспетчера с блокнотом. Файберы и есть этот диспетчер: он отмечает, кто чего ждёт, и занимается следующим.

### Bedi's counterpoint

«Scaling Agentic Software» (Ashpreet Bedi, 2026) утверждает, что большинство команд усложняет архитектуру раньше, чем измеряет нагрузку. Прагматичный дефолт:

- FastAPI + Postgres.
- Каждый прогон агента — это строка; состояние обновляется на месте с оптимистичной блокировкой.
- Фоновые задачи через `pg_notify` или простого воркера Celery.
- Политика повторов в коде приложения.

Для нагрузок примерно до 100 одновременных прогонов агентов на посильных задачах этого часто достаточно. Обновляйтесь, когда измерите отказ.

Правило: берите фреймворки durable execution, когда упёрлись в конкретную проблему, которую простая архитектура не решает. Преждевременное внедрение сжигает время на ритуалы, которые не отбиваются.

> 🎒 **На пальцах.** Обратите внимание на границу: сотня одновременных прогонов — это уже приличный продукт, и он живёт на двух технологиях, которые вы и так знаете. Temporal и LangGraph-рантайм добавляют не скорость, а гарантии, и платить за них имеет смысл, когда у вас есть выписанная проблема вроде «агент ждёт человека сутки». Пока такой проблемы нет, вы просто учите команду новому фреймворку вместо того, чтобы делать продукт.

### Exactly-once semantics

Для платных прогонов агентов вам нужен «exactly-once effective» (доставка at-least-once плюс идемпотентный потребитель). Инженерные приёмы:

- **Dedup key per run.** Включайте его в каждый вызов с побочным эффектом.
- **Outbox pattern.** Побочные эффекты сперва пишутся в таблицу, а выполняет их отдельный процесс. Оба шага идемпотентны.
- **Compensating transactions.** Когда побочный эффект удался, а запись о нём — нет, планируйте компенсацию.

Это паттерны инженерии баз данных, а не что-то специфичное для LLM. Налог на LLM только в том, что вызовы модели медленные; всё остальное — обычные распределённые системы.

> 🎒 **На пальцах.** Идея outbox как заказ в кафе: сначала официант записывает заказ в блокнот, и только потом повар его готовит. Если официант упал на полпути, заказ виден в блокноте и его выполнят один раз; если бы он держал заказ в голове, вы получили бы либо ноль порций, либо две. Dedup key — это номер заказа, по которому повар понимает, что эту порцию уже отдавали.

### Rainbow deployment

Многоагентная исследовательская система Anthropic использует «rainbow deployments»: несколько версий рантайма агента работают одновременно, чтобы долгие агенты не приходилось убивать при каждом деплое кода. Пускайте новую версию канарейкой на часть трафика; выводите старые версии, когда их агенты закончат.

Это стандарт для долгоживущих stateful-систем; адаптация 2026 года в том, что агенты живут часами, поэтому цикл деплоя должен это учитывать.

> 🎒 **На пальцах.** Представьте, что вы меняете рельсы, пока по ним идёт поезд длиной в три часа: рельсы кладут рядом, а старые снимают, когда последний вагон прошёл. Практический вывод простой: агент, стартовавший на версии 1.4, доживает на 1.4 до конца, даже если в продакшене уже 1.5. Иначе каждый деплой в середине дня стирает все идущие прогоны.

### The canonical production checklist

- Durable-состояние (чекпоинты, снимки или outbox плюс переигрываемый лог).
- Идемпотентные побочные эффекты.
- Асинхронный слой I/O для вызовов LLM.
- Доставка at-least-once с дедупликацией.
- Rainbow/канареечный деплой для stateful-нагрузок.
- Наблюдаемость: трейсы по каждому агенту, аудит super-step, счётчик повторов.

```figure
sw-checkpoint-replay
```

> 🎒 **На пальцах.** Читайте этот список как шесть галочек перед запуском, а не как теорию: пять из шести пунктов вы уже видели выше по отдельности, шестой — наблюдаемость — склеивает их. Если из шести есть только первый, вы восстанавливаетесь после сбоев, но не знаете, как часто они происходят и сколько повторов стоят.

## Build It

`code/main.py` реализует:

- `CheckpointStore` — лог чекпоинтов на SQLite с ключами по thread-id. Каждый super-step добавляет строку.
- `run_with_checkpoint(agent, thread_id)` — моделирует падение посреди прогона; второй воркер продолжает с последнего чекпоинта.
- `AgentQueue` — конечный автомат Idle / Processing / Response на каждого агента с небольшой очередью работ.
- `demo_async_vs_threads()` — прогоняет 500 одновременных смоделированных «вызовов LLM» через asyncio и через потоки; сообщает время по часам и пик памяти (приблизительно).

Запустите:

```
python3 code/main.py
```

Ожидаемый вывод: продолжение с чекпоинта проходит успешно после смоделированного падения; async-версия обрабатывает 500 одновременных вызовов меньше чем за секунду; версия на потоках тратит несколько секунд и потребляет на порядки больше памяти на каждую одновременную единицу.

> 🎒 **На пальцах.** Сравните два числа из вывода: 500 вызовов за долю секунды против нескольких секунд у потоков — и это на пустой имитации, где вычислений вообще нет. Разница берётся не из скорости кода, а из того, что 500 потоков надо создать, разложить по стекам и переключать. Async тут выигрывает не потому что умнее, а потому что ничего лишнего не создаёт.

## Use It

`outputs/skill-scaling-advisor.md` советует, что выбрать для durable execution: FastAPI + Postgres, рантайм LangGraph, Temporal или своё. Калибруется по нагрузке, требованиям к хранению состояния и частоте деплоев.

> 🎒 **На пальцах.** Три входных параметра здесь не случайные: нагрузка решает, хватит ли одного Postgres, время хранения состояния — нужны ли чекпоинты вообще, а частота деплоев — нужен ли rainbow. Продукт с деплоем раз в неделю и агентами на 30 секунд не нуждается ни в одном из тяжёлых движков.

## Ship It

Канонические приёмы усиления для продакшена:

- **Start simple (Bedi's rule).** FastAPI + Postgres, пока не измерите отказ.
- **Instrument everything before optimizing.** Гистограмма задержки по прогонам, время по шагам, число повторов, классификация отказов.
- **Outbox pattern for side effects.** Особенно для платежей и вызовов внешних API.
- **Rainbow deploys.** Никогда не убивайте идущие прогоны агентов во время деплоя.
- **Adopt durable-execution engines (Temporal / LangGraph / Restate) when** вы упёрлись в конкретные проблемы: часовые ожидания человека в цикле, координация между регионами, сложные политики повторов и компенсаций.
- **Async for the I/O layer.** Потоки — только для постобработки, упирающейся в процессор.

> 🎒 **На пальцах.** Второй пункт стоит на втором месте не случайно: без гистограммы задержек вы не отличите «медленно у всех» от «медленно у одного процента». Простой пример: средние 2 секунды при 95-м процентиле 40 секунд означают, что каждый двадцатый пользователь ждёт почти минуту, а среднее об этом молчит.

## Exercises

1. Запустите `code/main.py`. Убедитесь, что продолжение с чекпоинта работает; замерьте разницу в конкурентности между async и потоками.
2. Реализуйте таблицу **outbox**: каждый вызов инструмента сперва пишется в outbox, а выполняет его отдельная горутина или задача. Проверьте идемпотентность, выполнив вызов инструмента дважды.
3. Смоделируйте **rainbow deploy**: две одновременные версии рантайма; направьте половину новых thread_id на каждую; убедитесь, что идущие потоки на старой версии не прерываются.
4. Прочитайте документацию рантайма LangGraph (ссылка ниже). Определите, какие возможности рантайма дольше всего воспроизводить в самодельной версии на FastAPI + Postgres. Это причина внедрять или можно отложить?
5. Прочитайте раздел 3 работы MegaAgent (arXiv:2408.09955). Двухслойная координация (чат внутри группы плюс админ-чат между группами) там описана прямо. Набросайте, как вы отобразите её на очередь сообщений с двумя семействами очередей.

> 🎒 **На пальцах.** Задание 2 — самая полезная тренировка идемпотентности: выполните вызов дважды и посмотрите, стало ли записей в целевой таблице две. Если да, ключ дедупликации у вас не работает, и в продакшене это будет двойное списание, а не учебная ошибка. Пять минут проверки экономят один неприятный разговор с поддержкой.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Durable execution | «Сохраняем состояние программы» | Движок пишет состояние после каждого super-step; восстановление после сбоя детерминировано. |
| Super-step | «Транзакционная граница» | Единица работы между чекпоинтами. Термин LangGraph. |
| thread_id | «Идентификатор прогона агента» | Ключ, который связывает чекпоинты и логику продолжения. |
| Idempotency | «Безопасно повторить» | Повтор побочного эффекта даёт тот же результат, что и одна попытка. |
| Outbox pattern | «Развязать побочные эффекты» | Пишем намерение в таблицу; отдельный исполнитель выполняет его и ставит отметку. |
| At-least-once delivery | «Возможны дубли» | Семантика очереди сообщений; ключ дедупликации делает потребителя effective-once. |
| Rainbow deploy | «Версии живут одновременно» | Несколько версий рантайма работают вместе, пока идут долгие нагрузки. |
| Async fiber | «Кооперативная передача управления» | Конкурентность в пользовательском режиме; дешевле потоков на нагрузках с I/O. |
| Checkpoint | «Снимок состояния» | Сериализованное состояние на границе super-step; ключ для продолжения. |

> 🎒 **На пальцах.** Три строки здесь описывают одну связку: чекпоинт даёт куда вернуться, thread_id — по какому ключу искать, идемпотентность — чтобы возврат не удвоил побочные эффекты. Уберите любую из трёх, и восстановление после сбоя перестанет быть безопасным.
