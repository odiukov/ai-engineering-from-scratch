# Групповой чат и выбор говорящего

> Оркестрация через общий диалог сажает N агентов в один разговор, а функция-селектор (LLM, round-robin или своя) выбирает, кто говорит следующим. Это архетип эмерджентного многоагентного разговора: агенты не знают своей роли в статическом графе, они просто реагируют на общий пул. AutoGen GroupChat и AG2 GroupChat — референсные реализации. Семантику GroupChat из AutoGen v0.2 сохранили в форке AG2, а AutoGen v0.4 переписал её на событийную модель акторов. В феврале 2026-го Microsoft перевела AutoGen в режим поддержки и слила её с Semantic Kernel в Microsoft Agent Framework (RC — февраль 2026). Примитив GroupChat выжил в обеих ветках — выучите его один раз и применяйте везде.

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 04 (Primitive Model)
**Time:** ~60 minutes

## Problem

Статические графы (LangGraph) хороши, когда workflow известен заранее. Настоящие разговоры не статичны: иногда кодер спрашивает ревьюера, иногда исследователя, иногда писателя. Если прописывать руками каждую возможную передачу, получается взрыв числа рёбер. Вам нужны *агенты, которые реагируют на общий пул*, и какая-то функция, которая решает, кто говорит дальше.

Именно это и делает AutoGen GroupChat.

> 🎒 **На пальцах.** Посчитайте взрыв рёбер: 5 агентов, каждый умеет передать любому другому — это 5×4 = 20 переходов, которые надо описать руками. Групповой чат заменяет все 20 одной функцией-селектором: агенты просто говорят в общий чат, а кто следующий — решает она. Как в рабочем чате: никто не расписывает заранее, кто кому отвечает.

## Concept

### The shape

```
              ┌─── shared pool ────┐
              │   m1  m2  m3  ...  │
              └─────────┬──────────┘
                        │ (everyone reads all)
      ┌───────┬─────────┼─────────┬───────┐
      ▼       ▼         ▼         ▼       ▼
    Agent A  Agent B  Agent C  Agent D  Selector
                                           │
                                           ▼
                                  "next speaker = C"
```

Каждый агент видит каждое сообщение. На каждом ходу вызывается функция-селектор и выбирает, кто говорит следующим.

> 🎒 **На пальцах.** На схеме выше четыре агента и один общий пул, и стрелки идут ко всем сразу — это буквально групповой чат в мессенджере, где нет личных сообщений. Если в пуле лежит 10 сообщений, то каждый из четырёх агентов прочитает все 10, то есть система оплатит 40 прочтений вместо 10. Отсюда потом вырастет проблема context bloat.

### The three selector flavors

**Round-robin.** Фиксированный цикл. Детерминированный. Растёт линейно по N, но игнорирует контекст: кодер получит ход даже тогда, когда обсуждают юридическую проверку.

**LLM-selected.** Вызов LLM, которая читает свежий пул и возвращает лучшего следующего говорящего. Учитывает контекст, но медленно: каждый ход добавляет ещё один вызов LLM. Вариант по умолчанию в AutoGen.

**Custom.** Python-функция с любой логикой, какая вам нужна. Типичный вариант: LLM-selected плюс правила подстраховки (например, «после кодера ход всегда получает верификатор»).

> 🎒 **На пальцах.** Разница в цене видна сразу. Разговор на 20 ходов при round-robin стоит 20 вызовов LLM — по одному на реплику агента. Тот же разговор при LLM-selected стоит 40 вызовов: перед каждой репликой ещё один вызов, чтобы выбрать говорящего. Ровно вдвое дороже и вдвое медленнее — за то, что выбор учитывает контекст.

> 🎒 **На пальцах.** Слабость round-robin легко почувствовать на примере: агенты идут по кругу кодер → ревьюер → юрист, обсуждают текст договора, и каждый третий ход отдаётся кодеру, которому сказать нечего. Из 12 ходов 4 уходят в пустоту. Custom-селектор нужен как раз для таких случаев: берём выбор от LLM, но накрываем его правилами вроде «юрист не пропускается, кодер молчит, пока нет кода».

### The ConversableAgent API

```
agent = ConversableAgent(
    name="coder",
    system_message="You write Python.",
    llm_config={...},
)
chat = GroupChat(agents=[coder, reviewer, tester], messages=[])
manager = GroupChatManager(groupchat=chat, llm_config={...})
```

`GroupChatManager` владеет селектором. Когда агент закончил ход, менеджер зовёт селектор, и тот возвращает следующего агента. Цикл идёт, пока не сработает условие остановки.

> 🎒 **На пальцах.** Обратите внимание: в коде выше нет ни одного ребра и ни одного `if`. Есть список из трёх агентов и менеджер — вся маршрутизация спрятана внутри селектора менеджера. Как ведущий на совещании: список участников у него на бумажке, а кому дать слово, он решает по ходу.

### Termination

Три частых схемы:

- **Max rounds.** Жёсткий лимит на общее число ходов.
- **"TERMINATE" token.** Агент может выдать сообщение-маркер, и менеджер останавливается, как только оно появилось.
- **Goal-reached check.** Легковесный верификатор работает на каждом ходу и закрывает чат, когда цель достигнута.

> 🎒 **На пальцах.** Три схемы не конкурируют, а страхуют друг друга. Лимит раундов — это будильник: сработает даже если агенты залипли в бесконечной вежливости. `TERMINATE` — это «всё, разошлись», которое агенты говорят сами, когда работа сделана раньше срока. Верификатор — самый честный, но он платный: при лимите 20 раундов вы делаете до 20 дополнительных проверок.

### Lineage: forks and mergers

В начале 2025-го Microsoft начала большую переработку AutoGen (v0.4) вокруг событийной модели акторов. Сообщество форкнуло семантику GroupChat из AutoGen v0.2 под именем AG2, сохранив тот API, который ранние пользователи уже успели встроить у себя.

В феврале 2026-го Microsoft объявила, что AutoGen уходит в режим поддержки, а событийная модель акторов переезжает в **Microsoft Agent Framework** (RC — февраль 2026, уже слит с Semantic Kernel). Понятие GroupChat выжило в обеих ветках, различаются детали реализации. AG2 — предпочтительный upstream для кода, совместимого с v0.2.

> 🎒 **На пальцах.** Проследите развилку по датам: v0.2 → форк AG2 (2025) → v0.4 на акторах → февраль 2026, всё уезжает в Microsoft Agent Framework. Итог: два живых наследника вместо одного фреймворка. Практический вывод простой — учите примитив (общий пул плюс селектор), а не имена классов: классы за год поменялись дважды, примитив не поменялся ни разу.

### When GroupChat fits

- **Emergent conversations.** Вы не хотите заранее прописывать каждого возможного следующего говорящего.
- **Role-mixing tasks.** Кодер спрашивает исследователя, исследователь — архивиста, архивист — снова кодера. Поток не является DAG.
- **Exploratory problem-solving.** Думайте «мозговой штурм», а не «конвейер».

> 🎒 **На пальцах.** Ключевое слово во втором пункте — «снова». Если поток возвращается назад, это уже не DAG, и статический граф вам его не опишет без циклов и костылей. Мозговой штурм именно такой: вопрос отскакивает по кругу несколько раз, пока не найдётся ответ. Конвейер — нет, и для него групповой чат лишний.

### When it fails

- **Strict determinism.** LLM-селектор бывает непоследовательным. Тот же промпт, другой прогон — другой следующий говорящий.
- **Sycophancy cascades.** Агенты подстраиваются под того, кто говорил увереннее всех. Прописывайте контрмеры в промпте явно.
- **Context bloat.** Каждый агент читает каждое сообщение, и после 10 ходов контекст огромный. Используйте проекции (Lesson 15), чтобы сузить обзор.
- **Hot speakers.** Один агент забирает разговор себе, потому что селектор любит его специализацию. Добавьте баланс говорящих как признак в селектор.

> 🎒 **На пальцах.** Посчитаем context bloat на цифрах. Пусть каждое сообщение — 200 токенов. На первом ходу агент читает 200 токенов, на десятом — уже 2 000, а суммарно за 10 ходов система прочитала около 11 000 токенов вместо 2 000. Растёт квадратично, и это при трёх агентах. Проекция (каждому только его срез) режет этот квадрат обратно почти в линию.

> 🎒 **На пальцах.** Hot speaker — это коллега, который на любом совещании говорит за всех. Если из 10 ходов селектор 8 раз выбрал кодера, то ревьюер высказался один раз, и вы платите за групповой чат, а получаете одного агента. Лечится счётчиком: селектор просто вычёркивает того, кто уже набрал свой лимит ходов.

### Group chat vs supervisor

Одни и те же примитивы, разные значения по умолчанию:

- Supervisor: один агент планирует, остальные исполняют. Селектор — это «спроси у планировщика, что делать».
- Group chat: все агенты равны, а селектор — функция над общим пулом.

Оба варианта опираются на четыре примитива из Lesson 04. Групповой чат по умолчанию берёт оркестрацию через LLM-селектор и общее состояние в виде полного пула.

```figure
swarm-speaker
```

> 🎒 **На пальцах.** Разница только в том, кто держит власть. Supervisor — это начальник отдела: слово всегда возвращается к нему. Групповой чат — это круглый стол: слово даёт нейтральный ведущий. Кода в обоих случаях примерно одинаково — меняется одна функция выбора, а поведение системы меняется целиком.

## Build It

`code/main.py` реализует GroupChat с нуля на стандартной библиотеке. Три агента (кодер, ревьюер, менеджер), варианты round-robin и LLM-selected, остановка по токену `TERMINATE`.

Демо печатает стенограмму разговора плюс трассу решений селектора для обоих вариантов.

Запуск:

```
python3 code/main.py
```

> 🎒 **На пальцах.** Смотрите не на стенограмму, а на трассу селектора рядом с ней. Именно там видно, что при round-robin порядок ходов ровно повторяется каждые три реплики, а при LLM-selected он рваный. Один и тот же набор из трёх агентов, две разные функции выбора — и два совершенно разных разговора.

## Use It

`outputs/skill-groupchat-selector.md` настраивает селектор GroupChat под конкретную задачу: round-robin против LLM-selected против своей функции, плюс какие входы давать селектору (свежие сообщения, специализации агентов, счётчики ходов).

> 🎒 **На пальцах.** Обратите внимание на список входов — их три, и они отвечают на три разных вопроса: о чём сейчас речь, кто в этом силён, кто уже наговорился. Если убрать третий вход, селектор физически не сможет заметить hot speaker: у него просто нет данных о числе ходов.

## Ship It

Чек-лист:

- **Max rounds cap.** Всегда. Для типовых задач 10-20.
- **Speaker-balance metric.** Считайте ходы на каждого агента и поднимайте тревогу, когда перекос превысил порог.
- **Termination token.** `TERMINATE` или отдельный агент-верификатор.
- **Projection or scoped memory.** После ~10 сообщений подумайте о том, чтобы давать каждому агенту только суженный обзор — иначе контекст распухнет.
- **Selector logging.** Для варианта с LLM-селектором логируйте и вход селектора, и его выбор. Иначе отладка невозможна.

> 🎒 **На пальцах.** Последний пункт спасает больше всего времени. Без лога вы видите только «почему-то опять говорил кодер» и гадаете. С логом видно вход («последние 5 сообщений про баг в парсере») и выбор («coder») — и сразу понятно, что селектор прав, а виноват промпт ревьюера, который не сказал ничего по делу.

## Exercises

1. Запустите `code/main.py`. Сравните разговор при round-robin и при LLM-selected. Кто доминирует в каждом случае?
2. Добавьте в селектор правило «максимум ходов на агента». Как это меняет стенограмму?
3. Реализуйте остановку по достижению цели: стоп, когда ревьюер вернул «approved». Насколько часто это срабатывает раньше лимита раундов?
4. Прочитайте стабильную документацию AutoGen про GroupChat (https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/group-chat.html). Найдите селектор, который `GroupChatManager` использует по умолчанию.
5. Прочитайте репозиторий AG2 (https://github.com/ag2ai/ag2) и сравните GroupChat из v0.2 с событийной версией v0.4. Какое конкретное свойство (пропускная способность, устойчивость к сбоям, композируемость) добавляет v0.4?

> 🎒 **На пальцах.** Задание 3 интереснее, чем кажется, потому что учит мерить, а не верить. Прогоните чат 10 раз при лимите 15 раундов и посчитайте, сколько прогонов закончились словом «approved», а сколько — упёрлись в лимит. Если по цели закрылось 3 прогона из 10, значит ваша реальная схема остановки — это лимит раундов, а верификатор пока просто украшение.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| GroupChat | «Агенты в одной комнате» | Общий пул сообщений плюс функция-селектор. Примитив AutoGen / AG2. |
| Speaker selection | «Кто говорит следующим» | Функция, которая выбирает следующего агента. Round-robin, LLM-selected или своя. |
| GroupChatManager | «Ведущий совещания» | Компонент AutoGen, который владеет селектором и крутит цикл ходов. |
| ConversableAgent | «Базовый агент» | Базовый класс AutoGen: агент, умеющий отправлять и получать сообщения. |
| Termination token | «Стоп-слово» | Строка-маркер (обычно `TERMINATE`), которая заканчивает чат. |
| Hot speaker | «Один агент доминирует» | Режим отказа, когда селектор снова и снова выбирает одного и того же агента. |
| Context bloat | «Пул растёт без границ» | Каждый агент читает все предыдущие сообщения, и контекст растёт вместе с числом ходов. |
| Projection | «Суженный обзор» | Ролевой срез общего пула, который не даёт контексту распухнуть. |

> 🎒 **На пальцах.** Две последние строки таблицы — это болезнь и лекарство. Context bloat — то, что происходит само: 10 ходов, и каждый агент тащит всю переписку. Projection — то, что вы делаете руками: ревьюеру отдаёте только код и замечания, а исследователю — только вопросы. Один и тот же пул, разные окна в него.
