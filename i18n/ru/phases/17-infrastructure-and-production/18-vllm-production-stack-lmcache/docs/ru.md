# Продакшен-стек сервинга — выгрузка KV и роутинг с учётом кэша

> Продакшен-стек сервинга сшивает роутер, движки и observability в одно развёртывание Kubernetes — и относится к KV-кэшу как к ресурсу, который может покинуть GPU. Выгрузка KV вытаскивает KV-кэш из памяти GPU и переиспользует его между запросами и движками (сперва CPU DRAM, затем диск или Ceph). production-stack от vLLM — это референсное развёртывание; LMCache — слой выгрузки. KV Offloading Connector из vLLM 0.11.0 (январь 2026) делает выгрузку асинхронной и подключаемой через Connector API (с версии 0.9.0). Путь выгрузки обычно скрыт от пути запроса, хотя промахи кэша и подъёмы блоков наверх могут добавлять сквозную задержку. LMCache полезен даже без общих префиксов: когда у GPU кончаются слоты под KV, вытесненные запросы можно восстановить из CPU вместо повторного prefill. Опубликованные бенчмарки на 16 H100 (80 ГБ HBM) на четырёх машинах a3-highgpu-4g: когда KV-кэш перестаёт влезать в HBM, и родная выгрузка в CPU, и LMCache заметно поднимают пропускную способность; при малом объёме KV все конфигурации совпадают с базовой линией при небольших накладных расходах.

**Type:** Learn
**Languages:** Python (stdlib, toy KV-spill simulator)
**Prerequisites:** Phase 17 · 04 (Serving Engine Internals), Phase 17 · 06 (SGLang/RadixAttention)
**Time:** ~60 minutes

## Learning Objectives

- Нарисовать слои vLLM production-stack: роутер, движки, выгрузка KV, observability.
- Объяснить KV Offloading Connector API (с версии 0.9.0) и то, как асинхронный путь в 0.11.0 прячет задержку выгрузки.
- Посчитать, когда CPU DRAM через LMCache помогает (KV больше HBM), а когда добавляет накладные расходы (KV влезает в HBM).
- Выбрать между родной выгрузкой vLLM в CPU и коннектором LMCache при заданных ограничениях развёртывания.

## The Problem

Ваш сервинг на vLLM показывает GPU со 100% занятой HBM и события вытеснения при каждом росте одновременности. Запросы выкидываются, ставятся обратно в очередь, и один и тот же промпт на 2K токенов вы пересчитываете четыре раза за минуту. Вычисления GPU уходят на избыточные prefill; goodput сильно ниже сырой пропускной способности.

> 🎒 **На пальцах.** Посчитайте цену этого повтора: prefill на 2K токенов — это работа, выполненная четыре раза за минуту, то есть три четверти этих вычислений выброшены. Если такой prefill занимает 200 мс, вы теряете 600 мс полезного времени GPU на каждый повторяющийся запрос. Как перечитывать книгу с начала каждый раз, когда вас отвлекли на середине.

Добавлять GPU — линейный рост цены. Добавить HBM невозможно. Зато CPU DRAM дешёвая: один сокет тянет 512 ГБ и больше, задержка там на порядки хуже, чем у HBM, но для «временно тёплого» KV-кэша этого достаточно.

LMCache вытаскивает KV-кэш в CPU DRAM, чтобы вытесненные запросы быстро восстанавливались, а повторяющиеся префиксы делились между движками без повторного prefill на каждом из них.

> 🎒 **На пальцах.** Сравните две величины: HBM у H100 — 80 ГБ, а DRAM одного сокета — 512 ГБ и больше, то есть места в шесть раз больше и радикально дешевле за гигабайт. Да, DRAM медленнее HBM, но переслать готовый KV всё равно быстрее, чем считать prefill заново. Это как полка в кладовке: ходить туда дольше, чем тянуться к столу, но дешевле, чем покупать второй стол.

## The Concept

### vLLM production-stack

`github.com/vllm-project/production-stack` — это референсное развёртывание на Kubernetes:

- **Router** — с учётом кэша (Phase 17 · 11). Потребляет события KV.
- **Engines** — воркеры vLLM. По одному на GPU или на группу TP/PP.
- **KV cache offload** — развёртывание LMCache или родной коннектор.
- **Observability** — сбор метрик Prometheus, дашборды Grafana, трейсы OTel.
- **Control plane** — обнаружение сервисов, конфигурация, накатывающиеся обновления.

Поставляется как Helm-чарт плюс оператор.

> 🎒 **На пальцах.** Обратите внимание на первую строку: роутер «потребляет события KV» — то есть движки рассказывают ему, какие префиксы у них лежат. Без этого потока событий роутер шлёт запрос в случайный из, скажем, 16 движков, и шанс попасть в нужный кэш примерно 1 к 16. С событиями он попадает почти всегда. Как гардероб с номерками против гардероба, где пальто ищут наугад.

### The KV Offloading Connector API (v0.9.0+)

vLLM 0.9.0 ввёл Connector API для подключаемых бэкендов KV-кэша. Ваш движок выгружает блоки в коннектор; коннектор складывает их куда умеет (RAM, диск, объектное хранилище, LMCache). Когда запросу нужен блок, коннектор загружает его обратно.

> 🎒 **На пальцах.** Ключевое слово тут «блоки»: выгружается не весь кэш запроса целиком, а те же страницы по 16 токенов, которыми оперирует PagedAttention. Поэтому запрос на 2000 токенов — это около 125 блоков, и вернуть можно ровно те, которые нужны. Как книга по главам в разных ящиках, а не один неразрезаемый рулон.

vLLM 0.11.0 (январь 2026) добавляет асинхронный путь выгрузки: выгрузка может идти в фоне, так что в обычном случае движок на ней не блокируется. Сквозная задержка и пропускная способность всё равно зависят от формы нагрузки, доли попаданий в KV-кэш и давления на систему; сами заметки vLLM отмечают, что выгрузка на кастомных ядрах может ухудшить пропускную способность при низкой доле попаданий, а у асинхронного планирования есть известные проблемы взаимодействия со speculative decoding.

> 🎒 **На пальцах.** «Асинхронно» не значит «бесплатно»: фоновая выгрузка всё равно занимает шину PCIe и такты CPU, просто вы этого не видите в графике задержки. При низкой доле попаданий вы платите за каждую выгрузку и почти никогда не забираете выгоду — чистый минус. Как заранее упаковывать вещи в кладовку, которые вам потом ни разу не понадобятся.

### Native CPU offload vs LMCache

**Native vLLM CPU offload**: локальный для движка. Складывает блоки KV в RAM хоста. Быстро внедряется, ноль сетевых переходов. Между движками не работает.

**LMCache connector**: масштаба кластера. Складывает блоки в общий сервер LMCache (CPU DRAM плюс уровень Ceph/S3). Блоки доступны любому движку. Есть опубликованные бенчмарки на 16 H100.

> 🎒 **На пальцах.** Вся разница в одном слове — «между движками». Если у вас 16 движков и общий системный промпт, родная выгрузка заставит каждый из них хранить свою копию и делать свой prefill: 16 одинаковых работ. LMCache делает эту работу один раз и раздаёт результат. Как один общий склад на весь район вместо шестнадцати одинаковых кладовок.

Берите родную выгрузку, когда давление на HBM испытывает один движок. Берите LMCache, когда несколько движков делят префиксы (RAG с общими системными промптами, мультитенантность с общими шаблонами).

> 🎒 **На пальцах.** Правило простое: сначала посчитайте, сколько у вас движков делят один и тот же текст. Один движок — берите родную выгрузку, потому что за сетевой переход платить не за что. Два и больше с общими префиксами — LMCache, и выгода растёт линейно с числом движков.

### Benchmark behavior

Тест на 16 H100 (80 ГБ HBM), разложенных по четырём a3-highgpu-4g:

- Малый объём KV (короткие промпты, низкая одновременность): все конфигурации совпадают с базовой линией, LMCache добавляет 3-5% накладных расходов.
- Средний объём: LMCache начинает помогать за счёт переиспользования префиксов между движками.
- KV превышает HBM: и родная выгрузка в CPU, и LMCache заметно поднимают пропускную способность; у LMCache выигрыш больше из-за обмена между движками.

> 🎒 **На пальцах.** Здесь важен порядок трёх строк: сначала минус 3-5%, потом ноль, потом большой плюс. То есть LMCache — это не «включил и стало лучше», а страховка, которая стоит денег до того момента, как KV перестанет влезать в 80 ГБ HBM. Как зимние шины: летом они вам только мешают.

### When LMCache is decisive

- Мультитенантный сервинг, где системные промпты общие для нескольких тенантов.
- RAG, где куски документов повторяются между запросами.
- Донастроенные варианты (LoRA) на одной базе, где переиспользование KV базовой модели убирает лишнюю работу.
- Нагрузки с частым вытеснением: восстановить из CPU дешевле, чем сделать prefill заново.

> 🎒 **На пальцах.** Четвёртый пункт — самый недооценённый: он работает даже когда у вас вообще нет общих префиксов. Вытесненный запрос — это уже посчитанный KV, который иначе просто выбрасывают, а потом считают заново. Как отложить недочитанную книгу закладкой вместо того, чтобы каждый раз начинать с первой страницы.

### When NOT to enable

- Слабое давление на HBM — вы платите накладные расходы без выгоды.
- Короткие контексты (меньше 1K токенов) — время передачи больше времени повторного prefill.
- Однотенантная нагрузка с одним промптом — переиспользовать нечего.

> 🎒 **На пальцах.** Второй пункт легко проверить арифметикой: prefill на 500 токенов — это десятки миллисекунд, а переслать соответствующий KV по PCIe плюс накладные расходы коннектора занимает столько же или больше. Считать заново дешевле, чем ходить за готовым. Ровно как в жизни: за солью проще дойти до полки, чем звонить соседу.

### Integration with disaggregated serving

Дезагрегированный сервинг из Phase 17 · 17 и LMCache складываются друг с другом: KV, который едет из пула prefill в пул decode, попадает в LMCache, если не использован, а последующие запросы забирают его оттуда. Роутер с учётом кэша из Phase 17 · 11 умеет направить запрос в тот движок, чей локальный ИЛИ общий через LMCache кэш совпал с запросом.

> 🎒 **На пальцах.** Заметьте, что здесь у KV появляется третья жизнь: сначала он нужен для decode текущего запроса, потом лежит в LMCache для следующих. Один prefill обслуживает и живой запрос, и будущие попадания в кэш — тот же вычислительный труд продаётся дважды. Как приготовить большую кастрюлю супа: сегодня обед, завтра тоже.

### Numbers you should remember

- vLLM 0.9.0: появился Connector API.
- vLLM 0.11.0 (январь 2026): асинхронный путь выгрузки; влияние на сквозную задержку зависит от нагрузки, доли попаданий в KV и давления на систему (это не абсолютная гарантия).
- Бенчмарк на 16 H100: LMCache помогает, когда объём KV превышает HBM.
- Слабое давление на HBM: 3-5% накладных расходов без выгоды.

> 🎒 **На пальцах.** Из четырёх пунктов запомните пару «3-5% против превышения HBM» — это вся логика решения. Пока KV влезает в 80 ГБ, вы теряете 3-5% пропускной способности; как только перестал влезать, начинаются вытеснения и повторные prefill, а они стоят десятки процентов. Порог решения — не версия vLLM, а утилизация HBM.

## Use It

`code/main.py` моделирует нагрузку с частым вытеснением с LMCache и без него. Выводит число избежавших повтора prefill, прирост пропускной способности и точку безубыточности по утилизации HBM.

> 🎒 **На пальцах.** Главное число здесь — точка безубыточности по утилизации HBM, потому что это единственная метрика, которую вы реально видите в Prometheus. Скажем, симулятор говорит «окупается с 85%»: значит, вы просто ставите алерт на утилизацию HBM и включаете LMCache, когда он срабатывает. Остальные два числа нужны, чтобы объяснить решение начальнику.

Этот урок даёт `outputs/skill-vllm-stack-decider.md`. По форме нагрузки и вашему развёртыванию vLLM навык решает: родная выгрузка, LMCache или ничего.

## Exercises

1. Запустите `code/main.py`. При какой утилизации HBM LMCache начинает окупаться?
2. Тенант делит системный промпт на 6K токенов между 200 запросами в час. Посчитайте ожидаемую экономию от LMCache на одного тенанта.
3. Сервер LMCache — единая точка отказа. Спроектируйте стратегию высокой доступности (реплики, откат на родную выгрузку).
4. LMCache пишет в Ceph на вращающихся дисках. Для KV промпта на 4K токенов на 70B в FP8 (500 МБ) сравните время чтения и время повторного prefill.
5. Обоснуйте, «бесплатен» ли асинхронный путь vLLM 0.11.0 — где спрятаны накладные расходы?

> 🎒 **На пальцах.** Начните со второго задания, там всё считается в уме: 200 запросов в час по 6K токенов префикса — это 1.2 млн токенов prefill, из которых при кэше нужно посчитать только первые 6K. Экономия — 199 из 200 prefill, то есть 99.5% работы над префиксом. Умножьте на цену секунды GPU, и получите сумму, за которую стоит воевать.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Production-stack | «референсное развёртывание» | Helm-чарт и оператор Kubernetes от vLLM |
| Connector API | «интерфейс бэкенда KV» | Подключаемый интерфейс хранилища KV с vLLM 0.9.0 |
| Native CPU offload | «слив внутри движка» | Хранить KV в RAM хоста того же движка |
| LMCache | «кластерный KV-кэш» | Сервер KV-кэша между движками на CPU DRAM плюс диск |
| 0.11.0 async | «неблокирующая выгрузка» | Выгрузка спрятана за потоком движка |
| Preemption | «вытеснить, чтобы освободить место» | Перетряска KV-кэша, когда HBM заполнена |
| Prefix reuse | «тот же системный промпт» | Несколько запросов делят начало; попадание в кэш |
| Ceph tier | «дисковый уровень» | Долговечное хранилище под DRAM в иерархии кэша |

> 🎒 **На пальцах.** Две строки таблицы образуют цепочку причин: Preemption — это болезнь, а Native CPU offload и LMCache — два лекарства. Вытеснение при заполненной HBM само по себе не ошибка, оно становится дорогим только потому, что выброшенный KV приходится считать заново. Уровень Ceph здесь — последний рубеж: медленно, зато переживает перезапуск движка.
