# Слой роутинга LLM — LiteLLM, OpenRouter, Portkey

> Привязка к одному провайдеру стоит дорого. Разным задачам с вызовом инструментов подходят разные модели. Шлюзы роутинга дают единый API, ретраи, failover, учёт стоимости и guardrails. В 2026 году правят три архетипа: LiteLLM (open-source, свой хостинг), OpenRouter (managed SaaS), Portkey (продакшен-уровень, код открыт в марте 2026). Этот урок называет критерии выбора и разбирает шлюз роутинга на стандартной библиотеке.

**Type:** Learn
**Languages:** Python (stdlib, routing + failover + cost tracker)
**Prerequisites:** Phase 13 · 02 (function calling), Phase 13 · 17 (gateways)
**Time:** ~45 minutes

## Learning Objectives

- Различать варианты роутинга: свой хостинг, managed-сервис и продакшен-уровень.
- Собрать цепочку fallback, которая при сбоях провайдера повторяет запрос в заданном порядке приоритета.
- Считать стоимость и расход токенов на каждый запрос по всем провайдерам.
- Выбирать между LiteLLM, OpenRouter и Portkey под конкретное продакшен-ограничение.

## The Problem

Сценарии, где роутинг между провайдерами важен:

1. **Cost.** Claude Sonnet стоит в 3 раза дороже Haiku. Для сортировки задач хватит Haiku; для синтеза Sonnet оправдан. Роутить нужно на каждый запрос.

2. **Failover.** У OpenAI выдался плохой час. Все запросы падают. Вам нужен автоматический переход на Anthropic без передеплоя.

3. **Latency.** Живому чату важно быстрое время до первого токена. Пакетному суммаризатору — нет. Роутьте по SLA на задержку.

4. **Compliance.** Пользователи из ЕС должны оставаться в регионах ЕС. Роутьте по региону.

5. **Experimentation.** A/B-тест двух моделей на одной нагрузке. Роутьте по группе теста.

Писать всё это руками в каждой интеграции — однообразная работа. Шлюз роутинга даёт один OpenAI-совместимый API и берёт остальное на себя.

> 🎒 **На пальцах.** Посмотрите на первый пункт в цифрах: если из 100 запросов 80 — это сортировка, то на Haiku они стоят втрое дешевле, и общий счёт падает примерно с 100 условных единиц до 47. Роутер — это как разные курьеры: за пиццей через двор не посылают фуру.

## The Concept

### OpenAI-compatible proxy shape

Формат OpenAI понимают все. Шлюз роутинга выставляет `/v1/chat/completions`, принимает схему OpenAI, а внутри проксирует в Anthropic / Gemini / Cohere / Ollama / куда угодно. Клиенту всё равно.

> 🎒 **На пальцах.** Это розетка-переходник. Ваш код втыкает вилку формата OpenAI, а с другой стороны провод уходит хоть в Anthropic, хоть в локальную Ollama. Менять вилку на каждом устройстве не нужно — достаточно переходника.

### Model aliases

Вместо прибитого id снапшота ваш код говорит `our_smart_model`. Шлюз сопоставляет алиасы с реальными моделями. Когда провайдер выпускает новое поколение, вы меняете алиас на сервере; код не трогаете вообще.

> 🎒 **На пальцах.** Алиас — это как «мама» в контактах телефона: номер меняется, запись остаётся. Замена `claude-3-5-sonnet-20241022` на новую версию — это одна правка в конфиге шлюза вместо поиска строки по сорока файлам вашего проекта.

### Fallback chains

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

Шлюзы описывают такую цепочку в конфиге. Ретраи списываются с бюджета, чтобы каскад fallback не разнёс стоимость.

> 🎒 **На пальцах.** Прочитайте цепочку сверху вниз: три попытки, и только потом отказ. Без бюджета на ретраи один упавший запрос легко превращается в три оплаченных вызова — то есть в тройную цену за один ответ. Как ловить такси: обзвонить три службы можно, но за каждый подъехавший автомобиль платят отдельно.

### Semantic caching

Одинаковые или почти одинаковые промпты попадают в кэш, а не к провайдеру. На повторяющихся циклах агента экономия бывает от 30 до 60 процентов. Ключи строятся на эмбеддингах; почти-дубликаты делят одну ячейку кэша.

> 🎒 **На пальцах.** Возьмите агента, который за прогон делает 20 вызовов и половину из них повторяет почти дословно. При экономии 50% счёт за прогон падает вдвое, а ответы из кэша приходят за миллисекунды вместо секунд. Это как заглянуть в блокнот вместо повторного звонка в справочную.

### Guardrails

На уровне шлюза:

- **PII redaction.** Проход по регуляркам или ML-моделью перед отправкой промпта.
- **Policy violations.** Отклонять промпты с запрещённым содержимым.
- **Output filters.** Вычищать утечки из ответов модели.

У Portkey и Kong guardrails идут в комплекте и с готовым мнением. LiteLLM оставляет их опциональными.

> 🎒 **На пальцах.** Три пункта — это три разные точки на пути запроса: до модели, вместо модели и после модели. Если чистить только вход, ответ всё равно может процитировать номер карты из контекста. Как досмотр в аэропорту: проверяют и на входе, и на выходе из зоны.

### Per-key rate limits

Один ключ API — одна команда. Бюджет на ключ не даёт одной команде выесть общую квоту. Так умеют почти все шлюзы.

> 🎒 **На пальцах.** Без лимита на ключ одна команда с багом в цикле съедает месячную квоту за ночь, и утром без модели остаются все шесть команд. Отдельный ключ с бюджетом — это отдельный счётчик электричества на каждую квартиру, а не один общий на подъезд.

### Self-hosted vs managed trade-offs

| Factor | LiteLLM (self-hosted) | OpenRouter (managed) | Portkey (production) |
|--------|----------------------|----------------------|----------------------|
| Code | Открытый код, Python | Managed SaaS | Открытый код (март 2026) + managed |
| Setup | Развернуть прокси | Зарегистрироваться | Любой вариант |
| Providers | 100+ | 300+ | 100+ |
| Billing | Ваши собственные ключи | Кредиты OpenRouter | Ваши собственные ключи |
| Observability | OpenTelemetry | Дашборд | Полный OTel + вычистка PII |
| Best for | Команды, которым нужен полный контроль | Быстрое прототипирование | Продакшен с требованиями комплаенса |

LiteLLM выигрывает, когда у вас есть SRE-команда и нужен контроль над данными. OpenRouter выигрывает, когда хочется одной подписки и никакой инфраструктуры. Portkey выигрывает, когда guardrails и комплаенс нужны из коробки.

> 🎒 **На пальцах.** Сравните строку Billing: у LiteLLM и Portkey деньги идут по вашим ключам напрямую провайдеру, у OpenRouter — через кредиты сервиса. Значит, у OpenRouter вы платите наценку за удобство, зато не заводите шесть отдельных договоров. Это разница между своей кухней и подпиской на доставку.

### Cost tracking

В каждом запросе есть `provider`, `model`, `input_tokens`, `output_tokens`. Умножаем на цену за токен для конкретной модели (её шлюз держит в своей таблице цен). Дальше агрегируем по пользователю, команде или проекту.

> 🎒 **На пальцах.** Четыре поля — это вся бухгалтерия. Запрос на 2000 входных и 500 выходных токенов к модели по $3/$15 за миллион стоит 2000/1e6 × 3 + 500/1e6 × 15 = $0.0135. Сложите такие строки по метке команды — и увидите, кто именно съел бюджет.

### MCP plus routing

Шлюз умеет роутить и вызовы LLM, И запросы sampling из MCP. Когда в sampling-запросе modelPreferences просит конкретную модель, шлюз переводит это в нужный бэкенд. Именно здесь Phase 13 · 17 (MCP gateway) и шлюз роутинга из этого урока иногда сливаются в один сервис.

> 🎒 **На пальцах.** MCP-сервер тоже иногда хочет спросить у модели — это и есть sampling. Если такой запрос идёт мимо шлюза, вы теряете и учёт стоимости, и failover ровно на той части трафика, которую сложнее всего отладить. Один вход в дом лучше, чем парадная дверь и лаз через подвал.

### Routing strategies

- **Static priority.** Первый в списке; при ошибке падаем на следующий.
- **Load balancing.** По кругу или с весами.
- **Cost-aware.** Берём самую дешёвую модель, которая укладывается в задержку и качество.
- **Latency-aware.** Берём самую быструю модель за последние N минут.
- **Task-aware.** Классификатор промптов отправляет код в одну модель, суммаризацию — в другую.

```figure
tp-router-failover
```

> 🎒 **На пальцах.** Пять стратегий стоят разное. Static priority — это ноль накладных расходов и ноль ума. Task-aware требует классификатора, то есть ещё одного вызова модели на каждый запрос — примерно 100-200 токенов сверху. Считайте: если экономия от правильной модели меньше цены классификатора, стратегия вредна.

## Use It

`code/main.py` реализует шлюз роутинга примерно в 150 строк: принимает запросы в формате OpenAI, переводит их в заглушки конкретных провайдеров, прогоняет цепочку fallback по приоритету, считает стоимость каждого запроса и вычищает PII на входе. Запустите его на трёх сценариях: обычный запрос, авария основного провайдера с переходом на резервный, утечка PII, которую поймала вычистка.

На что смотреть:

- Словарь `ROUTES`: алиас -> список конкретных провайдеров по приоритету.
- Цикл fallback повторяет запрос при 5xx.
- Трекер стоимости умножает расход токенов на тарифы для каждой модели.
- Вычистка PII затирает шаблоны вида номера SSN до отправки.

> 🎒 **На пальцах.** Три сценария подобраны неслучайно: первый проверяет счастливый путь, второй — что fallback вообще срабатывает, третий — что стоимость приписалась тому провайдеру, который реально ответил. Без третьей проверки отчёт по деньгам врёт ровно в тех случаях, когда что-то сломалось.

## Ship It

Этот урок даёт `outputs/skill-routing-config-designer.md`. По профилю нагрузки (задержка, стоимость, комплаенс) навык выбирает LiteLLM / OpenRouter / Portkey и выдаёт готовый конфиг роутинга.

> 🎒 **На пальцах.** Обратите внимание: навык принимает ровно три входных параметра. Это и есть весь спор о шлюзах, сведённый к трём числам. Если у вас есть требование «данные не покидают наш контур», выбор сузился до одного варианта ещё до обсуждения фич.

## Exercises

1. Запустите `code/main.py`. Включите сценарий аварии; убедитесь, что fallback приземляется на второго провайдера и стоимость приписана правильно.

2. Добавьте семантическое кэширование: ключ поиска — SHA256 от промпта, попадание в кэш отвечает мгновенно. Измерьте экономию на повторном вызове.

3. Добавьте классификатор промптов, который отправляет промпты вида "code ..." на алиас с упором на интеллект, а "summarize ..." — на алиас с упором на скорость.

4. Спроектируйте бюджеты по командам: у каждой команды есть месячный лимит траты, шлюз отказывает в запросах, когда лимит выбран. Выберите гранулярность контроля (на каждый запрос или по окну).

5. Прочитайте документацию LiteLLM, OpenRouter и Portkey рядом. Назовите по одной фиче каждого, которой нет у двух остальных.

> 🎒 **На пальцах.** Начните со второго задания — оно самое благодарное. SHA256 от промпта — это точный кэш, а не семантический: «Summarize this» и «Summarize this.» дадут разные ключи и два оплаченных вызова. Замерьте долю попаданий, и вы сразу поймёте, стоит ли платить за эмбеддинги ради ловли перефразировок.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Routing gateway | «LLM-прокси» | Слой с единым API перед множеством провайдеров |
| OpenAI-compatible | «Говорит на схеме OpenAI» | Принимает формат `/v1/chat/completions` и переводит его в любой бэкенд |
| Model alias | «our_smart_model» | Имя в вашем коде, которое шлюз сопоставляет с конкретной моделью |
| Fallback chain | «Список ретраев» | Упорядоченный список провайдеров, которых пробуют при сбое |
| Semantic caching | «Кэш по эмбеддингу промпта» | Ключ — эмбеддинг промпта; почти-дубликаты дают попадание в кэш |
| Guardrails | «Фильтры на входе и выходе» | Вычистить PII, отклонить нарушения политики |
| Per-key rate limit | «Бюджет команды» | Квота, привязанная к ключу API |
| Cost tracking | «Трата на запрос» | Суммарный расход токенов x цена по модели |
| LiteLLM | «Открытый прокси» | OSS-шлюз роутинга, который можно развернуть у себя |
| OpenRouter | «Managed SaaS» | Хостится провайдером, оплата по кредитам |
| Portkey | «Продакшен-вариант» | Открытый код плюс managed, guardrails встроены |

> 🎒 **На пальцах.** Две строки таблицы легко перепутать. Fallback chain срабатывает, когда провайдер ответил ошибкой; per-key rate limit срабатывает, когда ошибку возвращает сам шлюз, потому что команда выбрала бюджет. В первом случае надо ретраить, во втором — бесполезно, и путать их в коде дорого.
