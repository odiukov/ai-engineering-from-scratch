# Структурированный вывод — JSON Schema, Pydantic, Zod, constrained decoding

> «Вежливо попросить модель вернуть JSON» подводит в 5-15 % случаев даже на топовых моделях. Структурированный вывод закрывает этот зазор через constrained decoding: модели буквально не дают выдать токен, который нарушил бы схему. Strict mode у OpenAI, tool use с типизированной схемой у Anthropic, `responseSchema` у Gemini, `output_type` у Pydantic AI и `.parse` у Zod — это пять внешних форм одной и той же идеи. В этом уроке вы собираете валидатор схемы и контракт strict mode, которые дальше пригодятся в любом продакшен-конвейере извлечения.

**Type:** Build
**Languages:** Python (stdlib, JSON Schema 2020-12 subset)
**Prerequisites:** Phase 13 · 02 (function calling deep dive)
**Time:** ~75 minutes

## Learning Objectives

- Написать JSON Schema 2020-12 для цели извлечения, используя правильные ограничения (enum, min/max, required, pattern).
- Объяснить, почему strict mode и constrained decoding дают другие гарантии, чем «валидировать после генерации».
- Различать три режима отказа: ошибка разбора, нарушение схемы, отказ модели.
- Выпустить конвейер извлечения с типизированным ремонтом и типизированной обработкой отказа.

## The Problem

Агенту, читающему письмо с заказом, нужно превратить свободный текст в `{customer, line_items, total_usd}`. Есть три подхода.

**Approach one: prompt for JSON.** «Ответь в JSON с полями customer, line_items, total_usd». На топовых моделях работает в 85-95 % случаев. Ломается шестью способами: пропущенная скобка, лишняя запятая, неверные типы, выдуманные поля, обрезка на лимите токенов, просочившаяся проза вроде «Here is your JSON:».

> 🎒 **На пальцах.** 85-95 % звучит прилично, пока вы не подставите объём: на 10 000 писем в день это от 500 до 1500 упавших разборов. Каждый из них — либо потерянный заказ, либо ночной звонок дежурному. Шесть способов поломки — это шесть разных багов, и каждый вы будете чинить отдельно.

**Approach two: validate after generation.** Генерируем свободно, разбираем, проверяем по схеме, при провале повторяем. Надёжно, но дорого: вы платите за каждый повтор, а баги с обрезкой стоят по одному лишнему ходу каждый.

**Approach three: constrained decoding.** Провайдер принуждает к схеме на этапе декодирования. Невалидные токены вымаскированы из распределения выборки. Вывод гарантированно разберётся и гарантированно пройдёт валидацию. Режим отказа сжимается до одного: refusal (модель решила, что вход не укладывается в схему).

> 🎒 **На пальцах.** Второй подход — это корректор, который вычитывает готовый текст и отправляет его на переписывание. Третий — клавиатура, на которой запрещённых букв просто нет. Корректор берёт деньги за каждый круг, клавиатура не берёт ничего и не ошибается.

Каждый передовой провайдер 2026 года поставляет какую-то форму третьего подхода.

- **OpenAI.** `response_format: {type: "json_schema", strict: true}` плюс поле `refusal` в ответе, если модель отказалась.
- **Anthropic.** Принуждение к схеме на входах `tool_use`; `stop_reason: "refusal"` как такового нет, но сигналом служит `end_turn` без вызова инструмента.
- **Gemini.** `responseSchema` на уровне запроса; в 2026 году Gemini умеет ограничения по грамматике на уровне токенов для отдельных типов.
- **Pydantic AI.** `output_type=InvoiceModel` выдаёт структурированный `RunResult`, типизированный как `InvoiceModel`.
- **Zod (TypeScript).** Рантайм-парсер, который проверяет вывод провайдера по схеме Zod; работает в паре с `beta.chat.completions.parse` у OpenAI.

Общая нить: объявить схему один раз и принуждать к ней по всей цепочке.

> 🎒 **На пальцах.** У Anthropic отказ выглядит хитрее всех: нет специального `stop_reason`, поэтому «модель отказалась» вы распознаёте по факту `end_turn`, при котором ни один инструмент не вызван. Если ваш код этого не проверяет, отказ выглядит как пустой успех и тихо ломает конвейер.

## The Concept

### JSON Schema 2020-12 — the lingua franca

JSON Schema 2020-12 принимает каждый провайдер. Конструкции, которыми вы будете пользоваться чаще всего:

- `type`: одно из `object`, `array`, `string`, `number`, `integer`, `boolean`, `null`.
- `properties`: соответствие имени поля его подсхеме.
- `required`: список имён полей, которые обязаны присутствовать.
- `enum`: закрытый набор допустимых значений.
- `minimum` / `maximum` (для чисел), `minLength` / `maxLength` / `pattern` (для строк).
- `items`: подсхема, применяемая к каждому элементу массива.
- `additionalProperties`: значение `false` запрещает лишние поля (по умолчанию зависит от режима).

> 🎒 **На пальцах.** Это весь ваш словарный запас для 95 % задач извлечения — семь конструкций. Хотите, чтобы `status` был только «paid», «unpaid» или «void»? Это `enum` из трёх значений. Хотите, чтобы сумма не была отрицательной? Это `minimum: 0`. Больше ничего изобретать не надо.

Strict mode у OpenAI добавляет три требования: каждое свойство обязано быть перечислено в `required`, `additionalProperties: false` должен стоять везде, и не должно остаться неразрешённых `$ref`. Нарушите — и API вернёт 400 уже на этапе запроса.

> 🎒 **На пальцах.** «Каждое свойство в `required`» звучит странно: а как же необязательные поля? Ответ — через тип: пишете `"type": ["string", "null"]` и модель обязана явно выдать `null`. Пропуск поля запрещён, «ничего» превращается в честное значение.

### Pydantic, the Python binding

Pydantic v2 генерирует JSON Schema из моделей, похожих на dataclass, через `model_json_schema()`. Pydantic AI оборачивает это так, что вы пишете:

```python
class Invoice(BaseModel):
    customer: str
    line_items: list[LineItem]
    total_usd: Decimal
```

а фреймворк агента уже на границе переводит схему в strict mode для OpenAI, в `input_schema` для Anthropic или в `responseSchema` для Gemini. Вывод модели возвращается как типизированный экземпляр `Invoice`. Ошибки валидации поднимают `ValidationError` с типизированными путями до ошибок.

> 🎒 **На пальцах.** Три строки объявления полей — и вы больше не пишете JSON Schema руками ни для одного провайдера. `total_usd: Decimal` превращается в число с ограничениями, а обратно приходит не строка, а объект, у которого `invoice.total_usd` можно сразу складывать. Схема живёт в одном месте — в классе.

### Zod, the TypeScript binding

Zod (`z.object({customer: z.string(), ...})`) — это эквивалент для TypeScript. Node SDK от OpenAI даёт `zodResponseFormat(Invoice)`, который переводит схему в JSON-Schema-нагрузку для API.

> 🎒 **На пальцах.** Zod для TypeScript — ровно то же, что Pydantic для Python: один класс, из которого и схема для модели, и проверка на входе в ваш код. Названия разные, идея одна, так что переехать с одного стека на другой — это переименовать `BaseModel` в `z.object`.

### Refusals

Strict mode не может заставить модель ответить. Если вход не укладывается в схему («в письме было стихотворение, а не счёт»), модель выдаёт поле `refusal` с причиной. Ваш код обязан обрабатывать это как полноправный исход, а не как сбой. Отказ полезен ещё и как сигнал безопасности: модель, которую попросили извлечь номер кредитной карты из письма с защищённым содержимым, вернёт отказ с приложенной причиной по безопасности.

> 🎒 **На пальцах.** Отказ — это не ошибка, а осмысленный ответ «в этом тексте нет счёта». Повторять запрос бессмысленно: стихотворение не станет счётом с третьей попытки, вы просто трижды заплатите. Отказ надо логировать и отдавать наверх, как отдельную ветку логики.

### Constrained decoding in the open

Реализации на открытых весах используют три техники.

1. **Grammar-based decoding** (`outlines`, `guidance`, `lm-format-enforcer`): из схемы строится детерминированный конечный автомат, и на каждом шаге маскируются логиты токенов, которые нарушили бы этот автомат.
2. **Logit masking with a JSON parser**: потоковый парсер JSON идёт в ногу с моделью и на каждом шаге вычисляет набор допустимых следующих токенов.
3. **Speculative decoding with a verifier**: дешёвая черновая модель предлагает токены, а проверяющая принуждает к схеме.

Коммерческие провайдеры выбирают одну из этих техник у себя под капотом. Состояние дел на 2026 год такое: на коротких структурированных выводах это быстрее обычной генерации, на длинных — примерно так же.

> 🎒 **На пальцах.** Все три техники делают одно: перед каждым токеном спрашивают «а этот вариант ещё может привести к валидному JSON?» и вычёркивают все, где ответ «нет». Отсюда и неожиданный результат про скорость: когда из 100 000 вариантов остаётся десяток, модель меньше мучается выбором.

### The three failure modes

1. **Parse error.** Вывод не является валидным JSON. В strict mode невозможно. На провайдерах без strict — вполне возможно.
2. **Schema violation.** Вывод разбирается, но нарушает схему. В strict mode невозможно. Вне него — обычное дело.
3. **Refusal.** Модель отказывается. Обрабатывать нужно как типизированный исход.

> 🎒 **На пальцах.** Ключевая мысль в двух словах: strict mode убивает первые два режима из трёх и оставляет ровно один. Значит ваш обработчик ошибок вместо трёх ветвей с повторами и регулярками содержит одну проверку `if refusal:`. Это и есть та экономия сложности, за которую стоит держаться.

### Retry strategy

Когда вы вне strict mode (tool use у Anthropic, нестрогий режим OpenAI, старые Gemini), схема восстановления такая:

```
generate -> parse -> validate -> if fail, inject error and retry, max 3x
```

Одного повтора обычно достаточно. Три повтора выгребают случайные сбои слабых моделей. Больше трёх — признак плохой схемы: модель не может её удовлетворить на некоторых входах, и чинить надо промпт или схему.

> 🎒 **На пальцах.** Правило простое: если восьмой повтор всё-таки «попал», не радуйтесь — вы просто выиграли в лотерею и заплатили за восемь запросов. Стабильно нужные четыре и больше попытки означают, что где-то в схеме противоречие или поле, которого в тексте физически нет.

### Small-model support

Constrained decoding работает и на маленьких моделях. Открытая модель на 3 миллиарда параметров с принуждением по грамматике обыгрывает модель на 70 миллиардов с обычным промптингом на структурированных задачах. Это главная причина, почему структурированный вывод важен в продакшене: он отвязывает надёжность от размера модели.

```figure
constrained-decoding
```

> 🎒 **На пальцах.** Разница в 23 раза по размеру — и маленькая модель выигрывает. Причина не в уме: большая модель понимает текст лучше, но иногда ошибается в оформлении, а маленькая физически не может ошибиться в оформлении. Для извлечения полей форма важнее красноречия, а маленькая модель ещё и дешевле и быстрее.

## Use It

`code/main.py` поставляет минимальный валидатор JSON Schema 2020-12 на стандартной библиотеке (типы, required, enum, min/max, pattern, items, additionalProperties). Он оборачивает схему `Invoice` и прогоняет через валидатор поддельный вывод LLM, показывая пути ошибки разбора, нарушения схемы и отказа. В продакшене подмените поддельный вывод настоящим ответом любого провайдера.

Что смотреть:

- Валидатор возвращает типизированный список `[ValidationError]` с путём и сообщением. Именно в такой форме их и надо подавать в промпт для повтора.
- Ветка отказа НЕ делает повтор. Она пишет в лог и возвращает типизированный отказ. Phase 14 · 09 использует отказы как сигнал безопасности.
- Проверка `additionalProperties: false` срабатывает на враждебном тестовом входе — видно, почему strict mode закрывает дверь перед выдуманными полями.

> 🎒 **На пальцах.** Обратите внимание на пару «путь + сообщение»: строка вида `line_items[2].qty: expected integer` говорит модели ровно, что чинить, — а «validation failed» не говорит ничего. Разница в проценте успешных повторов огромная, а стоит она одной лишней строчки в валидаторе.

## Ship It

Этот урок производит `outputs/skill-structured-output-designer.md`. По цели извлечения из свободного текста (счета, тикеты поддержки, резюме и так далее) навык выдаёт JSON Schema 2020-12, совместимую со strict mode, и зеркальную ей модель Pydantic, с заготовками для типизированного отказа и повторов.

> 🎒 **На пальцах.** Полезность навыка именно в слове «зеркальную»: схема и модель Pydantic обязаны совпадать поле в поле, иначе у вас две правды и один тихий баг. Генерировать их вместе — дешёвый способ не разъехаться.

## Exercises

1. Запустите `code/main.py`. Добавьте четвёртый тестовый случай, в котором `total_usd` — отрицательное число. Убедитесь, что валидатор отвергает его по пути ограничения `minimum`.

2. Расширьте валидатор поддержкой `oneOf` с дискриминатором. Типичный случай: `line_item` — это либо товар, либо услуга, размеченные полем `kind`. У strict mode тут тонкие правила, посмотрите руководство OpenAI по структурированным выводам.

3. Опишите ту же схему Invoice как Pydantic BaseModel и сравните вывод `model_json_schema()` со своей рукописной схемой. Найдите то единственное поле, которое Pydantic ставит по умолчанию, а рукописная версия опускает.

4. Измерьте частоту отказов. Соберите десять входов, которые не должны извлекаться (текст песни, математическое доказательство, пустое письмо), и прогоните их через настоящего провайдера в strict mode. Посчитайте отказы против выдуманных выводов. Это ваша эталонная разметка для повторов с учётом отказов.

5. Прочитайте руководство OpenAI по структурированным выводам от начала до конца. Найдите ту единственную конструкцию, которую strict mode запрещает явно, хотя обычная JSON Schema её разрешает. Затем спроектируйте схему, которая использует запрещённую конструкцию не по необходимости, и перепишите её так, чтобы она стала strict-совместимой.

> 🎒 **На пальцах.** Начните с четвёртого задания: десять заведомо непригодных входов — это полчаса работы и честная цифра. Если из десяти вы получили семь отказов и три выдуманных счёта, значит 30 % мусора уходит к вам в базу как настоящие данные, и никакая схема этого не поймает. Дальше уже понятно, что чинить в промпте.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| JSON Schema 2020-12 | «Та самая спека схем» | Диалект схем на уровне черновика IETF, на котором говорит любой современный провайдер |
| Strict mode | «Гарантированная схема» | Флаг OpenAI, который принуждает к схеме через constrained decoding |
| Constrained decoding | «Маскирование логитов» | Принуждение на этапе декодирования: маскируются невалидные следующие токены |
| Refusal | «Модель отказалась» | Типизированный исход, когда вход не укладывается в схему |
| Parse error | «Невалидный JSON» | Вывод не разобрался как JSON; в strict mode невозможно |
| Schema violation | «Не та форма» | Разобралось, но нарушены типы, required, enum или диапазоны |
| `additionalProperties: false` | «Лишнего не пускать» | Запрещает неизвестные поля; обязательно в strict mode у OpenAI |
| Pydantic BaseModel | «Типизированный вывод» | Класс Python, который и выдаёт JSON Schema, и проверяет по ней данные |
| Zod schema | «Тип вывода в TypeScript» | Рантайм-схема для TS, проверяющая вывод провайдера |
| Grammar enforcement | «Constrained decode на открытых весах» | Маскирование логитов по конечному автомату, как в outlines и guidance |
