# Асинхронные задачи (SEP-1686) — вызвал сейчас, забрал результат потом

> Настоящая работа агента занимает минуты и часы: прогон CI, синтез глубокого исследования, пакетные экспорты. Синхронный вызов инструмента рвёт соединение, ловит таймаут или морозит интерфейс. SEP-1686, влитый 2025-11-25, добавляет примитив Tasks: любой запрос можно расширить до задачи, а результат забрать позже или получать поток уведомлений о состоянии. Про риск устаревания: до середины 2026 года Tasks остаются экспериментом, поверхность SDK всё ещё проектируется вокруг спецификации.

**Type:** Build
**Languages:** Python (stdlib, async task state machine)
**Prerequisites:** Phase 13 · 07 (MCP server), Phase 13 · 09 (transports)
**Time:** ~75 minutes

## Learning Objectives

- Понимать, когда инструмент пора переводить из синхронного в задачный (работа на сервере дольше 30 секунд).
- Пройти жизненный цикл задачи: `working` → `input_required` → `completed` / `failed` / `cancelled`.
- Сохранять состояние задачи так, чтобы падение процесса не съело работу на полпути.
- Правильно опрашивать `tasks/get` и забирать исходный результат через блокирующий `tasks/result`.

## The Problem

Инструмент `generate_report` крутит конвейер извлечения данных на несколько минут. Что можно сделать в синхронной модели:

1. Держать соединение открытым три минуты. Удалённые транспорты его сбрасывают, клиенты ловят таймаут, интерфейсы подвисают.
2. Сразу вернуть заглушку и заставить клиента опрашивать свою самодельную ручку. Это ломает единообразие MCP.
3. Выстрелить и забыть — результата не будет вообще.

Ни один вариант не годится. SEP-1686 добавляет четвёртый: расширение поддерживаемого запроса до задачи. Запрос (обычно `tools/call`) несёт `params.task`, получатель сразу возвращает `CreateTaskResult`, а запрашивающая сторона опрашивает `tasks/get` и получает исходный результат операции через `tasks/result`.

> 🎒 **На пальцах.** Это гардероб в театре: вы отдаёте пальто и получаете номерок, а не стоите три минуты у стойки. Номерок здесь — `taskId: "tsk_9f7b..."`, вопрос «как там моё?» — `tasks/get`, а выдача пальто — `tasks/result`.

## The Concept

### Task augmentation

Запрос становится задачей, если включить `task` прямо в его `params`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "generate_report",
    "arguments": {"size": "large"},
    "task": {"ttl": 900000}
  }
}
```


Получатель сразу отвечает `CreateTaskResult`; его единственное обязательное поле — задача:

```json
{"result": {"task": {
  "taskId": "tsk_9f7b...",
  "status": "working",
  "createdAt": "2025-11-25T10:30:00Z",
  "lastUpdatedAt": "2025-11-25T10:30:00Z",
  "ttl": 900000,
  "pollInterval": 1000
}}}
```

`createdAt` и `lastUpdatedAt` — метки времени ISO 8601. `ttl` — фактический срок хранения, принятый получателем; `null` означает бессрочное хранение.

> 🎒 **На пальцах.** Посмотрите на числа в ответе выше: `ttl: 900000` — это миллисекунды, то есть 900 000 / 1000 / 60 = 15 минут. Забрали результат за 15 минут — получили; пришли на шестнадцатой — сервер уже имеет право сказать «не знаю такой задачи». Как камера хранения с оплаченным сроком.

### Per-tool opt-in

Аннотации инструмента могут объявлять поддержку задач:

- `execution.taskSupport: "forbidden"` (или поле отсутствует) — не расширять вызов до задачи.
- `execution.taskSupport: "optional"` — клиент может попросить расширение до задачи.
- `execution.taskSupport: "required"` — клиент обязан использовать расширение до задачи.

У инструмента `generate_report` было бы `required`. У инструмента `notes_search` — `forbidden`.

> 🎒 **На пальцах.** Флаг — это честная табличка на двери. `notes_search` отвечает за 50 мс, ему номерок не нужен: `forbidden`. `generate_report` работает три минуты, и синхронный вызов сломается гарантированно, поэтому `required` запрещает клиенту даже пробовать по-быстрому. `optional` — для инструментов, которые то за секунду, то за пять минут.

### States

```text
working  -> input_required -> working  (loop via elicitation)
input_required -> completed / failed / cancelled
working  -> completed
working  -> failed
working  -> cancelled
```

Машина состояний работает только вперёд: как только задача стала `completed`, `failed` или `cancelled`, это конец пути.

> 🎒 **На пальцах.** Считайте: из `working` есть четыре выхода, а обратных дорог из трёх последних нет ни одной. Единственная петля — `input_required`, когда сервер посреди работы спрашивает у пользователя чего-то ещё, получает ответ и возвращается в `working`. Как посылка: «в пути» может стать «доставлено», но «доставлено» уже никогда не станет «в пути».

### Methods

- `tasks/get {taskId}` — возвращает полный Task, включая `status` и метки времени.
- `tasks/result {taskId}` — блокируется до терминального состояния, затем возвращает ровно исходный результат операции или JSON-RPC-ошибку.
- `tasks/cancel {taskId}` — отменяет нетерминальную задачу; для терминальной возвращает `-32602` Invalid params.
- `tasks/list` — необязателен; перечисляет активные и недавно завершённые задачи.

> 🎒 **На пальцах.** Четыре метода — это четыре вопроса к гардеробщику: «как там моё?», «дай», «отмени», «покажи все номерки». `tasks/result` сам ждёт готовности и возвращает исходную посылку, а не обёртку статуса.

### Streaming state changes

Если сервер это умеет, клиент может подписаться на уведомления о смене состояния:

```text
receiver -> notifications/tasks/status {taskId, status, createdAt, lastUpdatedAt, ttl}
```

Клиенты, которые слушают поток, а не долбят опросами, дают пользователю приятнее опыт. Опрос поддерживается всегда как минимальный обязательный вариант.

> 🎒 **На пальцах.** Разница как между «звонить в пиццерию каждую минуту» и «получить SMS, когда курьер выехал». Опрос раз в две секунды на трёхминутной задаче — это 90 бессмысленных запросов; уведомлений будет штук пять. Но опрос обязан работать всегда: это тот минимум, который сервер не имеет права не поддерживать.

### Durable state

Спецификация требует, чтобы серверы, объявившие поддержку задач, сохраняли состояние. Падение процесса не должно терять готовые результаты, пока не вышел ttl. Хранилища бывают разные: SQLite, Redis, обычная файловая система. Стенд урока 13 использует файловую систему.

> 🎒 **На пальцах.** Держать состояние задач в памяти процесса — это писать номерки мелом на ладони: одно падение, и все пальто ничьи. Файл на диске переживает и падение, и деплой. Именно поэтому в стенде состояние лежит в `/tmp/lesson-13-tasks/<id>.json` — самое дешёвое честное хранилище, какое можно взять без зависимостей.

### Cancellation semantics

Для нетерминальной задачи `tasks/cancel` пытается остановить выполнение и переводит Task в `cancelled` до ответа. Отмена `completed`, `failed` или уже `cancelled` Task недопустима и возвращает JSON-RPC `-32602`; повторная отмена не является идемпотентным no-op.

> 🎒 **На пальцах.** Первое нажатие «отмена» переводит работающую задачу в `cancelled`. Второе уже обращается к терминальной задаче и потому получает `-32602`. Сам воркер всё равно должен кооперативно проверять флаг отмены между шагами.

### Crash recovery

Когда процесс сервера перезапускается:

1. Загрузить все сохранённые состояния задач.
2. Пометить как `failed` с ошибкой `CRASH_RECOVERY` все задачи в состоянии `working`, чей процесс умер.
3. Сохранить `completed` / `failed` / `cancelled` до конца их ttl.

> 🎒 **На пальцах.** Логика простая: если в файле написано `working`, а живого воркера нет, значит задача умерла вместе с процессом — врать клиенту «ещё работаю» нельзя, честнее сразу сказать `failed`. Иначе клиент будет опрашивать статус до конца ttl и ждать призрака. А вот готовые результаты трогать не надо: они уже посчитаны и лежат на диске.

### Async tasks plus sampling

Задача сама может вызвать `sampling/createMessage`. Именно так работают долгие исследовательские задачи: поток задачи на сервере по мере надобности дёргает модель клиента, а интерфейс клиента всё это время показывает задачу как `working` с периодическими обновлениями прогресса.

> 🎒 **На пальцах.** Тут стрелки разворачиваются: обычно клиент просит сервер, а при sampling сервер просит модель клиента подумать. Задача «изучи 40 статей» внутри себя делает 40 вызовов модели, и все они умещаются в один номерок для пользователя. Считайте это субподрядом: подрядчик пользуется вашими же рабочими, но отчитывается одной строкой прогресса.

### Why this is experimental

SEP-1686 вышел 2025-11-25, но в общей дорожной карте помечены три открытых вопроса: примитивы долговечных подписок, подзадачи (связь «родитель — ребёнок») и стандартизация TTL результата. Ждите, что спецификация будет меняться весь 2026 год. Продакшен-код должен считать Tasks стабильными только для типового случая и подстраховываться от будущих изменений SDK в части подзадач.

> 🎒 **На пальцах.** Практический вывод: заворачивайте вызовы `tasks/*` в свой тонкий слой из трёх-четырёх функций. Когда SDK поменяет имена полей ради подзадач, вы правите один файл, а не сорок мест в коде. «Экспериментально» не значит «не используй» — значит «не вплетай в каждую строчку».

```figure
tp-task-lifecycle
```

## Use It

`code/main.py` реализует долговечное хранилище задач (на файловой системе) и инструмент `generate_report`, который работает в фоновом потоке. Клиенты передают `params.task`, получают `CreateTaskResult`, опрашивают `tasks/get` и вызывают блокирующий `tasks/result`, который возвращает исходный `CallToolResult`. Демо отмены также показывает обязательный ответ `-32602` на повторную отмену терминальной задачи.

На что смотреть:

- JSON состояния задачи сохраняется в `/tmp/lesson-13-tasks/<id>.json`.
- Поток-воркер обновляет поле `progress`; опрос показывает, как оно растёт.
- Отмена со стороны клиента выставляет событие; воркер его проверяет и выходит досрочно.
- Перезагрузка состояния после «падения» помечает незавершённую задачу как `failed` с `CRASH_RECOVERY`.

> 🎒 **На пальцах.** Откройте файл состояния прямо во время прогона — увидите, как `progress` в JSON меняется с 0 на 40, потом на 80. Это и есть весь фокус: клиент и воркер не разговаривают напрямую, они общаются через один файл на диске. Поэтому воркер может умереть, а клиент всё равно узнает, где всё остановилось.

## Ship It

Этот урок производит `outputs/skill-task-store-designer.md`. По описанию долгого инструмента (исследование, сборка, экспорт) навык проектирует хранилище задач (форма состояния, ttl, долговечность), выбирает правильный флаг taskSupport и набрасывает уведомления о прогрессе.

> 🎒 **На пальцах.** Обратите внимание, что навык решает три вопроса, а не один: что хранить, как долго и кто обязан пользоваться задачами. Забудете ttl — хранилище раздуется до бесконечности. Забудете taskSupport — клиент попробует синхронный вызов и упадёт на таймауте. Три поля, три класса аварий.

## Exercises

1. Запустите `code/main.py`. Запустите задачу `generate_report`, опросите статус, потом забери́те результат.

2. Добавьте вызов `tasks/cancel` посреди выполнения. Убедитесь, что воркер его уважает и состояние становится `cancelled`.

3. Сымитируйте восстановление после падения: убейте поток-воркер, перезапустите загрузчик и посмотрите на режим отказа `CRASH_RECOVERY`.

4. Переведите хранилище на SQLite. Выигрыш по долговечности тот же, зато открываются запросы (перечислить все задачи из сессии X).

5. Прочитайте пост о дорожной карте MCP на 2026 год. Найдите тот один открытый вопрос по Tasks, который с наибольшей вероятностью повлияет на дизайн API в SDK в следующем году.

> 🎒 **На пальцах.** Во втором задании легко обмануться: отмена «не работает» не потому, что вы неправильно её послали, а потому что воркер спит в длинном `time.sleep(60)` и просто не смотрит на флаг. Правило: дробите долгую работу на шаги по секунде и проверяйте флаг отмены между шагами. Иначе отмена сработает ровно тогда, когда задача и так закончилась.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Task | «Долгий запрос» | Долговечная машина состояний вокруг поддерживаемого MCP-запроса |
| SEP-1686 | «Спека про Tasks» | Spec Evolution Proposal, добавивший Tasks 2025-11-25 |
| `params.task` | «Расширение до задачи» | Метаданные запроса, сейчас с необязательным запрошенным `ttl` |
| `execution.taskSupport` | «Флаг инструмента» | `forbidden` / `optional` / `required` для каждого инструмента |
| `tasks/get` | «Метод опроса» | Забрать полный Task с `taskId`, `status` и ISO-метками времени |
| `tasks/result` | «Забрать результат» | Блокируется до финала и возвращает исходный результат или ошибку |
| `tasks/cancel` | «Останови это» | Отменяет нетерминальный Task; для терминального возвращает `-32602` |
| ttl | «Бюджет хранения» | Миллисекунды, которые сервер обещает держать состояние задачи |
| `notifications/tasks/status` | «Пуш состояния» | Необязательное событие с полным статусом Task, инициированное получателем |
| Durable store | «Состояние, пережившее падение» | Слой сохранения на файловой системе, SQLite или Redis |
