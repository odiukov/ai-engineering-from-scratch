# Собираем MCP-сервер — SDK для Python и TypeScript

> Большинство туториалов по MCP показывают только stdio-хелловорлды. Настоящий сервер отдаёт инструменты плюс ресурсы плюс промпты, договаривается о возможностях, выдаёт структурированные ошибки и ведёт себя одинаково в любом SDK. В этом уроке мы соберём сервер заметок от начала до конца: stdio-транспорт на стандартной библиотеке, разбор JSON-RPC, три серверных примитива и стиль чистых функций, который потом без переделки ложится и на FastMCP из Python SDK, и на TypeScript SDK.

**Type:** Build
**Languages:** Python (stdlib, stdio MCP server)
**Prerequisites:** Phase 13 · 06 (MCP fundamentals)
**Time:** ~75 minutes

## Learning Objectives

- Реализовать методы `initialize`, `tools/list`, `tools/call`, `resources/list`, `resources/read`, `prompts/list` и `prompts/get`.
- Написать цикл разбора, который читает JSON-RPC-сообщения из stdin и пишет ответы в stdout.
- Выдавать структурированные ответы об ошибках по спецификации JSON-RPC 2.0 и по дополнительным кодам MCP.
- Перевести реализацию со стандартной библиотеки на FastMCP (Python SDK) или на TypeScript SDK, не переписывая логику инструментов.

## The Problem

Прежде чем браться за удалённый транспорт (Phase 13 · 09) или за слой авторизации (Phase 13 · 16), нужен опрятный локальный сервер. Локальный — значит stdio: клиент сам запускает сервер дочерним процессом, а сообщения текут через stdin/stdout, разделённые переводом строки.

Спецификация 2025-11-25 предписывает кодировать stdio-сообщения как JSON-объекты с явным разделителем `\n`. Никакого SSE здесь нет: SSE был старым удалённым режимом, и его выпиливают в середине 2026 года (Rovo MCP от Atlassian объявил его устаревшим 30 июня 2026-го, Keboola — 1 апреля 2026-го). Для stdio весь формат провода — это один JSON-объект на строку.

> 🎒 **На пальцах.** stdio — это разговор через щель в двери: одна записка на строку, порядок строгий. Один объект `{"jsonrpc":"2.0","id":1,...}` — одна строка, в конце `\n`. Если ваша записка растянется на две строки, собеседник прочитает половину и решит, что это мусор.

Сервер заметок — удачная форма для примера, потому что он задействует все три серверных примитива. Инструменты меняют состояние (`notes_create`). Ресурсы отдают данные (`notes://{id}`). Промпты поставляют шаблоны (`review_note`). Схема этого урока переносится на любую предметную область.

> 🎒 **На пальцах.** Проверьте на заметках, что примитивов ровно три и они не пересекаются: `notes_create` меняет мир — это tool; `notes://14` просто отдаёт текст заметки номер 14 — это resource; `review_note` — заготовка для человека, то есть prompt. Любая другая предметная область раскладывается так же: три ящика, и каждая возможность лежит ровно в одном.

## The Concept

### Dispatch loop

```
loop:
  line = stdin.readline()
  msg = json.loads(line)
  if has id:
    handle request -> write response
  else:
    handle notification -> no response
```

Три правила:

- Не печатайте в stdout ничего, кроме конверта JSON-RPC. Отладочные логи идут в stderr.
- На каждый запрос ОБЯЗАН прийти ответ с тем же `id`.
- На уведомления отвечать НЕЛЬЗЯ.

> 🎒 **На пальцах.** Цикл — это турникет: прочитал строку, посмотрел, есть ли `id`. Есть `id` — обязан вернуть ответ с тем же номером, как в очереди по талонам. Нет `id` — это уведомление, и отвечать на него запрещено: клиент такой ответ не ждёт и упрётся в лишнее сообщение. Один отладочный `print()` в stdout убивает соединение мгновенно.

### Implementing `initialize`

```python
def initialize(params):
    return {
        "protocolVersion": "2025-11-25",
        "capabilities": {
            "tools": {"listChanged": True},
            "resources": {"listChanged": True, "subscribe": False},
            "prompts": {"listChanged": False},
        },
        "serverInfo": {"name": "notes", "version": "1.0.0"},
    }
```

Объявляйте только то, что действительно поддерживаете. Клиент опирается на этот набор возможностей, чтобы включать и выключать функции.

> 🎒 **На пальцах.** Пересчитайте по блоку выше: сервер заявил `tools` и `resources` с `listChanged: true`, но `subscribe: false`. Значит клиент будет перезапрашивать список при изменениях, а подписку на ресурс даже не попробует — он поверил на слово. Врать в capabilities нельзя: заявите `subscribe`, не реализовав его, и клиент повиснет в ожидании пуша, которого не будет.

### Implementing `tools/list` and `tools/call`

`tools/list` возвращает `{tools: [...]}`, где у каждой записи есть `name`, `description` и `inputSchema`. `tools/call` принимает `{name, arguments}` и возвращает `{content: [blocks], isError: bool}`.

Блоки контента типизированы. Самые ходовые:

```json
{"type": "text", "text": "Found 2 notes"}
{"type": "resource", "resource": {"uri": "notes://14", "text": "..."}}
{"type": "image", "data": "<base64>", "mimeType": "image/png"}
```

Ошибки инструментов бывают двух видов. Ошибки уровня протокола (неизвестный метод, плохие параметры) — это ошибки JSON-RPC. Ошибки уровня инструмента (вызов корректный, но инструмент упал) возвращаются как `{content: [...], isError: true}`. Так модель видит провал у себя в контексте.

> 🎒 **На пальцах.** Блок контента — это конверт с наклейкой типа. Три наклейки из примера выше: `text` для строки «Found 2 notes», `resource` для ссылки на `notes://14` вместе с текстом, `image` для картинки в base64. Возвращать всегда список: даже единственный результат — это список из одного блока.

> 🎒 **На пальцах.** Разница между двумя видами ошибок чисто практическая. «Метода `notes_delet` не существует» — ошибка JSON-RPC, модель её даже не увидит, это баг клиента. «Заметки 999 в базе нет» — это `isError: true` с текстом внутри, модель прочитает его в контексте и попробует другой id. Первое чините вы, второе — модель.

### Implementing resources

Ресурсы по своей природе только для чтения. `resources/list` возвращает манифест, `resources/read` — само содержимое. URI могут быть `file://...`, `http://...` или своей схемой вроде `notes://`.

Что меняется, когда вы отдаёте данные ресурсом, а не инструментом:

- Модель его не «вызывает»; клиент может подложить его в контекст по просьбе пользователя.
- Подписки позволяют серверу сам пушить обновления, когда ресурс изменился (Phase 13 · 10).
- Phase 13 · 14 расширяет эту идею схемой `ui://` для интерактивных ресурсов.

> 🎒 **На пальцах.** Ресурс — как файл в общей папке: лежит и ждёт, пока откроют, сам никуда не лезет. Модель не может «позвать» `notes://14`; подложить заметку в контекст решает пользователь или клиент. Поэтому 200 заметок в виде 200 ресурсов безопасны, а 200 инструментов — нет: ресурсы не тратят бюджет инструментов.

### Implementing prompts

Промпты — это шаблоны с именованными аргументами. Хост показывает их как слэш-команды. Промпт `review_note` может принимать аргумент `note_id` и разворачиваться в шаблон из нескольких сообщений, который клиент скармливает своей модели.

> 🎒 **На пальцах.** Промпт — это бланк с пропусками. `review_note(note_id=14)` разворачивается в готовые сообщения вида «вот текст заметки 14, проверь её по чек-листу». Пользователь в Claude Desktop видит просто `/review_note` в списке команд и даже не подозревает, что за ней стоит ваш сервер.

### Stdio transport subtleties

- JSON, разделённый переводами строк. Никаких префиксов с длиной сообщения.
- Не буферизуйте. `sys.stdout.flush()` после каждой записи.
- Временем жизни распоряжается клиент. Когда stdin закрылся (EOF), выходите аккуратно.
- Не глотайте SIGPIPE молча: залогируйте и выходите.

> 🎒 **На пальцах.** Без `flush()` ваш ответ может тихо лежать в буфере на 4 КБ, пока клиент ждёт его и ловит таймаут. Строку написали — сразу `flush()`, как письмо отправляют сразу, а не копят до полного мешка. А EOF на stdin — не ошибка, а вежливое «мы закончили»: закрывайтесь молча и без трейсбека.

### Annotations

Каждый инструмент может нести `annotations` — описание свойств с точки зрения безопасности:

- `readOnlyHint: true` — чистое чтение, повторить безопасно.
- `destructiveHint: true` — необратимые побочные эффекты; клиент должен спросить подтверждение.
- `idempotentHint: true` — одинаковый вход даёт одинаковый выход.
- `openWorldHint: true` — взаимодействует с внешними системами.

Клиент по ним решает, как строить интерфейс (окна подтверждения, индикаторы статуса) и как маршрутизировать вызовы (Phase 13 · 17).

> 🎒 **На пальцах.** Аннотации — это наклейки на кнопках. `notes_search` с `readOnlyHint: true` клиент выполнит сам и хоть десять раз подряд. А `notes_delete` с `destructiveHint: true` вызовет окно «Точно удалить?» — потому что откатить нельзя. Технически аннотации ничего не запрещают, они лишь показывают клиенту, где ставить предохранитель.

### Graduation path

Сервер на стандартной библиотеке в `code/main.py` занимает около 180 строк. FastMCP (Python) сворачивает ту же логику до стиля с декораторами:

```python
from fastmcp import FastMCP
app = FastMCP("notes")

@app.tool()
def notes_search(query: str, limit: int = 10) -> list[dict]:
    ...
```

У TypeScript SDK форма такая же. Переход можно сделать в любой момент, когда будете готовы; понятия (возможности, разбор сообщений, блоки контента) остаются те же.

```figure
t3-dispatch-loop
```

> 🎒 **На пальцах.** Посчитайте выигрыш: 180 строк на стандартной библиотеке против шести строк с `@app.tool()`. Схема входа при этом берётся из аннотаций `query: str, limit: int = 10` сама. Но 180 строк вы писали не зря: когда FastMCP отдаст странный ответ, вы уже знаете, какой именно JSON-RPC-конверт он собрал под капотом.

## Use It

`code/main.py` — законченный MCP-сервер заметок поверх stdio, только на стандартной библиотеке. Он обслуживает `initialize`, `tools/list`, `tools/call` для трёх инструментов (`notes_list`, `notes_search`, `notes_create`), `resources/list` и `resources/read` для каждой заметки, плюс промпт `review_note`. Погонять его можно, подавая JSON-RPC-сообщения через пайп:

```
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' | python main.py
```

На что посмотреть:

- Диспетчер — это `dict[str, Callable]` с ключом по имени метода.
- Каждый исполнитель инструмента возвращает список блоков контента, а не голую строку.
- `isError: true` выставляется, когда исполнитель бросает исключение.

> 🎒 **На пальцах.** Та строчка с `echo` и пайпом — ваш дешёвый отладчик: одно сообщение на входе, одно на выходе, никакая модель не нужна. Начните с `initialize`, потом `tools/list` — и убедитесь, что в ответе ровно три инструмента. Если в stdout прилетело что-то помимо JSON, вы нашли свой первый баг именно так.

## Ship It

Этот урок производит `outputs/skill-mcp-server-scaffolder.md`. Получив предметную область (заметки, тикеты, файлы, база данных), навык разворачивает каркас MCP-сервера с правильным делением на инструменты / ресурсы / промпты и с путём перехода на SDK.

> 🎒 **На пальцах.** Навык-каркасник берёт на себя ровно скучное: разложить область на три ящика и не забыть `annotations` у разрушающих инструментов. Скажете ему «тикеты» — получите `tickets_search` (только чтение), `tickets_close` (destructive), ресурс `tickets://{id}` и промпт для разбора. Дальше вы правите логику, а не структуру.

## Exercises

1. Запустите `code/main.py` и погоняйте его вручную собранными JSON-RPC-сообщениями. Задействуйте `notes_create`, а потом `resources/read`, чтобы вытащить новую заметку.

2. Добавьте инструмент `notes_delete` с `annotations: {destructiveHint: true}`. Убедитесь, что клиент показал бы окно подтверждения (для этого нужен настоящий хост; Claude Desktop подойдёт).

3. Реализуйте `resources/subscribe`, чтобы сервер пушил `notifications/resources/updated` каждый раз, когда заметку меняют. Добавьте задачу-keepalive.

4. Перенесите сервер на FastMCP. Файл на Python должен усохнуть меньше 80 строк. Поведение на проводе обязано остаться идентичным; проверьте тем же самым JSON-RPC-стендом.

5. Прочитайте раздел `server/tools` спецификации и найдите хотя бы одно поле определения инструмента, которого нет в сервере из этого урока. (Подсказка: их там несколько; выберите одно и добавьте.)

> 🎒 **На пальцах.** Задание 4 — главная проверка понимания: если после переезда на FastMCP тот же `echo` с `tools/list` даёт байт в байт тот же ответ, значит вы усвоили не библиотеку, а протокол. Держите оба файла рядом и сравнивайте вывод через `diff`: 80 строк против 180 при одинаковом поведении на проводе.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| MCP server | «То, что отдаёт инструменты» | Процесс, который говорит на MCP-JSON-RPC через stdio или HTTP |
| stdio transport | «Модель дочернего процесса» | Клиент сам запускает сервер; общение идёт через stdin/stdout |
| Dispatcher | «Роутер методов» | Таблица соответствия имени JSON-RPC-метода и функции-обработчика |
| Content block | «Кусок результата инструмента» | Типизированный элемент массива `content` в ответе инструмента |
| `isError` | «Провал на уровне инструмента» | Сигнал, что инструмент упал; отличается от ошибки JSON-RPC |
| Annotations | «Подсказки про безопасность» | Флаги readOnly / destructive / idempotent / openWorld |
| FastMCP | «Python SDK» | Высокоуровневый фреймворк на декораторах поверх протокола MCP |
| Resource URI | «Адресуемые данные» | `file://`, `db://` или своя схема, идентифицирующая ресурс |
| Prompt template | «Бриф для слэш-команды» | Шаблон от сервера со слотами под аргументы для интерфейсов хоста |
| Capability declaration | «Переключатель фич» | Флаги по каждому примитиву, объявленные в `initialize` |
