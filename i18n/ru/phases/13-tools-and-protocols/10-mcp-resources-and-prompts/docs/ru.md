# Ресурсы и промпты MCP — контекст помимо инструментов

> Инструментам достаётся 90 процентов внимания вокруг MCP. Два других примитива сервера решают другие задачи. Ресурсы отдают данные на чтение; промпты отдают переиспользуемые шаблоны в виде слэш-команд. Многим серверам стоило бы отдавать ресурсы вместо обёртывания чтения в инструменты, а промпты — вместо зашитых в клиентский промпт сценариев. Этот урок формулирует правило выбора и разбирает сообщения `resources/*` и `prompts/*`.

**Type:** Build
**Languages:** Python (stdlib, resource + prompt handler)
**Prerequisites:** Phase 13 · 07 (MCP server)
**Time:** ~45 minutes

## Learning Objectives

- Решать, чем выставить возможность в конкретной предметной области: инструментом, ресурсом или промптом.
- Реализовать `resources/list`, `resources/read`, `resources/subscribe` и обработку `notifications/resources/updated`.
- Реализовать `prompts/list` и `prompts/get` с шаблонами аргументов.
- Понимать, когда host показывает промпты как слэш-команды, а когда подмешивает контекст автоматически.

> 🎒 **На пальцах.** Три примитива — это три разных двери в один и тот же сервер. Инструмент дёргает модель, ресурс подсовывает пользователь, промпт запускает человек командой. Весь урок сводится к тому, чтобы каждый раз выбрать правильную дверь и не тащить всё через одну.

## The Problem

Наивный MCP-сервер для приложения заметок выставляет всё инструментами: `notes_read`, `notes_list`, `notes_search`. Так каждый доступ к данным заворачивается в вызов инструмента, которым управляет модель. Последствия:

- Модель обязана решать, звать ли `notes_read`, на каждый запрос, которому мог бы помочь контекст.
- На контент только для чтения нельзя подписаться и нельзя лить его в боковую панель хоста.
- Интерфейсы клиентов (панель приложения ресурсов в Claude Desktop, выбор «Include file» в Cursor) не могут показать эти данные.

Правильное разделение: данные выставляем ресурсом, изменяющие или вычисляющие действия — инструментами, переиспользуемые многошаговые сценарии — промптами. У каждого примитива своя роль в интерфейсе и свой способ доступа.

> 🎒 **На пальцах.** Посчитайте цену наивного варианта: три инструмента живут в бюджете инструментов и на каждом ходу тратят токены схем, а модель ещё и должна догадаться их позвать. Замените `notes_read` и `notes_list` на ресурсы — и пользователь просто прикрепляет заметку сам, как файл в мессенджере. Ноль вызовов, ноль догадок.

## The Concept

### Tools vs resources vs prompts — the decision rule

| Capability | Primitive |
|------------|-----------|
| Пользователь хочет искать, фильтровать или преобразовывать данные | tool |
| Пользователь хочет, чтобы host подложил эти данные как контекст | resource |
| Пользователь хочет шаблонный сценарий, который можно запускать снова | prompt |

Ориентир: если модели полезно звать это на каждом связанном запросе — это инструмент. Если пользователю полезно прикрепить это к разговору — это ресурс. Если единицей переиспользования выступает целый многошаговый сценарий — это промпт.

> 🎒 **На пальцах.** Прогоните по таблице «покажи мне заметку про MCP». Данные? Да. Прикрепляются к разговору? Да. Значит ресурс `notes://note-14`, а не инструмент. А вот «найди все заметки со словом MCP» — это уже поиск, то есть tool: URI заранее неизвестен, его надо вычислить.

### Resources

`resources/list` возвращает `{resources: [{uri, name, mimeType, description?}]}`. `resources/read` принимает `{uri}` и возвращает `{contents: [{uri, mimeType, text | blob}]}`.

URI может быть чем угодно адресуемым:

- `file:///Users/alice/notes/mcp.md`
- `postgres://my-db/query/SELECT ...`
- `notes://note-14` (custom scheme)
- `memory://session-2026-04-22/recent` (server-specific)

`contents[]` поддерживает и текст, и бинарные данные. Для бинарных используется `blob` — строка в base64 плюс `mimeType`.

> 🎒 **На пальцах.** Схема URI — это просто префикс, по которому ваш сервер понимает, что делать дальше. `notes://note-14` не существует ни в какой файловой системе: сервер видит `notes://`, берёт число 14 и достаёт четырнадцатую заметку из базы. Придумывать свои схемы разрешено и нормально.

### Resource subscriptions

Объявите `{resources: {subscribe: true}}` в возможностях. Клиент вызывает `resources/subscribe {uri}`. Сервер присылает `notifications/resources/updated {uri}`, когда ресурс изменился. Клиент перечитывает его.

Пример применения: сервер заметок, чьи ресурсы — файлы на диске; наблюдатель за файлами дёргает уведомления об изменении; Claude Desktop заново подтягивает файл в контекст, когда его отредактировали вне хоста.

> 🎒 **На пальцах.** Это подписка на канал, а не проверка почты каждые пять секунд. Вы правите `mcp.md` в редакторе, файловый watcher замечает запись, сервер отправляет одно уведомление, и Claude Desktop подтягивает новую версию. Без подписки в контексте разговора висел бы текст, устаревший десять минут назад.

### Resource templates (2025-11-25 addition)

`resourceTemplates` позволяют выставить наружу параметризованный шаблон URI: `notes://{id}`, где `id` — цель автодополнения. Клиент может подсказывать id в выборе ресурсов.

> 🎒 **На пальцах.** Без шаблонов вам пришлось бы перечислять в `resources/list` все 5000 заметок по одной. С шаблоном вы отдаёте одну строку `notes://{id}` — и хост сам показывает поле автодополнения. Одна запись вместо пяти тысяч, и список не надо пересобирать при каждой новой заметке.

### Prompts

`prompts/list` возвращает `{prompts: [{name, description, arguments?}]}`. `prompts/get` принимает `{name, arguments}` и возвращает `{description, messages: [{role, content}]}`.

Промпт — это шаблон, который разворачивается в список сообщений, а их host скармливает своей модели. Например, промпт `code_review` принимает аргумент `file_path` и возвращает последовательность из трёх сообщений: системное сообщение, пользовательское сообщение с телом файла и заготовку ответа ассистента с шаблоном размышления.

> 🎒 **На пальцах.** Обратите внимание, что `prompts/get` возвращает не строку, а список сообщений с ролями. Это важно: сервер задаёт целую сцену разговора, включая первые слова ассистента. Одна команда `/code_review` разворачивается в три сообщения, которые пользователю пришлось бы набирать руками каждый раз.

### Hosts and prompts

Claude Desktop, VS Code и Cursor показывают промпты как слэш-команды в интерфейсе чата. Пользователь набирает `/code_review` и выбирает аргументы в форме. Промпт сервера — это контракт между «сокращением для пользователя» и «полным промптом, который уйдёт в модель».

Не каждый клиент пока поддерживает промпты — смотрите согласование возможностей. Сервер объявил возможность промптов, а клиент её не поддерживает — значит слэш-команд пользователь просто не увидит.

> 🎒 **На пальцах.** Ключевое слово здесь — «контракт». Пользователь видит короткое `/code_review` с двумя полями, а модель получает три выверенных сообщения. Промпт-инженерию вы делаете один раз на сервере, а не пересказываете её каждому коллеге в чате.

### The "list changed" notification

И ресурсы, и промпты присылают `notifications/list_changed`, когда набор изменился. Сервер заметок, который только что импортировал 20 новых заметок, отправляет `notifications/resources/list_changed`; клиент заново вызывает `resources/list` и подхватывает добавления.

> 🎒 **На пальцах.** Разница с прошлым разделом на одном слове. `updated` — «содержимое вот этого URI поменялось», перечитай один ресурс. `list_changed` — «набор URI поменялся», перечитай список. Импортировали 20 заметок — это второй случай: одно уведомление вместо двадцати.

### Content type conventions

Для текста: `mimeType: "text/plain"`, `text/markdown`, `application/json`.
Для бинарных данных: `image/png`, `application/pdf` плюс поле `blob`.
Для MCP Apps (урок 14): `text/html;profile=mcp-app` в URI со схемой `ui://`.

> 🎒 **На пальцах.** `mimeType` — это подпись на конверте: по ней хост решает, показать текст как markdown, картинку как картинку или отрисовать HTML-виджет. Поставите `text/plain` вместо `text/markdown` — пользователь увидит решётки и звёздочки вместо заголовков и жирного.

### Dynamic resources

URI ресурса вовсе не обязан соответствовать статическому файлу. `notes://recent` может отдавать пять последних заметок при каждом чтении. `db://query/users/active` может выполнять параметризованный запрос. Сервер имеет полное право вычислять содержимое на ходу.

Правило: если клиент может кэшировать по URI, то URI обязан быть стабильным. Если вычисление одноразовое, в URI надо положить метку времени или nonce, чтобы кэш клиента не отдавал устаревшее.

> 🎒 **На пальцах.** Сравните два URI. `notes://recent` стабилен, но содержимое меняется — клиент рискует показать вчерашние заметки из кэша. `notes://recent?t=2026-04-22T10:00` меняется вместе с содержимым, поэтому кэш промахивается честно. Правило простое: URI меняется тогда и только тогда, когда меняется ответ.

### Subscriptions vs polling

Клиенты с поддержкой подписок получают push от сервера через `notifications/resources/updated`. Клиенты без подписок и хосты, которые их не поддерживают, опрашивают сервер повторными чтениями. Оба варианта соответствуют спецификации. Объявление возможностей сервера сообщает клиенту, что именно он поддерживает.

Цена подписок: состояние на сервере для каждой сессии (кто на что подписан). Держите множество подписок ограниченным; отвалившимся клиентам ставьте таймаут.

> 🎒 **На пальцах.** Считаем цену: 100 клиентов, по 50 подписок каждый — это 5000 записей в памяти сервера, которые кто-то должен убирать. Отвалился клиент без таймаута — его 50 подписок висят навсегда. Push дешевле по трафику, но дороже по состоянию; опрос наоборот.

### Prompts vs system prompts

Промпты в MCP — это не системные промпты. Системный промпт хоста (его собственные рабочие инструкции) и MCP-промпты (шаблоны от сервера, вызываемые пользователем) живут рядом. Правильно устроенный клиент никогда не позволяет промпту сервера перебить свой собственный системный промпт; он накладывает их слоями.

> 🎒 **На пальцах.** Это та же граница доверия, что и с ресурсами. Сервер — гость: он может предложить текст, но не может переписать правила дома. Иначе любой подключённый MCP-сервер мог бы прислать промпт «игнорируй прежние инструкции» и снести все ограничения хоста одной командой.

```figure
t3-primitive-sort
```

## Use It

`code/main.py` расширяет сервер заметок из урока 07 следующим:

- Ресурсы на каждую заметку (`notes://note-1` и так далее) с поддержкой `resources/subscribe`.
- Промпт `review_note`, который разворачивается в шаблон из трёх сообщений.
- Имитация наблюдателя за файлами: она отправляет `notifications/resources/updated`, когда заметку изменили.
- Динамический ресурс `notes://recent`, который всегда отдаёт пять последних заметок.

Запустите демо, чтобы увидеть весь поток целиком.

> 🎒 **На пальцах.** Обратите внимание, что в этом сервере вообще нет инструмента чтения заметок — только ресурсы. Модель не тратит ход на «дай мне заметку», данные приходят как контекст. Инструменты в таком сервере остаются лишь для того, что действительно что-то меняет.

## Exercises

1. Запустите `code/main.py`. Посмотрите на начальный список ресурсов, затем инициируйте правку заметки и убедитесь, что событие `notifications/resources/updated` сработало.

2. Добавьте отправку `resources/list_changed`: когда создана новая заметка, пришлите уведомление, чтобы клиенты заново обнаружили список.

3. Спроектируйте три промпта для MCP-сервера GitHub: `summarize_pr`, `triage_issue`, `release_notes`. Каждый со схемой аргументов. Тело промпта должно работать без дальнейших правок.

4. Возьмите существующий инструмент из сервера урока 07 и решите, остаться ему инструментом или разделиться на пару «ресурс плюс инструмент». Обоснуйте одним предложением.

5. Прочитайте разделы спецификации `server/resources` и `server/prompts`. Найдите то единственное поле в `resources/read`, которое почти никто не заполняет, хотя спецификация его поддерживает. Подсказка: смотрите на `_meta` у содержимого ресурса.

> 🎒 **На пальцах.** Задание 4 решается одним вопросом: сколько ответственностей у инструмента. Если `notes_search` возвращает и список найденного, и полный текст каждой заметки — это две вещи в одной. Разделите: инструмент отдаёт список URI, ресурсы отдают тела. Тогда модель ищет, а пользователь сам решает, что прикрепить.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Resource | «Выставленные данные» | Контент с адресацией по URI, который host может прочитать |
| Resource URI | «Указатель на данные» | Идентификатор с префиксом схемы (`file://`, `notes://` и так далее) |
| `resources/subscribe` | «Следить за изменениями» | Push-обновления от сервера по конкретному URI, включаемые самим клиентом |
| `notifications/resources/updated` | «Ресурс изменился» | Сигнал клиенту, что у ресурса с подпиской появилось новое содержимое |
| Resource template | «Параметризованный URI» | Шаблон URI с подсказками автодополнения для выбора ресурсов в хосте |
| Prompt | «Шаблон слэш-команды» | Именованный шаблон из нескольких сообщений с местами под аргументы |
| Prompt arguments | «Входы шаблона» | Типизированные параметры, которые host собирает перед разворачиванием |
| `prompts/get` | «Развернуть шаблон» | Сервер возвращает готовый список сообщений с подставленными значениями |
| Content block | «Типизированный кусок» | `{type: text \| image \| resource \| ui_resource}` |
| Slash-command UX | «Сокращение для пользователя» | Host показывает промпты как команды, начинающиеся с `/` |
