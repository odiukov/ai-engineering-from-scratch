# Безопасность MCP II — OAuth 2.1, resource indicators, инкрементальные scopes

> Удалённым MCP-серверам нужна авторизация, а не просто аутентификация. Спецификация от 2025-11-25 выравнивается по OAuth 2.1 плюс PKCE плюс resource indicators (RFC 8707) плюс метаданные защищённого ресурса (RFC 9728). SEP-835 добавляет инкрементальное согласие на scopes со step-up-авторизацией по ответу 403 с заголовком WWW-Authenticate. В этом уроке мы реализуем step-up-поток как конечный автомат, чтобы увидеть каждый шаг.

**Type:** Build
**Languages:** Python (stdlib, OAuth state machine simulator)
**Prerequisites:** Phase 13 · 09 (transports), Phase 13 · 15 (security I)
**Time:** ~75 minutes

## Learning Objectives

- Различать обязанности resource server и authorization server.
- Пройти по шагам поток authorization code в OAuth 2.1 под защитой PKCE.
- Использовать `resource` (RFC 8707) и метаданные защищённого ресурса (RFC 9728), чтобы не допустить атаку confused deputy.
- Реализовать step-up-авторизацию: сервер отвечает 403 и через WWW-Authenticate просит scope побольше; клиент заново спрашивает согласие пользователя и повторяет запрос.

## The Problem

Ранний MCP (до 2025 года) выпускал удалённые серверы с самодельными API-ключами, а иногда и вовсе без авторизации. Спецификация от 2025-11-25 закрывает эту дыру полноценным профилем OAuth 2.1.

Три реальные потребности:

- **Ordinary remote servers.** Пользователь ставит удалённый MCP-сервер, который лезет в его Notion, GitHub или Gmail. OAuth 2.1 с PKCE — правильная форма для этого.
- **Scope escalation.** Серверу заметок выдали `notes:read`, а потом для конкретного действия ему понадобился `notes:write`. Вместо повторения всего потока с нуля step-up (SEP-835) просит только дополнительный scope.
- **Confused deputy prevention.** У клиента есть токен, у которого audience прибит к серверу A. Сервер A вредоносный и пытается предъявить этот токен серверу B. Resource indicators (RFC 8707) привязывают токен к той аудитории, для которой он выдан.

> 🎒 **На пальцах.** Разница между аутентификацией и авторизацией в одну строку: первая отвечает «кто ты», вторая — «что тебе можно». API-ключ отвечает только на первый вопрос, поэтому кто угодно с этим ключом может всё. Токен доступа с scopes отвечает на второй: «это Оля, и ей можно только читать заметки».

OAuth 2.1 — не новость. Новость — именно профиль MCP: строго определённый набор разрешённых потоков (только authorization code плюс PKCE; никакого implicit, по умолчанию никакого client credentials), обязательные resource indicators в каждом запросе токена и опубликованные метаданные защищённого ресурса, чтобы клиент знал, куда идти.

> 🎒 **На пальцах.** «Профиль» здесь значит «подмножество с запретами». OAuth 2.1 разрешает несколько потоков, а MCP из них оставляет один и запрещает остальные. Меньше вариантов — меньше способов ошибиться: реализуете один поток правильно и вы закрыли всю спецификацию.

## The Concept

### Roles

- **Client.** MCP-клиент (Claude Desktop, Cursor и так далее).
- **Resource server.** MCP-сервер (заметки, GitHub, Postgres, что угодно).
- **Authorization server.** Выдаёт токены. Может быть той же службой, что и resource server, а может быть отдельным IdP (Auth0, Keycloak, Cognito).

В профиле MCP resource server и authorization server МОГУТ быть одним и тем же хостом, но их СЛЕДУЕТ различать по URL.

> 🎒 **На пальцах.** Аналогия из жизни: authorization server — это касса, которая продаёт билет, resource server — контролёр на входе в зал. Иногда это один и тот же человек, но роли всё равно две: один выдаёт право, другой его проверяет. Разные URL нужны как раз для того, чтобы токен знал, к какому залу он относится.

### Authorization code + PKCE

Поток:

1. Клиент генерирует `code_verifier` (случайный) и `code_challenge` (SHA256).
2. Клиент перенаправляет пользователя на `/authorize?response_type=code&client_id=...&redirect_uri=...&scope=notes:read&code_challenge=...&resource=https://notes.example.com`.
3. Пользователь даёт согласие. Authorization server перенаправляет на `redirect_uri?code=...`.
4. Клиент делает POST на `/token?grant_type=authorization_code&code=...&code_verifier=...&resource=...`.
5. Authorization server сверяет хеш verifier'а с сохранённым challenge и выдаёт токен доступа.
6. Клиент использует токен: `Authorization: Bearer ...` в каждом запросе к resource server.

PKCE защищает от перехвата кода авторизации. Resource indicators не дают токену быть валидным где-то ещё.

> 🎒 **На пальцах.** PKCE работает как чек в камере хранения. На шаге 1 клиент придумывает секрет и отдаёт только его отпечаток SHA256; на шаге 4 предъявляет сам секрет. Кто перехватил `code` на шаге 3, обменять его не сможет — секрета у вора нет, а из хеша его не достать.

### Protected-resource metadata (RFC 9728)

Resource server публикует документ `.well-known/oauth-protected-resource`:

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:read", "notes:write", "notes:delete"]
}
```

Клиент узнаёт authorization server от самого resource server. Это уменьшает объём конфигурации — клиенту достаточно знать URL ресурса.

> 🎒 **На пальцах.** Посчитайте, что пользователь вводит руками: без этого документа — URL сервера, URL авторизации и список scopes, то есть три поля; с документом — одно поле, URL сервера. Остальное клиент вычитывает сам, как браузер вычитывает favicon по фиксированному пути.

### Resource indicators (RFC 8707)

Параметр `resource` в запросе токена прибивает токен к той аудитории, для которой он предназначен. В выданном токене лежит `aud: "https://notes.example.com"`. Другой MCP-сервер, получив такой токен, проверит `aud` и отвергнет его.

> 🎒 **На пальцах.** Это как надпись «действителен только в зале №3» на билете. Даже если билет украли, в зал №5 по нему не пустят. Без `aud` токен — это универсальный пропуск, и любой сервер, которому его показали, может ходить с ним куда угодно.

### Scope model

Scopes — это строки, разделённые пробелами. Обычные соглашения в MCP:

- `notes:read`, `notes:write`, `notes:delete`
- `admin:*` для админских возможностей (использовать скупо)
- `profile:read` для идентификации

Выбирать scopes надо по принципу минимальных прав: просите то, что нужно сейчас, а за остальным приходите через step-up.

> 🎒 **На пальцах.** Разница между `notes:read` и `admin:*` — это разница между ключом от своей комнаты и связкой ключей от всего здания. Утечка первого стоит вам одной комнаты, утечка второй — всего. Поэтому в списке рядом с `admin:*` и стоит приписка «скупо».

### Step-up authorization (SEP-835)

Пользователь выдал `notes:read`. Потом он просит агента удалить заметку. Сервер отвечает:

```
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
    scope="notes:delete", resource="https://notes.example.com"
```

Клиент видит ошибку insufficient_scope, показывает пользователю диалог согласия на дополнительный scope, проходит мини-поток OAuth ради него и повторяет запрос уже с новым токеном.

> 🎒 **На пальцах.** Так работают разрешения в телефоне: приложение не просит доступ к камере при установке, а спрашивает в момент, когда вы нажали «сфотографировать». Обратите внимание, что сервер в ответе 403 прямо называет нужный scope — `notes:delete`, — поэтому клиенту не надо угадывать, чего именно ему не хватает.

### Token audience validation

Каждый запрос: сервер проверяет `token.aud == self.resource_url`. Не совпало — 401. Это ставит крест на переиспользовании токена между серверами.

> 🎒 **На пальцах.** Одна строка сравнения строк — и целый класс атак закрыт. Дешевле защиты не бывает, но её постоянно забывают: сервер проверяет подпись токена, радуется, что она валидна, и не смотрит, для кого этот токен вообще выписан.

### Short-lived tokens and rotation

Токены доступа СЛЕДУЕТ делать короткоживущими (по умолчанию один час). Refresh-токены ротируются при каждом обновлении. Клиент делает тихое обновление в фоне.

> 🎒 **На пальцах.** Час жизни — это окно, в котором украденный токен работает. Утёк токен в 10:00 — в 11:00 он уже мусор. Ротация refresh-токена добавляет вторую сеть: если старый refresh кто-то попробует использовать после обновления, сервер видит, что им уже пользовались, и рвёт всю цепочку.

### No token passthrough

Серверы sampling (Phase 13 · 11) НЕ ДОЛЖНЫ пробрасывать токен клиента дальше в другие сервисы. Граница проходит по sampling-запросу.

> 🎒 **На пальцах.** Правило простое: токен, который вам дали, дальше не передаётся никому. Это как банковская карта — ей платите вы, а не отдаёте её курьеру «просто чтобы он тоже смог». Как только токен уехал в третий сервис, вы больше не знаете, кто им пользуется и от чьего имени.

### Confused deputy prevention

Токен привязан к `aud`. Клиент привязан к `client_id`. Каждый запрос проверяется по обоим. Спецификация прямо запрещает старый паттерн «прокинь токен дальше», который был обычным делом в удалённых экосистемах инструментов до MCP.

### Client ID discovery

Каждый MCP-клиент публикует свои метаданные по фиксированному URL. Authorization server может забрать документ с метаданными клиента и узнать оттуда redirect URI и контактные данные. Это убирает ручную регистрацию клиента.

### Gateways and OAuth

Phase 13 · 17 показывает, как с OAuth работает корпоративный gateway: gateway держит креденшелы для вышестоящих серверов, токены клиенту выписывает сам gateway, а токены вышестоящих серверов из gateway не выходят. Это переворачивает модель доверия — пользователь аутентифицируется у gateway один раз, а gateway разбирается с авторизацией у N серверов.

```figure
t3-scope-stepup
```

> 🎒 **На пальцах.** Посчитайте на числах: подключили 10 удалённых серверов — без gateway это 10 походов по OAuth и 10 токенов у клиента; с gateway это один вход и один токен. Минус в том, что gateway становится самым лакомым местом в системе: там лежат все креденшелы сразу.

## Use It

`code/main.py` имитирует полный step-up-поток OAuth 2.1 как конечный автомат. В нём реализованы:

- Генерация code-verifier и challenge для PKCE.
- Поток authorization code с resource indicator.
- Эндпоинт метаданных защищённого ресурса.
- Валидация токена с проверкой audience.
- Step-up по ошибке `insufficient_scope`.

HTTP-сервера в этом уроке нет; автомат работает в памяти, чтобы можно было проследить каждый шаг. Урок про gateway в Phase 13 · 17 прикручивает всё это к настоящему транспорту.

> 🎒 **На пальцах.** Автомат в памяти — это лучший способ разобраться в OAuth: нет сети, нет браузера, нет редиректов, есть только переходы между состояниями, которые видно в выводе. Один запуск печатает шесть шагов из раздела про PKCE, а на step-up вы увидите, что повторяются только шаги 2-5, а не весь поток.

## Ship It

Этот урок даёт на выходе `outputs/skill-oauth-scope-planner.md`. Для удалённого MCP-сервера с набором инструментов навык проектирует набор scopes, правила привязки токена и политику step-up.

> 🎒 **На пальцах.** Полезный порядок работы: сначала выпишите инструменты, потом сгруппируйте их по действию (read / write / delete), и группы сами превратятся в scopes. Если один scope нужен всем инструментам подряд — вы нарезали слишком грубо, а если scopes больше, чем инструментов, — слишком мелко.

## Exercises

1. Запустите `code/main.py`. Проследите step-up-поток на двух scopes. Отметьте, какие шаги повторяются при step-up.

2. Добавьте ротацию refresh-токенов: каждое обновление выдаёт новый refresh-токен и гасит старый. Сымитируйте использование украденного refresh-токена после ротации и убедитесь, что он не работает.

3. Реализуйте эндпоинт метаданных защищённого ресурса как настоящий HTTP-ответ на stdlib http.server. Повторите форму эндпоинта /mcp из урока 09.

4. Спроектируйте иерархию scopes для MCP-сервера GitHub: читать репозиторий, писать PR, одобрять PR, мержить PR, админить. Между каждыми уровнями используйте step-up.

5. Прочитайте RFC 8707 и RFC 9728. Найдите то единственное поле в 9728, которое MCP использует иначе, чем в примере из RFC. (Подсказка: речь про `scopes_supported`.)

> 🎒 **На пальцах.** Во втором задании главное — понять, зачем вообще ротация. Без неё украденный refresh-токен живёт вечно и печёт новые токены доступа хоть год. С ротацией первое же обновление настоящим клиентом делает копию вора недействительной, а попытка ею воспользоваться — это сигнал, что утечка была.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| OAuth 2.1 | «Современный OAuth» | Сводный RFC, который делает PKCE обязательным и запрещает implicit-поток |
| PKCE | «Доказательство владения» | Пара verifier и challenge, побеждающая перехват кода авторизации |
| Resource indicator | «Audience токена» | Параметр `resource` из RFC 8707, прибивающий токен к одному серверу |
| Protected-resource metadata | «Документ обнаружения» | `.well-known/oauth-protected-resource` из RFC 9728 |
| Step-up authorization | «Инкрементальное согласие» | Поток SEP-835 для добавления scopes по требованию |
| `insufficient_scope` | «403 с WWW-Authenticate» | Сигнал сервера, что нужно заново согласовать более широкий scope |
| Confused deputy | «Переиспользование токена между сервисами» | Атака, в которой доверенный держатель пробрасывает токен не туда |
| Short-lived token | «TTL токена доступа» | Bearer, который быстро истекает; продлевается refresh-токеном |
| Scope hierarchy | «Стопка минимальных прав» | Набор scopes по возрастанию, со step-up между уровнями |
| Client ID metadata | «Документ обнаружения клиента» | URL, по которому клиент публикует собственные метаданные OAuth |
