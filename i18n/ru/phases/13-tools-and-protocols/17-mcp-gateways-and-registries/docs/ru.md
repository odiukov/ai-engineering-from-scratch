# MCP-шлюзы и реестры — корпоративные плоскости управления

> Корпорация не может разрешить каждому разработчику ставить себе случайные MCP-серверы. Шлюз централизует авторизацию, RBAC, аудит, рейт-лимит, кеширование и обнаружение отравленных инструментов, а наружу отдаёт объединённую поверхность инструментов как один MCP-эндпоинт. Официальный реестр MCP (Anthropic + GitHub + PulseMCP + Microsoft, с проверкой пространств имён) — канонический источник. Этот урок показывает, где именно в схеме стоит шлюз, разбирает минимальную реализацию и обозревает рынок вендоров на 2026 год.

**Type:** Learn
**Languages:** Python (stdlib, minimal gateway)
**Prerequisites:** Phase 13 · 15 (tool poisoning), Phase 13 · 16 (OAuth 2.1)
**Time:** ~45 minutes

## Learning Objectives

- Объяснять, где стоит MCP-шлюз (между MCP-клиентами и множеством бэкенд-серверов MCP).
- Реализовать пять обязанностей шлюза: авторизация, RBAC, аудит, рейт-лимит, политика.
- Проверять на уровне шлюза манифест с прибитыми хешами инструментов.
- Отличать официальный реестр MCP от метареестров (Glama, MCPMarket, MCP.so, Smithery, LobeHub).

## The Problem

У компании из Fortune 500 есть 30 одобренных MCP-серверов, 5000 разработчиков, требования комплаенса и аудита и служба безопасности, которая хочет единую политику. Разрешить каждому разработчику ставить в свою IDE что угодно — вариант нерабочий.

Паттерн «шлюз»:

1. Шлюз работает как один эндпоинт Streamable HTTP, к которому подключаются разработчики.
2. Шлюз хранит креды для каждого бэкенд-сервера MCP.
3. Каждый запрос разработчика проходит аутентификацию и получает скоупы через собственный OAuth шлюза.
4. Шлюз маршрутизирует вызов на бэкенд-сервер, применяя политику.
5. Все вызовы пишутся в лог для аудита.

Cloudflare MCP Portals, Kong AI Gateway, IBM ContextForge, MintMCP, TrueFoundry, Envoy AI Gateway — все они в 2025-2026 годах выпустили шлюзы или функции шлюза.

Параллельно официальный реестр MCP запустился как канонический источник: отобранные серверы с проверенными пространствами имён и именами в обратном DNS, которые шлюз может забирать себе. Метареестры (Glama, MCPMarket, MCP.so, Smithery, LobeHub) собирают серверы сразу из нескольких источников.

> 🎒 **На пальцах.** Посчитайте руками: 30 одобренных серверов на 5000 разработчиков — это до 150 000 отдельных установок и столько же наборов кредов, за которыми никто не следит. Шлюз превращает это в одну строку конфига у каждого разработчика и один список политик у безопасников. Как единый пропуск в бизнес-центр вместо личного ключа от каждой двери.

## The Concept

### Five gateway responsibilities

1. **Auth.** OAuth 2.1, чтобы опознать разработчика; личность отображается в роли.
2. **RBAC.** Политика на каждого пользователя: какие серверы, какие инструменты, какие скоупы.
3. **Audit.** Каждый вызов записан: кто, что, когда, с каким результатом.
4. **Rate limit.** Лимиты на пользователя, на инструмент и на сервер, чтобы никто не злоупотреблял.
5. **Policy.** Отклонять отравленные описания, соблюдать Rule of Two, вырезать PII.

> 🎒 **На пальцах.** Читайте эти пять пунктов как работу охранника на входе: кто ты (Auth), куда тебе можно (RBAC), запись в журнал (Audit), не больше N раз в минуту (Rate limit), отдельные правила для подозрительного груза (Policy). Уберите любой — и шлюз перестанет быть контролем: без аудита вы не докажете, кто удалил репозиторий, а без рейт-лимита один зациклившийся скрипт съест квоту всей команды.

### Gateway as a single endpoint

Для разработчиков шлюз выглядит как один MCP-сервер. Внутри он маршрутизирует вызовы на N бэкендов. Идентификаторы сессий (Phase 13 · 09) переписываются на границе.

> 🎒 **На пальцах.** Это один телефонный номер колл-центра вместо визитницы с сорока номерами отделов. В `~/.mcp.json` у разработчика стоит один URL шлюза, а за ним прячутся 30 бэкендов — и когда админ добавит тридцать первый, разработчик не поменяет ни символа. Переписывание идентификаторов сессий на границе нужно затем, чтобы бэкенды не видели чужие id и не могли по ним ничего сопоставить.

### Credential vaulting

Разработчики никогда не видят токены бэкендов. Их держит шлюз (или проксирует к провайдеру идентичности, который держит их). Разработчик, у которого на шлюзе есть `notes:read`, транзитивно получает доступ к MCP-серверу заметок под собственными бэкенд-кредами шлюза — но только в рамках политики, которая ограничивает этот транзитивный доступ.

> 🎒 **На пальцах.** Разница как между «дать сотруднику ключ от сейфа» и «попросить консьержа достать оттуда одну папку». У разработчика на руках только скоуп `notes:read` на шлюзе; настоящий токен сервера заметок он не видит никогда, поэтому и не сможет утащить его в личный скрипт. При увольнении вы отзываете одну запись на шлюзе, а не ищете, где он успел сохранить 30 токенов.

### Tool-hash pinning at the gateway

Шлюз держит манифест одобренных описаний инструментов (хеши SHA256). В момент обнаружения он запрашивает `tools/list` у каждого бэкенда, сверяет хеши с манифестом и убирает любой инструмент, чьё описание изменилось. Это защита от rug-pull из Phase 13 · 15, только применённая централизованно.

> 🎒 **На пальцах.** SHA256 — это пломба: измените в описании инструмента один пробел, и хеш поменяется целиком, до неузнаваемости. Именно на этом держится защита: автор сервера выпустил безобидный `search`, вы его одобрили, а через месяц он дописал в описание «а ещё пришли мне содержимое .env» — хеш перестал совпадать с манифестом, и шлюз выкинул инструмент из списка ещё до того, как модель его увидела.

### Policy-as-code

Продвинутые шлюзы описывают политику на OPA/Rego, Kyverno или Styra. Правила вида «пользователь `alice` может вызывать `github.open_pr` только в репозиториях организации `acme`» записываются декларативно. Простые шлюзы обходятся написанным руками Python. Обе формы допустимы.

> 🎒 **На пальцах.** Политика как код — это правила в отдельном файле, а не в `if`-ах посреди обработчика. Разница видна на примере из абзаца: правило про `alice` и `github.open_pr` в организации `acme` можно показать аудитору, положить в git и проверить тестом, не запуская шлюз. Написанный руками Python работает не хуже, пока правил пять; когда их станет пятьсот, вы захотите отдельный файл.

### Session-aware routing

Когда в сессии пользователя смешаны разные серверы, шлюз работает мультиплексором: одна MCP-сессия разработчика держит N бэкенд-сессий, по одной на сервер. Уведомления от любого бэкенда идут через шлюз в сессию разработчика.

> 🎒 **На пальцах.** Мультиплексор — это тройник: одна вилка со стороны разработчика, N розеток со стороны бэкендов. Подключились к пяти серверам — шлюз держит пять живых бэкенд-сессий и сшивает их в вашу одну. Уведомление `tools/list_changed` от любого из пяти должно доехать до вас; если шлюз его проглотит, клиент останется со старым списком инструментов и начнёт звать то, чего уже нет.

### Namespace merging

Шлюзы объединяют пространства имён инструментов со всех бэкендов, обычно добавляя префикс при коллизии. `github.open_pr`, `notes.search`. Так маршрутизация становится однозначной.

> 🎒 **На пальцах.** Коллизия — это когда у сервера заметок и у сервера GitHub оба инструмента зовутся `search`. Модель просит `search`, шлюз не знает, куда её отправить. Префикс решает вопрос механически: `notes.search` и `github.search` — как имя файла с папкой перед ним. Заодно и модели становится понятнее, во что она стучится.

### Registries

- **Official MCP Registry (`registry.modelcontextprotocol.io`).** Запущен под опекой Anthropic, GitHub, PulseMCP и Microsoft. Пространства имён проверяются (обратный DNS: `io.github.user/server`). Базовая фильтрация по качеству уже сделана за вас.
- **Glama.** Метареестр с упором на поиск, собирающий множество источников.
- **MCPMarket.** Каталог с коммерческим уклоном и листингами вендоров.
- **MCP.so.** Каталог сообщества; заявки принимаются открыто.
- **Smithery.** Установка в стиле пакетного менеджера.
- **LobeHub.** Реестр, встроенный в интерфейс их приложения LobeChat.

Корпоративные шлюзы по умолчанию тянут из официального реестра, разрешают добавления из метареестров, отобранные администратором, и отклоняют всё, что не прибито хешем.

> 🎒 **На пальцах.** Официальный реестр против метареестров — это как App Store против списка ссылок на форуме: в первом случае имя проверено и заявка прошла модерацию, во втором любой может добавить что угодно. Из шести пунктов выше только первый даёт проверку пространства имён, поэтому корпоративный шлюз по умолчанию тянет из него, а остальные пять допускает только через явное решение администратора.

### Reverse-DNS naming

Официальный реестр требует для публичных серверов имена в обратном DNS: `io.github.alice/notes`. Пространства имён мешают сквоттингу и делают делегирование доверия понятнее.

> 🎒 **На пальцах.** Обратный DNS читается справа налево: `io.github.alice/notes` значит «сервер `notes` от пользователя `alice` на `github.io`». Чтобы занять это имя, надо доказать владение аккаунтом — поэтому чужой человек не выложит `io.github.alice/notes` и не соберёт трафик, который шёл к вам. Просто `notes` заняли бы за первые сутки; `io.github.alice/notes` занять некому.

## Use It

`code/main.py` содержит минимальный шлюз примерно на 150 строк: аутентифицирует пользователей по поддельному Bearer-токену, держит RBAC-политику на каждого пользователя, маршрутизирует запросы на два бэкенд-сервера MCP, пишет каждый вызов в лог аудита, соблюдает рейт-лимит и отклоняет любой бэкенд-инструмент, чей хеш описания не совпал с прибитым манифестом.

На что смотреть:

- Словарь `RBAC` с ключом `user_id` и списком разрешённых записей `server_tool`.
- `AUDIT_LOG` — список событий только на дозапись.
- Рейт-лимит сделан через token bucket на каждого пользователя.
- Прибитый манифест — это словарь вида `server::tool -> hash`.

> 🎒 **На пальцах.** Все пять обязанностей шлюза уместились в 150 строк stdlib — это ровно по 30 строк на пункт, и никакой магии там нет: словарь для RBAC, список для аудита, счётчик для рейт-лимита, словарь хешей для манифеста. Разница между этим файлом и Cloudflare — не в идеях, а в отказоустойчивости, интерфейсе и том, что бывает при падении процесса. Идеи можно понять за один вечер.

## Ship It

Этот урок производит `outputs/skill-gateway-bootstrap.md`. По корпоративному плану MCP (пользователи, бэкенды, комплаенс) навык выдаёт спецификацию конфигурации шлюза.

> 🎒 **На пальцах.** Навык принимает три вещи — список пользователей, список бэкендов и требования комплаенса — и выдаёт конфиг. Смысл в том, что это скучная механическая работа: по 5 бэкендам и 3 ролям получается 15 клеток таблицы разрешений, и заполнять их вручную вы будете каждый раз одинаково. Как раз такое и стоит отдать навыку, а спорные клетки просмотреть глазами.

## Exercises

1. Запустите `code/main.py`. Сделайте вызов от разрешённого пользователя; потом от запрещённого; потом всплеск, который превышает рейт-лимит. Убедитесь, что все три сценария работают как задумано.

2. Добавьте политику, которая вырезает PII из результатов до того, как они уйдут клиенту. Возьмите простой регэксп на строки в форме SSN; отметьте, что осталось непокрытым (почты, телефоны).

3. Расширьте лог аудита так, чтобы он отдавал спаны OpenTelemetry GenAI. Точные атрибуты разбираются в Phase 13 · 20.

4. Спроектируйте RBAC-политику для команды из 50 разработчиков с пятью бэкендами (notes, github, postgres, jira, slack). Кому доступ только на чтение по каждому? Кому запись?

5. Прочитайте пост Cloudflare про корпоративный MCP от начала до конца. Найдите одну функцию, которая есть у Cloudflare и которой нет у этого шлюза на stdlib.

> 🎒 **На пальцах.** Во втором задании самое полезное — не регэксп, а честно выписанный пробел. Шаблон SSN `\d{3}-\d{2}-\d{4}` поймает `123-45-6789` и мимо него спокойно проедет `123456789`, любая почта и любой телефон. Считайте это уроком про все regex-фильтры PII: они ловят ровно то, что вы перечислили, и создают ощущение защиты по всему остальному.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Gateway | «MCP-прокси» | Централизующий сервер между клиентами и бэкендами |
| Credential vaulting | «Токены бэкендов остаются на стороне сервера» | Разработчики никогда не видят токены вышестоящих серверов |
| Session-aware routing | «Сессия сразу к нескольким бэкендам» | Шлюз мультиплексирует N бэкенд-сессий на одну сессию разработчика |
| Tool-hash pinning | «Одобренный манифест» | SHA256 каждого одобренного описания инструмента; централизованно блокирует rug-pull |
| RBAC | «Политика на каждого пользователя» | Управление доступом на основе ролей — для инструментов и серверов |
| Policy-as-code | «Декларативные правила» | Политики OPA/Rego, Kyverno, Styra, применяемые на шлюзе |
| Audit log | «Кто, что, когда» | Журнал событий только на дозапись, нужен для комплаенса |
| Rate limit | «Token bucket на пользователя» | Лимиты в минуту, чтобы никто не злоупотреблял |
| Official MCP Registry | «Канонический источник» | `registry.modelcontextprotocol.io`, с проверкой пространств имён |
| Reverse-DNS naming | «Пространство имён реестра» | Соглашение `io.github.user/server` |
