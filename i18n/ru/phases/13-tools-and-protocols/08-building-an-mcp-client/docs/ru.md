# Собираем MCP-клиент — обнаружение, вызов, управление сессией

> Большинство материалов про MCP выпускают туториалы по серверам и машут рукой в сторону клиента. А ведь именно в клиентском коде живёт вся сложная оркестрация: запуск процессов, согласование возможностей, слияние списков инструментов от нескольких серверов, коллбэки для сэмплинга, переподключение и разбор коллизий имён. В этом уроке мы собираем клиент для нескольких серверов, который поднимает три разных MCP-сервера и подаёт модели их инструменты одним плоским списком.

**Type:** Build
**Languages:** Python (stdlib, multi-server MCP client)
**Prerequisites:** Phase 13 · 07 (building an MCP server)
**Time:** ~75 minutes

## Learning Objectives

- Запустить MCP-сервер дочерним процессом, завершить `initialize` и отправить `notifications/initialized`.
- Держать состояние сессии по каждому серверу (возможности, список инструментов, последние увиденные id уведомлений).
- Слить списки инструментов от нескольких серверов в одно пространство имён с разбором коллизий.
- Отправить вызов инструмента тому серверу, которому он принадлежит, и собрать ответ обратно.

## The Problem

Настоящий агентный хост (Claude Desktop, Cursor, Goose, Gemini CLI) грузит несколько MCP-серверов сразу. У пользователя одновременно могут работать сервер файловой системы, сервер Postgres и сервер GitHub. Работа клиента:

1. Запустить каждый сервер.
2. Провести хендшейк с каждым независимо.
3. Вызвать `tools/list` у каждого и сплющить результат.
4. Когда модель выдала `notes_search`, найти его в общем пространстве имён и отправить на нужный сервер.
5. Обрабатывать уведомления от любого сервера (`tools/list_changed`), никого при этом не блокируя.
6. Переподключаться при сбое транспорта.

> 🎒 **На пальцах.** Клиент здесь — телефонистка на коммутаторе: три линии подняты, у каждой свой абонент, и нельзя перепутать, кому переключить звонок. Три сервера дают три хендшейка и три списка инструментов; если у одного 3 инструмента, у второго 2 и у третьего 2 — модель увидит один список из 7 имён и о трёх линиях даже не узнает.

Написать всё это руками — как раз то, что отличает «игрушку» от «рабочего инструмента». Официальные SDK всё это оборачивают, но модель в голове должна быть ваша.

> 🎒 **На пальцах.** Игрушку от рабочего клиента отличает один вопрос: что будет, если сервер B пришлёт уведомление, пока вы ждёте ответа от сервера A? Игрушка зависнет, рабочий клиент положит сообщение в очередь. Все шесть пунктов выше про это же: ничто не должно блокировать ничто.

## The Concept

### Child-process spawning

`subprocess.Popen` с `stdin=PIPE, stdout=PIPE, stderr=PIPE`. Ставьте `bufsize=1` и текстовый режим, чтобы читать построчно. Каждый сервер — один процесс; клиент держит по одному хендлу `Popen` на сервер.

> 🎒 **На пальцах.** `bufsize=1` — это построчная буферизация: Python отдаёт данные, как только увидел перевод строки, а не когда наберёт 8 КБ. Без этого вы отправите запрос и будете ждать ответ, который уже готов и просто лежит в трубе. Три сервера — три хендла `Popen`, три пары труб, три отдельных PID в `ps`.

### Per-server session state

Объект `Session` на каждый сервер хранит:

- `process` — хендл `Popen`.
- `capabilities` — то, что сервер заявил на `initialize`.
- `tools` — последний результат `tools/list`.
- `pending` — карта «id запроса → promise/future, ждущий ответа».

Запросы по своей природе асинхронны: `tools/call`, отправленный серверу A, не должен блокироваться, пока сервер B в середине своего вызова. Либо потоки с очередями, либо asyncio.

> 🎒 **На пальцах.** `pending` — это гардеробные номерки. Отправили запрос с `id: 7` — положили в `pending[7]` пустое обещание; пришёл ответ с `id: 7` — достали и заполнили. Без такой карты вы не сможете отправить второй запрос, не дождавшись первого, и весь клиент поедет со скоростью самого медленного сервера.

### Merged namespace

Когда клиент собирает сводный список инструментов, имена могут столкнуться. Два сервера вполне могут отдавать `search`. У клиента три варианта:

1. **Prefix by server name.** `notes/search`, `files/search`. Понятно, но некрасиво.
2. **Silent first-come.** `search` от более позднего сервера перекрывает более ранний. Рискованно; коллизия прячется.
3. **Collision rejection.** Отказаться загружать второй сервер и сообщить пользователю. Самое безопасное для хостов, чувствительных к безопасности.

Claude Desktop использует префиксы по имени сервера. Cursor — отказ по коллизии с внятной ошибкой. VS Code MCP тоже взял префиксы по серверу.

> 🎒 **На пальцах.** Представьте двух коллег по имени Саша: можно звать их «Саша из продаж» и «Саша из бэкенда» (префикс), можно всегда откликаться одному и тому же (first-come, вот тут и начинаются беды), а можно потребовать переименоваться (отказ). Ставки настоящие: `search` у файлового сервера читает диск, `search` у GitHub-сервера уходит в сеть.

> 🎒 **На пальцах.** Заметьте расклад: два крупных хоста из трёх выбрали префиксы, а Cursor — отказ. Правило простое: если хост показывает пользователю, что именно делает инструмент, префикс безопасен; если вызовы уходят молча, лучше отказать на старте, чем однажды удалить файл вместо issue.

### Routing

После слияния таблица маршрутизации связывает `tool_name -> session`. Модель выдаёт вызов по имени; клиент находит сессию, пишет сообщение `tools/call` в stdin именно этого сервера и ждёт ответа.

> 🎒 **На пальцах.** Маршрутизация — это адресная книга в один словарь: `{"notes_search": session_notes, "files_read": session_files}`. Модель называет только имя, координат она не знает и знать не должна. Если имени в словаре нет, отвечайте ошибкой инструмента, а не падайте: модель промахнулась именем, это её работа — исправиться.

### Sampling callback

Если сервер на `initialize` заявил возможность `sampling`, он может присылать `sampling/createMessage` — просьбу к клиенту прогнать свою LLM. Клиент обязан:

1. Заблокировать дальнейшие запросы к этому серверу, пока сэмпл не готов, — или конвейеризовать их, если его реализация умеет параллельность.
2. Вызвать своего LLM-провайдера.
3. Отправить ответ назад серверу.

Урок 11 разбирает сэмплинг целиком. Здесь мы делаем заглушку для полноты картины.

> 🎒 **На пальцах.** Сэмплинг переворачивает роли: обычно клиент просит сервер («вызови инструмент»), а тут сервер просит клиента («прогони свою модель на этом тексте»). Как повар, который отправляет официанта к гостю уточнить прожарку. За токены платит клиент, поэтому такие запросы стоит и ограничивать по количеству, и показывать пользователю.

### Notification handling

`notifications/tools/list_changed` означает «перезапроси `tools/list`». `notifications/resources/updated` означает «перечитай ресурс, если он используется». На уведомления нельзя отвечать — не пытайтесь их подтверждать.

Типичный баг клиента: заблокировать цикл чтения на `tools/call`, пока в потоке ждёт уведомление. Заведите фоновый поток-читатель, который сбрасывает каждое сообщение в очередь; главный поток разбирает очередь и раздаёт по обработчикам.

> 🎒 **На пальцах.** Ловушка называется «читаю только то, чего жду». Вы ждёте ответ на `tools/call` с `id: 7`, а из трубы первым выходит уведомление `tools/list_changed` вообще без `id`. Клиент, умеющий читать только ответы, либо выбросит его, либо подавится. Поэтому один поток читает всё подряд в очередь, а разбор идёт отдельно.

### Reconnection

Транспорт может отвалиться: сервер упал, ОС прибила процесс, stdio-труба порвалась. Клиент видит EOF на stdout и считает сессию мёртвой. Варианты:

- Молча перезапустить сервер и заново провести хендшейк. Нормально для серверов, которые только читают.
- Показать сбой пользователю. Нормально для серверов с состоянием и видимыми пользователю сессиями.

Phase 13 · 09 разбирает семантику переподключения для Streamable HTTP; со stdio всё проще.

> 🎒 **На пальцах.** EOF на stdout — это не «пока ничего не пришло», это «больше никогда ничего не придёт». Разница как между молчанием в трубке и гудками отбоя. Файловый сервер после падения можно молча поднять заново — он ничего не помнил. А сервер с открытой транзакцией в базе тихо перезапускать нельзя: пользователь должен узнать, что его работа потерялась.

### Keepalive and session id

Streamable HTTP использует заголовок `Mcp-Session-Id`. У stdio никакого id сессии нет — сессия и есть сам процесс. Пинги-keepalive не обязательны: stdio-трубы не рвутся от простоя.

> 🎒 **На пальцах.** У stdio сессия — это сам процесс: пока PID жив, жива и сессия, никакой `Mcp-Session-Id` не нужен. У HTTP так не выйдет: запросы приходят по разным соединениям, поэтому и нужен номерок в заголовке. Отсюда вывод: keepalive-пинги для stdio — бессмысленная работа, труба от простоя не портится.

```figure
tp-client-merge
```

## Use It

`code/main.py` поднимает три симулированных MCP-сервера дочерними процессами, проводит хендшейк с каждым, сливает их списки инструментов и маршрутизирует вызовы туда, куда надо. «Серверы» на самом деле — другие процессы на Python с игрушечными ответчиками (никакой настоящей LLM). Запустите и увидите:

- Три инициализации, у каждой свой набор возможностей.
- Три результата `tools/list`, слитые в пространство имён из 7 инструментов.
- Решение о маршрутизации по имени инструмента.
- Коллизию, предотвращённую префиксом пространства имён.

На что посмотреть:

- Датакласс `Session` аккуратно держит состояние по каждому серверу.
- Фоновый поток-читатель забирает каждую строку из stdout, не блокируя главный поток.
- Таблица маршрутизации — обычный `dict[str, Session]`.
- Разбор коллизий явный: когда два сервера объявляют одно имя, поздний переименовывается с префиксом.

> 🎒 **На пальцах.** Обратите внимание на цифру 7: три сервера в сумме отдали 7 инструментов, и хотя бы одно имя у них совпало — иначе демо не показало бы коллизию. Запустите и сверьте руками: сколько имён в итоговом списке, у какого из них появился префикс и какому PID достался вызов.

## Ship It

Этот урок производит `outputs/skill-mcp-client-harness.md`. Получив декларативный список MCP-серверов (имя, команда, аргументы), навык выдаёт обвязку, которая их поднимает, сливает списки инструментов и отдаёт функцию маршрутизации с разбором коллизий.

> 🎒 **На пальцах.** Смысл навыка — превратить три строки декларации вроде «notes: python notes_server.py» в готовую обвязку. Вы описываете, что подключить, а он пишет скучное: запуск, хендшейк, слияние, маршрутизацию. Ровно тот код, который в каждом проекте пишут заново и одинаково неправильно.

## Exercises

1. Запустите `code/main.py` и посмотрите лог запуска серверов. Прибейте один из симулированных серверных процессов через SIGTERM и проследите, как клиент замечает EOF и помечает эту сессию мёртвой.

2. Реализуйте префиксы пространства имён. Когда два сервера отдают `search`, переименуйте второй в `<server>/search`. Обновите таблицу маршрутизации и убедитесь, что вызовы уходят по адресу.

3. Добавьте отступ в стиле пула соединений для перезапуска сервера: экспоненциальный бэкофф на подряд идущих сбоях, потолок 30 секунд, уведомление пользователю после трёх неудач.

4. Набросайте клиент, который держит 100 MCP-серверов одновременно. Какая структура данных заменит простой словарь маршрутизации? (Подсказка: trie для префиксных пространств имён плюс метрика «сколько инструментов на сервер».)

5. Перенесите клиент на официальный MCP Python SDK. SDK оборачивает `stdio_client` и `ClientSession`. Код должен усохнуть с ~200 строк до ~40, сохранив маршрутизацию по нескольким серверам.

> 🎒 **На пальцах.** Задание 3 стоит посчитать заранее: бэкофф даёт паузы 1, 2, 4, 8, 16, 30, 30 секунд — то есть за первую минуту вы сделаете шесть попыток, а не шестьсот. Без потолка на 30 секундах десятая попытка уехала бы на 512 секунд, и пользователь давно бы решил, что сервер мёртв навсегда.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| MCP client | «Агентный хост» | Процесс, который запускает серверы и оркестрирует вызовы инструментов |
| Session | «Состояние по серверу» | Возможности, список инструментов и учёт ожидающих запросов |
| Merged namespace | «Один список инструментов» | Плоское множество имён инструментов со всех активных серверов |
| Namespace collision | «Два сервера, один инструмент» | Клиент обязан добавить префикс, отказать или взять первый пришедший |
| Routing | «Кому уйдёт этот вызов?» | Отправка от имени инструмента к серверу-владельцу |
| Background reader | «Неблокирующий stdout» | Поток или задача, сливающая stdout сервера в очередь |
| Sampling callback | «LLM как сервис» | Обработчик клиента для `sampling/createMessage` от сервера |
| `notifications/*_changed` | «Примитив изменился» | Сигнал, что клиенту надо заново обнаружить или перечитать |
| Reconnection policy | «Когда сервер умер» | Правила перезапуска при сбое транспорта |
| Stdio session | «Процесс = сессия» | Никакого id сессии; время жизни дочернего процесса и есть сессия |
