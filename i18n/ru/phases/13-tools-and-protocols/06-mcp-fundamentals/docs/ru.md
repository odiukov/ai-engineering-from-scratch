# Основы MCP — примитивы, жизненный цикл, база на JSON-RPC

> Любая интеграция до MCP была самоделкой. Model Context Protocol, впервые выпущенный Anthropic в ноябре 2024 года и теперь опекаемый Agentic AI Foundation при Linux Foundation, стандартизует обнаружение и вызов, так что любой клиент может говорить с любым сервером. Спецификация 2025-11-25 называет шесть примитивов (три серверных, три клиентских), трёхфазный жизненный цикл и формат передачи на JSON-RPC 2.0. Выучите их — и остальная MCP-часть этой фазы превратится в чтение.

**Type:** Learn
**Languages:** Python (stdlib, JSON-RPC parser)
**Prerequisites:** Phase 13 · 01 through 05 (the tool interface and function calling)
**Time:** ~45 minutes

## Learning Objectives

- Назвать все шесть примитивов MCP (tools, resources, prompts на сервере; roots, sampling, elicitation на клиенте) и привести по одному применению для каждого.
- Пройти трёхфазный жизненный цикл (initialize, operation, shutdown) и сказать, кто отправляет какое сообщение на каждой фазе.
- Разобрать и собрать конверты JSON-RPC 2.0: запрос, ответ и уведомление.
- Объяснить, что такое согласование возможностей на `initialize` и что ломается без него.

## The Problem

До MCP у каждого агента с инструментами был свой протокол. У Cursor — система инструментов, похожая на MCP по форме, но несовместимая. Claude Desktop приехал с другой. Расширение Copilot в VS Code — с третьей. Команда, собравшая инструмент «запрос к Postgres», писала один и тот же инструмент трижды, каждый раз под API конкретного хоста. Переиспользование сводилось к копированию кода.

Итогом стал кембрийский взрыв одноразовых интеграций и потолок скорости развития экосистемы.

MCP закрывает эту проблему стандартизацией формата передачи. Один MCP-сервер работает в каждом MCP-клиенте: Claude Desktop, ChatGPT, Cursor, VS Code, Gemini, Goose, Zed, Windsurf — 300+ клиентов к апрелю 2026 года. 110 млн загрузок SDK в месяц. 10 000+ публичных серверов. В декабре 2025 года опеку над протоколом взяла Linux Foundation в рамках новой Agentic AI Foundation.

В этой фазе используется ревизия спецификации **2025-11-25**. Она добавляет асинхронные Tasks (SEP-1686), elicitation через URL (SEP-1036), sampling с инструментами (SEP-1577), пошаговое согласие на области доступа (SEP-835) и семантику resource-indicator из OAuth 2.1. Эти расширения разбираются в уроках Phase 13 · 09–16. Этот урок останавливается на базе.

> 🎒 **На пальцах.** Посчитайте цену самоделок: один инструмент «запрос к Postgres» и три хоста — это три реализации и три места, где придётся править баг. С MCP это одна реализация и 300+ клиентов бесплатно. Именно поэтому за год набежало 10 000 публичных серверов: писать стало нужно один раз.

## The Concept

### Three server primitives

1. **Tools.** Вызываемые действия. Тот же четырёхшаговый цикл, что в Phase 13 · 01.
2. **Resources.** Выставленные наружу данные. Контент только на чтение, адресуемый по URI: `file:///path`, `db://query/...`, свои схемы.
3. **Prompts.** Переиспользуемые шаблоны. В интерфейсе хоста это слэш-команды; шаблон даёт сервер, аргументы подставляет клиент.

> 🎒 **На пальцах.** Правило разграничения простое: tool что-то делает, resource что-то отдаёт, prompt заготовлен для человека. «Создай заметку» — tool. «Покажи файл `file:///etc/hosts`» — resource. «Проверь этот код по чек-листу» — prompt. Спросите себя: после вызова мир изменился? Изменился — значит tool.

### Three client primitives

4. **Roots.** Набор URI, к которым серверу разрешено прикасаться. Клиент их объявляет, сервер уважает.
5. **Sampling.** Сервер просит модель клиента выполнить генерацию. Это позволяет держать агентные циклы на сервере без серверных ключей к API.
6. **Elicitation.** Сервер спрашивает у пользователя клиента структурированный ввод прямо посреди работы. Формы или URL (SEP-1036).

Каждая возможность в MCP относится ровно к одному из этих шести примитивов. Каждый подробно разбирается в уроках Phase 13 · 10–14.

> 🎒 **На пальцах.** Обратите внимание, что стрелки смотрят в обе стороны: серверные примитивы — это то, что сервер предлагает клиенту, а клиентские — то, что клиент разрешает просить у себя. Sampling особенно приятен экономически: серверу не нужен свой ключ к API, он занимает модель клиента, и за токены платит клиент. Roots — обратная сторона: клиент говорит «трогать можно только `file:///home/me/project`», и это его страховка.

### Wire format: JSON-RPC 2.0

Каждое сообщение — это JSON-объект вот с такими полями:

- Запросы: `{jsonrpc: "2.0", id, method, params}`.
- Ответы: `{jsonrpc: "2.0", id, result | error}`.
- Уведомления: `{jsonrpc: "2.0", method, params}` — без `id`, ответа не ждут.

В базовой спецификации около 15 методов, сгруппированных по примитивам. Важные из них:

- `initialize` / `initialized` (рукопожатие)
- `tools/list`, `tools/call`
- `resources/list`, `resources/read`, `resources/subscribe`
- `prompts/list`, `prompts/get`
- `sampling/createMessage` (от сервера к клиенту)
- `notifications/tools/list_changed`, `notifications/resources/updated`, `notifications/progress`

> 🎒 **На пальцах.** Разница между запросом и уведомлением ровно в одном поле: есть `id` — ждём ответ, нет `id` — крикнули и пошли дальше. Поэтому `notifications/progress` не имеет `id`: никто не отвечает «спасибо, принял прогресс 40 %». А `id` работает как номерок в гардеробе: летит пять запросов одновременно, и ответы находят свои запросы по номеру.

### Three-phase lifecycle

**Phase 1: initialize.**

Клиент отправляет `initialize` со своими `capabilities` и `clientInfo`. Сервер отвечает своими `capabilities`, `serverInfo` и версией спецификации, на которой говорит. Клиент отправляет `notifications/initialized`, когда переварил ответ. Дальше любая сторона может отправлять запросы в рамках согласованных возможностей.

**Phase 2: operation.**

Двунаправленная фаза. Клиент вызывает `tools/list`, чтобы обнаружить инструменты, потом `tools/call`, чтобы вызвать. Сервер может отправить `sampling/createMessage`, если объявил такую возможность. Сервер может отправить `notifications/tools/list_changed`, когда его набор инструментов изменился. Клиент может отправить `notifications/roots/list_changed`, когда пользователь поменял разрешённые корни.

**Phase 3: shutdown.**

Любая сторона закрывает транспорт. Отдельного метода завершения в MCP нет; сигнал о конце соединения несёт транспорт (stdio или Streamable HTTP, Phase 13 · 09).

> 🎒 **На пальцах.** Три фазы — это как телефонный звонок: сначала «алло, кто это и что умеешь», потом разговор, потом трубка положена. Заметьте асимметрию последней фазы: никакого вежливого `shutdown` не предусмотрено, соединение просто рвётся на уровне транспорта. Поэтому сервер обязан быть готов умереть в любой момент — никакого состояния «в процессе», которое нельзя потерять.

### Capability negotiation

`capabilities` в рукопожатии `initialize` — это и есть контракт. Пример со стороны сервера:

```json
{
  "tools": {"listChanged": true},
  "resources": {"subscribe": true, "listChanged": true},
  "prompts": {"listChanged": true}
}
```

Сервер объявляет, что умеет присылать уведомления `tools/list_changed` и поддерживает `resources/subscribe`. Клиент отвечает согласием, объявляя своё:

```json
{
  "roots": {"listChanged": true},
  "sampling": {},
  "elicitation": {}
}
```

Если клиент не объявил `sampling`, сервер не имеет права вызывать `sampling/createMessage`. Симметрично: если сервер не объявил `resources.subscribe`, клиент не должен пытаться подписаться.

Именно это удерживает экосистему от расползания. Клиент, который не поддерживает sampling, всё равно остаётся полноценным MCP-клиентом; сервер, который не вызывает `sampling`, тоже остаётся полноценным MCP-сервером. Просто вместе они этой функцией не пользуются.

> 🎒 **На пальцах.** Это обмен визитками в начале встречи: «я умею вот это, а ты?». Посмотрите на две схемы выше: сервер обещает три вещи, клиент — три других, и пересечение обещаний определяет весь дальнейший разговор. Если в клиентской схеме нет `sampling`, то вызов `sampling/createMessage` — это не «не сработало», а прямое нарушение контракта.

### Structured content and error shapes

`tools/call` возвращает массив `content` из типизированных блоков: `text`, `image`, `resource`. Phase 13 · 14 добавляет к этому списку MCP Apps (интерактивный интерфейс через `ui://`).

Ошибки используют коды ошибок JSON-RPC. Что добавила спецификация: `-32002` «Resource not found», `-32603` «Internal error», плюс специфичные для MCP данные об ошибке в `error.data`.

> 🎒 **На пальцах.** Результат инструмента — это не строка, а массив блоков, и это важнее, чем кажется: один вызов может вернуть текст, картинку и ссылку на resource сразу. Инструмент «сделай скриншот» отдаёт блок `image`, инструмент «покажи лог» — блок `text`, а «открой отчёт» — блок `resource`, который клиент подтянет по URI сам.

### Client capabilities vs tool call details

Частая путаница: `capabilities.tools` — это про то, поддерживает ли клиент уведомления об изменении списка инструментов. А будет ли клиент ВЫЗЫВАТЬ конкретные инструменты — это решение во время работы, которое принимает его модель, а не флаг возможности. Флаг возможности — контракт на уровне спецификации. Выбор модели лежит в другой плоскости.

> 🎒 **На пальцах.** Сравните с квартирой: `capabilities.tools` — это «в доме есть газ», а вызов инструмента — «я сегодня готовлю». Первое обещает инфраструктуру, второе — сиюминутное решение. Отсюда практический вывод: если модель не вызывает ваш инструмент, лезть в `capabilities` бессмысленно — проблема в описании инструмента (Phase 13 · 05), а не в рукопожатии.

### Why JSON-RPC and not REST?

JSON-RPC 2.0 (2010) — легковесный двунаправленный протокол. REST инициируется клиентом. А MCP нужны сообщения, инициированные сервером (sampling, уведомления), поэтому JSON-RPC с его симметричной формой запрос/ответ подошёл естественно. JSON-RPC вдобавок чисто ложится и на stdio, и на WebSocket/Streamable HTTP, не переизобретая форму HTTP-запроса.

```figure
mcp-tool-call
```

> 🎒 **На пальцах.** В REST разговор всегда начинает клиент — это как звонок в поддержку: обратно вам никто не позвонит. А серверу MCP нужно самому дёргать клиента: попросить модель через `sampling/createMessage` или сообщить `notifications/tools/list_changed`. Вот и весь выбор: нужен протокол, где трубку может снять любая сторона.

## Use It

`code/main.py` привозит минимальный парсер и генератор JSON-RPC 2.0, а потом вручную проходит последовательность `initialize` → `tools/list` → `tools/call` → `shutdown`, печатая каждое сообщение. Никакого настоящего транспорта, только формы сообщений. Сверьте их со спецификацией из Further Reading и проверьте каждый конверт.

На что смотреть:

- `initialize` объявляет возможности в обе стороны; в ответе есть `serverInfo` и `protocolVersion: "2025-11-25"`.
- `tools/list` возвращает массив `tools`; у каждого элемента есть `name`, `description`, `inputSchema`.
- `tools/call` использует `params.name` и `params.arguments`.
- В ответе `content` — это массив блоков вида `{type, text}`.

> 🎒 **На пальцах.** Ценность этого демо в том, что оно снимает магию: MCP — это четыре JSON-объекта, которые можно распечатать и прочитать глазами. Пройдите глазами по полям и сверьте со спецификацией: `id` у запроса есть, у уведомления нет, `protocolVersion` совпадает с ревизией. Ошибку в конверте вы после этого увидите в чужом сервере за секунды.

## Ship It

Урок даёт `outputs/skill-mcp-handshake-tracer.md`. Получив расшифровку взаимодействия MCP-клиента и сервера в стиле pcap, навык подписывает каждому сообщению, к какому примитиву оно относится, в какой фазе жизненного цикла находится и от какой возможности зависит.

> 🎒 **На пальцах.** Такой трассировщик — первое, за что вы схватитесь при отладке. Типичная находка: клиент зовёт `resources/read`, а сервер в рукопожатии `resources` вообще не объявлял — то есть ошибка случилась на первом сообщении, а проявилась на пятнадцатом. Подпись «фаза, примитив, возможность» у каждой строки лога находит такое сразу.

## Exercises

1. Запустите `code/main.py`. Найдите строку, где происходит согласование возможностей, и опишите, что изменилось бы, если сервер не объявил `tools.listChanged`.

2. Расширьте парсер поддержкой `notifications/progress`. Форма сообщения: `{method: "notifications/progress", params: {progressToken, progress, total}}`. Отправляйте его, пока идёт долгий `tools/call`, и убедитесь, что обработчик клиента показал бы полосу прогресса.

3. Прочитайте спецификацию MCP 2025-11-25 от начала до конца — весь документ примерно на 80 страниц. Найдите тот флаг возможности, который большинству серверов НЕ нужен. Подсказка: он про подписку на resources.

4. Набросайте на бумаге, к какому примитиву относилась бы гипотетическая функция «cron job». (Подсказка: сервер хочет, чтобы клиент вызвал его в назначенное время. Ни один из шести примитивов сегодня не подходит.) В дорожной карте MCP на 2026 год под это есть черновик SEP.

5. Разберите один лог сессии открытого MCP-сервера с GitHub. Посчитайте, сколько там запросов, сколько ответов и сколько уведомлений. Вычислите, какая доля трафика приходится на жизненный цикл, а какая — на работу.

> 🎒 **На пальцах.** Задание 5 даёт неожиданно полезное число. На короткой сессии рукопожатие — это 3 сообщения из, скажем, 12, то есть четверть трафика уходит на знакомство. На долгой сессии те же 3 сообщения растворяются до 1 %. Отсюда практический вывод: держать соединение открытым дешевле, чем поднимать сервер на каждый вызов.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| MCP | «Model Context Protocol» | Открытый протокол для обнаружения и вызова инструментов моделью |
| Server primitive | «Что сервер отдаёт наружу» | tools (действия), resources (данные), prompts (шаблоны) |
| Client primitive | «Что клиент разрешает серверам» | roots (область доступа), sampling (обратные вызовы к LLM), elicitation (ввод от пользователя) |
| JSON-RPC 2.0 | «Формат передачи» | Симметричные конверты запроса, ответа и уведомления |
| `initialize` handshake | «Согласование возможностей» | Первая пара сообщений; серверы и клиенты объявляют, что поддерживают |
| `tools/list` | «Обнаружение» | Клиент спрашивает у сервера его текущий набор инструментов |
| `tools/call` | «Вызов» | Клиент просит сервер выполнить инструмент с аргументами |
| `notifications/*_changed` | «События изменения» | Сервер сообщает клиенту, что его список примитивов поменялся |
| Content block | «Типизированный результат» | `{type: "text" \| "image" \| "resource" \| "ui_resource"}` в результате инструмента |
| SEP | «Spec Evolution Proposal» | Именованное черновое предложение (например, SEP-1686 про асинхронные Tasks) |
