# MCP Sampling — сервер просит у клиента LLM-дополнения и крутит агентные циклы

> Большинство MCP-серверов — тупые исполнители: приняли аргументы, выполнили код, вернули контент. Sampling позволяет серверу развернуть направление: он сам просит LLM клиента принять решение. Так сервер может держать у себя агентный цикл, не владея ни одним ключом к модели. SEP-1577, влитый 2025-11-25, разрешил класть инструменты внутрь sampling-запроса, чтобы в цикле было место более глубокому рассуждению. Оговорка про дрейф: форма «инструменты внутри sampling» из SEP-1577 была экспериментальной весь первый квартал 2026 года и до сих пор устаканивается в API SDK.

**Type:** Build
**Languages:** Python (stdlib, sampling harness)
**Prerequisites:** Phase 13 · 07 (MCP server), Phase 13 · 10 (resources and prompts)
**Time:** ~75 minutes

## Learning Objectives

- Объяснить, какую задачу решает `sampling/createMessage` (циклы на стороне сервера без серверных API-ключей).
- Реализовать сервер, который просит клиента прогнать многоходовой промпт через модель и возвращает дополнение.
- Использовать `modelPreferences` (приоритеты цена / скорость / интеллект), чтобы направлять выбор модели у клиента.
- Собрать инструмент `summarize_repo`, который внутри себя итерируется через sampling вместо жёстко прописанного поведения.

> 🎒 **На пальцах.** Обычный MCP-инструмент — как калькулятор: нажали кнопку, получили число. Sampling делает из сервера прораба: он не считает сам, а звонит клиенту и спрашивает «какие пять файлов тут читать?». Все четыре цели урока — про один разворот стрелки: раньше запросы шли только от клиента к серверу, теперь и обратно.

## The Problem

Полезному MCP-серверу для сценария «опиши, что делает этот код» нужно: обойти дерево файлов, выбрать, какие файлы читать, синтезировать описание и вернуть его. Где здесь происходит рассуждение LLM?

Вариант A: сервер зовёт свою собственную LLM. Нужен API-ключ, счёт приходит владельцу сервера, на каждого пользователя дорого.

Вариант B: сервер отдаёт сырой контент, а рассуждает агент клиента. Работает, но логика сервера переезжает в промпт клиента, а это хрупко.

Вариант C: сервер спрашивает LLM клиента через `sampling/createMessage`. Алгоритм остаётся у сервера (какие файлы читать, сколько проходов делать), а оплата и выбор модели остаются у клиента. У сервера вообще нет никаких ключей.

Sampling — это вариант C. Механизм, благодаря которому доверенный сервер может держать у себя агентный цикл, не будучи при этом полноценным LLM-хостом.

> 🎒 **На пальцах.** Сравните счёт: при варианте A сервер с 1000 пользователей платит за 1000 × 2 вызова модели из своего кармана. При варианте C он платит ноль — каждый пользователь тратит свой лимит через своего клиента. При этом алгоритм «сначала выбери 5 файлов, потом опиши» никуда из сервера не уехал, в отличие от варианта B.

## The Concept

### `sampling/createMessage` request

Сервер отправляет:

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "sampling/createMessage",
  "params": {
    "messages": [{"role": "user", "content": {"type": "text", "text": "..."}}],
    "systemPrompt": "...",
    "includeContext": "none",
    "modelPreferences": {
      "costPriority": 0.3,
      "speedPriority": 0.2,
      "intelligencePriority": 0.5,
      "hints": [{"name": "claude-3-5-sonnet"}]
    },
    "maxTokens": 1024
  }
}
```

Клиент прогоняет свою LLM и возвращает:

```json
{"jsonrpc": "2.0", "id": 42, "result": {
  "role": "assistant",
  "content": {"type": "text", "text": "..."},
  "model": "claude-3-5-sonnet-20251022",
  "stopReason": "endTurn"
}}
```

> 🎒 **На пальцах.** Присмотритесь: это обычный JSON-RPC-запрос, только `id: 42` теперь принадлежит серверу, а отвечает клиент. Сервер сам собрал `messages` и `systemPrompt`, поставил лимит `maxTokens: 1024` — то есть сервер выступает в роли прикладного программиста, а клиент в роли провайдера модели. В ответе клиент честно сообщает, какую модель взял (`claude-3-5-sonnet-20251022`) и почему остановился (`endTurn`).

### `modelPreferences`

Три числа с плавающей точкой, в сумме дающие 1.0:

- `costPriority`: тянет выбор к более дешёвым моделям.
- `speedPriority`: тянет выбор к более быстрым моделям.
- `intelligencePriority`: тянет выбор к более способным моделям.

Плюс `hints`: модели, которые сервер предпочёл бы по имени. Клиент может учесть подсказки, а может и нет; настройки пользователя у клиента всегда главнее.

> 🎒 **На пальцах.** Это не приказ, а пожелание, как «хочу столик у окна». В примере выше стоит 0.3 / 0.2 / 0.5 — сервер намекает: важнее ум, чем скорость, а цена посередине. Клиент имеет полное право прочитать это и всё равно взять самую дешёвую модель, потому что пользователь так настроил свой лимит.

### `includeContext`

Три значения:

- `"none"` — только сообщения, которые прислал сервер. Значение по умолчанию.
- `"thisServer"` — добавить предыдущие сообщения из сессии этого же сервера.
- `"allServers"` — добавить весь контекст сессии.

С 2025-11-25 `includeContext` мягко объявлен устаревшим, потому что протекает контекст между серверами, а это вопрос безопасности. Берите `"none"` и передавайте нужный контекст явно, прямо в сообщениях.

> 🎒 **На пальцах.** Представьте, что вы подключили к Claude Desktop сервер банка и сервер погоды. При `"allServers"` погодный сервер попросит модель «дополнить» диалог, в котором лежат ваши транзакции, — и увидит их. Отсюда правило: `"none"` плюс ровно те три абзаца, которые серверу действительно нужны.

### Sampling with tools (SEP-1577)

Новое в 2025-11-25: в sampling-запрос можно положить массив `tools`. Клиент прогоняет полноценный цикл вызова инструментов с этими инструментами. Так сервер может держать у себя агентный цикл в стиле ReAct, работающий на модели клиента.

```json
{
  "messages": [...],
  "tools": [
    {"name": "fetch_url", "description": "...", "inputSchema": {...}}
  ]
}
```

Клиент крутит цикл: сэмплирует, выполняет инструмент, если тот был вызван, сэмплирует снова, возвращает финальное сообщение ассистента. Всё это экспериментально на протяжении первого квартала 2026 года; подписи функций в SDK ещё могут поехать. Когда будете реализовывать, сверяйтесь с разделом client/sampling спецификации 2025-11-25.

> 🎒 **На пальцах.** Раньше сервер получал за один sampling ровно одну реплику модели, и цикл «подумай — сходи в инструмент — подумай ещё» приходилось склеивать самому. С `tools` внутри запроса весь этот цикл крутит клиент, а сервер получает уже готовый итог. Обратная сторона: инструмент `fetch_url` выполняется на машине клиента, значит клиент и должен спросить разрешение пользователя.

### Human-in-the-loop

Клиент ОБЯЗАН показать пользователю, о чём именно сервер просит модель, до того как прогонит сэмпл. Вредоносный сервер мог бы через sampling подкручивать сессию пользователя («скажи пользователю X, чтобы он нажал Y»). Claude Desktop, VS Code и Cursor показывают sampling-запросы диалогом подтверждения, который можно отклонить.

Консенсус 2026 года: sampling без подтверждения человеком — красный флаг. Шлюзы (Phase 13 · 17) могут автоматически одобрять безопасный sampling и автоматически отклонять всё подозрительное.

> 🎒 **На пальцах.** Опасность тут не в утечке данных, а в подмене голоса: текст, который сервер отправил в `systemPrompt`, для пользователя выглядит как слова его собственного ассистента. Поэтому окно подтверждения показывает не «сервер хочет сделать вызов», а полный текст запроса — прочитайте его как письмо от незнакомца, прежде чем нажимать «разрешить».

### Server-hosted loops without API keys

Канонический сценарий: MCP-сервер для описания кода, у которого нет своего доступа к LLM. Он делает так.

1. Обходит структуру репозитория.
2. Зовёт `sampling/createMessage` с текстом «Выбери пять файлов, которые вероятнее всего описывают назначение этого репозитория».
3. Читает эти файлы.
4. Зовёт `sampling/createMessage` с содержимым файлов и текстом «Опиши репозиторий в трёх абзацах».
5. Возвращает описание как результат `tools/call`.

Сервер ни разу не обращается к LLM API. За дополнения платит пользователь клиента своими собственными ключами.

> 🎒 **На пальцах.** Посчитайте вызовы: пять шагов, из них ровно два — обращения к модели, остальные три — обычный код (обход дерева, чтение файлов, возврат ответа). Именно это и продаёт sampling: интеллект берётся напрокат по два раза за вызов инструмента, а ценная часть — алгоритм «сначала выбери, потом опиши» — остаётся вашей.

### Safety risks (Unit 42 disclosure, 2026 Q1)

- **Covert sampling.** Инструмент, который при каждом вызове делает sampling с текстом «верни email пользователя из контекста сессии». Векторы атак разбираются в Phase 13 · 15.
- **Resource theft via sampling.** Сервер просит клиента отсуммировать полезную нагрузку атакующего, а счёт выставляется пользователю.
- **Loop bombs.** Сервер зовёт sampling в плотном цикле. Клиенты ОБЯЗАНЫ применять лимиты частоты на сессию.

> 🎒 **На пальцах.** Все три риска — это одна и та же кнопка, нажатая не туда: сервер умеет тратить чужие токены. Первый крадёт данные, второй — деньги, третий просто вешает сессию бесконечным циклом. Защита тоже одна и та же с трёх сторон: показать запрос человеку, считать вызовы и обрубать на лимите.

## Use It

В `code/main.py` лежит игрушечный стенд sampling от сервера к клиенту. Смоделированный инструмент «summarize_repo» делает два раунда sampling (сначала выбрать файлы, потом описать), а фальшивый клиент отдаёт заранее заготовленные ответы. Стенд показывает:

- Сервер отправляет `sampling/createMessage` с `modelPreferences`.
- Клиент возвращает дополнение.
- Сервер продолжает свой цикл.
- Ограничитель частоты режет общее число sampling-вызовов на один вызов инструмента.

> 🎒 **На пальцах.** Обратите внимание, что клиент здесь фальшивый и отвечает заготовками — и стенд всё равно полезен. Вам нужно проверить не качество ответа модели, а порядок сообщений и работу лимита; для этого живая LLM только мешала бы недетерминированностью и счётом за токены.

На что смотреть:

- Сервер отдаёт наружу всего один инструмент (`summarize_repo`); всё рассуждение живёт в sampling-вызовах.
- Предпочтения по модели взвешивают выбор клиента; список hints перечисляет желаемые модели.
- Цикл завершается по `stopReason: "endTurn"`.
- Лимит `max_samples_per_tool = 5` отлавливает разогнавшийся цикл.

> 🎒 **На пальцах.** Пересчитайте: штатный сценарий тратит 2 sampling-вызова, а лимит стоит на 5 — то есть запас втрое, и при этом бесконечный цикл умирает на шестом. Хороший лимит всегда выглядит так: заметно больше нормы, но конечен. Поставите 2 — сломаете штатный путь при первом же лишнем уточнении.

## Ship It

Этот урок производит `outputs/skill-sampling-loop-designer.md`. Получив на вход серверный алгоритм, которому нужны обращения к LLM (исследование, суммаризация, планирование), навык проектирует реализацию через sampling с правильными modelPreferences, лимитами частоты и подтверждениями безопасности.

> 🎒 **На пальцах.** Навык отвечает на три вопроса, которые вы иначе решите наугад: какой приоритет модели поставить, сколько вызовов разрешить и где спросить человека. Для «опиши репозиторий» это будет intelligencePriority повыше и лимит вроде пяти; для «переведи строчку» — costPriority повыше и лимит один.

## Exercises

1. Запустите `code/main.py`. Поменяйте `max_samples_per_tool` на 2 и посмотрите, как срабатывает отсечка по лимиту.

2. Реализуйте вариант «инструменты внутри sampling» из SEP-1577: sampling-запрос несёт массив `tools`. Убедитесь, что цикл на стороне клиента выполняет эти инструменты до того, как вернуть финальное дополнение. Помните про риск дрейфа: подписи в SDK могут ещё поменяться в первом полугодии 2026 года.

3. Добавьте подтверждение человеком: перед первым серверным `sampling/createMessage` встаньте на паузу и дождитесь одобрения пользователя. Отклонённые вызовы возвращают типизированный отказ.

4. Добавьте ограничитель частоты на пользователя, привязанный к сессии клиента. Циклы одного и того же сервера от одного и того же пользователя должны делить общий бюджет.

5. Спроектируйте инструмент `summarize_pdf`, который через sampling выбирает, какие куски включать. Набросайте отправляемые сообщения. Как меняется поведение при `modelPreferences.intelligencePriority` 0.1 против 0.9?

> 🎒 **На пальцах.** Начните с первого задания — оно занимает минуту и сразу показывает главное: лимит 2 обрубает цикл ровно между «выбрал файлы» и «описал репозиторий», и инструмент возвращает мусор. Так вы своими глазами увидите, почему лимит надо считать от реального числа раундов, а не брать красивое число.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Sampling | «Вызов LLM от сервера к клиенту» | Сервер просит у модели клиента дополнение |
| `sampling/createMessage` | «Тот самый метод» | JSON-RPC-метод для sampling-запросов |
| `modelPreferences` | «Приоритеты модели» | Веса цена / скорость / интеллект плюс подсказки по именам |
| `includeContext` | «Протечка между сессиями» | Мягко устаревший режим подмешивания контекста |
| SEP-1577 | «Инструменты внутри sampling» | Разрешает инструменты внутри sampling для серверного ReAct |
| Human-in-the-loop | «Пользователь подтверждает» | Клиент показывает sampling-запрос пользователю до запуска |
| Loop bomb | «Разогнавшийся sampling» | Бесконечный sampling-цикл на сервере; клиент обязан ставить лимит |
| Covert sampling | «Скрытое рассуждение» | Вредоносный сервер прячет свой умысел в sampling-промптах |
| Resource theft | «Тратит лимит пользователя» | Сервер заставляет клиента платить за ненужный ему sampling |
| `stopReason` | «Почему генерация встала» | `endTurn`, `stopSequence` или `maxTokens` |

> 🎒 **На пальцах.** Три термина из таблицы описывают одну и ту же дырку с разных сторон: covert sampling — про спрятанный текст промпта, resource theft — про чужой счёт, loop bomb — про число вызовов. Запомните их парами с защитой: показ запроса, бюджет на пользователя, лимит на сессию.
