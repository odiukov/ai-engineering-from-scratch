# Транспорты MCP — stdio против Streamable HTTP и миграция с SSE

> stdio работает локально и больше нигде. Streamable HTTP (ревизия 2025-03-26) — стандарт для удалённых серверов. Старый транспорт HTTP+SSE объявлен устаревшим и выпиливается в середине 2026 года. Выберете транспорт неправильно — заплатите миграцией; выберете правильно — получите MCP-сервер, который можно хостить удалённо, с непрерывностью сессии и защитой от DNS-rebinding.

**Type:** Learn
**Languages:** Python (stdlib, Streamable HTTP endpoint skeleton)
**Prerequisites:** Phase 13 · 07, 08 (MCP server and client)
**Time:** ~45 minutes

## Learning Objectives

- Выбирать между stdio и Streamable HTTP по форме деплоя (локально или удалённо, один процесс или флот).
- Реализовать паттерн единой точки Streamable HTTP: POST для запросов, GET для потока сессии.
- Заставить работать проверку `Origin` и семантику session-id, чтобы закрыть DNS-rebinding.
- Перевести legacy-сервер на HTTP+SSE в Streamable HTTP до дедлайнов середины 2026 года.

> 🎒 **На пальцах.** Весь урок — про один провод между клиентом и сервером. Четыре цели складываются в два вопроса: «какой провод выбрать» и «как не дать чужому в него влезть». Держите в голове одну картинку: stdio — это трубка внутри одной машины, Streamable HTTP — это один URL наружу.

## The Problem

Первый удалённый транспорт MCP (ревизия 2024-11) назывался HTTP+SSE: две точки входа, одна для POST-запросов клиента и один канал Server-Sent-Events для потока от сервера к клиенту. Он работал. Он же был неуклюжим: две точки на каждую сессию, поломанные кэши перед некоторыми CDN и жёсткая зависимость от долгоживущих SSE-соединений, которые часть WAF рубит без разговоров.

Спецификация 2025-03-26 заменила его на Streamable HTTP: одна точка входа, POST для запросов клиента, GET для установки потока сессии, обе разделяют заголовок `Mcp-Session-Id`. Каждый сервер, собранный или переведённый после этого, использует Streamable HTTP. Старый SSE-режим объявляют устаревшим: Atlassian Rovo убрал его 30 июня 2026 года, Keboola — 1 апреля 2026 года, большинство остальных корпоративных серверов — до конца 2026 года.

При этом stdio по-прежнему важен для локальных серверов. Claude Desktop, VS Code и любой клиент в форме IDE поднимают серверы через stdio. Правильная модель в голове: stdio для «эта машина», Streamable HTTP для «через сеть». Пересечений нет.

> 🎒 **На пальцах.** Представьте домофон и телефон. Домофон (stdio) работает, только если вы стоите у той же двери — тянуть его в другой город бессмысленно. Телефон (Streamable HTTP) работает откуда угодно, но требует, чтобы вы проверяли, кто звонит. Два разных инструмента, а не «плохой и хороший».

## The Concept

### stdio

- Транспорт через дочерний процесс. Клиент запускает сервер и общается с ним через stdin/stdout.
- Один JSON-объект на строку. Разделитель — перевод строки.
- Никакого session id: сессия — это сам процесс.
- Аутентификация не нужна (дочерний процесс наследует периметр доверия родителя).
- Никогда не используйте для удалённых серверов — придётся тянуть туннель через SSH или socat, а на этом месте проще взять Streamable HTTP.

> 🎒 **На пальцах.** Пять пунктов сводятся к одному: процесс = сессия. Клиент убил процесс — сессия кончилась, ничего чистить не надо, никаких токенов и заголовков. Отсюда и главный запрет из прошлого урока: в stdout нельзя писать логи, там живут те самые «один JSON на строку».

### Streamable HTTP

Одна точка входа `/mcp` (или любой другой путь). Поддерживает три HTTP-метода:

- **POST /mcp.** Клиент отправляет сообщение JSON-RPC. Сервер отвечает либо одним JSON-ответом, либо SSE-потоком из одного или нескольких ответов (полезно для пакетов ответов и уведомлений, связанных с этим запросом).
- **GET /mcp.** Клиент открывает долгоживущий SSE-канал. Сервер использует его для запросов в обратную сторону — от сервера к клиенту (sampling, уведомления, elicitation).
- **DELETE /mcp.** Клиент явно завершает сессию.

Сессии опознаются по заголовку `Mcp-Session-Id`: сервер выставляет его в первом ответе, а клиент возвращает в каждом следующем запросе. Session id ОБЯЗАН быть криптографически случайным (128 бит и больше); id, выбранные клиентом, отклоняются из соображений безопасности.

> 🎒 **На пальцах.** Три метода на один URL — как одна дверь в кафе с тремя ролями: зашёл заказать (POST), сел и ждёшь, когда позовут (GET), ушёл и освободил столик (DELETE). А `Mcp-Session-Id` — номерок на столике: 128 случайных бит это 32 hex-символа, угадать такой перебором нельзя, поэтому сервер и не даёт клиенту придумывать его самому.

### Single endpoint vs two

Двухточечный режим из старой спецификации в 2026 году всё ещё можно вызвать — спецификация называет его «legacy compatible». Но все новые серверы должны быть одноточечными. Официальные SDK отдают одноточечный вариант; legacy-режим включайте только когда говорите с непереведённым удалённым сервером.

> 🎒 **На пальцах.** Разница чисто арифметическая: было два URL на сессию, стало один. Меньше URL — меньше мест, где прокси или CDN могут по-своему решить, что этот запрос надо закэшировать. Legacy-режим держите как переходник для чужого старого железа, а не как опцию для своего кода.

### `Origin` validation and DNS-rebinding

Браузеры не являются MCP-клиентами (пока), но атакующий может собрать веб-страницу, которая заставит браузер сделать POST на `localhost:1234/mcp` — туда, где слушает локальный MCP-сервер пользователя. Если сервер не проверяет `Origin`, политика same-origin браузера его не спасёт: `Origin: http://evil.com` — совершенно валидный cross-origin.

Спецификация 2025-11-25 требует, чтобы серверы отклоняли запросы, чей `Origin` не входит в allowlist. Обычно в allowlist лежит хост MCP-клиента (`https://claude.ai`, `vscode-webview://*`) и варианты localhost для локальных интерфейсов.

> 🎒 **На пальцах.** Ловушка в том, что «localhost» звучит как «только я». Но браузер тоже живёт на вашей машине: открыли вкладку с чужого сайта — и её JavaScript стучится на ваш `localhost:1234` от вашего же имени. Проверка `Origin` — это вопрос «а кто тебя послал?»: `http://evil.com` в списке нет, значит 403, и разговор закончен.

### Session id lifecycle

1. Клиент отправляет первый запрос без `Mcp-Session-Id`.
2. Сервер выдаёт случайный id и выставляет `Mcp-Session-Id` в заголовке ответа.
3. Клиент возвращает этот заголовок во всех последующих запросах и в `GET /mcp` для потока.
4. Сессию может отозвать сервер; клиент видит 404 на следующих запросах и обязан заново пройти инициализацию.
5. Клиент может явно сделать DELETE сессии для аккуратного завершения.

> 🎒 **На пальцах.** Это гардероб: пришли без номерка (шаг 1), получили номерок (шаг 2), показываете его каждый раз (шаг 3). Гардероб закрылся — номерок недействителен, вам говорят 404, и надо становиться в очередь заново (шаг 4). Сдали номерок сами — освободили крючок (шаг 5).

### Keepalive and reconnect

SSE-соединения обрываются. Клиент восстанавливает их повторным GET с тем же `Mcp-Session-Id`. Сервер ОБЯЗАН складывать в очередь события, пропущенные во время обрыва (в пределах разумного окна), и переигрывать их по заголовку `last-event-id`, который присылает клиент.

Phase 13 · 13 разбирает Tasks — они позволяют долгой работе выжить даже при полном переподключении сессии.

> 🎒 **На пальцах.** Это как досмотреть сериал с места, где выключился интернет. `last-event-id` — это номер последней просмотренной серии: клиент говорит «я видел до 42-го», сервер отдаёт с 43-го. Если бы этого номера не было, вы бы либо начинали с начала, либо теряли середину.

### Backwards compatibility probe

Клиент, который хочет поддерживать и старые, и новые серверы:

1. Делает POST на `/mcp`.
2. Если ответ `200 OK` с JSON или SSE — это Streamable HTTP.
3. Если ответ `200 OK` с `Content-Type: text/event-stream` И заголовком `Location`, указывающим на вторичную точку входа, — это legacy HTTP+SSE; идите по `Location`.

> 🎒 **На пальцах.** Клиент не спрашивает «какой ты версии», он смотрит на форму ответа. Пришёл заголовок `Location` — значит сервер говорит «моя вторая дверь вон там», и это признак старого двухточечного режима. Такое определение по поведению надёжнее, чем доверять номеру версии в конфиге.

### Cloudflare, ngrok, and hosting

Продакшен-серверы MCP в 2026 году живут на Cloudflare Workers (с их MCP Agents SDK), Vercel Functions или в контейнерах с Node/Python. Главное: ваш хостинг обязан держать долгоживущие HTTP-соединения для SSE-запроса GET. Бесплатный тариф Vercel режет на 10 секундах и для этого не подходит. Cloudflare Workers держат потоки неограниченно.

> 🎒 **На пальцах.** Считайте на пальцах: SSE-канал должен жить минутами, а лимит 10 секунд — значит клиент будет переподключаться шесть раз в минуту, и каждый раз переигрывать события. Один параметр тарифа убивает весь транспорт. Проверяйте лимит на длину запроса раньше, чем пишете код.

### Gateway composition

Когда вы ставите перед несколькими MCP-серверами шлюз (Phase 13 · 17), шлюз выглядит как одна точка Streamable HTTP: он переписывает session id и мультиплексирует запросы к вышестоящим серверам. Инструменты объединяются на уровне шлюза; клиент видит один логический сервер.

> 🎒 **На пальцах.** Шлюз — это ресепшен в бизнес-центре: вы звоните на один номер, а внутри вас переключают на нужную контору. Клиент видит один `Mcp-Session-Id`, а шлюз держит у себя таблицу «твоя сессия = сессия 1 у Filesystem + сессия 2 у GitHub». Отсюда и главная работа шлюза — разруливать одинаковые имена инструментов.

### Transport failure modes

- **stdio SIGPIPE.** Смерть дочернего процесса посреди записи поднимает SIGPIPE; серверы должны завершаться аккуратно. Клиенты должны замечать EOF и помечать сессию мёртвой.
- **HTTP 502 / 504.** Cloudflare, nginx и другие прокси отдают их при сбое вышестоящего сервиса. Клиенты Streamable HTTP должны повторить запрос один раз после короткой паузы.
- **SSE connection drop.** TCP RST, таймаут прокси или смена сети у клиента закрывают поток. Клиент переподключается с `Mcp-Session-Id` и опциональным `last-event-id`, чтобы продолжить с места обрыва.
- **Session revocation.** Сервер аннулирует session id; клиент получает 404 на следующем запросе. Клиент обязан заново пройти рукопожатие.
- **Clock skew.** Расчёты TTL ресурсов на клиенте разъезжаются с серверными. Клиент должен считать метки времени сервера единственно верными.

> 🎒 **На пальцах.** Пять режимов отказа делятся на две реакции: «повторить» (502/504, обрыв SSE) и «начать сессию заново» (SIGPIPE, отзыв сессии). Различить их просто по коду: 502 — сервер жив, но споткнулся, повторяем; 404 — сервер вас не помнит, идём на `initialize`. Путать нельзя: бесконечные ретраи на 404 — это цикл, который никогда не сойдётся.

### When to bypass Streamable HTTP

Некоторые компании разворачивают MCP-серверы поверх gRPC или очередей сообщений внутри собственных сетей. Это нестандартно — спецификация MCP формально таких транспортов не описывает. Шлюзы могут показывать наружу поверхность Streamable HTTP для MCP-клиентов, а внутри ходить по gRPC. Держите внешнюю поверхность соответствующей спецификации; трансляцию берёт на себя шлюз.

> 🎒 **На пальцах.** Правило простое: экзотику прячьте за шлюзом. Внутри дата-центра можете хоть по голубиной почте, но клиент снаружи должен видеть обычный `POST /mcp`. Как только вы просите клиента говорить на нестандартном транспорте, вы теряете совместимость со всеми готовыми хостами сразу.

## Use It

`code/main.py` реализует минимальную точку Streamable HTTP на `http.server` (стандартная библиотека). Она обрабатывает POST, GET и DELETE на `/mcp`, выставляет `Mcp-Session-Id` в первом ответе, проверяет `Origin` и отклоняет запросы с origin вне allowlist. Обработчик переиспользует логику диспетчеризации из сервера заметок из урока 07.

Что смотреть:

- Обработчик POST читает тело JSON-RPC, диспетчеризует его и пишет JSON-ответ (вариант с одним ответом; вариант с SSE устроен так же по структуре).
- Проверка `Origin` отклоняет пробный запрос с дефолтным `http://evil.example`, но принимает `http://localhost`.
- Session id — случайные 128-битные hex-строки; состояние каждой сессии сервер держит в памяти.

> 🎒 **На пальцах.** Обратите внимание, что весь этот транспорт влез в стандартную библиотеку — никакого фреймворка. Три метода, один заголовок, один список разрешённых origin. Если в вашем коде на транспорт уходит больше двух сотен строк, скорее всего вы пишете что-то помимо транспорта.

## Exercises

1. Запустите `code/main.py`. Отправьте `initialize` через `curl` и посмотрите на заголовок ответа `Mcp-Session-Id`. Отправьте второй запрос, вернув этот заголовок, и убедитесь, что сессия продолжается.

2. Добавьте обработчик GET, открывающий SSE-поток. Отправляйте одно событие `notifications/progress` каждые пять секунд. Переподключитесь повторным GET с тем же session id и проверьте, что сервер его принимает.

3. Реализуйте логику переигрывания по `last-event-id`. При переподключении отдайте заново все события, появившиеся после этого id.

4. Расширьте проверку `Origin` поддержкой шаблона с подстановкой (`https://*.example.com`) и убедитесь, что она принимает `https://app.example.com`, но отклоняет `https://evil.example.com.attacker.net`.

5. Возьмите legacy-сервер на HTTP+SSE из официального реестра (их там несколько) и набросайте миграцию: что меняется в обработке точек входа, генерации session id и семантике заголовков.

> 🎒 **На пальцах.** Задание 4 — главная ловушка всего урока. Наивная проверка «строка содержит `.example.com`» пропустит `https://evil.example.com.attacker.net`, потому что домен там на самом деле `attacker.net`. Правильно: разобрать URL, взять хост и сравнивать его конец с `.example.com` целиком, а не искать подстроку где попало.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| stdio transport | «Локальный дочерний процесс» | JSON-RPC через stdin/stdout, по одному объекту на строку |
| Streamable HTTP | «Тот самый удалённый транспорт» | Одна точка входа: POST + GET + опциональный SSE, спецификация 2025-03-26 |
| HTTP+SSE | «Legacy» | Двухточечная модель, которую убирают в середине 2026 года |
| `Mcp-Session-Id` | «Заголовок сессии» | Случайный id, выданный сервером и возвращаемый в каждом следующем запросе |
| `Origin` allowlist | «Защита от DNS-rebinding» | Отклонять запросы, чей Origin не одобрен |
| Single endpoint | «Один URL» | `/mcp` обслуживает POST / GET / DELETE для всех операций сессии |
| `last-event-id` | «Переигрывание SSE» | Заголовок для возобновления оборвавшегося потока без потери событий |
| Backwards-compat probe | «Определение старого и нового» | Проверка формы ответа на клиенте, автоматически выбирающая транспорт |
| Long-lived HTTP | «Стриминг по SSE» | Сервер льёт события минуты или часы в одно TCP-соединение |
| Session revocation | «Принудительная переинициализация» | Сервер аннулирует session id; клиент обязан заново пройти рукопожатие |
