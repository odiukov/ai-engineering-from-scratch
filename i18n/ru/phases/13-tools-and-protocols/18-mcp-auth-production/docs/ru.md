# Авторизация MCP в продакшене — регистрация клиентов, обновление JWKS, токены с прибитой аудиторией

> В уроке 16 конечный автомат OAuth 2.1 жил в памяти. К 2026 году любой MCP-сервер, который вы отдаёте настоящей организации, стоит за продакшен-авторизацией: регистрация клиентов, которая масштабируется на неограниченное их число (сначала Client ID Metadata Documents, динамическая регистрация клиентов — как обратно совместимый запасной путь), обнаружение метаданных сервера авторизации (RFC 8414 *или* OpenID Connect Discovery), обновление кеша JWKS, которое не сломает проверку токена в три часа ночи, и токены с прибитой аудиторией, которые не дают переиграть себя против другого ресурса. Этот урок собирает всю поверхность целиком, с тремя ролями — сервер авторизации, сервер ресурсов (он же MCP-сервер) и клиент, — чтобы вы могли проследить каждый переход от обнаружения до проверенного вызова инструмента.
>
> **Spec note (2025-11-25):** ноябрьская спецификация авторизации MCP 2025 года понизила динамическую регистрацию клиентов с `SHOULD` до `MAY` и сделала **Client ID Metadata Documents (CIMD)** рекомендованным механизмом регистрации по умолчанию. Урок учит и тому, и другому, в порядке приоритета из спецификации, а код для разбора оставляет DCR — потому что он полностью самодостаточен внутри одного процесса.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 13 · 16 (OAuth 2.1 state machine), Phase 13 · 17 (gateways)
**Time:** ~90 minutes

## Learning Objectives

- Найти сервер авторизации через метаданные RFC 8414 и проверить контракт.
- Реализовать динамическую регистрацию клиентов по RFC 7591, чтобы MCP-клиенты регистрировались без участия администратора.
- Кешировать и обновлять ключи JWKS по расписанию, чтобы проверка подписи выживала при смене ключей.
- Прибивать токен к одному MCP-ресурсу через resource indicators из RFC 8707 и отказывать в переиспользовании по схеме confused deputy.
- Аккуратно разделить три роли — сервер авторизации, сервер ресурсов, клиент — так, чтобы каждая делала только свои проверки.
- Читать матрицу возможностей IdP и отказываться от деплоя, когда IdP не покрывает профиль авторизации MCP.

## The Problem

Симулятор из урока 16 гоняет OAuth 2.1 в памяти. В продакшене есть три эксплуатационных разрыва, которых симулятор в памяти не видит.

Первый разрыв — регистрация. Настоящая организация держит сотни MCP-серверов и тысячи MCP-клиентов. Никто не будет вручную регистрировать каждого пользователя Cursor как OAuth-клиента. Спецификация 2025-11-25 даёт клиентам порядок приоритетов: если есть заранее зарегистрированный `client_id` — используйте его, иначе **Client ID Metadata Document** (клиент представляется HTTPS-адресом, которым владеет, а сервер авторизации *забирает* метаданные сам), иначе откат на **динамическую регистрацию клиентов по RFC 7591** (клиент *сам присылает* `POST /register` и тут же получает `client_id`), иначе спросите пользователя. CIMD рекомендован по умолчанию, потому что он вообще убирает регистрацию на каждом сервере, сохраняя при этом модель доверия, укоренённую в DNS; DCR оставлен для обратной совместимости. Точку входа оба способа берут из метаданных сервера авторизации: `client_id_metadata_document_supported` для CIMD, `registration_endpoint` для DCR.

Второй разрыв — смена ключей. Проверка JWT опирается на подписывающие ключи сервера авторизации, опубликованные как JSON Web Key Set (JWKS). Сервер авторизации меняет их по расписанию (часто раз в час, иногда чаще, если разбирается с инцидентом). MCP-сервер, который забрал JWKS один раз при старте, проверяет всё нормально — до окна смены ключей, а потом каждый запрос падает до перезапуска. В продакшене JWKS живёт в кеше, а рядом стоит задача обновления, которая перезаписывает кеш до того, как прежние ключи истекут, плюс запасной поход за ключами при промахе кеша — на случай, когда приходит токен, подписанный ключом новее кеша.

Третий разрыв — привязка аудитории. В уроке 16 появились resource indicators из RFC 8707. В продакшене этот индикатор превращается в жёсткую проверку клейма на каждом запросе. MCP-сервер сравнивает `token.aud` со своим каноническим URL ресурса и на расхождении отвечает HTTP 401. Это единственная защита от того, что вышестоящий MCP-сервер (или злонамеренный клиент с токеном, выписанным для другого сервера) переиграет этот токен против другого сервера внутри одной сетки доверия.

Урок раскладывает каждый разрыв на конкретный кусок поверхности. Документ с метаданными — это HTTP-эндпоинт. Обновление кеша JWKS — задача по расписанию плюс кеш «ключ-значение». Проверка JWT — процедура, которую сервер ресурсов выполняет перед вызовом любого инструмента. Держите три роли раздельно, и каждая будет делать только свои проверки: сервер авторизации выписывает и меняет ключи, сервер ресурсов кеширует и проверяет, клиент обнаруживает и регистрируется.

> 🎒 **На пальцах.** Три разрыва легко запомнить по вопросам: «кто ты вообще такой?» (регистрация), «чем проверить подпись сегодня?» (JWKS), «а этот пропуск точно в нашу дверь?» (аудитория). Симулятор в памяти не видит их именно потому, что там один процесс живёт минуту: клиенты заведены руками, ключи не успевают поменяться, а других серверов просто нет. Все три проблемы появляются от того, что система живёт долго и в ней много участников.

## The Concept

### RFC 8414 — OAuth Authorization Server Metadata

Документ по адресу `/.well-known/oauth-authorization-server` описывает всё, что нужно клиенту:

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "registration_endpoint": "https://auth.example.com/register",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["mcp:tools.read", "mcp:tools.invoke"],
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"]
}
```

Клиент, которому дали URL MCP-ресурса, выстраивает цепочку обнаружения: `oauth-protected-resource` из RFC 9728 (документ сервера ресурсов) называет issuer, а `oauth-authorization-server` (этот RFC) называет все эндпоинты. Клиент никогда не прописывает адрес авторизации в коде.

Контракт, который вы проверяете, прежде чем доверить IdP авторизацию для MCP:

- `code_challenge_methods_supported` содержит `S256` (PKCE по RFC 7636). Спецификация тут прямолинейна: если поля **нет**, значит сервер авторизации не поддерживает PKCE, и клиент **MUST** отказаться продолжать.
- `grant_types_supported` содержит `authorization_code` и отвергает `password` и `implicit`.
- Заявлен хотя бы один путь регистрации: `client_id_metadata_document_supported: true` (CIMD, предпочтительно) **или** `registration_endpoint` (DCR по RFC 7591, запасной путь). Годится любой; жёстко требовать DCR больше не нужно.
- `response_types_supported` для OAuth 2.1 — это ровно `["code"]`.

Если `S256` отсутствует, MCP-сервер отказывается разворачиваться против такого IdP: для PKCE нет режима «ну хоть как-нибудь». Если *ни один* путь регистрации не заявлен, а заранее зарегистрированного `client_id` у вас нет, то зарегистрироваться тоже не получится — и виноват тут манифест деплоя, а не код.

> 🎒 **На пальцах.** Этот JSON — как расписание на двери учреждения: где вход, где касса, где выдают справки. Клиент читает его один раз и дальше знает все адреса, вместо того чтобы держать их в своём коде. Обратите внимание, что три пункта контракта из четырёх — это про запреты: `password` и `implicit` не пускаем, `response_types` строго `["code"]`, и без `S256` вообще не работаем.

### RFC 9728 (recap) — Protected Resource Metadata

RFC 9728 разбирался в уроке 16. Разница в продакшене такая: этот документ — единственное место, куда клиент смотрит, чтобы узнать серверы авторизации, которым доверяет *именно этот* MCP-сервер. Один MCP-сервер может принимать токены от нескольких IdP (один для сотрудников, другой для партнёров). RFC 9728 объявляет это множество; RFC 8414 описывает, что умеет каждый IdP.

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com", "https://partners.example.com"],
  "scopes_supported": ["mcp:tools.invoke"],
  "bearer_methods_supported": ["header"],
  "resource_documentation": "https://notes.example.com/docs"
}
```

### Client ID Metadata Documents (the recommended default)

CIMD переворачивает регистрацию из *push* в *pull*. Вместо того чтобы просить сервер авторизации выписать `client_id`, клиент использует **как** свой `client_id` тот HTTPS-адрес, которым он владеет. По адресу лежит JSON-документ с метаданными; сервер авторизации забирает его по необходимости, прямо во время OAuth-потока. Доверие укоренено в DNS: если оператор сервера доверяет `app.example.com`, он доверяет клиенту, который отдаётся с `https://app.example.com/client.json`. Ни лишнего круга на регистрацию, ни пространства имён `client_id`, которое можно исчерпать, ни состояния на каждом сервере, которое надо держать в синхроне.

Документ с метаданными, который хостит клиент:

```json
{
  "client_id": "https://app.example.com/oauth/client.json",
  "client_name": "Example MCP Client",
  "client_uri": "https://app.example.com",
  "redirect_uris": ["http://127.0.0.1:7333/callback", "http://localhost:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

Значение `client_id` внутри документа **MUST** совпадать с URL, откуда документ отдан (сервер авторизации это проверяет; расхождения отклоняются). О поддержке сервер авторизации сообщает полем `client_id_metadata_document_supported: true` в своих метаданных RFC 8414.

Два факта о безопасности, о которых спецификация говорит прямо:

- **SSRF.** Сервер авторизации ходит по URL, который дал ему потенциальный злоумышленник. Он обязан защищаться от server-side request forgery (никаких походов на внутренние и админские эндпоинты).
- **localhost impersonation.** Сам по себе CIMD не мешает локальному злоумышленнику назвать своим адрес метаданных легитимного клиента и привязать любой `localhost`-редирект. Сервер авторизации **MUST** явно показывать хост redirect URI на экране согласия и **SHOULD** предупреждать, когда редиректы ведут только на `localhost`.

Поскольку CIMD не нужно никакого состояния на стороне сервера, здесь нет регистратора, которого приходится поднимать ради DCR. Со стороны клиента всё только на чтение: отдавайте свой документ с метаданными со статического HTTPS-эндпоинта и дайте серверу авторизации забрать его самому.

> 🎒 **На пальцах.** Разница между DCR и CIMD — как между «прийти в бюро и получить номерок» и «показать визитку со своим адресом, который проверяющий может открыть сам». В CIMD `client_id` — это буквально ссылка `https://app.example.com/oauth/client.json`, и требование «`client_id` внутри документа равен адресу документа» закрывает подмену: чужой файл не сможет объявить себя вашим клиентом, потому что лежит по другому адресу.

### RFC 7591 — Dynamic Client Registration (fallback / backwards compatibility)

DCR теперь `MAY`; его держат для обратной совместимости с деплоями до 2025-11-25 и с IdP, которые пока не умеют CIMD. Без него (и без CIMD, и без предварительной регистрации) каждому MCP-клиенту — Cursor, Claude Desktop, вашему самописному агенту — нужен обмен письмами с администратором IdP. С DCR клиент отправляет:

```json
POST /register
Content-Type: application/json

{
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none",
  "scope": "mcp:tools.invoke",
  "client_name": "Cursor",
  "software_id": "com.cursor.cursor",
  "software_version": "0.42.0"
}
```

Сервер отвечает `client_id` и токеном `registration_access_token` для будущих изменений:

```json
{
  "client_id": "c_3e7f1a",
  "client_id_issued_at": 1769472000,
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "registration_access_token": "regt_b2...",
  "registration_client_uri": "https://auth.example.com/register/c_3e7f1a"
}
```

`token_endpoint_auth_method: none` — правильное значение по умолчанию для MCP-клиентов, которые работают на устройстве пользователя. Им достаётся только `client_id` и никакого `client_secret`, который можно было бы утащить. Доказательство владения, нужное публичным клиентам, обеспечивает PKCE.

Три продакшен-грабли:

- Эндпоинт регистрации обязан ограничивать частоту запросов по исходному IP. Без этого враждебный актор скриптом наделает миллионы фальшивых регистраций и исчерпает пространство имён `client_id`. Проверку рейт-лимита ставьте до того, как регистратор возьмётся за запрос.
- `software_statement` (подписанный JWT, который ручается за клиента) требуют некоторые корпоративные IdP. Мок из этого урока его пропускает; в продакшене подключают шаг проверки, который отклоняет неподписанные регистрации от всего, кроме redirect URI на localhost.
- `registration_access_token` надо хранить хешем, а не открытым текстом. Кража этого токена означает, что злоумышленник сможет переписать redirect URI клиента.

> 🎒 **На пальцах.** Смотрите, что происходит без рейт-лимита: эндпоинт `/register` открыт для всех и на каждый запрос создаёт запись. Скрипт с одной машины сделает тысячу регистраций в секунду и за сутки набьёт вам под сто миллионов мусорных клиентов. Отсюда и порядок в подсказке — сначала проверка частоты, потом регистратор, а не наоборот.

### RFC 8707 (recap) — Resource Indicators

В уроке 16 разобрана форма. Продакшен-правило: каждый запрос токена содержит `resource=<canonical-mcp-url>`, а MCP-сервер на каждом вызове проверяет, что `token.aud` совпадает с его собственным URL ресурса. Канонический URI — это *самый конкретный* идентификатор сервера: схема и хост в нижнем регистре, без фрагмента, и по соглашению без слеша на конце. Путь по правилу **не** отрезается — спецификация оставляет его, когда он нужен, чтобы отличить отдельный MCP-сервер. `https://mcp.example.com`, `https://mcp.example.com/mcp`, `https://mcp.example.com:8443` и `https://mcp.example.com/server/mcp` — всё это валидные канонические URI. Выберите по одному на сервер и прибейте `aud` ровно к нему. (Мок из этого урока для краткости использует аудитории вида голого хоста, например `https://notes.example.com`; деплой, где на одном origin живёт несколько MCP-серверов, различает их путём.)

> 🎒 **На пальцах.** Канонический URI — это как полный адрес на конверте: одна и та же квартира, записанная четырьмя способами, — это четыре разных `aud`, и токен подойдёт только к одной записи. Поэтому решение принимают один раз: выбрали `https://notes.example.com/mcp` — значит и в запросе токена, и в проверке на сервере стоит ровно эта строка, без слеша на конце и без верхнего регистра.

### RFC 7636 (recap) — PKCE

В OAuth 2.1 PKCE обязателен. Поток authorization code в этом уроке всегда несёт `code_challenge` и `code_verifier`. Сервер отклоняет любой запрос токена, в котором verifier отсутствует или хешируется не в сохранённый challenge.

> 🎒 **На пальцах.** PKCE работает как чек из камеры хранения: сначала вы оставляете отрывной корешок (`code_challenge` — хеш), потом предъявляете сам секрет (`code_verifier`). Перехватить код авторизации в браузере или в логах мало: без verifier его не обменять на токен, а восстановить verifier из хеша SHA256 нельзя. Именно поэтому публичному клиенту не нужен `client_secret`.

### MCP Spec 2025-11-25 Auth Profile

Спецификация MCP (2025-11-25) точно описывает, что обязан делать слой авторизации MCP-сервера:

- Реализовать метаданные защищённого ресурса по RFC 9728 и сообщать их адрес либо заголовком `WWW-Authenticate: Bearer resource_metadata="..."` на 401, **либо** по well-known-адресу `/.well-known/oauth-protected-resource` (SEP-985 сделал заголовок необязательным при наличии well-known-запасного пути). Поле `authorization_servers` в метаданных **MUST** называть хотя бы один сервер.
- Принимать токены только через `Authorization: Bearer ...` и на **каждом** запросе — никогда в query-строке, никогда с проверкой только при старте сессии.
- Проверять `aud`, `iss`, `exp` и требуемые скоупы на каждом запросе. Сервер **MUST** убедиться, что токен выписан именно для него (аудитория); отсутствующий или несовпадающий `aud` отклоняется и никогда не трактуется как «подходит любому».
- На 401/403 возвращать `WWW-Authenticate: Bearer` с `error=...`, параметром `resource_metadata="<PRM-URL>"` (адрес документа с метаданными, а *не* сам ресурс) и `scope="..."` в случае `insufficient_scope` (403). Обратите внимание: параметр называется `resource_metadata` и указывает на обнаружение — параметра `resource` в этом челлендже нет.
- Обнаружение сервера авторизации принимает **либо** метаданные OAuth по RFC 8414, **либо** OpenID Connect Discovery 1.0; клиенты обязаны пробовать оба well-known-суффикса в порядке приоритета.
- От **mix-up-атак** защищается клиент, а не сервер: он запоминает ожидаемый `issuer` до редиректа и проверяет параметр `iss` в ответе авторизации (RFC 9207) до того, как обменять код. Один PKCE от mix-up не спасает, потому что клиент отдаёт свой `code_verifier` тому эндпоинту токенов, куда его завели.

Черновик OAuth 2.1 — это основа; RFC 8414/7591/8707/9728/9207 плюс RFC 7636 плюс CIMD — это поверхность; спецификация MCP — это профиль.

> 🎒 **На пальцах.** Ключевое слово во втором и третьем пунктах — «на каждом запросе». Соблазн понятен: проверил токен один раз при открытии сессии и дальше гоняешь вызовы быстрее. Но сессия живёт часами, а `exp` у токена — минуты, и за это время токен успевает истечь, а скоупы — измениться. Одна проверка при старте — это пропуск, который охрана смотрит только утром.

### IdP capability matrix

Не каждый IdP поддерживает полный профиль MCP. Матрица ниже фиксирует фактические возможности на момент спецификации 2025-11-25. Это *шлагбаум для деплоя*, а не рекомендация.

CIMD появился в спецификации 2025-11-25, а лежащий под ним черновик OAuth приняли только в октябре 2025 года, так что поддержка у вендоров ещё подъезжает — читайте колонку «CIMD» ниже как «как дела на сегодня, проверьте в своём тенанте», а не как вечную истину.

|---|---|---|---|---|---|---|
| Self-hosted (Keycloak) | да | появляется | да | да (с 24.x) | да | Референсный IdP для профиля MCP в этом уроке; путь DCR работает от начала до конца, CIMD подтягивается за новой спецификацией. |
| Enterprise SSO (Microsoft Entra ID) | да | появляется | да (на премиум-тарифах) | да | да | Доступность DCR зависит от уровня тенанта; проверяйте в целевом тенанте до деплоя. |

Правило отказа для манифеста деплоя: если у выбранного IdP в `code_challenge_methods_supported` нет `S256`, MCP-сервер отказывается стартовать — у PKCE нет ослабленного режима. С регистрацией шлагбаум мягче: вам нужен *один* работающий путь (заранее зарегистрированный `client_id`, `client_id_metadata_document_supported: true` или `registration_endpoint`). Само по себе отсутствие DCR больше не повод для отказа, потому что его закрывают CIMD или предварительная регистрация.

А вот строка про социальные IdP показывает мягкий случай: DCR там «редко», CIMD «нет», но жить можно — берёте их как источник личности и ставите свой сервер авторизации сверху.

### JWKS refresh pattern (rotate at the AS, refresh at the resource server)

Держите два глагола раздельно, потому что их смешение — реальный продакшен-баг:

- **Rotate** — это то, что делает *сервер авторизации*: выпускает новый подписывающий ключ, публикует его в JWKS, позже выводит старый из обращения. Сервер ресурсов в этом не участвует и не может участвовать — приватных ключей IdP у него нет.
- **Refresh** — это то, что делает *сервер ресурсов*: заново делает `GET` опубликованного JWKS в свой кеш. Это вообще единственное действие с JWKS, которое сервер ресурсов когда-либо выполняет.

Продакшен-режим отказа здесь — устаревший кеш. Лечится задачей обновления по расписанию плюс кешем «ключ-значение». Сервер ресурсов запускает задачу (cron, таймер, что даёт ваш рантайм), которая с фиксированным интервалом забирает `<issuer>/.well-known/jwks.json` и перезаписывает `cache[issuer] = {keys, fetched_at}`. Валидатор читает из этого кеша. Токен, чьего `kid` в кеше нет, вызывает **одно** синхронное обновление как запасной путь, после чего проверка повторяется. Это разом закрывает два случая: обновление по расписанию и окна перекрытия ключей, когда токен, подписанный совсем новым ключом, приходит раньше следующего планового обновления.

Запасной путь **обязан быть повторным получением, а не сменой ключей**. Если подвесить на промах кеша выпуск нового ключа, ломаются две вещи: (1) свежий ключ даёт `kid`, который *всё равно* не совпадает с токеном, так что поиск снова провалится; и (2) злоумышленник, который сыплет токенами со случайными `kid`, заставляет вас бесконечно создавать ключи — это DoS своими руками. Повторное получение идемпотентно, поэтому фальшивый `kid` стоит максимум одного лишнего запроса.

Форма кеша:

```json
{
  "https://auth.example.com": {
    "keys": [
      {"kid": "k_2026_03", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"},
      {"kid": "k_2026_04", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"}
    ],
    "fetched_at": 1772668800
  }
}
```

Два ключа одновременно — это нормальное состояние. Серверы авторизации меняют ключи так: сначала вводят следующий (`k_2026_04`), и только потом выводят предыдущий (`k_2026_03`), чтобы токены, выписанные под старым ключом, оставались валидными до своего истечения. Кеш держит объединение; валидатор выбирает по `kid`.

> 🎒 **На пальцах.** Смена ключей похожа на замену замка в подъезде: неделю работают оба, чтобы у людей со старыми ключами было время получить новые. В кеше поэтому лежат два `kid` сразу, а валидатор просто берёт нужный. И запомните разницу глаголов: сервер ресурсов не имеет права «сделать новый ключ», он умеет только «перечитать список» — второе идемпотентно, первое превращает мусорный запрос в бесконечную фабрику ключей.

### The validation routine

MCP-сервер выполняет проверку до вызова любого инструмента. Форма, которую использует `code/main.py`:

```python
result = server.validate(bearer_token, required_scope="mcp:tools.invoke")
if not result["valid"]:
    return {"status": result["status"], "WWW-Authenticate": result["www_authenticate"]}
```

`validate` разбирает JWT, находит подписывающий ключ в кеше JWKS (при промахе обновляя его один раз), проверяет подпись, а затем сверяет `iss` со списком разрешённых, `aud` с каноническим ресурсом этого сервера, `exp` и требуемый скоуп — возвращая челлендж `WWW-Authenticate` на первом же провале. Оформить это одной процедурой на сервере ресурсов важно затем, чтобы любая точка входа (каждый вызов инструмента, каждый транспорт) проходила одни и те же проверки; пути, ведущего к инструменту без проверки, просто не существует.

> 🎒 **На пальцах.** Обратите внимание на форму кода: три строки, и ни одного `if` про конкретный инструмент. Все проверки собраны в одном месте, поэтому добавление нового инструмента не может случайно открыть чёрный ход. Так же работает единственная дверь с рамкой металлоискателя: пока входов пять, кто-нибудь однажды забудет включить рамку на пятом.

### Audience-replay walkthrough (access-token privilege restriction)

Сервер A (`notes.example.com`) и сервер B (`tasks.example.com`) зарегистрированы на одном сервере авторизации. Сервер A скомпрометирован. Злоумышленник берёт пользовательский токен для заметок и переигрывает его против сервера B.

Валидатор сервера B:

1. Разбирает JWT, забирает JWKS по `kid`, проверяет подпись.
2. Сверяет `iss` со списком `authorization_servers` из своих метаданных защищённого ресурса. (Проходит — тот же IdP.)
3. Проверяет `aud == "https://tasks.example.com"`. (Провал — в токене `aud` равен `https://notes.example.com`.)
4. Возвращает 401 с `WWW-Authenticate: Bearer error="invalid_token", error_description="audience mismatch", resource_metadata="https://tasks.example.com/.well-known/oauth-protected-resource"`.

Клейм аудитории — единственная защита от этой атаки на уровне протокола. Пропустить его ради производительности — самая частая продакшен-ошибка; валидатор должен работать на каждом запросе, а не только при старте сессии. Спецификация называет это **access-token privilege restriction**: MCP-сервер `MUST` отклонить любой токен, который не называет его в аудитории.

> **Naming note.** Термин *confused deputy* спецификация оставляет за похожей, но другой проблемой: MCP-сервер работает OAuth-**прокси** к сторонним API, использует статический client ID и пробрасывает токен, не получив согласия пользователя для каждого клиента. Привязка аудитории лечит переигрывание, описанное выше; confused deputy лечится согласием на каждого клиента **плюс** правилом никогда не пробрасывать входящий токен во внешние API (MCP-сервер `MUST` получить собственный отдельный токен для вышестоящего сервиса).

> 🎒 **На пальцах.** Пройдите четыре шага глазами: подпись верна, issuer тот же, и всё равно 401 — потому что на третьем шаге строки `https://tasks.example.com` и `https://notes.example.com` не совпали. Один клейм из четырёх остановил кражу. Это как настоящий пропуск с чужой фотографией: печать подлинная, выдан вашим же бюро, но не тому человеку.

### Mix-up attacks (a client-side defense the server cannot provide)

Клиент за свою жизнь общается с множеством серверов авторизации. Злонамеренный AS может попытаться заставить клиента обменять код авторизации, выданный честным AS, на эндпоинте токенов злоумышленника. Привязка аудитории здесь не помогает — атака происходит раньше, чем появляется хоть какой-то токен. Защита живёт в клиенте (RFC 9207):

1. Перед редиректом клиент запоминает ожидаемый `issuer` из проверенных метаданных AS.
2. В ответе авторизации клиент сравнивает вернувшийся параметр `iss` с этим запомненным issuer (простым сравнением строк, без нормализации) — и только потом куда-либо отправляет код.
3. Не совпало (или `iss` отсутствует, хотя AS заявлял `authorization_response_iss_parameter_supported`) → отклоняем, и даже поля `error` не показываем.

Один PKCE от mix-up не спасает, потому что клиент отдаёт свой `code_verifier` тому эндпоинту токенов, куда его завели. Именно поэтому спецификация велит запоминать issuer на каждый запрос — рядом с PKCE-verifier и `state`.

> 🎒 **На пальцах.** Mix-up — это как позвонить в банк по номеру из фишингового письма и продиктовать туда код из СМС: код настоящий, банк настоящий, а трубку взяли не те. Защита ровно такая же, как в жизни: запомнить, куда вы собирались звонить, до звонка, и сверить, кто ответил. Сервер ресурсов вам тут не поможет — на момент атаки токена ещё нет.

### Failure modes

- **Stale JWKS.** Валидатор отклоняет валидные токены после смены ключа на AS. Лечится описанной выше связкой «обновление по расписанию + повторное получение при промахе кеша». Никогда не кешируйте JWKS без задачи обновления.
- **Rotate-as-fall-back.** Подвесить на промах кеша выпуск нового ключа вместо повторного получения — реальный баг: нужного `kid` это не создаёт никогда, а `kid`, которыми управляет злоумышленник, превращает в DoS через создание ключей. Запасным путём должен быть идемпотентный `refresh-jwks`.
- **Missing `aud` claim.** Некоторые IdP по умолчанию не кладут `aud`, если в запросе токена нет `resource`. Валидатор обязан отклонять токены без `aud`, а не считать его отсутствие «подходит любому».
- **Mix-up via missing `iss` check.** Клиент, который не сверяет параметр `iss` из ответа авторизации (RFC 9207) с issuer, запомненным до редиректа, можно завести на обмен кода честного AS у злоумышленника. Это провал на стороне клиента; сервер ресурсов его не компенсирует.
- **Scope upgrade race.** Два одновременных потока повышения прав для одного пользователя могут оба завершиться успешно и выдать два токена доступа с разными скоупами. Валидатор обязан работать с токеном, предъявленным в запросе, а не смотреть «текущий скоуп пользователя» — иначе получается окно TOCTOU.
- **Registration token theft.** Утёкший `registration_access_token` позволяет злоумышленнику переписать redirect URI. Храните их хешем, требуйте от клиента открытое значение на каждое изменение, меняйте при малейшем подозрении.
- **`iss` not pinned.** Валидатор, который принимает любой `iss`, позволяет злоумышленнику поднять собственный сервер авторизации, зарегистрировать там клиента на нужную аудиторию и выписывать токены. Список разрешённых — это `authorization_servers` из метаданных защищённого ресурса; следите за его соблюдением.

> 🎒 **На пальцах.** Семь режимов отказа делятся на две кучки: четыре — про то, что проверка не сделана (`aud`, `iss`, скоуп из запроса, `iss` на клиенте), и три — про то, что кеш и токены живут неправильной жизнью. Полезное упражнение: для каждого пункта назовите одну строку кода, которая его закрывает. Почти везде это одна строка сравнения — поэтому такие баги и доезжают до продакшена, их слишком легко не написать.

```figure
t3-jwks-rotate
```

## Use It

`code/main.py` проходит полный продакшен-поток на stdlib Python с тремя ролями — `AuthorizationServer`, `ResourceServer` и `Client`. Поток такой:

1. Сервер авторизации публикует метаданные RFC 8414 по адресу `/.well-known/oauth-authorization-server`.
2. MCP-клиент вызывает эндпоинт метаданных и проверяет свои варианты регистрации (`client_id_metadata_document_supported` для CIMD, `registration_endpoint` для DCR) и поддержку PKCE `S256`.
3. Разбор идёт по запасному пути DCR: клиент отправляет `POST` на `/register` (RFC 7591) и получает `client_id`. (CIMD-клиент вместо этого предъявил бы свой HTTPS-адрес в роли `client_id` и пропустил бы этот шаг.)
4. MCP-клиент проходит поток authorization code под защитой PKCE (RFC 7636) с индикатором `resource` (RFC 8707).
5. MCP-клиент вызывает инструмент на MCP-сервере с заголовком `Authorization: Bearer ...`.
6. MCP-сервер выполняет `validate`, находя подписывающий ключ в кеше JWKS.
7. IdP меняет ключ; обновление по расписанию заново затягивает JWKS в кеш.
8. Следующий вызов проверяется по обновлённым ключам без перезапуска, а прежний токен продолжает проходить проверку в окне перекрытия.
9. Попытка переиграть токен против другого MCP-ресурса получает 401 с `audience mismatch` и указателем `resource_metadata`.

JWT здесь использует HS256 с общим секретом (чтобы урок запускался на одной стандартной библиотеке). В продакшене берут RS256 или EdDSA вместе с описанным выше паттерном JWKS; логика проверки при этом та же. Поскольку IdP и сервер ресурсов живут в одном процессе, `refresh_jwks` читает список ключей сервера авторизации напрямую; по сети это был бы HTTP `GET` на `jwks_uri`.

> 🎒 **На пальцах.** Шаги 6-8 — это ровно тот сценарий, который валит продакшен: ключ поменялся, а сервис работает дальше. Проследите по демо, что перезапуска нигде нет и что старый токен в шаге 8 всё ещё валиден — именно за это отвечает перекрытие двух ключей в кеше. Если бы AS выводил старый ключ мгновенно, все выписанные минуту назад токены умерли бы разом.

7. Реализуйте клиентскую проверку `iss` из RFC 9207, описанную в разделе про mix-up: запомните ожидаемый issuer до запроса авторизации, а потом отклоните ответ авторизации, чей `iss` не совпал.

> 🎒 **На пальцах.** Шестое задание стоит сделать честно, с обеими половинами. Отправьте сто токенов со случайными `kid`: в правильной версии число ключей на AS останется тем же, а запросов на обновление будет максимум сто (по одному на токен). В сломанной версии вы получите сто новых ключей, ни один из которых ничего не проверяет. Разница между идемпотентной операцией и неидемпотентной — вот она, в двух числах.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| ASM | «Документ метаданных OAuth» | JSON по адресу `/.well-known/oauth-authorization-server` из RFC 8414 |
| CIMD | «URL с метаданными клиента» | Client ID Metadata Document — HTTPS-адрес, используемый как `client_id`; AS сам забирает этот JSON. Рекомендованное значение по умолчанию с 2025-11-25 |
| DCR | «Самостоятельная регистрация клиента» | Поток `POST /register` из RFC 7591; в 2025-11-25 понижен до запасного `MAY` |
| JWKS | «Публичные ключи для проверки JWT» | JSON Web Key Set, забирается с `jwks_uri`, индексируется по `kid` |
| Rotate vs refresh | «Обновление ключей» | *Rotate* = AS выпускает и выводит подписывающие ключи; *refresh* = сервер ресурсов заново получает опубликованный набор. Серверы ресурсов только refresh, и ничего больше |
| Resource indicator | «Параметр аудитории» | Параметр `resource` из RFC 8707, прибивающий токен к одному серверу |
| `aud` claim | «Аудитория» | Клейм JWT, который валидатор сравнивает с каноническим URL ресурса |
| Audience replay | «Переигрывание токена» | Токен, выписанный для сервера A, предъявляют серверу B; защита — проверка аудитории (в спецификации: access-token privilege restriction) |
| Confused deputy | «Злоупотребление токеном через прокси» | MCP-прокси со статическим client ID пробрасывает токен без согласия на каждого клиента; это не то же самое, что переигрывание аудитории |
| Mix-up attack | «Не тот эндпоинт токенов» | Клиента заводят обменять код честного AS у злоумышленника; защита на стороне клиента через `iss` из RFC 9207 |
| `iss` allow-list | «Доверенные серверы авторизации» | Множество, названное в `authorization_servers` метаданных защищённого ресурса |
| `resource_metadata` | «Где искать документ PRM» | Параметр `WWW-Authenticate`, называющий адрес метаданных RFC 9728 на 401/403 |
| Public client | «Нативный или браузерный клиент» | OAuth-клиент без `client_secret`; компенсирует PKCE |
| `WWW-Authenticate` | «Заголовок ответа 401/403» | Несёт директивы `Bearer error=...`, по которым клиент понимает, как восстанавливаться |
