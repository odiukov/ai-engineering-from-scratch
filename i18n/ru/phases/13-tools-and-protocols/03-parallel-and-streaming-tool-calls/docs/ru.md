# Параллельные вызовы инструментов и стриминг с инструментами

> Три независимых запроса погоды, выполненных по очереди, — это три похода к модели. Запустите их параллельно, и общее время сожмётся до одного самого медленного вызова. Сегодня любой передовой провайдер умеет выдавать несколько вызовов инструментов за один ход. Выгода настоящая, а вот проводка тонкая. Урок разбирает обе половины: параллельный веер и сборку аргументов из стрима, с упором на ловушку сопоставления по id.

**Type:** Build
**Languages:** Python (stdlib, thread pool + streaming harness)
**Prerequisites:** Phase 13 · 02 (function calling deep dive)
**Time:** ~75 minutes

## Learning Objectives

- Объяснить, зачем существует `parallel_tool_calls: true` и когда его нужно выключать.
- Сопоставлять куски аргументов из стрима с правильным id вызова во время параллельного веера.
- Собирать частичные строки `arguments` в целый JSON, не разбирая их раньше времени.
- Прогнать бенчмарк на трёх городах, который показывает разницу задержки между последовательным и параллельным режимом.

## The Problem

Без параллельных вызовов агент, отвечающий на вопрос «какая погода в Бангалоре, Токио и Цюрихе», делает так:

```
user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer
```

Три похода к LLM, и каждый вдобавок платит задержкой исполнителя. Примерно четырёхкратное время по часам от идеального.

> 🎒 **На пальцах.** Это как звонить в справочную три раза подряд: набрал, спросил про Бангалор, положил трубку, набрал снова. Каждый круг — это и время на дозвон (поход к модели), и время на ответ (работа инструмента). Четыре хода вместо одного.

С параллельными вызовами:

```
user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer
```

Один поход к LLM. Время исполнителей — максимум из трёх, а не сумма. Продакшен-бенчмарки на OpenAI, Anthropic и Gemini показывают сокращение времени по часам на 60-70 % на веерных задачах.

> 🎒 **На пальцах.** Теперь вы звоните один раз и спрашиваете про все три города сразу, а справочная поручает их трём разным сотрудникам. Если запросы занимали 400, 600 и 800 мс, по очереди это 1800 мс, а разом — 800 мс. Экономия 55 %, и она растёт с числом городов.

Цена — сложность сопоставления. Когда три вызова заканчиваются не в том порядке, в котором их отправили, каждый результат обязан нести подходящий `tool_call_id`, чтобы модель разложила ответы по местам. Когда результаты приходят стримом, вы обязаны собрать обрывки аргументов в целый JSON до того, как что-то выполнять. Gemini 3 добавил уникальные id отчасти ради реальной проблемы: два параллельных вызова одного и того же инструмента было невозможно отличить друг от друга.

> 🎒 **На пальцах.** Представьте гардероб без номерков: три человека сдали три одинаковых чёрных куртки. Пока номерков нет, вернуть их правильным владельцам нельзя — ровно это и происходило в Gemini 2, где вызовы сопоставлялись по имени инструмента. Два вызова `get_weather` подряд — и имя перестаёт быть номерком.

## The Concept

### Enabling parallel

- **OpenAI.** `parallel_tool_calls: true` включён по умолчанию. Поставьте `false`, чтобы принудительно сделать вызовы последовательными.
- **Anthropic.** Параллельность через `disable_parallel_tool_use: false` (по умолчанию так на Claude 3.5 и выше). Поставьте `true` для последовательного режима.
- **Gemini.** Параллельность доступна всегда; `tool_config.function_calling_config.mode = "AUTO"` отдаёт решение модели.

Выключайте параллельность, когда у инструментов есть зависимости по порядку (`create_file`, потом `write_file`), когда вывод одного вызова становится входом другого или когда ограничитель частоты не выдерживает веер.

> 🎒 **На пальцах.** У Anthropic флаг перевёрнут: у OpenAI `true` означает «можно параллельно», а у Anthropic `true` означает «нельзя». Одна и та же настройка, противоположные значения — на этом ошибаются постоянно. И запомните пример с файлом: писать в файл, который ещё не создан, параллельно бессмысленно, тут нужен строгий порядок.

### Id correlation

У каждого вызова, который выдаёт модель, есть `id`. Каждый результат, который возвращает хост, обязан содержать тот же самый id. Без этого результаты неоднозначны.

- **OpenAI.** `tool_call_id` в каждом сообщении с ролью tool.
- **Anthropic.** `tool_use_id` в каждом блоке `tool_result`.
- **Gemini.** `id` в каждом `functionResponse` (Gemini 3 и выше; Gemini 2 сопоставлял по имени, и на параллельных вызовах с одинаковым именем это ломалось).

> 🎒 **На пальцах.** Три провайдера, три названия одного и того же поля: `tool_call_id`, `tool_use_id`, `id`. Смысл один — номерок из гардероба. Если вы вернёте результат без него или с чужим номерком, модель спокойно приклеит погоду Цюриха к Токио и напишет уверенный неверный ответ.

### Running calls concurrently

Хост запускает исполнителя каждого вызова в своём потоке, корутине или на удалённом воркере. Самая простая обвязка — пул потоков; в продакшене берут asyncio с `asyncio.gather` или структурную конкурентность. Порядок завершения предсказать нельзя — опознавательный знак только id.

> 🎒 **На пальцах.** Пул потоков — это трое курьеров, которых вы отправили одновременно и ждёте у двери. Кто вернётся первым, вы не знаете: тот, у кого дорога короче. Поэтому нельзя полагаться на «первый пришедший ответ — это первый вызов»; надо смотреть на id.

Частый баг: отвечать результатами в порядке списка вызовов вместо порядка завершения. Обычно это работает, потому что модель смотрит только на `tool_call_id`, но если результат потерялся или продублировался, отправка не по порядку сильно усложняет отладку. Лучше отвечать в порядке завершения и с явными id.

> 🎒 **На пальцах.** Разница как между «раздать куртки в том порядке, в котором их сдавали» и «раздать по номеркам, как только каждая нашлась». Второй способ ещё и быстрее: результат уходит модели сразу, а не ждёт самого медленного соседа.

### Streaming tool calls

Когда модель стримит, `arguments` приходят кусками. Три отдельных потока кусков для трёх параллельных вызовов перемешиваются в одном проводе. Вам нужен отдельный накопитель на каждый id.

Форма по провайдерам:

- **OpenAI.** Каждый кусок — это `choices[0].delta.tool_calls[i].function.arguments` (частичная строка). В куске есть `index` (позиция в списке вызовов). Вы накапливаете по index, читаете `id`, когда он впервые появляется, и разбираете JSON, когда `finish_reason = "tool_calls"`.
- **Anthropic.** События стрима: сперва `message_start`, затем по одному `content_block_start` на блок с типом `tool_use` (внутри — id, имя, пустой input). События `content_block_delta` несут куски `input_json_delta`. `content_block_stop` закрывает каждый блок.
- **Gemini.** `streamFunctionCallArguments` (Gemini 3 и выше) выдаёт куски с полем `functionCallId`, так что вызовы аккуратно перемешиваются. До Gemini 3 стриминг возвращал по одному целому вызову за раз.

> 🎒 **На пальцах.** Представьте, что три человека диктуют вам адреса в одну трубку, вперемешку по слогам. Единственный способ не перепутать — вести три листка и подписать их именами говорящих. Накопитель по id — это и есть три листка; у OpenAI подпись сначала приходит как `index`, у Anthropic и Gemini — сразу как id.

### Partial JSON and the parse-early trap

Разбирать `arguments` нельзя, пока строка не дописана. Частичный JSON вида `{"city": "Beng` невалиден и выбросит исключение. Правильный шлагбаум — сигнал конца вызова от провайдера: `finish_reason = "tool_calls"` у OpenAI, `content_block_stop` у Anthropic или событие конца стрима у Gemini. Только после этого пробуйте `json.loads`. Более надёжный вариант — инкрементальный парсер JSON, который выдаёт события по мере того, как структура достраивается; руководство OpenAI по стримингу советует именно это для интерфейса с живым индикатором «думаю». Подсчёт скобок как проверка полноты ненадёжен (скобки внутри строк в кавычках или экранированный текст дают ложные срабатывания) и годится только как грубая отладочная эвристика.

> 🎒 **На пальцах.** Это как читать письмо, которое ещё печатают: «переведи 100» — а через секунду допечатали «000 рублей». Строка `{"city": "Beng` разберётся не в «Бангалор», а в исключение. И не считайте фигурные скобки: в аргументе `{"note": "смайлик }"}` скобка внутри кавычек соврёт вам, что объект закрыт.

### Out-of-order completion

```
call_A: fast API, returns first
call_B: slow API, returns second
call_C: median API, returns third
```

Ответ хоста всё равно обязан ссылаться на id:

```
[{role: "tool", tool_call_id: "call_A", content: ...},
 {role: "tool", tool_call_id: "call_B", content: ...},
 {role: "tool", tool_call_id: "call_C", content: ...}]
```

Порядок в ответе не влияет на корректность ни у OpenAI, ни у Anthropic. Gemini принимает любой порядок, лишь бы совпадали id.

> 🎒 **На пальцах.** Три вызова закончились в порядке A, B, C по скорости API, но в ответе они могут стоять как угодно — модель читает `tool_call_id`, а не позицию. Это освобождает вам руки: собирайте ответы по мере готовности и не выстраивайте их обратно в исходный порядок.

### Benchmark: sequential vs parallel

Обвязка в `code/main.py` имитирует трёх исполнителей с задержками 400, 600 и 800 мс. Последовательный прогон занимает 1800 мс. Параллельный — max(400, 600, 800) = 800 мс. Разница постоянная, а не пропорциональная, поэтому с ростом числа инструментов экономия растёт.

> 🎒 **На пальцах.** Посчитайте сами: 400 + 600 + 800 = 1800 против 800, то есть в 2,25 раза быстрее. Добавьте четвёртый инструмент на 500 мс — последовательно станет 2300 мс, а параллельно останется 800 мс. Именно поэтому у агента с десятью инструментами выигрыш кажется почти волшебным.

Оговорка из реальной жизни: параллельные вызовы нагружают внешние API. Веер из десяти вызовов к сервису с лимитом частоты просто упадёт. Phase 13 · 17 разбирает создание обратного давления на уровне шлюза; семантика повторов запланирована в одной из следующих фаз.

> 🎒 **На пальцах.** Если у API лимит пять запросов в секунду, а вы выстрелили десятью разом, половина вернёт 429 и вы потеряете больше времени на повторах, чем сэкономили на параллельности. Параллельность — это газ, а лимитер — дорога: газ имеет смысл ровно до её ширины.

### Streaming fan-out wall-clock

Если модель сама стримит, вы можете начать выполнять вызов сразу, как только у него дописались аргументы, а не ждать, пока дострумятся все вызовы. Это оптимизация, которую OpenAI описывает в документации, но не все SDK её открывают наружу. Обвязка этого урока так и делает: как только имитированный стрим выдал целый объект аргументов, хост запускает этот вызов.

```figure
tp-parallel-fanout
```

> 🎒 **На пальцах.** Это как начать варить макароны, не дослушав весь список покупок: первый пункт понятен — можно действовать. Если аргументы Бангалора дописались на 200 мс раньше остальных, вы стартуете его API на 200 мс раньше и ровно столько же выигрываете в конце.

## Use It

В `code/main.py` две половины. Первая прогоняет три имитированных запроса погоды последовательно и параллельно через `concurrent.futures.ThreadPoolExecutor` и печатает время по часам. Вторая проигрывает поддельный стриминговый ответ — куски `arguments` для трёх параллельных вызовов, перемешанные в одном стриме, — и собирает их по id с помощью `StreamAccumulator`. Никакой LLM, никакой сети, только логика сборки.

Что смотреть:

- Последовательный таймер показывает 1,8 секунды. Параллельный на тех же поддельных задержках — 0,8 секунды.
- Накопитель переживает куски, приходящие не по порядку: он буферизует их по id и разбирает JSON только тогда, когда у конкретного вызова строка дописана.
- Исполнитель стартует сразу, как только у очередного id аргументы дописаны, а не после конца всех стримов.

> 🎒 **На пальцах.** Обратите внимание, что весь урок работает без единого сетевого запроса: задержки имитированы, стрим поддельный. Это сделано специально — ошибки сопоставления по id ловятся именно в такой песочнице, где вы точно знаете, какой кусок к какому вызову относится.

По вашему реестру инструментов навык проверяет, какие инструменты безопасно распараллеливать, у каких есть зависимости по порядку, а какие задавят внешние лимиты частоты, — и возвращает исправленный реестр с флагом `parallel_safe` у каждого инструмента.

## Exercises

1. Запустите `code/main.py` и меняйте имитированные задержки. Убедитесь, что отношение параллельного времени к последовательному примерно равно `max/sum` (реальные прогоны немного отходят от идеала из-за планировщика потоков, сериализации и накладных расходов обвязки). При каком распределении задержек параллельность перестаёт что-либо давать?

2. Расширьте накопитель на случай «вызов отменили посреди стрима»: сбрасывайте его буфер и выдавайте событие `cancelled`. Какой провайдер описывает этот случай явно? Посмотрите семантику `content_block_stop` у Anthropic и поведение `finish_reason: "length"` у OpenAI.

3. Замените пул потоков на `asyncio.gather`. Прогоните бенчмарк для обоих. На async вы должны увидеть небольшой выигрыш за счёт более дешёвого переключения контекста, но только если исполнители делают настоящий ввод-вывод.

4. Выберите два инструмента, которые распараллеливать НЕЛЬЗЯ (например, `create_file`, а затем `write_file`). Добавьте в реестр граф `ordering_dependency` и пропускайте параллельный веер только через этот граф. Это минимальная машинерия для планирования с учётом зависимостей, которую одна из следующих фаз по агентам оформит как следует.

5. Прочитайте раздел OpenAI про параллельный вызов функций и документацию Anthropic про `disable_parallel_tool_use`. Найдите тот единственный реальный тип инструментов, для которого Anthropic советует отключать параллельность. (Подсказка: изменения с последствиями над одним и тем же ресурсом.)

> 🎒 **На пальцах.** Начните с первого задания — оно даёт интуицию за одну минуту. Поставьте задержки 500, 500, 500: последовательно 1500 мс, параллельно 500 мс, выигрыш втрое. А теперь 1500, 10, 10: последовательно 1520 мс, параллельно 1500 мс — экономия всего 1 %. Параллельность помогает ровно тогда, когда вызовы сравнимы по времени.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Parallel tool calls | «Веер за один ход» | Модель выдаёт несколько вызовов инструментов в одном сообщении ассистента |
| `parallel_tool_calls` | «Флаг OpenAI» | Включает или выключает выдачу нескольких вызовов сразу |
| `disable_parallel_tool_use` | «Обратный флаг Anthropic» | Флаг отказа; по умолчанию параллельность включена |
| Tool call id | «Ручка сопоставления» | Идентификатор вызова, который сообщение с результатом обязано повторить |
| Accumulator | «Буфер стрима» | Строковый буфер на каждый id для частичных кусков `arguments` |
| Out-of-order completion | «Кто быстрее, тот первый» | Параллельные вызовы завершаются в непредсказуемом порядке; склеивают их id |
| Dependency graph | «Ограничения порядка» | Инструменты, чей вывод идёт на вход другим; параллелить их нельзя |
| Parse-early trap | «JSON.parse взорвался» | Попытка разобрать недописанную строку `arguments` |
| `streamFunctionCallArguments` | «Фича Gemini 3» | Куски аргументов в стриме с уникальным id на каждый вызов |
| Completion-order reply | «Не ждать всех» | Отвечать результатами по мере их прихода, привязывая их к id |
