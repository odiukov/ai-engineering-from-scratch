# Суммаризация текста

> Extractive-системы говорят, что было сказано в документе. Abstractive-системы говорят, что автор имел в виду. Разные задачи, разные ловушки.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 5 · 02 (BoW + TF-IDF), Phase 5 · 11 (Machine Translation)
**Time:** ~75 minutes

## The Problem

В вашу ленту прилетела новостная статья на 2000 слов. Вам нужны 120 слов, которые её передают. Можно либо выбрать три самых важных предложения из статьи (extractive), либо пересказать содержание своими словами (abstractive). И то и другое называется суммаризацией. Это совершенно разные задачи.

Extractive-суммаризация — задача ранжирования. Оцениваем каждое предложение, возвращаем топ-`k`. Выход всегда грамматически правильный, потому что взят дословно. Риск в том, что можно упустить содержание, размазанное по всей статье.

Abstractive-суммаризация — задача генерации. Трансформер порождает новый текст, обусловленный входом. Выход беглый и хорошо сжатый, но может выдумать факты, которых в источнике не было. Риск — уверенная выдумка.

Этот урок строит и то и другое, вместе с фирменным режимом отказа каждого подхода.

> 🎒 **На пальцах.** Посчитайте сжатие: 2000 слов в 120 — это примерно в 17 раз. Extractive-подход обязан выбрать те самые 6% текста, которые несут смысл; abstractive может переписать всё компактнее и уложиться свободнее. Разница как между «подчеркнуть три предложения маркером» и «пересказать статью другу за минуту».

## The Concept

![Extractive TextRank vs abstractive transformer](../assets/summarization.svg)

**Extractive.** Смотрим на статью как на граф: узлы — предложения, рёбра — их похожесть. Прогоняем по графу PageRank (или что-то похожее) и оцениваем предложения по тому, насколько сильно они связаны со всеми остальными. Предложения с наибольшей оценкой и есть выжимка. Каноническая реализация — **TextRank** (Михалча и Тарау, 2004).

**Abstractive.** Дообучаем трансформер encoder-decoder (BART, T5, Pegasus) на парах «документ — выжимка». На инференсе модель читает документ и порождает выжимку токен за токеном через cross-attention. Pegasus вдобавок использует предобучение с пропуском предложений, из-за чего он отлично суммаризует почти без дообучения.

Оценка через **ROUGE** (Recall-Oriented Understudy for Gisting Evaluation). ROUGE-1 и ROUGE-2 считают пересечение по униграммам и биграммам. ROUGE-L считает самую длинную общую подпоследовательность. Больше — лучше, но 40 ROUGE-L это «хорошо», а 50 — «выдающееся». Все три числа приводят в каждой статье. Используйте пакет `rouge-score`.

> 🎒 **На пальцах.** PageRank по предложениям работает как выборы, где голосуют не люди, а предложения. Каждое предложение отдаёт свой голос тем, на кого похоже, и вес голоса зависит от того, сколько голосов набрал сам голосующий. Предложение, которое перекликается со всей статьёй, соберёт больше всех — обычно это и есть главная мысль.

> 🎒 **На пальцах.** Разница между ROUGE-2 и ROUGE-L на примере. Эталон «кот сидел на коврике», выжимка «кот тихо сидел на коврике». По биграммам совпало 2 из 4 («сидел на», «на коврике»), ROUGE-2 около 0.5. По самой длинной общей подпоследовательности совпало 4 слова из 4 — вставленное слово ничего не сломало, ROUGE-L около 0.9. Поэтому ROUGE-L терпимее к перефразированию.

## Build It

### Step 1: TextRank (extractive)

```python
import math
import re
from collections import Counter


def sentence_split(text):
    return re.split(r"(?<=[.!?])\s+", text.strip())


def similarity(s1, s2):
    t1 = s1.lower().split()
    t2 = s2.lower().split()
    intersection = sum((Counter(t1) & Counter(t2)).values())
    # Михалча и Тарау нормируют на длину предложения в словах, а не на размер
    # словаря. len(Counter(...)) считал бы только различные слова.
    denom = math.log(len(t1) + 1) + math.log(len(t2) + 1)
    if denom == 0:
        return 0.0
    return intersection / denom


def textrank(text, top_k=3, damping=0.85, iterations=50, epsilon=1e-4):
    sentences = sentence_split(text)
    n = len(sentences)
    if n <= top_k:
        return sentences

    sim = [[0.0] * n for _ in range(n)]
    for i in range(n):
        for j in range(n):
            if i != j:
                sim[i][j] = similarity(sentences[i], sentences[j])

    scores = [1.0] * n
    for _ in range(iterations):
        new_scores = [1 - damping] * n
        for i in range(n):
            total_out = sum(sim[i]) or 1e-9
            for j in range(n):
                if sim[i][j] > 0:
                    new_scores[j] += damping * sim[i][j] / total_out * scores[i]
        converged = max(abs(s - ns) for s, ns in zip(scores, new_scores)) < epsilon
        scores = new_scores
        if converged:
            break

    ranked = sorted(range(n), key=lambda k: scores[k], reverse=True)[:top_k]
    ranked.sort()
    return [sentences[i] for i in ranked]
```

Стоит назвать две вещи. Функция похожести использует пересечение слов, нормированное логарифмами, — это исходный вариант из TextRank. Косинус между TF-IDF-векторами тоже работает. Коэффициент затухания 0.85 и число итераций — значения по умолчанию из PageRank.

> 🎒 **На пальцах.** Разберём `similarity` на числах. Два предложения по 10 слов, общих слов 4. Тогда числитель равен 4, знаменатель `log(11) + log(11) ≈ 2.40 + 2.40 = 4.80`, похожесть примерно 0.83. Логарифмы в знаменателе нужны, чтобы длинные предложения не выигрывали автоматически: у пары предложений по 40 слов с теми же 4 общими похожесть упадёт до 0.54. И обратите внимание, что в знаменателе стоит `len(t1)` — длина предложения в словах, а не число различных слов: повторяющееся слово всё равно добавляет предложению длины. Если бы там стояло `len(Counter(t1))`, у болтливого предложения с повторами знаменатель оказался бы меньше, а похожесть — искусственно завышенной. Нормировка именно на длину в словах — это оригинальный вариант Михалчи и Тарау.

> 🎒 **На пальцах.** Коэффициент 0.85 пришёл из веб-поиска: он означает, что читатель с вероятностью 85% переходит по ссылке и с вероятностью 15% прыгает на случайную страницу. Отсюда и `1 - damping = 0.15` в стартовых оценках — это гарантия, что ни одно предложение не получит ровно ноль и граф не схлопнется.

### Step 2: abstractive with BART

```python
from transformers import pipeline

summarizer = pipeline("summarization", model="facebook/bart-large-cnn")

article = """(long news article text)"""

summary = summarizer(article, max_length=120, min_length=60, do_sample=False)
print(summary[0]["summary_text"])
```

BART-large-CNN дообучен на корпусе CNN/DailyMail. Он выдаёт выжимки в новостном стиле прямо из коробки. Для других доменов (научные статьи, диалоги, юридические тексты) берите подходящий чекпоинт Pegasus или дообучайте на своих данных.

> 🎒 **На пальцах.** Параметры `max_length=120` и `min_length=60` заданы в токенах, а не в словах: для английского это примерно 90 и 45 слов. Нижняя граница важнее, чем кажется, — без неё модель охотно выдаёт одно предложение на 15 слов и формально считает работу сделанной. `do_sample=False` означает детерминированный выход: один и тот же текст на входе всегда даёт одну и ту же выжимку.

### Step 3: ROUGE evaluation

```python
from rouge_score import rouge_scorer

scorer = rouge_scorer.RougeScorer(["rouge1", "rouge2", "rougeL"], use_stemmer=True)
scores = scorer.score(reference_summary, generated_summary)
print({k: round(v.fmeasure, 3) for k, v in scores.items()})
```

Всегда включайте стемминг. Без него «running» и «run» считаются разными словами, и ROUGE недосчитывает совпадений.

> 🎒 **На пальцах.** Цена отключённого стемминга вполне измерима: если в выжимке из 40 слов десяток отличается от эталона только формой («companies» против «company», «reported» против «reports»), ROUGE-1 просядет примерно с 0.75 до 0.5. Число упадёт на треть, хотя текст не изменился ни на слово.

### Beyond ROUGE (2026 summarization eval)

ROUGE был главной метрикой суммаризации двадцать лет, и в 2026 году его одного уже недостаточно. Крупный метаанализ статей по генерации текста показал:

- **BERTScore** (похожесть контекстных эмбеддингов) набирал популярность до 2023 года, и сейчас его приводят рядом с ROUGE в большинстве статей по суммаризации.
- **BARTScore** рассматривает оценку как генерацию: выжимка оценивается по тому, насколько вероятной её считает предобученный BART при данном источнике.
- **MoverScore** (расстояние Earth Mover над контекстными эмбеддингами) вышел на первое место в бенчмарках суммаризации 2025 года, потому что улавливает смысловое пересечение лучше ROUGE.
- **FactCC** и **QA-based faithfulness** были в ходу в 2021-2023 годах, теперь их часто заменяет **G-Eval** — цепочка промптов к GPT-4, которая оценивает связность, непротиворечивость, беглость и релевантность с рассуждением по шагам.
- **G-Eval** и похожие подходы с LLM в роли судьи совпадают с человеческой оценкой примерно в 80% случаев, если рубрики составлены аккуратно.

Рекомендация для production: приводите ROUGE-L для сравнения со старыми результатами, BERTScore для смыслового пересечения и G-Eval для связности и фактической точности. Калибруйте на 50-100 выжимках с человеческой разметкой.

> 🎒 **На пальцах.** Почему ROUGE в одиночку врёт: возьмите эталон «компания уволила 200 человек» и выжимку «фирма сократила 200 сотрудников». Совпало одно слово из четырёх, ROUGE-1 около 0.25 — по этой метрике выжимка провальная, хотя смысл передан идеально. BERTScore на той же паре даст порядка 0.9, потому что сравнивает эмбеддинги, а не буквы.

### Step 4: the factuality problem

Abstractive-выжимки склонны к галлюцинациям. У extractive-выжимок риск галлюцинаций намного ниже, потому что текст берётся из источника дословно, — хотя они всё равно могут вводить в заблуждение, если исходные предложения вырваны из контекста, устарели или переставлены местами. Именно поэтому production-системы до сих пор предпочитают extractive-подход для контента, связанного с регулированием.

Типы галлюцинаций, у которых есть имена:

- **Entity swap.** В источнике «John Smith». В выжимке «John Brown».
- **Number drift.** В источнике «25,000». В выжимке «25 million».
- **Polarity flip.** В источнике «rejected the offer». В выжимке «accepted the offer».
- **Fact invention.** Источник вообще не упоминает CEO. Выжимка сообщает, что CEO всё одобрил.

Подходы к оценке, которые работают:

- **FactCC.** Бинарный классификатор, обученный на выводимости предложения выжимки из предложения источника. Предсказывает «фактично / нефактично».
- **QA-based factuality.** Задаём QA-модели вопросы, ответы на которые есть в источнике. Если по выжимке получаются другие ответы, поднимаем флаг.
- **Entity-level F1.** Сравниваем именованные сущности источника и выжимки. Сущности, которые есть только в выжимке, подозрительны.

Для всего, что видит пользователь и где важна фактическая точность (новости, медицина, право, финансы), extractive — более безопасный выбор по умолчанию. Abstractive требует проверки фактов внутри пайплайна.

> 🎒 **На пальцах.** Number drift опаснее всех остальных, потому что читается гладко. «25,000» и «25 million» отличаются в тысячу раз, но глаз не спотыкается ни на одном слове. Отсюда простейшая защита, которая ловит и entity swap, и number drift: выдерните из выжимки все числа и имена собственные и проверьте, что каждое встречается в источнике дословно.

## Use It

Стек 2026 года:

| Use case | Recommended |
|---------|-------------|
| Новости, выжимка на 3-5 предложений, английский | `facebook/bart-large-cnn` |
| Научные статьи | `google/pegasus-pubmed` или дообученный T5 |
| Много документов, длинный текст | Любая LLM с контекстом от 32k, через промпт |
| Суммаризация диалогов | `philschmid/bart-large-cnn-samsum` |
| Extractive, низкий риск галлюцинаций по построению | TextRank или LSA / LexRank из `sumy` |

В 2026 году LLM с длинным контекстом часто обходят специализированные модели, если вычисления не в дефиците. Плата за это — стоимость и воспроизводимость; специализированные модели дают более стабильный выход.

> 🎒 **На пальцах.** Контекст в 32k токенов — это примерно 24 тысячи английских слов, то есть книга страниц на сто. Именно поэтому LLM выигрывают на многодокументной суммаризации: BART-large-CNN упирается в 1024 токена и физически не видит больше полутора страниц за раз.

## Ship It

Сохраните как `outputs/skill-summary-picker.md`:

```markdown
---
name: summary-picker
description: Pick extractive or abstractive, named library, factuality check.
version: 1.0.0
phase: 5
lesson: 12
tags: [nlp, summarization]
---

Given a task (document type, compliance requirement, length, compute budget), output:

1. Approach. Extractive or abstractive. Explain in one sentence why.
2. Starting model / library. Name it. `sumy.TextRankSummarizer`, `facebook/bart-large-cnn`, `google/pegasus-pubmed`, or an LLM prompt.
3. Evaluation plan. ROUGE-1, ROUGE-2, ROUGE-L (use rouge-score with stemming). Plus factuality check if abstractive.
4. One failure mode to probe. Entity swap is the most common in abstractive news summarization; flag samples where source entities do not appear in summary.

Refuse abstractive summarization for medical, legal, financial, or regulated content without a factuality gate. Flag input over the model's context window as needing chunked map-reduce summarization (not just truncation).
```

> 🎒 **На пальцах.** Ключевая фраза в этом промпте — «chunked map-reduce, а не просто обрезка». Разница на примере: статья на 4000 токенов при лимите модели в 1024 либо теряет три четверти текста (обрезка), либо режется на 4 куска, каждый суммаризуется отдельно, а потом четыре выжимки сводятся в одну. Второй способ дороже вчетверо и единственный правильный.

## Exercises

1. **Easy.** Прогоните TextRank на 5 новостных статьях. Сравните топ-3 предложения с эталонной выжимкой. Измерьте ROUGE-L. На статьях в стиле CNN/DailyMail должно получиться 30-45 ROUGE-L.
2. **Medium.** Реализуйте фактическую проверку на уровне сущностей: извлеките именованные сущности из источника и выжимки (spaCy), посчитайте полноту сущностей источника в выжимке и точность сущностей выжимки относительно источника. Высокая точность при низкой полноте означает «безопасно, но скупо»; низкая точность означает выдуманные сущности.
3. **Hard.** Сравните BART-large-CNN с LLM (Claude или GPT-4) на 50 статьях CNN/DailyMail. Приведите ROUGE-L, фактическую точность (через F1 по сущностям) и стоимость одной выжимки. Опишите, где выигрывает каждый вариант.

> 🎒 **На пальцах.** Подсказка ко второму заданию: считайте по формуле пересечения множеств. Если в источнике 10 сущностей, в выжимке 4, и все 4 нашлись в источнике — точность 4/4 = 1.0, полнота 4/10 = 0.4. Это нормальная безопасная выжимка. А вот если из 4 сущностей выжимки в источнике нашлись только 3, точность падает до 0.75, и одна сущность выдумана — вот её и надо смотреть глазами.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| Extractive | Выбрать предложения | Вернуть предложения из источника дословно. Никогда не галлюцинирует. |
| Abstractive | Переписать | Породить новый текст, обусловленный источником. Может галлюцинировать. |
| ROUGE | Метрика выжимки | Пересечение по n-граммам или по LCS между выходом системы и эталоном. |
| TextRank | Extractive на графе | PageRank по графу похожести предложений. |
| Factuality | Правда ли это | Подтверждаются ли утверждения выжимки источником. |
| Hallucination | Выдуманное содержание | Содержание выжимки, которого источник не подтверждает. |
