# Кэширование промптов и кэширование контекста

> Ваш системный промпт — 4 000 токенов. Ваш RAG-контекст — 20 000 токенов. Вы шлёте и то и другое в каждом запросе. И платите тоже за то и другое — каждый раз. Кэширование промптов позволяет провайдеру держать этот префикс тёплым у себя и выставлять вам 10% обычной цены при переиспользовании. Если пользоваться правильно, стоимость инференса падает на 50–90%, а задержка до первого токена — на 40–85%.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 11 · 01 (Prompt Engineering), Phase 11 · 05 (Context Engineering), Phase 11 · 11 (Caching and Cost)
**Time:** ~60 minutes

## The Problem

Агент-программист шлёт Claude один и тот же системный промпт на 15 000 токенов в каждом ходу разговора. Двадцать ходов по $3 за миллион входных токенов — это $0.90 на одном только входе, до единого сообщения от пользователя. Умножьте на 10 000 разговоров в день, и счёт вырастает до $9 000 в сутки за текст, который вообще не меняется.

Промпт нельзя ужать, не потеряв качество. Не слать его тоже нельзя — модели он нужен в каждом ходу. Единственный ход — перестать платить полную цену за префикс, который провайдер уже видел.

Этот ход и есть кэширование промптов. Anthropic выпустила его в августе 2024 (с вариантом расширенного TTL на час в 2025), OpenAI автоматизировала позже в том же году, Google выкатила явное кэширование контекста вместе с Gemini 1.5, и сейчас все трое предлагают это как полноценную функцию на своих фронтирных моделях.

> 🎒 **На пальцах.** Пройдите арифметику пальцем: 15 000 токенов × 20 ходов = 300 000 токенов входа за один разговор. По $3 за миллион это $0.90. Десять тысяч разговоров — $9 000 в день, то есть больше $3 миллионов в год. Кэш срезает эту строку до примерно $900 в день. Это как ксерокопия договора: печатать заново каждый раз или один раз и потом только доставать из папки.

## The Concept

![Prompt caching: write once, read cheap](../assets/prompt-caching.svg)

**The mechanic.** Когда префикс запроса совпадает с префиксом недавнего запроса, провайдер отдаёт KV-кэш прошлого прогона вместо повторного кодирования токенов. Первый раз вы платите небольшую надбавку за запись, а потом каждый раз получаете большую скидку на чтение.

**Three provider flavors in 2026.**

| Provider | API style | Hit discount | Write premium | Default TTL | Min cacheable |
|---------|-----------|--------------|---------------|-------------|---------------|
| Anthropic | Явные маркеры `cache_control` на блоках контента | −90% на вход | надбавка 25% | 5 минут (продлевается до часа) | 1 024 токена (Sonnet/Opus), 2 048 (Haiku) |
| OpenAI | Автоматическое определение префикса | −50% на вход | нет | До часа (как получится) | 1 024 токена |
| Google (Gemini) | Явный API `CachedContent` | Оплата за хранение; чтение около 25% обычной цены | Плата за хранение за токен·час | Задаёт пользователь (по умолчанию час) | 4 096 токенов (Flash), 32 768 (Pro) |

> 🎒 **На пальцах.** Сравните три подхода по одной фразе: Anthropic — «скажи явно, что кэшировать», OpenAI — «мы сами разберёмся, но скидка вдвое меньше», Gemini — «создай именованный объект и плати за хранение». Обратите внимание на нижний порог: блок в 900 токенов у Anthropic не закэшируется вообще, молча. И у Gemini Pro порог 32 768 — то есть кэшировать имеет смысл только очень большие корпусы.

**The invariant.** Все трое кэшируют только префиксы. Если хоть один токен между запросами отличается, всё, что идёт после первого разошедшегося токена, — промах. Ставьте *стабильные* части наверх, *переменные* — вниз.

> 🎒 **На пальцах.** Это как поиск по алфавиту: совпадение считается с самого начала строки. Промпты «Ты помощник. Сегодня 5 августа. Правила: …» и «Ты помощник. Сегодня 6 августа. Правила: …» расходятся на девятом слове — значит, все оставшиеся 15 000 токенов правил кэш не спасёт. Один символ в начале обесценивает весь хвост.

### The cache-friendly layout

```
[system prompt]          <-- cache this
[tool definitions]       <-- cache this
[few-shot examples]      <-- cache this
[retrieved documents]    <-- cache if reused, else don't
[conversation history]   <-- cache up to last turn
[current user message]   <-- never cache (different every time)
```

Нарушьте порядок — поставьте сообщение пользователя выше системного промпта, вклиньте динамические результаты поиска между few-shot примерами — и кэш не сработает никогда.

> 🎒 **На пальцах.** Порядок здесь ровно по убыванию стабильности: системный промпт не меняется месяцами, определения инструментов — неделями, история разговора — каждый ход, сообщение пользователя — всегда новое. Представьте стопку бумаг, где вниз кладут самое свежее: тогда верх стопки можно не перебирать. Строка `[current user message]` внизу не случайно — она меняется всегда, и кэшировать её бессмысленно.

### The break-even calculation

Надбавка Anthropic в 25% за запись означает, что закэшированный блок надо прочитать минимум дважды, чтобы выйти в плюс. 1 запись + 1 чтение дают в среднем 0.675x стоимости на запрос (экономия 32%); 1 запись + 10 чтений — 0.205x (экономия 80%). Правило большого пальца: кэшируйте всё, что рассчитываете переиспользовать хотя бы 3 раза в пределах TTL.

```figure
prompt-cache-hit
```

> 🎒 **На пальцах.** Проверим 0.675 руками: запись стоит 1.25, чтение 0.1, сумма 1.35 на два запроса, делим на два — 0.675. Для десяти чтений: (1.25 + 10 × 0.1) / 11 = 2.25 / 11 ≈ 0.205. Отсюда и видно, где точка безубыточности: одна запись без единого чтения — это чистый перерасход в 25%.

## Build It

### Step 1: Anthropic prompt caching with explicit markers

```python
import anthropic

client = anthropic.Anthropic()

SYSTEM = [
    {
        "type": "text",
        "text": "You are a senior Python reviewer. Follow the rubric exactly.\n\n" + RUBRIC_15K_TOKENS,
        "cache_control": {"type": "ephemeral"},
    }
]

def review(code: str):
    return client.messages.create(
        model="claude-opus-4-7",
        max_tokens=1024,
        system=SYSTEM,
        messages=[{"role": "user", "content": code}],
    )
```

Маркер `cache_control` говорит Anthropic хранить блок пять минут. Переиспользование внутри этого окна попадает в кэш; после истечения промахивается и пишет заново.

> 🎒 **На пальцах.** Обратите внимание, что маркер стоит на системном блоке, а сообщение пользователя с кодом идёт отдельно и не кэшируется. Так и надо: рубрика на 15 000 токенов стабильна, код каждый раз новый. И помните про пятиминутный таймер — он сбрасывается при каждом попадании, так что поток запросов раз в минуту держит кэш тёплым бесконечно.

**Response usage fields:**

```python
response = review(code_a)
response.usage
# InputTokensUsage(
#     input_tokens=120,
#     cache_creation_input_tokens=15023,   # paid at 1.25x
#     cache_read_input_tokens=0,
#     output_tokens=340,
# )

response_b = review(code_b)
response_b.usage
# cache_creation_input_tokens=0
# cache_read_input_tokens=15023           # paid at 0.1x
```

Проверяйте оба поля в CI — если `cache_read_input_tokens` из запроса в запрос остаётся нулём, значит ваши ключи кэша плывут.

> 🎒 **На пальцах.** Считаем деньги по этим числам: 15 023 токена записи по 1.25x — это как 18 779 обычных токенов. Второй запрос: те же 15 023 по 0.1x — как 1 502 токена. То есть второй вызов по входу дешевле первого примерно в 12 раз. Именно эти два поля и надо выводить на дашборд, а не общий «input tokens».

### Step 2: one-hour extended TTL

Для долгих batch-задач дефолтные пять минут истекают между заданиями. Задайте `ttl`:

```python
{"type": "text", "text": RUBRIC, "cache_control": {"type": "ephemeral", "ttl": "1h"}}
```

TTL на час стоит вдвое дороже по надбавке за запись (50% сверху вместо 25%), но окупается быстро на любом батче, который переиспользует префикс больше пяти раз.

> 🎒 **На пальцах.** Считаем окупаемость: запись по 1.5 вместо 1.25 — переплата 0.25. Одно чтение экономит 0.9 против полной цены. То есть уже второе чтение перекрывает разницу с запасом. Часовой TTL нужен там, где между запросами есть паузы: ночной прогон по 500 документам с обработкой по 40 секунд каждый пятиминутное окно не переживёт.

### Step 3: OpenAI automatic caching

OpenAI не даёт вам ничего настраивать. Любой префикс длиннее 1 024 токенов, совпавший с недавним запросом, автоматически получает скидку 50%.

```python
from openai import OpenAI
client = OpenAI()

resp = client.chat.completions.create(
    model="gpt-5",
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},   # long and stable
        {"role": "user", "content": user_msg},
    ],
)
resp.usage.prompt_tokens_details.cached_tokens  # the discounted portion
```

Правило удобной для кэша раскладки работает так же. Две вещи убивают кэш OpenAI, но не убивают кэш Anthropic: смена поля `user` (оно входит в ключ кэша) и перестановка инструментов.

> 🎒 **На пальцах.** Ловушка с полем `user` коварная: вы честно передаёте туда ID пользователя ради аналитики — и каждый пользователь получает свой отдельный кэш. При тысяче пользователей и одном общем системном промпте вы вместо одного тёплого префикса держите тысячу холодных. Скидка 50% против 90% у Anthropic — плата за то, что настраивать нечего.

### Step 4: Gemini explicit context caching

Gemini относится к кэшу как к полноценному объекту, который вы создаёте и называете:

```python
from google import genai
from google.genai import types

client = genai.Client()

cache = client.caches.create(
    model="gemini-3-pro",
    config=types.CreateCachedContentConfig(
        display_name="rubric-v3",
        system_instruction=RUBRIC,
        contents=[FEW_SHOT_EXAMPLES],
        ttl="3600s",
    ),
)

resp = client.models.generate_content(
    model="gemini-3-pro",
    contents=["Review this code:\n" + code],
    config=types.GenerateContentConfig(cached_content=cache.name),
)
```

Gemini берёт плату за хранение по токен·часам всё время жизни кэша, а чтение считает примерно по 25% обычной входной ставки. Это правильная форма, когда вы переиспользуете один и тот же гигантский промпт в множестве сессий на протяжении дней.

> 🎒 **На пальцах.** Разница в модели оплаты принципиальная: у Anthropic вы платите за события (записал, прочитал), у Google — за время хранения, как за аренду ячейки. Кэш на 100 000 токенов, который живёт сутки, тикает счётчиком даже в те часы, когда к нему никто не обращается. Поэтому `ttl="3600s"` в коде — это не «максимум на всякий случай», а осознанный срок аренды.

### Step 5: measuring hit rate in production

Смотрите `code/main.py` — там симулятор-бухгалтер по трём провайдерам, который считает число записей, чтений и промахов и выводит смешанную стоимость на 1 000 запросов. Пропускайте деплой через порог по доле попаданий: у большинства продакшен-установок на Anthropic после прогрева доля чтений должна быть выше 80%.

> 🎒 **На пальцах.** Почему именно 80%, а не 100%: первый запрос каждой новой сессии всегда пишет кэш, плюс часть попадает в паузы длиннее TTL. Если у вас 60% — ищите динамическое поле в префиксе. Если 5% — у вас кэш не работает вообще, и вы просто платите надбавку 25% ни за что.

## Pitfalls that still ship in 2026

- **Dynamic timestamps at the top.** Строка `"Current time: 2026-04-22 15:30:02"` в начале системного промпта. Промах на каждом запросе. Перенесите отметки времени ниже точки разреза кэша.
- **Tool reordering.** Сериализуйте инструменты в стабильном порядке — перетасовка словаря между деплоями ломает все попадания.
- **Free-text near-duplicates.** «You are helpful.» против «You are a helpful assistant.» — разница в один байт равна полному промаху.
- **Too-small blocks.** Anthropic держит нижнюю границу в 1 024 токена (2 048 для Haiku). Блоки меньше молча не кэшируются.
- **Blind cost dashboards.** Разделяйте «входные токены» на кэшированные и некэшированные. Иначе падение трафика будет выглядеть как победа кэша.

> 🎒 **На пальцах.** Первый пункт — чемпион по частоте. Секунды в отметке времени меняются буквально каждый запрос, так что кэш не попадает никогда, а надбавку 25% за запись вы платите всегда: получается дороже, чем вообще без кэша. Если время реально нужно модели, округлите его до суток или положите в сообщение пользователя, ниже разреза.

## Use It

Стек кэширования образца 2026 года:

| Situation | Pick |
|-----------|------|
| Агент со стабильным системным промптом от 10k токенов и множеством ходов | Anthropic `cache_control` с TTL пять минут |
| Batch-задача, переиспользующая префикс дольше 30 минут | Anthropic с `ttl: "1h"` |
| Бессерверные эндпоинты на GPT-5, своей инфраструктуры нет | Автоматика OpenAI (просто сделайте префикс длинным и стабильным) |
| Многодневное переиспользование гигантского корпуса кода или документов | Явный `CachedContent` у Gemini |
| Запасной вариант через другого провайдера | Держите раскладку кэшируемого префикса одинаковой у всех провайдеров, чтобы попадание сработало где угодно |

Комбинируйте с семантическим кэшированием (Phase 11 · 11) на слое пользовательских сообщений: кэширование промптов работает с *побайтово одинаковым* переиспользованием, семантическое — с *одинаковым по смыслу*.

> 🎒 **На пальцах.** Разделение обязанностей такое: prompt caching ловит «те же 15 000 токенов рубрики», семантический кэш ловит «пользователь спросил то же самое другими словами». Вопросы «как вернуть товар?» и «какие условия возврата?» для prompt caching — два разных запроса, а для семантического кэша — один. Первый экономит на префиксе, второй убирает вызов модели целиком.

## Ship It

Сохраните `outputs/skill-prompt-caching-planner.md`:

```markdown
---
name: prompt-caching-planner
description: Design a cache-friendly prompt layout and pick the right provider caching mode.
version: 1.0.0
phase: 11
lesson: 15
tags: [llm-engineering, caching, cost]
---

Given a prompt (system + tools + few-shot + retrieval + history + user) and a usage profile (requests per hour, TTL needed, provider), output:

1. Layout. Reordered sections with a single cache breakpoint marked; explain which sections are stable, which are volatile.
2. Provider mode. Anthropic cache_control, OpenAI automatic, or Gemini CachedContent. Justify from TTL and reuse pattern.
3. Break-even. Expected reads per write within TTL; net cost vs no-cache with math.
4. Verification plan. CI assertion that cache_read_input_tokens > 0 on the second identical request; dashboard split by cached vs uncached tokens.
5. Failure modes. List the three most likely reasons the cache will miss in this setup (dynamic timestamp, tool reorder, near-duplicate text) and how you will prevent each.

Refuse to ship a cache plan that places a dynamic field above the breakpoint. Refuse to enable 1h TTL without a reuse count that makes the 2x write premium pay back.
```

> 🎒 **На пальцах.** Пункт 4 — единственная защита от тихой поломки. Кэш никогда не падает с ошибкой: он просто перестаёт попадать, и вы узнаёте об этом из счёта в конце месяца. Тест «второй одинаковый запрос обязан вернуть `cache_read_input_tokens > 0`» пишется за десять минут и стоит своих денег с первого же деплоя.

## Exercises

1. **Easy.** Возьмите разговор на 10 ходов с системным промптом на 5 000 токенов против Claude. Прогоните его без `cache_control` и с ним. Сообщите счёт по входным токенам в обоих случаях.
2. **Medium.** Напишите тестовую обвязку, которая по шаблону промпта и логу запросов считает ожидаемую долю попаданий и экономию в долларах для каждого провайдера (Anthropic 5m, Anthropic 1h, автоматика OpenAI, явный Gemini).
3. **Hard.** Соберите оптимизатор раскладки: по промпту и списку полей с пометкой `stable=True/False` перепишите промпт так, чтобы единственная точка разреза кэша встала в максимально выгодную позицию без потери информации. Проверьте на настоящем эндпоинте Anthropic.

> 🎒 **На пальцах.** В первом задании ожидайте примерно такие числа: без кэша 10 ходов × 5 000 = 50 000 токенов входа. С кэшем — 5 000 на запись (по 1.25x, то есть как 6 250) плюс девять чтений по 500 эффективных, итого около 10 750. Экономия примерно в 4.6 раза, и она растёт с длиной разговора.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| Prompt caching | «Делает длинные промпты дешёвыми» | Переиспользование KV-кэша на стороне провайдера для совпавших префиксов; скидка 50–90% на повторные входные токены. |
| `cache_control` | «Маркер от Anthropic» | Атрибут блока контента, объявляющий «всё до этого места кэшируется»; `{"type": "ephemeral"}`. |
| Cache write | «Платим надбавку» | Первый запрос, который наполняет кэш; тарифицируется примерно по 1.25x входной ставки у Anthropic, бесплатен у OpenAI. |
| Cache read | «Скидка» | Последующие запросы, совпавшие по префиксу; тарифицируются по 10% (Anthropic), 50% (OpenAI), около 25% (Gemini). |
| TTL | «Сколько живёт» | Сколько секунд кэш остаётся тёплым; у Anthropic по умолчанию 5 минут (продлевается до часа), у OpenAI до часа как получится, у Gemini задаёт пользователь. |
| Extended TTL | «Часовой кэш Anthropic» | `{"type": "ephemeral", "ttl": "1h"}`; надбавка за запись вдвое больше, но для batch-переиспользования оно того стоит. |
| Prefix match | «Почему кэш промахнулся» | Кэш попадает только тогда, когда каждый токен от начала до точки разреза побайтово совпадает. |
| Context caching (Gemini) | «Тот, который явный» | Именованный объект кэша от Google с оплатой за хранение; лучше всего для многодневного переиспользования больших корпусов. |

- Phase 11 · 11 (Caching and Cost) — как соединить кэширование промптов с семантическим кэшем на сообщениях пользователя.
- [Pope et al., "Efficiently Scaling Transformer Inference" (2022)](https://arxiv.org/abs/2211.05102) — модель памяти KV-кэша, которую кэширование промптов открывает пользователям; объясняет, почему перечитать закэшированный префикс примерно в 10 раз дешевле, чем пересчитать.
- [Agrawal et al., "SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills" (2023)](https://arxiv.org/abs/2308.16369) — prefill это та фаза, которую срезает кэширование промптов; статья объясняет, почему при попадании резко падает TTFT, а TPOT не меняется.
- [Leviathan et al., "Fast Inference from Transformers via Speculative Decoding" (2023)](https://arxiv.org/abs/2211.17192) — кэширование промптов стоит в одном ряду со спекулятивным декодированием, Flash Attention и MQA/GQA как рычаг, гнущий кривую стоимости инференса; читайте про остальные три.
