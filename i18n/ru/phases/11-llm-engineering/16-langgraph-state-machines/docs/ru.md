# Конечные автоматы агента — графы, узлы, чекпоинты

> Цикл ReAct, написанный руками, — это `while True`. Тот же цикл, записанный явным графом, — это то, что можно чекпоинтить, прерывать, ветвить и отматывать назад во времени. Сам агент не изменился. Изменилась обвязка вокруг него.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 11 · 09 (Function Calling), Phase 11 · 14 (Model Context Protocol)
**Time:** ~75 minutes

## The Problem

Вы выкатываете агента с вызовом функций. Три хода он работает, а потом что-то ломается: модель дёргает инструмент, который возвращает 500, пользователь передумал на середине задачи, или агент решает вернуть деньги за заказ, ни у кого не спросив. У цикла `while True:` нет ни одного хука. Его нельзя поставить на паузу, нельзя отмотать назад и нельзя ответвиться в «а что было бы, выбери модель другой инструмент». Как только такое уходит дальше демо, агент превращается в чёрный ящик, который либо сработал, либо нет.

Следующий шаг очевиден, стоит его увидеть. Агент и так уже конечный автомат — системный промпт плюс история сообщений плюс отложенные вызовы инструментов плюс следующее действие. Сделайте автомат явным: узлы для «модель думает», «выполняется инструмент», «человек согласовывает» и рёбра для условных переходов между ними. Как только граф стал явным, обвязка бесплатно получает четыре вещи: чекпоинты (сохранение состояния между шагами), прерывания (пауза для человека), стриминг (поток токенов и промежуточных событий) и перемотку во времени (отмотать к прошлому состоянию и попробовать другую ветку).

Референсная реализация этой абстракции — LangGraph. Это не агентный фреймворк в смысле LangChain («вот вам AgentExecutor, удачи»). Это рантайм графа, где состояние, персистентность и прерывания — полноценные граждане первого класса. Цикл агента вы рисуете, а не пишете руками.

> 🎒 **На пальцах.** Разница как между магнитофонной кассетой и плейлистом. У `while True` есть только «играет» и «выключено»: остановили — начали сначала, ничего не помните. Явный граф даёт паузу, перемотку и закладки. И заметьте: код внутри узлов тот же самый, что был в цикле, — вы просто дали каждому шагу имя и адрес.

## The Concept

![LangGraph StateGraph: nodes, edges, and the checkpointer](../assets/langgraph-stategraph.svg)

В `StateGraph` есть три вещи.

1. **State.** Типизированный словарь (TypedDict или модель Pydantic), который течёт по графу. Каждый узел получает состояние целиком и возвращает частичное обновление, которое LangGraph сливает через *редьюсер*, свой на каждое поле — `operator.add` для списков, которые должны накапливаться, перезапись по умолчанию.
2. **Nodes.** Функции Python вида `state -> partial_state`. Каждая — отдельный шаг: «вызвать модель», «выполнить инструменты», «подвести итог».
3. **Edges.** Переходы между узлами. Статическое ребро ведёт в одно место. Условное ребро берёт функцию-маршрутизатор `state -> next_node_name`, чтобы граф мог ветвиться по выводу модели.

Дальше граф компилируется. Компиляция фиксирует топологию, подключает чекпоинтер (опционально, но для продакшена обязательно) и возвращает запускаемый объект. Вы вызываете его с начальным состоянием и `thread_id`. Каждый шаг выполнения сохраняет чекпоинт с ключом `(thread_id, checkpoint_id)`.

> 🎒 **На пальцах.** Прочтите три пункта как «данные, действия, стрелки». Состояние — это папка, которую передают из рук в руки; узел — сотрудник, который что-то дописывает в папку и отдаёт дальше; ребро — стрелка на схеме, кто кому передаёт. Важная деталь: узел возвращает не всю папку, а только свою правку, и как эту правку приклеить к папке, решает редьюсер.

### The four superpowers

**Checkpointing.** Каждый переход между узлами пишет новое состояние в хранилище (в память для тестов, Postgres/Redis/SQLite для продакшена). Чтобы продолжить, вызовите граф ещё раз с тем же `thread_id`. Граф подхватит с места остановки.

**Interrupts.** Пометьте узел через `interrupt_before=["human_review"]` — и выполнение остановится до того, как узел отработает. Состояние сохранено. Ваш API отвечает пользователю «ждём согласования». Следующий запрос по тому же `thread_id` с `Command(resume=...)` продолжает выполнение.

> 🎒 **На пальцах.** Ключевое слово тут `before`, а не `after`. Прерывание перед узлом `tools` — это шлагбаум до того, как база данных удалена. Прерывание после — это возможность красиво посмотреть на пепелище. Такая же логика, как у подтверждения перевода в банке: сначала спрашивают, потом отправляют деньги.

**Streaming.** `graph.stream(state, mode="updates")` выдаёт дельты состояния по мере их появления. `mode="messages"` стримит токены LLM внутри узлов модели. `mode="values"` выдаёт полные снимки. Что показывать в интерфейсе — выбираете вы.

**Time-travel.** `graph.get_state_history(thread_id)` возвращает полный журнал чекпоинтов. Передайте любой прошлый `checkpoint_id` в `graph.invoke` — и вы ответвитесь от той точки. Отлично для отладки («а что было бы, выбери модель инструмент B?») и для регрессионных тестов, которые переигрывают продакшен-трейсы.

> 🎒 **На пальцах.** Перемотка во времени работает потому, что чекпоинты — это не «последнее состояние», а весь журнал: шаг 1, шаг 2, шаг 3… Отладка бага на 12-м ходу превращается в «взять чекпоинт номер 11 и запустить оттуда» вместо «повторить весь разговор и надеяться, что модель ошибётся так же». Как сохранёнки в игре перед боссом.

### Reducers are the point

У каждого поля состояния есть редьюсер. Значения по умолчанию чаще всего годятся — новое значение затирает старое. Но спискам сообщений нужен `operator.add`, чтобы новые сообщения дописывались, а не заменяли предыдущие. Параллельные рёбра сливают свои обновления через редьюсер. Если два узла оба обновляют `messages`, а вы забыли `Annotated[list, add_messages]`, второй молча побеждает, и половина хода теряется. Редьюсер — единственная неочевидная штука в библиотеке; сделайте его правильно, и остальное соберётся само.

> 🎒 **На пальцах.** Разница на примере: было `messages = [вопрос]`, узел вернул `{"messages": [ответ]}`. С редьюсером по умолчанию в состоянии останется `[ответ]` — вопрос пропал. С `add_messages` будет `[вопрос, ответ]`. Ошибка не падает и не логируется: агент просто начинает «забывать» начало разговора, и вы неделю ищете это в промптах.

### The ReAct graph in four nodes

Продакшен-агент ReAct — это четыре узла и два ребра:

1. `agent` — зовёт LLM с текущей историей сообщений. Возвращает сообщение ассистента (в нём могут быть tool_calls).
2. `tools` — выполняет все tool_calls из последнего сообщения ассистента и дописывает результаты как сообщения инструментов.
3. Условное ребро из `agent`, которое ведёт в `tools`, если в последнем сообщении есть tool_calls, иначе в `END`.
4. Статическое ребро из `tools` обратно в `agent`.

Вот и всё. Вы получаете полный цикл ReAct (Thought → Action → Observation → Thought → …) с чекпоинтами, прерываниями и стримингом примерно в 40 строках кода.

> 🎒 **На пальцах.** Обратите внимание, что цикл здесь буквально нарисован: `tools` всегда возвращает в `agent`, а выйти можно только через условное ребро в `END`. Это тот же `while True` с `break`, только развёрнутый в две стрелки. Пункты 1 и 2 — это «подумал» и «сделал», пункт 3 — «а надо ли ещё?».

### StateGraph vs Send (fanout)

`Send(node_name, state)` позволяет узлу разослать параллельные подграфы. Пример: агент решает опросить три ретривера сразу. Каждый `Send` порождает параллельное выполнение целевого узла; их выходы сливаются через редьюсер состояния. Так LangGraph выражает паттерн «оркестратор и работники» без примитивов многопоточности.

> 🎒 **На пальцах.** Здесь редьюсер из прошлого раздела внезапно становится критичным. Три параллельных ретривера вернут по списку документов; с перезаписью по умолчанию вы получите документы только от того, кто финишировал последним, — две трети работы в мусор. С `operator.add` получите все три списка склеенными. Параллельность бесплатна, а вот про склейку надо подумать.

### Subgraphs

Скомпилированный граф может быть узлом другого графа. Внешний граф видит один узел; внутренний граф живёт со своим состоянием и своими чекпоинтами. Именно так команды строят агентов вида «супервизор и работники»: граф-супервизор направляет намерение пользователя в подграф-работник нужного домена.

> 🎒 **На пальцах.** Это ровно то же, что функция в обычном коде: снаружи один вызов, внутри своя жизнь и свои переменные. Подграф `researcher` может внутри крутить восемь шагов поиска, а супервизор видит один узел с одним результатом. Заодно у него свои чекпоинты — упал поиск, отматываете только поиск, а не весь разговор.

## Build It

### Step 1: state and nodes

```python
from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

def agent_node(state: State) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

tool_node = ToolNode(tools=[search_web, read_file])

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=MemorySaver())
```

`add_messages` — это тот самый редьюсер, из-за которого список сообщений накапливается, а не перезаписывается. Забыть его — самый частый баг в LangGraph.

> 🎒 **На пальцах.** Пройдите по коду глазами: три строки `add_node`/`set_entry_point` объявляют схему, `add_conditional_edges` вешает развилку, а `compile` превращает чертёж в работающую программу. Функция `should_continue` возвращает всего два значения — `"tools"` или `END`, — и именно эта строка решает, крутится цикл дальше или агент отвечает пользователю.

### Step 2: run with a thread

```python
config = {"configurable": {"thread_id": "user-42"}}
for event in app.stream(
    {"messages": [HumanMessage("find the Anthropic headquarters address")]},
    config,
    stream_mode="updates",
):
    print(event)
```

Каждое обновление — это словарь `{node_name: state_delta}`. Ваш фронтенд может стримить их в интерфейс, чтобы пользователь видел: «агент думает… вызывает search_web… получил результат… отвечает».

> 🎒 **На пальцах.** `thread_id: "user-42"` — это, по сути, номер папки с делом. Запустите тот же граф с тем же ID завтра — он достанет всю историю из чекпоинтера и продолжит. Смените ID на `"user-43"` — начнётся чистый разговор. Одна строчка конфига отделяет «помнит меня» от «видит впервые».

### Step 3: add a human-in-the-loop interrupt

Пометьте узел так, чтобы выполнение вставало на паузу перед его запуском.

```python
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"],  # pause before every tool call
)

state = app.invoke({"messages": [HumanMessage("delete the production database")]}, config)
# state["__interrupt__"] is set. Inspect proposed tool calls.
# If approved:
from langgraph.types import Command
app.invoke(Command(resume=True), config)
# If denied: write a rejection message and resume
app.update_state(config, {"messages": [AIMessage("Blocked by human reviewer.")]})
```

Состояние, чекпоинт и тред переживают прерывание целиком. В памяти не остаётся ничего, кроме момента самого выполнения.

> 🎒 **На пальцах.** Обратите внимание на пример: «delete the production database». Модель предложила вызов, но `interrupt_before=["tools"]` остановил её до выполнения, и в состоянии появился `__interrupt__`. Дальше два пути: `Command(resume=True)` — выполняем, или `update_state` с отказом — дописываем сообщение «Blocked by human reviewer» и продолжаем без удаления. Между предложением и действием встал человек.

### Step 4: time-travel for debugging

```python
history = list(app.get_state_history(config))
for snapshot in history:
    print(snapshot.values["messages"][-1].content[:80], snapshot.config)

# Fork from a prior checkpoint
target = history[3].config  # three steps back
for event in app.stream(None, target, stream_mode="values"):
    pass  # replay from that point forward
```

Передача `None` на вход переигрывает от указанного чекпоинта; передача значения дописывает его как обновление состояния этого чекпоинта перед возобновлением. Так вы воспроизводите неудачный прогон агента, не прогоняя заново весь разговор.

> 🎒 **На пальцах.** Смотрите на строку `target = history[3].config` — это буквально «три шага назад». Разговор на 20 ходов, баг проявился на 15-м: вместо 15 вызовов модели вы делаете один, стартуя с чекпоинта 14. И это же превращается в регрессионный тест — записали продакшен-трейс, переиграли его на новой версии промпта, сравнили.

### Step 5: swap the checkpointer for production

```python
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string("postgresql://...") as checkpointer:
    checkpointer.setup()
    app = graph.compile(checkpointer=checkpointer)
```

SQLite, Redis и Postgres идут в комплекте. `MemorySaver` — для тестов. Всё, что должно переживать перезапуск, требует настоящего хранилища.

> 🎒 **На пальцах.** Заметьте, что меняется ровно один аргумент у `compile` — граф, узлы и рёбра не трогаются вообще. Но последствия огромные: с `MemorySaver` перезапуск процесса стирает все треды разом, и пользователь, который ждал согласования, теряет свою задачу навсегда. С Postgres он вернётся через сутки и продолжит с той же точки.

## The Skill

> Агентов вы строите как графы, а не как циклы `while True`.

Прежде чем тянуться к LangGraph, потратьте 60 секунд на проектирование:

1. **Name the nodes.** Каждое отдельное решение или действие с побочным эффектом — это узел. «Агент думает», «выполняется инструмент», «ревьюер согласовывает», «ответ стримится». Если вы не можете их перечислить, задача пока не агентной формы.
2. **Declare the state.** Минимальный TypedDict с редьюсером на каждое поле-список. Не запихивайте всё в `messages`; поднимайте специфичные для задачи поля (рабочий `plan`, счётчик `budget`, список `retrieved_docs`) на верхний уровень.
3. **Draw the edges.** Статические, если только следующий шаг не зависит от вывода модели. Каждому условному ребру нужна функция-маршрутизатор с именованными ветками.
4. **Choose a checkpointer up front.** `MemorySaver` для тестов, Postgres/Redis/SQLite для всего остального. Не выкатывайте без него — нет чекпоинтера, значит нет ни возобновления, ни прерываний, ни перемотки во времени.
5. **Decide interrupts before tools run, not after.** Согласования вешаются на ребро, входящее в узел с побочным эффектом, чтобы отменить до того, как навредили; валидация вешается на ребро, выходящее из модели, чтобы дёшево отклонять плохие вызовы.
6. **Stream by default.** `mode="updates"` для интерфейса, `mode="messages"` для потока токенов внутри узлов модели, `mode="values"` для полных снимков во время оценки.

Отказывайтесь выкатывать агента на LangGraph без чекпоинтера. Отказывайтесь выкатывать того, кто прерывается *после* побочного эффекта. Отказывайтесь выкатывать поле `messages` без `add_messages` в качестве редьюсера.

> 🎒 **На пальцах.** Пункт 2 экономит больше всего нервов. Соблазн держать план работы прямо в тексте сообщений велик, но тогда, чтобы узнать «сколько шагов сделано», агенту придётся перечитывать свою же болтовню. Поле `plan: list[str]` на верхнем уровне читается одной строкой кода и не зависит от того, что модель написала прозой.

## Exercises

1. **Easy.** Реализуйте описанный выше граф ReAct из четырёх узлов с инструментом-калькулятором и инструментом веб-поиска. Убедитесь, что `list(app.get_state_history(config))` возвращает минимум четыре чекпоинта для разговора из двух ходов.
2. **Medium.** Добавьте узел `planner`, который отрабатывает перед `agent` и пишет в состояние структурированный `plan: list[str]`. Пусть `agent` помечает шаги плана выполненными. Тест должен падать, если `plan` теряется при возобновлении из чекпоинта (неверный редьюсер).
3. **Hard.** Соберите граф-супервизор, который маршрутизирует между тремя подграфами (`researcher`, `writer`, `reviewer`) через `Send`. У каждого подграфа своё состояние и свой чекпоинтер. Добавьте `interrupt_before=["writer"]` на внешнем графе, чтобы человек мог согласовать бриф исследования. Подтвердите, что перемотка во времени из прошлого чекпоинта перезапускает только ответвлённую ветку.

> 🎒 **На пальцах.** Во втором задании ловушка спрятана в формулировке. Поле `plan` — список, и рефлекс подсказывает навесить на него `operator.add`; тогда при каждой правке плана шаги начнут дублироваться: было три пункта, после отметки первого станет шесть. Здесь как раз нужна перезапись по умолчанию — накопление требуется сообщениям, а не плану.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| StateGraph | «Граф в LangGraph» | Объект-строитель, в который вы добавляете узлы и рёбра до компиляции. |
| Reducer | «Как поле сливается» | Функция `(old, new) -> merged`, применяемая, когда узел возвращает обновление этого поля; по умолчанию перезапись, `add_messages` дописывает. |
| Thread | «Идентификатор разговора» | Строка `thread_id`, которая ограничивает область всех чекпоинтов одной сессии. |
| Checkpoint | «Приостановленное состояние» | Сохранённый снимок полного состояния графа после перехода между узлами, с ключом `(thread_id, checkpoint_id)`. |
| Interrupt | «Пауза для человека» | `interrupt_before` / `interrupt_after` останавливают выполнение на границе узла; возобновление через `Command(resume=...)`. |
| Time-travel | «Ответвиться от прошлого шага» | `graph.invoke(None, config_with_old_checkpoint_id)` переигрывает от этого чекпоинта вперёд. |
| Send | «Параллельная рассылка по подграфам» | Конструктор, который узел может вернуть, чтобы породить N параллельных выполнений целевого узла. |
| Subgraph | «Скомпилированный граф как узел» | Скомпилированный StateGraph, используемый узлом другого графа; сохраняет собственную область состояния. |

> 🎒 **На пальцах.** Thread и Checkpoint путают чаще всего, а это разные уровни. Thread — папка всего разговора, чекпоинт — один файл внутри неё. У разговора на 12 переходов один `thread_id` и 12 разных `checkpoint_id`: возобновление работает по первому, перемотка во времени — по второму.
