# Гибридная память: вектор + граф + KV

> Гибридная память крутит три хранилища параллельно — вектор для семантической близости, KV для быстрого поиска фактов, граф для рассуждений о связях между сущностями — плюс скоринговый слой, который сплавляет их результаты при извлечении. Это широко используемый продакшен-паттерн для внешней памяти; Mem0 (Chhikara et al., 2025) — одна из эталонных реализаций.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 07 (MemGPT), Phase 14 · 08 (Letta Blocks)
**Time:** ~75 minutes

## Learning Objectives

- Объяснить, почему одного хранилища (только вектор, только граф, только KV) для памяти агента недостаточно.
- Назвать три параллельных хранилища Mem0 и то, под что каждое оптимизировано.
- Описать сплавляющий скоринг Mem0 — релевантность, важность, свежесть — и почему это взвешенная сумма, а не иерархия.
- Реализовать игрушечную память из трёх хранилищ на stdlib, где `add()` пишет во все три, а `search()` сплавляет результаты.

## The Problem

Одно хранилище всегда не подходит для одного из трёх классов запросов:

- **Semantic similarity** — «что мы обсуждали про дрейф агента на прошлой неделе?» Выигрывает вектор; KV и граф промахиваются.
- **Fact lookup** — «какой у пользователя номер телефона?» Выигрывает KV; вектор здесь расточителен, граф — перебор.
- **Relationship reasoning** — «какие клиенты завязаны на одно и то же платёжное юрлицо?» Выигрывает граф; вектор и KV на такое ответить не могут.

Продакшен-агенты выдают все три класса запросов в одной сессии. Память из одного хранилища всегда неправа в двух случаях из трёх. Вклад Mem0 — свести все три за одним общим интерфейсом `add`/`search` и добавить функцию скоринга, которая их сплавляет.

> 🎒 **На пальцах.** Это как искать в квартире: одежду вы ищете по виду (вектор), ключи — на конкретном крючке (KV), а «чей это зонт» — по связям с людьми (граф). Три класса запросов, и одно хранилище закрывает ровно один: два из трёх запросов оно провалит. Поэтому и держат все три сразу.

## The Concept

### Three stores in parallel

Что делает Mem0 (arXiv:2504.19413, апрель 2025) при `add(text, user_id, metadata)`:

1. Извлекает из текста факты-кандидаты (шаг, который делает LLM).
2. Пишет каждый факт в векторное хранилище (embedding) под семантический поиск.
3. Пишет каждый факт в KV-хранилище по ключу (user_id, fact_type, entity) для доступа за O(1).
4. Пишет каждый факт в графовое хранилище (Mem0g) как типизированные рёбра под запросы о связях.

> 🎒 **На пальцах.** Один факт записывается трижды — как если бы вы вписали новый телефон друга и в контакты, и в бумажную книжку, и в схему «кто кому родственник». Из фразы на два факта получается шесть записей: втрое больше места и втрое больше работы на запись, зато любой из трёх типов запроса найдёт своё.

Что происходит при `search(query, user_id)`:

1. Векторное хранилище возвращает top-k по косинусу embedding.
2. KV-хранилище возвращает прямые попадания по выведенному из запроса ключу (user_id, type, entity).
3. Графовое хранилище возвращает подграф, достижимый из сущностей запроса.
4. Скоринговый слой сплавляет эти три результата.

> 🎒 **На пальцах.** Три поиска идут параллельно, а не по очереди — это важно для задержки: общее время равно самому медленному из трёх, а не их сумме. Если вектор отвечает за 80 мс, KV за 1 мс, а граф за 40 мс, вся выборка займёт около 80 мс, и только потом скоринг ранжирует пришедшее.

### Fusion scoring

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **Relevance** — косинус для вектора, точное совпадение для KV, вес пути для графа.
- **Importance** — помечается при записи или выучивается (некоторые факты важнее: имена, идентификаторы, политики).
- **Recency** — экспоненциальное затухание по времени с последней записи или чтения.

Веса настраиваются под конкретный продукт. Выше `w_recency` для чат-агентов; выше `w_importance` для агентов соответствия требованиям; выше `w_relevance` для агентов, живущих на retrieval.

> 🎒 **На пальцах.** Это как выбор ресторана: важны и близость, и рейтинг, и «когда я там был в последний раз», просто веса у всех разные. Ключевое слово — сумма, а не иерархия. Возьмите веса 0.5 / 0.3 / 0.2: старый номер паспорта с релевантностью 0.6, важностью 1.0 и свежестью 0.5 наберёт 0.3 + 0.3 + 0.1 = 0.7, а вчерашняя болтовня с релевантностью 0.9, важностью 0 и свежестью 1.0 — только 0.45 + 0 + 0.2 = 0.65. Менее релевантный факт выигрывает за счёт важности.

### Mem0g and temporal reasoning

Mem0g добавляет детектор конфликтов. Когда новый факт противоречит существующему ребру, старое ребро помечается невалидным, но не удаляется. Временные запросы («в каком городе жил пользователь в марте?») обходят подграф, валидный на нужный момент.

Это то поведение уровня комплаенса, которое паттерн инвалидации в Letta обобщает.

> 🎒 **На пальцах.** Как в бухгалтерии: неверную проводку не стирают, а сторнируют отдельной записью, чтобы история осталась. Поэтому «пользователь живёт в Берлине» не исчезает при переезде в Лиссабон — у ребра просто закрывается интервал валидности, и запрос «где он жил в марте» всё ещё находит правильный ответ.

### Benchmark numbers

Статья Mem0 приводит такие числа (2025):

- **LoCoMo** (память о длинных разговорах): 91.6
- **LongMemEval** (эпизодическая память с долгим горизонтом): 93.4
- **BEAM 1M** (бенчмарк памяти на 1M токенов): 64.1

Все базовые решения для сравнения (LLM с полным контекстом на 128k, плоское векторное хранилище, плоское KV) проигрывают на 10+ пунктов. Бенчмарки сами по себе выбор не оправдывают — его оправдывает операционная форма, — но числа показывают, что сплавляющий дизайн даёт не погрешность округления.

> 🎒 **На пальцах.** Отрыв в 10+ пунктов — это как разница между «сдал на четвёрку» и «сдал на троечку»: заметно, но не магия. И обратите внимание на BEAM 1M: 64.1 против 91.6 на LoCoMo. Чем длиннее горизонт, тем хуже всем, включая гибрид, — просто остальным ещё хуже.

### Scope taxonomy

Mem0 делит память по областям видимости:

- **User memory** — живёт между сессиями, ключом идёт `user_id`.
- **Session memory** — живёт внутри одного треда.
- **Agent memory** — состояние конкретного экземпляра агента.

Каждая запись выбирает одну область. Извлечение может спрашивать сразу несколько областей со своими весами для каждой. Смешивание областей без раздумий — это ровно то, как получаются инциденты вида «ассистент рассказал Алисе про проект Боба».

> 🎒 **На пальцах.** Области видимости — как папки «личное», «этот чат», «этот бот»: перепутали папку, и приватное всплыло у чужого человека. Формально `user_id` — единственное, что отделяет память Алисы от памяти Боба, поэтому забытая фильтрация по нему — это не баг ранжирования, а утечка данных.

### Where this pattern goes wrong

- **Embedding drift.** Векторные результаты, которые на первой сотне запросов выглядели правильными, деградируют по мере роста корпуса. Добавьте периодический пересчёт embedding для топ-N самых используемых записей.
- **KV schema creep.** Ключ `(user_id, type, entity)` кажется простым, пока каждая команда не начнёт добавлять свой `type`. Проводите ревизию набора типов раз в квартал.
- **Graph explosion.** Один шумный экстрактор добавляет по 50 рёбер на сообщение. Ограничьте число записей в граф на один вызов `add`; выбрасывайте рёбра с низкой уверенностью.

```figure
ae-memory-fusion
```

> 🎒 **На пальцах.** Посчитайте graph explosion: 50 рёбер на сообщение при разговоре из 100 сообщений — это 5 000 рёбер за одну сессию, и обход подграфа замедляется на порядок. Лимит вида «не больше 5 рёбер на вызов `add`» звучит грубо, но именно он держит граф читаемым для агента, а не только для базы.

## Build It

`code/main.py` реализует паттерн трёх хранилищ на stdlib:

- `VectorStore` — наивная близость по пересечению токенов вместо настоящего embedding.
- `KVStore` — словарь с ключом `(user_id, fact_type, entity)`.
- `GraphStore` — типизированные рёбра (subject, relation, object, valid).
- `Mem0` — фасад верхнего уровня с `add()`, `search()`, сплавляющим скорингом и извлечением с учётом областей видимости.
- Разобранную трассу на разговоре с несколькими пользователями и несколькими сессиями.

> 🎒 **На пальцах.** Обратите внимание на поле `valid` у рёбер `GraphStore` — это тот самый мягкий делит из раздела про Mem0g, одна булева переменная вместо удаления. И заметьте, что настоящий embedding здесь заменён пересечением токенов: паттерн от этого не меняется, только качество вектора.

Запуск:

```
python3 code/main.py
```

Вывод показывает три отдельных пути вспоминания плюс сплавленный top-k. Поменяйте веса скоринга в начале `main()` и посмотрите, как поедет ранжирование.

> 🎒 **На пальцах.** Это самый полезный эксперимент урока: выкрутите `w_recency` в единицу, а остальные веса в ноль — и наверх выдачи вылезет последняя записанная реплика, даже если она вообще не про запрос. Так на своих глазах видно, что скоринг решает не меньше, чем сами хранилища.

## Use It

- **Mem0 (Apache 2.0)** — готово к продакшену. Self-host на Postgres + Qdrant + Neo4j либо управляемое облако.
- **Letta** — три уровня core/recall/archival; векторный и графовый бэкенды приносите свои.
- **Zep** — коммерческая альтернатива с временным графом знаний и извлечением фактов.
- **Custom builds** — когда нужен точный контроль над экстрактором (комплаенс) или над весами сплавления (голосовые агенты, где доминирует свежесть).

> 🎒 **На пальцах.** Обратите внимание на цену self-host у Mem0: три отдельные базы (Postgres, Qdrant, Neo4j), которые надо администрировать, бэкапить и обновлять. Именно это и означает «выбирайте по операционной форме»: паттерн у всех четырёх вариантов один, а вот сколько систем вам придётся держать живыми — разное.

## Ship It

`outputs/skill-hybrid-memory.md` порождает каркас памяти из трёх хранилищ со сплавляющим скорером, таксономией областей видимости и подключённой временной инвалидацией.

> 🎒 **На пальцах.** Skill сразу проставляет три вещи, которые руками забывают: веса скоринга, поле области видимости в каждой записи и флаг валидности. Забудете первое — получите случайное ранжирование, второе — утечку между пользователями, третье — потерянную историю фактов.

## Exercises

1. Замените игрушечную векторную близость настоящей embedding-моделью (sentence-transformers, Ollama, OpenAI embeddings). Померьте recall@10 на синтетическом длинном разговоре. Дрейфует ли ранжирование за 1000 записей?
2. Добавьте временной запрос: `search(query, as_of=timestamp)`. Возвращайте только записи, валидные на этот момент или раньше. Какому хранилищу придётся переделать больше всего?
3. Реализуйте детектор конфликтов: если входящий факт противоречит ребру графа, инвалидируйте старое ребро и залогируйте оба. Проверьте на «пользователь живёт в Берлине» -> «пользователь живёт в Лиссабоне».
4. Добавьте в сплавляющий скорер измерение `user_feedback` (лайк на найденную запись). Как не дать системе играть с этим показателем (агент возвращает только те записи, которые уже понравились)?
5. Прочитайте документацию Mem0 (`docs.mem0.ai`). Перенесите игрушку на вызовы клиента `mem0`. Сравните качество извлечения на тех же 20 тестовых запросах.

> 🎒 **На пальцах.** Начните с третьего задания — оно самое короткое и самое поучительное. На паре «Берлин -> Лиссабон» вы увидите, что правильный ответ — это не одна запись, а две: старое ребро с `valid=False` и новое с `valid=True`. Если после эксперимента в графе осталась только одна строка, вы сделали удаление, а не инвалидацию.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Hybrid memory | «Вектор плюс граф плюс KV» | Три хранилища, в которые пишут параллельно и результаты которых сплавляют при извлечении |
| Fact extraction | «Загрузка в память» | Шаг с LLM, который разбирает текст на кортежи (сущность, отношение, факт) |
| Fusion scoring | «Ранжирование по релевантности» | Взвешенная сумма релевантности, важности и свежести |
| Scope | «Пространство имён памяти» | user / session / agent — определяет, кто что видит |
| Mem0g | «Граф памяти» | Типизированные рёбра с временной валидностью под запросы о связях |
| Temporal invalidation | «Мягкое удаление» | Помечать опровергнутые рёбра невалидными; никогда не удалять |
| Embedding drift | «Гниение поиска» | Качество вектора падает с ростом корпуса; периодически пересчитывайте embedding |

> 🎒 **На пальцах.** Соберите таблицу в одну фразу: fact extraction кладёт факты в три хранилища, fusion scoring достаёт их обратно, scope решает, кому их видно, а temporal invalidation следит, чтобы старое не выдавалось за правду. Всё остальное в уроке — детали этих четырёх шагов.
