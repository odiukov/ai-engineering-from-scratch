# Блоки памяти и sleep-time compute

> Дискретные функциональные блоки памяти, которые модель может править напрямую, плюс sleep-time агент, который асинхронно консолидирует память, пока основной агент простаивает. Эти две идеи — способ масштабировать память дальше одного разговора.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 07 (MemGPT)
**Time:** ~75 minutes

## Learning Objectives

- Назвать три уровня памяти, которые использует Letta (core, recall, archival), и роль каждого.
- Объяснить паттерн блоков памяти: Human block, Persona block и пользовательские блоки как полноценные типизированные объекты.
- Описать, что такое sleep-time compute, почему он стоит вне критического пути и почему на нём можно крутить модель сильнее, чем у основного агента.
- Реализовать сценарный цикл из двух агентов, где основной агент отдаёт ответы, а sleep-time агент консолидирует блоки между ходами.

## The Problem

MemGPT (урок 07) решил вопрос управления потоком в виртуальной памяти. И тут же вылезли три продакшен-проблемы:

1. **Latency.** Каждая операция с памятью сидит на критическом пути. Если агенту приходится чистить, пересказывать или сверять факты, пока пользователь ждёт, хвостовая задержка взлетает.
2. **Memory rot.** Записи накапливаются. Опровергнутые факты остаются на месте. Поиск утопает в устаревшем содержимом.
3. **Structure loss.** Плоское архивное хранилище не умеет выразить мысль «Human block всегда в промпте; Persona block всегда в промпте; Task block меняется от сессии к сессии».

Letta (letta.com) — это имя платформы, которое изначальный проект MemGPT взял себе в 2024 году (за паттерном из статьи имя MemGPT сохранилось), а переписанная Letta V1 в 2026 году — это уже отдельный, более поздний шаг. Блоки памяти делают структуру явной; sleep-time compute убирает консолидацию с критического пути.

> 🎒 **На пальцах.** Latency тут как кассир, который посреди вашего чека уходит переставлять товар на полках: очередь стоит. Из трёх проблем выше первую лечит sleep-time compute (уборка в фоне), вторую — он же (дедупликация и инвалидация), а третью — блоки памяти. Один урок, два инструмента, три закрытые дыры.

## The Concept

### Three tiers

| Tier | Scope | Where it lives | Written by |
|------|-------|----------------|------------|
| Core | Всегда виден | Внутри главного промпта | Вызов инструмента агентом + перезаписи sleep-time агентом |
| Recall | История разговора | Достаётся по запросу | Автоматическое логирование ходов |
| Archival | Произвольные факты | Вектор + KV + граф | Вызов инструмента агентом + загрузка sleep-time агентом |

Core — это core из MemGPT. Recall — это буфер разговора вместе с вытесненным хвостом. Archival — внешнее хранилище. Такое разделение убирает перегруженность двух уровней MemGPT.

> 🎒 **На пальцах.** Три уровня — как рабочий стол, ящик стола и архив в подвале: доставать всё дороже по мере удаления. Посмотрите на колонку «Written by»: в двух строках из трёх пишут сразу двое — сам агент и sleep-time агент, — и именно эта двойная запись потом потребует версионирования блоков.

### Memory blocks

Блок — это типизированный, постоянный, редактируемый раздел уровня core. Оригинальная статья MemGPT определила два таких:

- **Human block** — факты о пользователе (имя, роль, предпочтения, цели).
- **Persona block** — самопредставление агента (личность, тон, ограничения).

Letta обобщает это до произвольных пользовательских блоков: блок `Task` под текущую цель, блок `Project` под факты о кодовой базе, блок `Safety` под жёсткие ограничения. У каждого блока есть `id`, `label`, `value`, `limit` (лимит символов), `description` (чтобы модель понимала, когда его править).

Блоки правятся через набор инструментов:

- `block_append(label, text)`
- `block_replace(label, old, new)`
- `block_read(label)`
- `block_summarize(label)` — сжать блок, который подошёл к своему лимиту.

> 🎒 **На пальцах.** Блок — это как отдельная страница в блокноте с подписанным заголовком: «про пользователя», «про себя», «текущая задача». Ключевое поле — `limit`: если у Human block лимит 2 000 символов, то двадцатая запись по 150 символов уже не влезет, и придётся вызывать `block_summarize`. Поле `description` нужно не человеку, а модели — по нему она решает, в какую страницу писать.

### Sleep-time compute

Добавление Letta 2025 года: запускать второго агента в фоне, вне критического пути. Sleep-time агенты обрабатывают транскрипты разговоров и контекст кодовой базы, пишут `learned_context` в общие блоки и консолидируют или инвалидируют архивные записи.

Свойства, которые из этого сами выпадают:

- **No latency cost.** Ответы основного агента не ждут операций с памятью.
- **Stronger model allowed.** Sleep-time агент может быть более дорогой и медленной моделью, потому что его не ограничивает задержка.
- **Natural consolidation window.** Дедупликация, пересказ и инвалидация опровергнутых фактов происходят, когда пользователь ничего не ждёт.

Форма совпадает с тем, как работают люди: вы делаете задачу, вы с ней спите, а долговременная память укладывается за ночь.

> 🎒 **На пальцах.** Буквально «утро вечера мудренее»: днём вы отвечаете, ночью мозг раскладывает по полкам. Экономика тут простая: если консолидация занимает 4 секунды, то на критическом пути это +4 секунды к каждому ответу, а в фоне — ноль, и за эти же 4 секунды можно позволить себе модель втрое дороже.

### Native reasoning

Letta V1 (`letta_v1_agent`, 2026) объявляет устаревшими `send_message`/heartbeat и встроенные в текст токены `Thought:` в пользу нативных рассуждений. Responses API (OpenAI) и Messages API с extended thinking (Anthropic) отдают рассуждения по отдельному каналу и прокидывают их между ходами (в продакшене — в зашифрованном виде у разных провайдеров). Цикл управления остался ReAct. Просто трасса размышлений теперь структурная, а не сделанная из промпта.

> 🎒 **На пальцах.** Разница как между «думать вслух в микрофон» и «думать в отдельной служебной записке». Раньше мысль была строкой `Thought:` внутри того же текста, который агент выдавал наружу, — её приходилось парсить и она сжигала токены общего ответа. Теперь это отдельное поле в ответе API, и ломать его случайной перефразировкой промпта уже нельзя.

### Where this pattern goes wrong

- **Block bloat.** Бесконечный `block_append` быстро упирается в лимит. Подключите суммаризатор блока прямо перед записью, которая выталкивает за предел.
- **Silent drift.** Sleep-time агент перезаписал блок, а основной агент этого не заметил. Версионируйте блоки и показывайте диффы в трассе.
- **Poisoned consolidation.** Sleep-time агент перемалывает в core контент, до которого может достать атакующий. Урок 27 применим и к sleep-time поверхности тоже.

```figure
memory-blocks
```

> 🎒 **На пальцах.** Silent drift — это как если бы кто-то ночью правил ваши конспекты без пометок: утром вы читаете и не понимаете, откуда взялась эта фраза. Лечится дёшево — храните старое значение и дифф при каждой записи, тогда вопрос «почему агент забыл X» становится одним вызовом `block_history`.

## Build It

`code/main.py` реализует:

- `Block` — поля id, label, value, limit, description.
- `BlockStore` — CRUD плюс хелпер `near_limit(label)`.
- Два сценарных агента: `PrimaryAgent` отрабатывает ход, `SleepTimeAgent` консолидирует между ходами.
- Трассу, где видно разговор на три хода с записями в блоки, а также sleep-time проход, который пересказывает блок и инвалидирует устаревший факт.

> 🎒 **На пальцах.** Заметьте, насколько мал `Block`: пять полей, и три из них (`id`, `label`, `value`) — это буквально «номер, название, текст». Вся сложность живёт не в структуре данных, а в двух агентах, которые её правят: один пишет быстро и грязно, второй приходит потом и убирает.

Запуск:

```
python3 code/main.py
```

Транскрипт показывает это разделение: ходы основного агента быстрые и оставляют сырые записи; sleep-проход уплотняет и убирает мусор.

> 🎒 **На пальцах.** Обратите внимание на `near_limit(label)` — это весь секрет автоматического пересказа: пока блок не подошёл к лимиту, sleep-time агент его не трогает. На разговоре из трёх ходов вы увидите ровно один sleep-проход и сможете сравнить блок до и после — сырые записи против уплотнённых.

## Use It

- **Letta** (letta.com) как эталонная реализация. Self-host или управляемое облако.
- **Claude Agent SDK skills** как знания в форме блоков: skill — это именованный, версионированный, доставаемый по требованию блок инструкций, который агент подгружает сам.
- **Custom builds** для команд, которым нужен контроль над бэкендом хранения. Используйте контракт Letta API, чтобы потом было куда переехать.

> 🎒 **На пальцах.** Совет про контракт API — самый практичный в уроке. Даже если вы пишете своё хранилище на Postgres, назовите методы как в Letta (`block_append`, `block_replace`, `block_read`), и переезд на Letta потом обойдётся в правку одного адаптера, а не в переписывание агента.

> 🎒 **На пальцах.** Skill выдаёт не текст про блоки, а готовый каркас: сами блоки, их лимиты и точку входа для sleep-time прохода. Две вещи, которые он подключает по умолчанию, — safety-правила и citation-поля, — это ровно те, о которых забывают, когда собирают блоки руками.

## Exercises

1. Добавьте инструмент `block_summarize`, который заменяет значение блока сгенерированным моделью пересказом, когда `near_limit` возвращает true. При каком пороге срабатывания одновременно минимальны и число вызовов суммаризации, и переполнение блоков?
2. Реализуйте sleep-time дедупликацию над архивом: две записи, у которых текст пересекается по токенам больше чем на 90%, сливаются в одну. Делайте это только в sleep-проходе, никогда на критическом пути.
3. Версионируйте блоки. При каждой записи фиксируйте старое значение и дифф. Выставьте наружу `block_history(label)`, чтобы операторы могли разобраться, «почему агент забыл X».
4. Относитесь к sleep-time агентам как к недоверенным писателям. Когда они трогают блок Persona или Safety, требуйте ревью вторым агентом перед фиксацией.
5. Перенесите пример на Letta API (`letta_v1_agent`). Что меняется в схеме блоков и как нативные рассуждения меняют форму трассы?

> 🎒 **На пальцах.** Начните со второго задания: порог 90% пересечения токенов легко проверить руками. Возьмите две записи по десять слов, у которых девять слов общие, — они сольются, а при восьми общих останутся раздельными. Заодно почувствуйте, почему такое считают в sleep-проходе: на тысяче записей это миллион сравнений пар, и в ответе пользователю такому места нет.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Memory block | «Редактируемый раздел промпта» | Типизированный постоянный сегмент core-памяти, который правит сама LLM |
| Human block | «Память о пользователе» | Факты о пользователе, приколоченные в core |
| Persona block | «Личность агента» | Самопредставление, тон, ограничения, приколоченные в core |
| Sleep-time compute | «Асинхронная работа с памятью» | Второй агент, делающий консолидацию вне критического пути |
| Core / Recall / Archival | «Уровни» | Трёхслойное разделение памяти: всегда видимое / разговор / внешнее |
| Block limit | «Ограничение» | Лимит символов на блок; вынуждает делать пересказ |
| Native reasoning | «Канал размышлений» | Вывод рассуждений на уровне провайдера, а не `Thought:` на уровне промпта |
| Learned context | «Вывод sleep-агента» | Факты, которые sleep-time агент пишет в общие блоки |

> 🎒 **На пальцах.** Свяжите две строки таблицы в одну мысль: Block limit заставляет пересказывать, а Sleep-time compute делает это в фоне. Именно поэтому learned context и block limit всегда идут парой: без лимита блок разрастётся, без фонового агента пересказ будет тормозить ответ пользователю.
