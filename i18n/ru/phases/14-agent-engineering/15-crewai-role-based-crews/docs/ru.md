# Команды агентов по ролям — роли, задачи, процессы

> Четыре примитива: Agent, Task, Crew, Process. Две формы верхнего уровня: Crews (автономная работа по ролям) и Flows (детерминированная работа по событиям). CrewAI — референсная реализация 2026 года, и её документация не стесняется: «для любого продакшен-приложения начинайте с Flow».

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 12 (Workflow Patterns), Phase 14 · 14 (Actor Model)
**Time:** ~75 minutes

## Learning Objectives

- Назвать четыре примитива CrewAI (Agent, Task, Crew, Process) и понять, что отвечает за что.
- Различать процессы Sequential, Hierarchical и запланированный Consensus; выбирать один под свою нагрузку.
- Различать Crews (автономная работа по ролям) и Flows (детерминированная работа по событиям) и объяснять, что документация советует для продакшена.
- Подключать инструменты декоратором `@tool` и наследником `BaseTool`; рассуждать про структурированный вывод против свободного текста.
- Назвать четыре типа памяти в CrewAI и понимать, когда каждый из них окупается.
- Реализовать команду из трёх агентов на стандартной библиотеке (researcher, writer, editor), которая выпускает справку.
- Замечать три типовые поломки CrewAI: раздувание промпта, налог на менеджера-LLM, хрупкие передачи работы.

> 🎒 **На пальцах.** Четыре примитива — это всё, что нужно выучить наизусть. Agent — кто, Task — что, Crew — коробка со всем этим, Process — в каком порядке. Дальше идёт конфигурация: три агента и три задачи — это шесть объектов и один список, а не новый язык.

## The Problem

Команды, которые берут многоагентные фреймворки, упираются в одну и ту же стену. «Автономная коллаборация» отлично звучит в демо. Потом клиент присылает баг-репорт, и вам нужно детерминированно воспроизвести прогон. Или финансисты спрашивают, сколько стоит один прогон команды с маршрутизацией на LLM. Или дежурному инженеру надо понять, какой агент завис в три часа ночи.

Свободные команды с маршрутизацией на LLM не отвечают ни на один из этих вопросов внятно. Чистые DAG отвечают на все, но теряют исследовательскую форму, которая нужна брейнсторм-агенту.

Разделение в CrewAI честно называет цену выбора. Crews — для совместной исследовательской работы по ролям. Flows — для событийного, кодом описанного, проверяемого продакшена. Один фреймворк, две формы, выбор под каждый участок.

> 🎒 **На пальцах.** Заметьте, что все три вопроса — от клиента, от финансов, от дежурного — про одно: воспроизводимость. Свободная команда на один и тот же запрос выдаст три разных пути и три разных счёта. Flow на один и тот же вход даёт один и тот же порядок шагов, а значит, вопросы получают ответы.

## The Concept

### Four primitives

Поверхность CrewAI маленькая. Запомните эти четыре штуки — остальное конфигурация.

- **Agent.** `role + goal + backstory + tools + (optional) llm`. Легенда (backstory) здесь несущая конструкция. Она задаёт тон, суждения и момент, когда агент остановится. Инструменты — функции, которые агент может вызвать (подробнее ниже).
- **Task.** `description + expected_output + agent + (optional) context + (optional) output_pydantic`. Переиспользуемая единица работы. `expected_output` — это контракт. В `context` перечислены задачи выше по потоку, чьи результаты передаются внутрь. `output_pydantic` заставляет вывод принять заданную форму.
- **Crew.** Контейнер. Держит список `agents`, список `tasks`, `process`, а также опциональные настройки `memory`, `verbose` и `manager_llm`.
- **Process.** Стратегия выполнения. Sequential, Hierarchical, Consensus (запланирован). Задаёт форму прогона.

Агенты не видят друг друга напрямую. Задачи ссылаются на агентов. Crew выстраивает задачи по порядку. Process решает, кто берёт следующую задачу. Вот и вся ментальная модель.

> **Validated against** CrewAI 0.86 (2026-05). В новых версиях типы процессов могут переименоваться или слиться; сверьтесь с [CrewAI Processes docs](https://docs.crewai.com/concepts/processes), прежде чем опираться на конкретную форму.

> 🎒 **На пальцах.** Ключевая фраза здесь — «агенты не видят друг друга напрямую». Общаются они только через результаты задач: писатель читает не мысли исследователя, а строку, которую тот вернул. Как в конторе с папками: вам передают папку, а не пересказывают, что человек думал, пока её собирал.

### Sequential vs Hierarchical vs Consensus

- **Sequential.** Задачи идут в порядке объявления. Результат задачи N доступен как `context` задаче N+1. Дешевле всего. Предсказуемо. Берите, когда порядок фиксирован.
- **Hierarchical.** Агент-менеджер (отдельный вызов LLM) маршрутизирует работу между специалистами. CrewAI поднимает менеджера либо из вашей настройки `manager_llm`, либо по умолчанию. Менеджер каждый раунд выбирает следующую задачу и может отказать или перенаправить. Берите, когда специалистов четыре и больше и порядок реально зависит от предыдущего результата.
- **Consensus.** Запланирован, в публичном API пока не реализован. Документация зарезервировала имя под будущий процесс с голосованием. Сегодня на него полагаться нельзя.

Hierarchical добавляет вызов LLM на каждый раунд (менеджер) сверху к каждому вызову специалиста. На прогоне из пяти шагов расход токенов может утроиться. Платите за это только тогда, когда маршрутизация действительно нужна.

> 🎒 **На пальцах.** Посчитайте налог на менеджера. Пять задач в Sequential — пять вызовов LLM. Те же пять задач в Hierarchical — шесть вызовов, и каждый вызов менеджера тащит с собой весь список задач и все предыдущие результаты, то есть самый жирный промпт в прогоне. Отсюда и «расход может утроиться»: дело не в числе вызовов, а в их размере.

### Crews vs Flows

Именно с этого противопоставления документация начинает в 2026 году.

- **Crew.** Автономия, которой управляет LLM. Форму прогона фреймворк выбирает на ходу. Хорошо для исследований, брейнсторма, первых черновиков — всюду, где путь сам является частью ответа. Плохо воспроизводится. Плохо тестируется. Дёшево прототипируется.
- **Flow.** Событийный граф, которым владеете вы. `@start` помечает вход. `@listen(topic)` помечает шаг, который срабатывает, когда другой шаг публикует эту тему. Каждый шаг — обычный Python (внутри может звать Crew). Хорошо для продакшена. Наблюдаемо. Тестируемо. Детерминированно.

Рекомендация документации для продакшена в 2026 году: начинайте с Flow. Вкладывайте Crew внутрь как вызовы `Crew.kickoff()` из шагов Flow там, где автономия отбивает свою цену. Flow даёт вам журнал аудита, Crew даёт исследование. Комбинируйте, а не выбирайте.

> 🎒 **На пальцах.** Композиция здесь важнее выбора. Представьте Flow из трёх шагов, где второй шаг — «набросать три варианта заголовка» — вызывает Crew. Шаги 1 и 3 воспроизводимы до буквы, а вся непредсказуемость заперта внутри одного шага. Дежурный сравнивает хороший прогон с плохим и сразу видит, что разошлось именно во втором шаге.

### Tool integration

Есть три способа дать агенту инструмент. Берите самый простой из подходящих.

1. **`@tool` decorator.** Обычные функции становятся инструментами. Сигнатура — это схема, докстринг — описание, которое видит LLM. Лучше всего для одноразовых помощников.

   ```python
   from crewai.tools import tool

   @tool("Search the web")
   def search(query: str) -> str:
       """Return top results for the query."""
       return run_search(query)
   ```

2. **`BaseTool` subclass.** Инструмент на классе: явная схема аргументов, поддержка async, ретраи. Берите, когда у инструмента есть состояние (клиент, кэш) или нужны структурированные аргументы.

   ```python
   from crewai.tools import BaseTool
   from pydantic import BaseModel

   class SearchArgs(BaseModel):
       query: str
       limit: int = 10

   class SearchTool(BaseTool):
       name = "web_search"
       description = "Search the web and return top results."
       args_schema = SearchArgs

       def _run(self, query: str, limit: int = 10) -> str:
           return self.client.search(query, limit=limit)
   ```

3. **Built-in toolkits.** CrewAI поставляет свои адаптеры: `SerperDevTool`, `FileReadTool`, `DirectoryReadTool`, `CodeInterpreterTool`, `RagTool`, `WebsiteSearchTool`. Подключаются одним импортом.

Для структурированного вывода используется Pydantic. Передайте `output_pydantic=MyModel` в Task. CrewAI проверит ответ модели по этой схеме и либо приведёт его к нужной форме, либо повторит запрос. В паре с этим держите плотную строку `expected_output`. Свободный текст нормален для черновиков; структурированный вывод — это то, что дальше сможет съесть Flow.

> 🎒 **На пальцах.** Разница между двумя блоками кода выше — в состоянии. Функция под `@tool` каждый раз начинает с нуля, а `SearchTool` держит внутри `self.client`, то есть открытое соединение, которое переиспользуется между вызовами. Пятьдесят поисков через декоратор — это пятьдесят новых клиентов, через класс — один.

### Memory hooks

CrewAI из коробки даёт четыре типа памяти. Они совместимы: команда может включить все четыре сразу.

> **Validated against** CrewAI 0.86 (2026-05). В свежих релизах всё идёт через единую систему `Memory`, которая оборачивает эти четыре хранилища. Концептуальная модель ниже остаётся верной, но публичные классы в новых версиях могут свернуться в одну точку входа `Memory`; проверьте текущее API в [CrewAI memory docs](https://docs.crewai.com/concepts/memory).

- **Short-term.** Буфер разговора внутри одного прогона. Стирается в конце.
- **Long-term.** Сохраняется между прогонами. Лежит в векторной базе (по умолчанию Chroma, заменяема). Достаётся по похожести на текущую задачу.
- **Entity.** Факты по сущностям. «Клиент X на корпоративном тарифе». Ключ — сущность, а не похожесть. Живёт между прогонами.
- **Contextual.** Извлечение в момент сборки промпта. Достаёт нужное тогда, когда агенту это понадобилось, а не грузит заранее.

Включается на уровне Crew через `memory=True` или настройками по типам. Работает на провайдере эмбеддингов, который вы настроите (по умолчанию OpenAI, можно заменить на локальный). Память — одно из мест, где CrewAI отбивает свой вес по сравнению с более тонкими фреймворками; в чистом LangGraph каждый из этих четырёх видов вы прикручиваете сами.

> 🎒 **На пальцах.** Long-term и Entity различаются способом поиска, а не сроком жизни. Long-term ищет по похожести: спросили про возвраты — вытащит три похожих обрывка из прошлых прогонов. Entity ищет по ключу: «клиент X» — и отдаёт ровно его факты. Первый ошибается и приносит лишнее, второй либо находит, либо нет.

### When role-based teams fit

- От трёх до шести агентов с названными ролями и совместным процессом. Черновики, ревью, планирование, брейнсторм.
- Маршрутизация, где суждение LLM о следующем шаге и есть часть ценности (Hierarchical).
- Всюду, где команде приятнее читать `role + goal + backstory`, чем описание графа.

### When they do not

- Детерминированные DAG со строгим порядком. Берите LangGraph (Lesson 13). Форма графа тут и есть правильная абстракция, а ролевая рамка CrewAI только мешает.
- Бюджеты задержки в доли секунды. Hierarchical добавляет круги по сети. Даже Sequential сериализует промпты, в которые вложены легенды агентов и предыдущие результаты.
- Одиночные агентные циклы. Пропустите фреймворк: цикл агента (Lesson 1) плюс реестр инструментов будет короче.

Lesson 17 (Agent Framework Tradeoffs) раскладывает всё это по матрице. Коротко: CrewAI сидит в углу «совместная работа по ролям».

> 🎒 **На пальцах.** Обратите внимание на границу «от трёх до шести агентов». Меньше трёх — фреймворк дороже задачи: один агент с инструментами пишется короче. Больше шести — легенды и предыдущие результаты забивают контекст, и агенты начинают путаться, кто здесь кто. Роли имеют смысл, только когда их достаточно, чтобы разделить работу, и мало, чтобы все влезли в промпт.

### Dependency shape

От LangChain не зависит. Python с 3.10 по 3.13. Использует `uv`. Число звёзд смотрите в [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) (снимок на 2026-05). Интеграция с AWS Bedrock задокументирована; бенчмарки от вендора обещают заметный выигрыш по скорости против LangGraph на задачах вопрос-ответ, но методика (датасет, железо, метрика) не опубликована, так что цифры от разработчиков фреймворка стоит воспринимать только как направление.

> 🎒 **На пальцах.** Независимость от LangChain — не идеология, а прикладная деталь. Она означает, что CrewAI не притащит за собой полдесятка версий чужих пакетов, и обновление LangChain в вашем проекте не сломает команду агентов. Заодно инструменты LangChain придётся подключать через адаптер, а не напрямую.

### Where this pattern goes wrong

- **Prompt-bloat from backstories.** Легенда на две тысячи слов у каждого агента плюс команда из пяти агентов сжигают бюджет контекста ещё до первого вызова инструмента. Держите легенды короче 200 слов. Переиспользуйте формулировки между агентами; не повторяйте описание правил дома пять раз.
- **Manager-LLM token tax.** Процесс Hierarchical добавляет вызов менеджера-LLM перед каждым вызовом специалиста. На команде из пяти задач это шесть вызовов LLM вместо пяти, причём вызов менеджера тащит весь список задач и предыдущие результаты. Переходите на Sequential, если маршрутизация не зависит от результата.
- **Brittle handoffs.** В задаче N `expected_output` — «план текста». Задача N+1 читает его как `context` и пытается разобрать три раздела. Модель написала четыре. Агент дальше по потоку начинает импровизировать. Лечится через `output_pydantic` на задаче N, чтобы задача N+1 читала типизированный объект, а не свободный текст.
- **Crew-as-prod.** Свободная Crew уехала в продакшен без обёртки Flow. Разброс результатов большой, воспроизвести прогон невозможно, дежурный не может сравнить плохой прогон с хорошим. Оберните во Flow.

## Build It

`code/main.py` реализует обе формы на стандартной библиотеке плюс команду из трёх агентов.

Shape:

- Датаклассы `Agent` и `Task`, повторяющие поверхность CrewAI.
- `SequentialCrew.kickoff(inputs)` прогоняет задачи в порядке объявления, продевая результаты через `context`.
- `HierarchicalCrew.kickoff(topic)` добавляет агента-менеджера, который каждый раунд выбирает следующего специалиста, и останавливается на «done».
- `Flow` с декораторами `@start` и `@listen(topic)`, крошечным циклом событий и трассой.
- Декоратор `tool(name)`, повторяющий форму `@tool` из CrewAI.
- `Memory` с хранилищами `short_term`, `long_term`, `entity`; похожесть считается на numpy, но данные фиктивные.
- Ответы модели — заранее прописанные строки, подобранные по роли и началу входа. Никакой сети. Детерминированно.

Конкретное демо: команда researcher, writer, editor выпускает справку по теме «agent engineering 2026». Исследователь достаёт (фиктивные) источники. Писатель пишет черновик. Редактор его подтягивает. Та же команда прогоняется через Flow, чтобы показать детерминированную форму.

Run it:

```bash
python3 code/main.py
```

Трасса покрывает: последовательную команду, которая продевает результаты через `context`; иерархическую команду с выборами менеджера (researcher, writer, editor, потом «done»); flow, который прогоняет те же три шага с явными темами (`researched`, `drafted`, `edited`); вызовы инструментов через `@tool`; и долгосрочную память, которая переживает два запуска.

> 🎒 **На пальцах.** Сравните две трассы в выводе. Иерархическая команда решает состав на ходу, поэтому в принципе может поменять порядок и вы увидите это только в логе. Flow объявляет темы заранее: `researched` → `drafted` → `edited`, и другого порядка просто нет. Разница между «обычно так» и «всегда так» — и есть тема урока.

## Use It

- **CrewAI Flow** для продакшена. Даже если Flow — это один шаг, который зовёт `Crew.kickoff()`. Flow даёт границу аудита.
- **CrewAI Crew (Sequential)** для совместной работы с понятным порядком, особенно для первых черновиков и циклов ревью.
- **CrewAI Crew (Hierarchical)** когда маршрутизация зависит от результата и специалистов у вас четыре или больше.
- **LangGraph** (Lesson 13) для явных конечных автоматов, надёжного возобновления и строгого порядка.
- **AutoGen v0.4** (Lesson 14) для конкурентности на акторной модели и изоляции сбоев.
- **OpenAI Agents SDK** (Lesson 16) для продуктов вокруг OpenAI с передачами работы и ограждениями.
- **Claude Agent SDK** (Lesson 17) для продуктов вокруг Claude с субагентами и хранилищем сессий.

> 🎒 **На пальцах.** Первый пункт стоит перечитать. «Flow из одного шага, который зовёт Crew» выглядит бессмысленной обёрткой, но именно она даёт вход, выход и точку, где можно записать трассу. Обёртка пишется за десять минут, а без неё вопрос «что именно случилось в прогоне номер 4712» останется без ответа.

## Ship It

`outputs/skill-crew-or-flow.md` выбирает Crew или Flow под задачу и собирает минимальную реализацию. Жёстко отклоняет Crew без легенды, Flow без явных тем и Hierarchical с меньше чем тремя специалистами.

## Pitfalls

- **Backstory as flavor.** Легенда влияет на результат. Протестируйте по три варианта на агента; разброс реальный. Выберите один и заморозьте.
- **Skipping `expected_output`.** Без контракта на каждую задачу задачи ниже по потоку подхватят то, что модель выдала. Команда работает; аудит проваливается.
- **Memory always-on.** Долгосрочная память пишется на каждом прогоне. Векторная база растёт. Поиск становится шумным. Ограничьте записи задачами, где факт действительно долгоживущий.
- **Manager prompt drift.** Промпт менеджера в Hierarchical неявный. Если маршрутизация начала чудить, включите verbose, выгрузите промпт и прочитайте его.
- **Tool side effects in Crews.** Crew может вызвать инструмент чаще, чем вы ожидали. POST, DELETE и оплата — это шаг Flow, но никогда не инструмент внутри Crew.

> 🎒 **На пальцах.** Последний пункт — про деньги в буквальном смысле. Свободная Crew, которой дали инструмент `charge_card`, может дёрнуть его дважды, потому что решила, что первый ответ был неубедительным. В шаге Flow вызов происходит ровно один раз, потому что порядок задан кодом, а не суждением модели.

## Exercises

1. Переведите последовательную команду во Flow. Посчитайте, в скольких точках упал разброс. Отметьте, где просела читаемость.
2. Добавьте команде память по сущностям: факты о клиенте должны жить между запусками. Проверьте, что поиск достаёт нужную сущность.
3. Реализуйте процесс Hierarchical, где менеджер отказывается отдавать работу редактору, пока в выводе писателя меньше трёх абзацев. Проследите повтор по трассе.
4. Сделайте инструмент (фиктивный веб-поиск) наследником `BaseTool`. Сравните форму трассы с версией на декораторе `@tool`.
5. Добавьте `output_pydantic=Brief` в задачу редактора, где у `Brief` есть `title`, `summary`, `sections`. Заставьте задачу писателя один раз выдать битый JSON; убедитесь по трассе, как CrewAI делает повтор.
6. Прочитайте вводную часть документации CrewAI. Перенесите игрушку на настоящее API `crewai`. Каких гарантий не было в версии на стандартной библиотеке?
7. Подключите AgentOps или Langfuse (Lesson 24) к настоящему прогону. Каких трасс вам не хватало в версии на стандартной библиотеке?

> 🎒 **На пальцах.** Задание 5 показывает цену контракта. Без `output_pydantic` битый JSON тихо уезжает дальше, и редактор начинает выдумывать разделы. С ним CrewAI видит непрохождение схемы и делает ещё один вызов: вы платите один лишний запрос вместо того, чтобы получить справку с четырьмя разделами вместо трёх.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Agent | «Персона» | Роль + цель + легенда + инструменты |
| Task | «Единица работы» | Описание + ожидаемый результат + исполнитель + опциональный структурированный вывод |
| Crew | «Команда агентов» | Контейнер для агентов, задач и процесса |
| Process | «Стратегия выполнения» | Sequential / Hierarchical / Consensus (запланирован) |
| Flow | «Детерминированный рабочий процесс» | Событийный, описанный кодом, тестируемый |
| Backstory | «Промпт персоны» | Задаёт агенту тон и манеру суждений |
| `@tool` | «Инструмент из функции» | Декоратор, превращающий функцию в инструмент для агента |
| `BaseTool` | «Инструмент на классе» | Класс со схемой аргументов, ретраями и поддержкой async |
| Entity memory | «Факты по сущностям» | Память в границах клиента, аккаунта или тикета |
| Long-term memory | «Память между прогонами» | Память на векторной базе, живущая между запусками |
| Contextual memory | «Извлечение по требованию» | Память, которую достают в тот момент, когда агенту она нужна |
| Manager LLM | «Агент-роутер» | Дополнительная LLM в процессе Hierarchical, выбирающая следующую задачу |
| `expected_output` | «Контракт задачи» | Строка, которая говорит агенту (и аудиту), какую форму вернуть |

> 🎒 **На пальцах.** Три строки про память — это три разных вопроса. Long-term: «что похожее мы уже делали?». Entity: «что мы знаем про этого клиента?». Contextual: «что подложить в промпт именно сейчас?». Включив всё сразу на команде из трёх агентов, вы получите три источника лишнего текста в каждом промпте — поэтому включайте по одному и смотрите, что окупается.
