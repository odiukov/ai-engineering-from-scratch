# Использование инструментов и вызов функций

> Toolformer (Schick et al., 2023) запустил самообучаемую разметку вызовов инструментов. Berkeley Function Calling Leaderboard V4 (Patil et al., 2025) задаёт планку 2026 года: 40% агентных сценариев, 30% многоходовых, 10% live, 10% non-live, 10% на галлюцинации. Одиночный вызов решён. Память, динамические решения и длинные цепочки инструментов — нет.

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 01 (Agent Loop), Phase 13 · 01 (Function Calling Deep Dive)
**Time:** ~60 minutes

## Learning Objectives

- Объяснить обучающий сигнал Toolformer: разметку вызова оставляем только тогда, когда исполнение снижает loss на следующем токене.
- Назвать пять оценочных категорий BFCL V4 и то, что измеряет каждая.
- Реализовать на stdlib реестр инструментов с валидацией схемы, приведением аргументов и песочницей для исполнения.
- Диагностировать три открытые проблемы 2026 года: длинные цепочки инструментов, динамическое принятие решений и память.

## The Problem

Раннее использование инструментов спрашивало: сумеет ли модель предсказать корректный вызов функции? Современное спрашивает: сумеет ли модель сцепить инструменты через 40 шагов — с памятью, при частичной наблюдаемости, с восстановлением после сбоев инструментов, ни разу не выдумав инструмент, которого не существует?

> 🎒 **На пальцах.** Разница как между «умеешь набрать номер?» и «умеешь провести на телефоне рабочий день»: 40 звонков подряд, кто-то не берёт трубку, что-то надо помнить с утра. Первое давно решено. Каждый из четырёх усложнителей в вопросе выше — память, частичная видимость, восстановление, отказ от несуществующих инструментов — это отдельная категория провалов.

Toolformer задал базовую линию: модели умеют учиться, когда звать инструменты, на самообучении. BFCL V4 определяет цель оценки на 2026 год. В разрыве между ними и живут продакшн-агенты.

## The Concept

### Toolformer (Schick et al., NeurIPS 2023)

Идея: пусть модель сама разметит свой предобучающий корпус кандидатами на вызовы API. Каждого кандидата — выполнить. Разметку оставить только если добавление результата инструмента снижает loss на следующем токене. Дообучить на отфильтрованном корпусе.

> 🎒 **На пальцах.** Критерий отбора красиво прост: помог ли результат инструмента угадать следующее слово. Если после «2 + 3 =» подстановка ответа калькулятора «5» делает предсказание увереннее, вызов оставляем; если нет — выбрасываем. Разметчики-люди не нужны, текст сам показывает, где инструмент был кстати.

Покрытые инструменты: калькулятор, вопросно-ответная система, поисковики, переводчик, календарь. Сигнал самообучения касается исключительно того, помогает ли инструмент предсказывать текст, — никаких человеческих метк.

Результат про масштаб: использование инструментов проявляется с размером. Маленьким моделям разметка инструментов вредит, большим — помогает. Именно поэтому у фронтир-моделей 2026 года использование инструментов встроено намертво, а большинству 7B-моделей нужно отдельное дообучение под инструменты, чтобы быть надёжными.

> 🎒 **На пальцах.** Это как выдать калькулятор первокласснику и десятикласснику: младшему он только мешает, потому что тот не понимает, когда его брать. Практический вывод: если ваша локальная 7B-модель путается в инструментах, дело не в промптах, а в пороге масштаба — либо дообучайте её под инструменты, либо берите модель побольше.

### Berkeley Function Calling Leaderboard V4 (Patil et al., ICML 2025)

BFCL — фактический стандарт оценки в 2026 году. Состав V4:

- **Agentic (40%)** — полные траектории агента: память, много ходов, динамические решения.
- **Multi-Turn (30%)** — интерактивные диалоги с цепочками инструментов.
- **Live (10%)** — реальные промпты от пользователей (более трудное распределение).
- **Non-Live (10%)** — синтетические тест-кейсы.
- **Hallucination (10%)** — распознать случай, когда никакой инструмент вызывать не нужно.

> 🎒 **На пальцах.** Сложите проценты: 40 + 30 = 70% оценки — это многоходовые сценарии, а на чистый одиночный вызов остаётся 10% non-live. Бенчмарк переехал туда, где живут настоящие агенты. Отдельно любопытна категория Hallucination на 10%: там правильный ответ — не вызывать вообще ничего.

V3 ввёл оценку по состоянию: после последовательности вызовов проверяется фактическое состояние API (например, «файл создан?»), а не совпадение AST вызовов. V4 добавил категории веб-поиска, памяти и чувствительности к формату.

> 🎒 **На пальцах.** Это разница между «ты правильно продиктовал рецепт» и «на столе стоит торт». Проверка по состоянию не спорит о форме вызова: файл либо создан, либо нет. То же правило берите в свои тесты — проверяйте результат в системе, а не текст вызова, иначе тест сломается от переименования аргумента.

Ключевая находка 2026 года: одиночный вызов функции практически решён. Провалы сконцентрированы в памяти (перенос контекста между ходами), в динамическом принятии решений (выбор инструментов по предыдущим результатам), в длинных цепочках (дрейф после 20+ шагов) и в распознавании галлюцинаций (отказ вызывать, когда ни один инструмент не подходит).

> 🎒 **На пальцах.** Четыре места провалов — это ваш чек-лист при отладке агента: помнит ли он, что было 10 ходов назад; выбирает ли следующий инструмент по итогу предыдущего; не рассыпается ли после 20 шагов; умеет ли сказать «здесь инструмент не нужен». Тестировать одиночный вызов уже почти незачем — он и так работает.

### Tool schema

Схема есть у каждого провайдера. Детали разные, форма одна:

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic использует `input_schema` напрямую. OpenAI использует `function.parameters`. Оба принимают JSON Schema. Описания несут нагрузку — модель читает именно их, чтобы выбрать нужный инструмент. Плохие описания инструментов — причина №1 провалов «выбран не тот инструмент».

> 🎒 **На пальцах.** Три строки в блоке выше — это весь контракт: имя, описание, схема входа. Разница провайдеров сводится к имени одного ключа: `input_schema` против `function.parameters`, а JSON Schema внутри одинаковая. Описание же — не комментарий для человека: сравните «Search» и «Use when the user asks about events after your knowledge cutoff» — во втором случае модель понимает, когда инструмент звать НЕ надо.

### Argument validation

Не доверяйте ни одному вызову инструмента. Проверяйте:

1. **Type coercion.** Модель может вернуть строку "5" там, где в схеме стоит int. Приведите, если однозначно; отклоните, если нет.
2. **Enum validation.** Если в схеме `status in {"open", "closed"}`, а модель выдала `"in_progress"`, отклоняйте с описательной ошибкой.
3. **Required fields.** Пропущено обязательное поле — сразу возвращаем модели наблюдение об ошибке, а не падаем.
4. **Format validation.** Даты, email, URL — проверяйте настоящими парсерами, а не регулярками.

> 🎒 **На пальцах.** Четыре проверки — четыре типа брака на входе: строка "5" вместо числа 5, `"in_progress"` вместо разрешённых `open`/`closed`, забытое обязательное поле и дата в формате, который не разбирается. Первый случай можно тихо починить, остальные три — только отклонить с внятным текстом, иначе вы протащите мусор дальше в систему.

Каждый провал валидации должен возвращать структурированное наблюдение, чтобы модель могла повторить попытку в правильной форме.

> 🎒 **На пальцах.** Ключевое слово — наблюдение, а не исключение. Упавший вызов не должен ронять агента: верните ему строку «поле status получило in_progress, допустимы open или closed», и он исправится на следующем ходу. Это ровно разница между агентом, который сам восстанавливается, и стектрейсом в логе, который читаете вы.

### Parallel tool calls

Современные провайдеры поддерживают параллельные вызовы инструментов в одном ходу ассистента. Цикл такой:

1. Модель выдаёт 3 вызова инструментов с разными `tool_use_id`.
2. Рантайм их выполняет (параллельно, если они независимы).
3. Каждый результат возвращается блоком `tool_result`, сопоставленным по `tool_use_id`.

Инженерное правило: считайте id сопоставления несущей конструкцией. Перепутайте их — и получите маршрутизацию «не тот инструмент к не тому результату».

> 🎒 **На пальцах.** Три вызова разом — это три курьера, отправленных одновременно: если один вызов идёт 400 мс, то три подряд займут 1,2 секунды, а три параллельно — те же 400 мс. Вся сложность в одном: перепутали два `tool_use_id` — вернули погоду Лондона на вопрос про Токио, и модель уверенно соврёт, потому что подмену ей не видно.

### Sandboxing

Исполнение инструментов — это граница песочницы. Подробности в уроке 09. Коротко: у каждого инструмента должны быть прописаны поверхность чтения и записи, доступ в сеть, таймаут и лимит памяти. Универсальный `run_shell(cmd)` — красный флаг; конкретный `git_status()` безопаснее.

> 🎒 **На пальцах.** Сравните два инструмента буквально: у `run_shell(cmd)` поверхность записи — вся файловая система, у `git_status()` — ноль. Поэтому четыре ограничения (что читает, что пишет, есть ли сеть, сколько секунд и памяти) прописываются не «на будущее»: инструмент с лишними правами рано или поздно ими воспользуется — по ошибке модели или по чужой подсказке в тексте.

## Build It

`code/main.py` реализует реестр инструментов продакшн-формы:

- Валидатор подмножества JSON Schema (только stdlib).
- Регистрацию инструмента с описанием, входной схемой, таймаутом и исполнителем.
- Приведение аргументов и валидацию enum.
- Параллельную отправку вызовов с id сопоставления.
- Наблюдения об ошибках в виде структурированных строк.

Запустите:

```
python3 code/main.py
```

Трасса показывает мини-агента, который зовёт три инструмента в одном ходу, причём один вызов заведомо испорчен и отклоняется с описательной ошибкой, по которой модель может действовать.

> 🎒 **На пальцах.** Самое важное в этой трассе — не то, что три правильных вызова прошли, а то, что четвёртый, испорченный, вернулся понятным текстом. Проверяйте свой реестр именно так: сломайте один аргумент нарочно и посмотрите, получил ли агент подсказку, достаточную для исправления со второй попытки.

## Use It

У каждого провайдера своя схема инструментов — Anthropic, OpenAI, Gemini, Bedrock. Если нужен мультипровайдер, берите слой трансляции (OpenAI Agents SDK, Vercel AI SDK, адаптер инструментов LangChain). BFCL — эталонный бенчмарк: прогоняйте его по своему агенту перед релизом, если использование инструментов для продукта центрально.

> 🎒 **На пальцах.** Слой трансляции — это тот самый транслятор из фазы 13: одно каноническое объявление и по одному маленькому переводчику на провайдера. А прогон BFCL перед релизом стоит того же, чего любой тест: узнать про свои провалы на многоходовых цепочках от бенчмарка, а не от пользователей в первый день.

## Exercises

1. Добавьте инструмент-пустышку, который позволяет модели явно отказаться от использования всех остальных. Замерьте на тесте на галлюцинации в духе BFCL.
2. Реализуйте приведение аргументов для int-в-строке и float-в-строке. С какого момента приведение начинает прятать настоящие баги?
3. Добавьте таймаут на инструмент и предохранитель (отказывать в инструменте на 60 секунд после 3 провалов подряд). Что это меняет в том, как модель восстанавливается?
4. Прочитайте описание BFCL V4. Выберите одну категорию (например, multi-turn) и прогоните 10 примеров промптов через своего агента. Отчитайтесь по доле прохождений.
5. Перенесите stdlib-валидатор на Pydantic или Zod. Что Pydantic/Zod поймал, а игрушечный валидатор пропустил?

> 🎒 **На пальцах.** Начните с третьего задания: таймаут и предохранитель — это то, что понадобится в проде первым, а логика «3 провала подряд → отдых 60 секунд» пишется в десяток строк. Второе задание даст самый полезный спор: строку "5" превратить в 5 безопасно, а "5 apples" — уже нет, и граница между этими двумя случаями и есть предмет вашего проектирования.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Function calling | «Tool use» | Вызов инструмента через структурированный вывод с валидацией по схеме |
| Toolformer | «Самообучаемая разметка инструментов» | Schick 2023 — оставляем те вызовы, чьи результаты снижают loss на следующем токене |
| BFCL | «Berkeley Function Calling Leaderboard» | Бенчмарк 2026 года: 40% агентных, 30% многоходовых, 10% live, 10% non-live, 10% на галлюцинации |
| Tool schema | «Сигнатура функции для модели» | Имя, описание, JSON Schema аргументов |
| tool_use_id | «Id сопоставления» | Связывает вызов инструмента с его результатом; обязателен для параллельной отправки |
| Hallucination detection | «Знать, когда не вызывать» | Категория V4: отказаться от вызова, когда ни один инструмент не подходит |
| Argument coercion | «Починка строки в число» | Узкие исправления предсказуемых расхождений со схемой; при неоднозначности — отклонять |
| Sandboxing | «Граница исполнения инструмента» | Поверхность чтения и записи, сеть, таймаут и лимит памяти для каждого инструмента |
