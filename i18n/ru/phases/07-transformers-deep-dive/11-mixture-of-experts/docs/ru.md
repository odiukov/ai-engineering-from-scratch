# Смесь экспертов (Mixture of Experts, MoE)

> Плотный трансформер на 70B активирует все параметры на каждый токен. MoE на 671B активирует всего 37B на токен и обходит его на каждом бенчмарке. Разреженность — главная идея масштабирования за десятилетие.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 7 · 05 (Full Transformer), Phase 7 · 07 (GPT)
**Time:** ~45 minutes

## The Problem

У плотного трансформера число FLOPs на инференсе равно числу параметров (умноженному на 2 за прямой проход). Увеличьте плотную модель — и каждый токен платит по полному счёту. К 2024 году фронтир упёрся в стену вычислений: чтобы стать заметно умнее, нужно было экспоненциально больше FLOPs на токен.

Mixture of Experts разрывает эту связь. Заменяем каждый FFN на `E` независимых экспертов плюс роутер, который выбирает `k` экспертов на токен. Всего параметров = `E × FFN_size`. Активных параметров на токен = `k × FFN_size`. Типичная конфигурация 2026 года: `E=256`, `k=8`. Хранение растёт с `E`, вычисления растут с `k`.

Фронтир 2026 года почти целиком состоит из MoE: DeepSeek-V3 (671B всего / 37B активных), Mixtral 8×22B, Qwen2.5-MoE, Llama 4, Kimi K2, gpt-oss. В независимом рейтинге Artificial Analysis все десять лучших открытых моделей — MoE.

> 🎒 **На пальцах.** Плотная модель — это завод, где на каждую деталь запускают все станки сразу. MoE — завод, где под деталь включают только нужные 8 станков из 256. Подставьте числа: 256 экспертов лежат в памяти, но работают 8, то есть считает примерно 3% железа. Хранить приходится все 256, платить за расчёт — только за 8.

## The Concept

![MoE layer: router selects k of E experts per token](../assets/moe.svg)

### The FFN swap

Блок плотного трансформера:

```
h = x + attn(norm(x))
h = h + FFN(norm(h))
```

Блок MoE:

```
h = x + attn(norm(x))
scores = router(norm(h))              # (N_tokens, E)
top_k = argmax_k(scores)              # pick k of E per token
h = h + sum_{e in top_k}(
        gate(scores[e]) * Expert_e(norm(h))
    )
```

Каждый эксперт — это независимый FFN (обычно SwiGLU). Роутер — один линейный слой. Каждый токен сам выбирает свои `k` экспертов и получает взвешенную смесь их выходов.

> 🎒 **На пальцах.** Разница между двумя блоками ровно в одной строке: было `FFN(norm(h))`, стало «посчитать `scores`, взять top-k, сложить их выходы с весами». Attention не изменился совсем. Это как в поликлинике заменить одного терапевта на регистратуру плюс 256 узких специалистов: путь пациента до регистратуры тот же, дальше его отправляют к двум-восьми нужным врачам.

### The load-balancing problem

Если роутер отправляет 90% токенов в эксперта 3, остальные эксперты голодают. Пробовали три лечения:

1. **Auxiliary load-balancing loss** (Switch Transformer, Mixtral). Добавить штраф, пропорциональный разбросу в загрузке экспертов. Работает, но добавляет гиперпараметр и второй градиентный сигнал.
2. **Expert capacity + token dropping** (ранний Switch). Каждый эксперт обрабатывает максимум `C × N/E` токенов; лишние токены просто пропускают слой. Бьёт по качеству.
3. **Auxiliary-loss-free balancing** (DeepSeek-V3). Добавить обучаемый сдвиг (bias) на каждого эксперта, который двигает top-k выбор роутера. Bias обновляется вне loss обучения. Никакого штрафа на основную задачу. Главное открытие 2024 года.

> 🎒 **На пальцах.** Возьмите 8 экспертов и 100 токенов. Идеал — по 12–13 токенов на эксперта. Перекос вида «эксперт 3 получил 90, остальные по 1–2» означает, что вы обучаете одну маленькую сеть, а 7/8 весов зря занимают память. Второй вариант из списка лечит перекос грубо: эксперт с лимитом `C × 100/8` просто выбрасывает всё, что не влезло, и эти токены проходят слой без FFN вообще.

Подход DeepSeek-V3: после каждого шага обучения для каждого эксперта проверяем, выше или ниже цели его загрузка. Двигаем bias на `±γ`. Выбор идёт по `scores + bias`. Вероятности экспертов для гейтинга берутся из исходных `scores` без изменений. Роутинг отвязывается от выражения.

> 🎒 **На пальцах.** Хитрость в том, что bias влияет только на «кого позвали», но не на «с каким весом сложили». Пример: у эксперта 3 оценка 5.0, у эксперта 7 — 4.8, но эксперт 3 перегружен и получил bias −0.5. Тогда выбирают эксперта 7 (4.8 против 4.5), а в формулу гейтинга всё равно идут честные 4.8 и 5.0. Так очередь выравнивается, а предсказания модели никто не подкручивает.

### Shared experts

DeepSeek-V2/V3 ещё и делит экспертов на *shared* и *routed*. Через всех shared-экспертов проходит каждый токен. Routed-эксперты выбираются через top-k. Shared-эксперты держат общие знания; routed-эксперты специализируются. V3 гоняет 1 shared-эксперта плюс top-8 из 256 routed.

> 🎒 **На пальцах.** Shared-эксперт — это школьная программа, которую проходят все, а routed — кружки по выбору. Без общего слоя каждому из 256 специалистов пришлось бы отдельно выучить, что такое пробел и точка. Один shared-эксперт делает эту чёрную работу один раз, и остальные 256 освобождаются под настоящую специализацию.

### Fine-grained experts

Классический MoE (GShard, Switch): каждый эксперт шириной с полный FFN. `E` маленькое (8–64), `k` маленькое (1–2).

Современный fine-grained MoE (DeepSeek-V3, Qwen-MoE): каждый эксперт уже (1/8 от размера FFN). `E` большое (256+), `k` больше (8+). Всего параметров столько же, но число комбинаций растёт куда быстрее. `C(256, 8) = 400 trillion` возможных «экспертов» на токен. Качество растёт, latency остаётся на месте.

> 🎒 **На пальцах.** Считаем в лоб: 8 больших экспертов при k=2 дают 28 комбинаций. 256 узких экспертов при k=8 дают 400 триллионов. Параметров и активных FLOPs при этом столько же — просто вместо двух крупных «отделов» токен собирает себе бригаду из восьми узких специалистов. Это как перейти от 8 готовых блюд в меню к конструктору из 256 ингредиентов.

### The cost profile

На токен, на слой:

| Config | Active params / token | Total params |
|--------|-----------------------|--------------|
| Mixtral 8×22B | ~39B | 141B |
| Llama 3 70B (dense) | 70B | 70B |
| DeepSeek-V3 | 37B | 671B |
| Kimi K2 (MoE) | ~32B | 1T |

DeepSeek-V3 обходит плотную Llama 3 70B почти на каждом бенчмарке, делая при этом **меньше активных FLOPs на токен**. Больше параметров = больше знаний. Больше активных FLOPs = больше вычислений на токен. MoE разводит эти две вещи.

> 🎒 **На пальцах.** Читаем строчку DeepSeek-V3: 37B из 671B — это примерно 5.5%, то есть на токен считается одна восемнадцатая модели. У Llama 3 70B оба числа равны: 70 и 70, считается всё. Итог парадоксальный только на первый взгляд — модель в 9.5 раза больше по весам считает почти вдвое дешевле на токен и при этом отвечает лучше.

### The catch: memory

Все эксперты лежат на GPU независимо от того, кто из них сработал. Модели на 671B нужно около 1.3 ТБ VRAM под веса в fp16. Деплой фронтирного MoE требует expert parallelism — эксперты размазываются по GPU, токены ездят по сети. Latency определяется коммуникацией all-to-all, а не матричным умножением.

> 🎒 **На пальцах.** Откуда 1.3 ТБ: 671 миллиард параметров по 2 байта на fp16 — это 1342 ГБ, то есть примерно 17 карт H100 по 80 ГБ только под веса. Экономия на FLOPs есть, экономии на памяти нет вообще. И дальше становится обиднее: токен, попавший к эксперту на соседней карте, ждёт не расчёта, а поездки по сети.

## Build It

Смотрите `code/main.py`. Компактный MoE-слой на чистой стандартной библиотеке:

- `n_experts=8` экспертов в духе SwiGLU (по одному линейному слою на каждого, для наглядности)
- роутинг top-k=2
- веса гейтинга, нормализованные softmax
- балансировка без вспомогательного loss через bias на каждого эксперта

### Step 1: the router

```python
def route(hidden, W_router, top_k, bias):
    scores = [sum(h * w for h, w in zip(hidden, W_router[e])) for e in range(len(W_router))]
    biased = [s + b for s, b in zip(scores, bias)]
    top_idx = sorted(range(len(biased)), key=lambda i: -biased[i])[:top_k]
    # softmax over ORIGINAL scores of the chosen experts
    chosen = [scores[i] for i in top_idx]
    m = max(chosen)
    exps = [math.exp(c - m) for c in chosen]
    s = sum(exps)
    gates = [e / s for e in exps]
    return top_idx, gates
```

Bias влияет на выбор, но не на вес гейта. Это и есть трюк DeepSeek-V3 — bias чинит перекос загрузки, не сдвигая предсказания модели.

> 🎒 **На пальцах.** Проследите за переменными: `biased` используется ровно один раз — в `sorted(...)`, чтобы получить `top_idx`. Дальше в `chosen` берутся `scores[i]`, то есть исходные оценки без bias. Одна строчка кода отделяет «кого выбрали» от «с каким весом сложили», и именно в этом весь фокус.

### Step 2: run 100 tokens through the router

Считаем, кто из экспертов сколько раз сработал. Без bias загрузка перекошена. С циклом обновления bias (`-γ` для перегруженных экспертов, `+γ` для недогруженных) загрузка выравнивается, а дальше *колеблется* вокруг равномерной, но не сходится к ней: шаг всегда фиксированный `±γ`, независимо от того, насколько сильно эксперт отклонился, поэтому стоит счётчику перейти цель — следующий шаг перебрасывает его обратно за неё. Амплитуду этих колебаний задаёт γ: малая γ — тесная орбита вокруг равномерного, большая γ — счётчики перелетают цель и скачут. Запустите `code/main.py` и увидите, как энтропия подбирается близко к `ln(E)` и залипает в повторяющемся цикле, а не в неподвижной точке.

> 🎒 **На пальцах.** 100 токенов при top-k=2 дают 200 назначений на 8 экспертов, то есть в идеале по 25 на каждого. Если эксперт набрал 60, ему на следующем шаге вычтут γ, и часть токенов уедет к соседям. Это буквально термостат: перегрелся — прикрутили, остыл — прибавили. И ведёт себя он как настоящий термостат: температура не встаёт ровно на заданной отметке, а вечно ходит вокруг неё, а насколько широко — решает размер шага γ.

### Step 3: param count comparison

Печатаем «плотный эквивалент» конфигурации MoE. В форме DeepSeek-V3: 256 routed + 1 shared, 8 активных, d_model=7168. Общее число параметров пугающее: ~806B весов FFN на 61 слое, примерно **в 14 раз больше, чем ~56B FFN** у плотной Llama 3 70B (80 слоёв, d_model 8192, hidden 28672 у SwiGLU).

Всегда говорите явно, какие два числа вы делите, потому что и «5%», и «половина» описывают одну и ту же модель:

| Сравнение | Отношение |
|-----------|-----------|
| Активный FFN DeepSeek против её же полного FFN | 28B / 806B ≈ 3.5% (это и есть разреженность по экспертам, `k/E`) |
| Активный FFN DeepSeek против FFN у Llama-3-70B | 28B / 56B ≈ **половина** |
| Активные параметры модели DeepSeek против всех параметров Llama-3-70B | 37B / 70B ≈ **53%** |

То есть MoE делает не седьмую часть работы плотной модели, а примерно половину вычислений на токен от плотной 70B — но носит с собой в ~14 раз больше накопленных знаний. В этом и весь обмен: вычисления на токен задаёт `k`, объём знаний задаёт `E`.

> 🎒 **На пальцах.** Скрипт печатает два числа рядом не просто так. Общее число (сотни миллиардов) говорит, сколько GPU надо купить и чем их заполнить. Активное число (десятки миллиардов) говорит, сколько вы платите за каждый сгенерированный токен. У плотной модели эти два числа совпадают, у MoE различаются в 10–30 раз — и вся выгода прячется именно в этом разрыве.

## Use It

Загрузка через HuggingFace:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
model = AutoModelForCausalLM.from_pretrained("mistralai/Mixtral-8x22B-v0.1")
```

Продакшен-инференс в 2026 году: vLLM поддерживает MoE-роутинг нативно. У SGLang самый быстрый путь для expert parallelism. Оба сами разбираются с выбором top-k и распределением экспертов.

**When to pick MoE:**
- Нужно фронтирное качество при меньшей стоимости инференса на токен.
- Есть VRAM и инфраструктура под expert parallelism.
- Нагрузка тяжёлая по токенам (чат, код), а не по контексту (длинные документы).

**When NOT to pick MoE:**
- Edge-деплой — вы платите за полное хранение ради любого активного FLOP.
- Обслуживание одного пользователя с жёстким требованием по latency — роутинг экспертов добавляет накладные расходы.
- Маленькие модели (<7B) — преимущество MoE по качеству появляется только выше порога вычислений (примерно 6B активных параметров).

> 🎒 **На пальцах.** Про edge всё видно на одном примере: чтобы получить свои 37B активных, вам всё равно надо где-то держать 671B весов. На ноутбуке с 32 ГБ это не помещается, даже если считает модель дёшево. MoE — выбор для сервера с горой памяти и толстым батчем, а не для телефона.

## Exercises

1. **Easy.** Запустите `code/main.py`. Посмотрите, как обновление bias без вспомогательного loss выравнивает загрузку экспертов за свои 10 итераций — и заметьте, что счётчики в итоге ходят по кругу вокруг цели, а не встают на неё. Поменяйте `gamma` и убедитесь, что амплитуда цикла следует за γ.
2. **Medium.** Замените обучаемый роутер на роутер по хешу (детерминированный, без обучения). Сравните качество и балансировку. Почему обучаемый роутер лучше?
3. **Hard.** Реализуйте «rollout-matched routing» в духе GRPO (трюк DeepSeek-V3.2): записывайте, какие эксперты сработали на инференсе, и принудительно повторяйте тот же роутинг при расчёте градиентов. Измерьте эффект на игрушечной задаче policy gradient.

> 🎒 **На пальцах.** Подсказка ко второму заданию: хеш-роутер балансировать умеет идеально — просто `hash(token) % 8` даёт ровно по 12–13 токенов на эксперта из 100. Проблема в другом: он раскидывает токены случайно, поэтому эксперт не может ни на чём специализироваться. Балансировка бесплатная, смысл нулевой — и это ровно то, что вы увидите в качестве.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| Expert | «Один FFN из многих» | Независимая сеть прямого распространения; параметры, выделенные под разреженный кусок вычислений FFN. |
| Router | «Гейт» | Крошечный линейный слой, который оценивает каждый токен против каждого эксперта; выбор top-k. |
| Top-k routing | «k активных экспертов на токен» | FFN-часть вычислений для токена проходит ровно через k экспертов, взвешенных гейтом. |
| Auxiliary loss | «Штраф за дисбаланс» | Дополнительное слагаемое в loss, наказывающее перекос в загрузке экспертов. |
| Auxiliary-loss-free | «Трюк DeepSeek-V3» | Балансировка через bias на каждого эксперта, влияющий только на выбор роутера; без лишнего градиента. |
| Shared expert | «Всегда включён» | Дополнительный эксперт, через которого проходит каждый токен; держит общие знания. |
| Expert parallelism | «Шардирование по экспертам» | Разные эксперты живут на разных GPU; токены ездят по сети. |
| Sparsity | «Активных параметров меньше, чем всего» | Два разных отношения, которые постоянно путают. **Разреженность по экспертам** внутри одного MoE-слоя: `k × expert_size / (E × expert_size)` = `k / E` = 8/256 ≈ 3.1% у DeepSeek-V3. **Доля активных параметров модели**: 37B / 671B ≈ 5.5% — больше, потому что attention, эмбеддинги и всегда включённый shared expert срабатывают на каждый токен и в дробь `k / E` не входят. |
