# KV-кэш, Flash Attention и оптимизация инференса

> Обучение параллельно и упирается в FLOPs. Инференс последователен и упирается в память. Другое узкое место — другие трюки.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 7 · 02 (Self-Attention), Phase 7 · 05 (Full Transformer), Phase 7 · 07 (GPT)
**Time:** ~75 minutes

## The Problem

Наивный авторегрессионный декодер делает `O(N²)` работы, чтобы сгенерировать `N` токенов: на каждом шаге он пересчитывает attention по всему префиксу. Для ответа в 4K токенов это 16 миллионов операций attention, и большая их часть лишняя. Каждое скрытое состояние префиксного токена детерминировано, как только его посчитали — вам нужно лишь прогнать query нового токена против закэшированных ключей и значений всего, что было раньше.

Вдобавок сам attention гоняет много данных. Стандартный attention материализует матрицу оценок N×N, выход softmax N×d, финальный выход N×d — слишком много чтений и записей в HBM. При N≥2K attention становится memory-bound раньше, чем FLOP-bound. Классические ядра attention недогружают современные GPU в 4–10 раз.

Две оптимизации, обе от Dao и соавторов, перевели фронтирный инференс из «медленно» в «быстро»:

1. **KV cache.** Храним векторы K и V каждого префиксного токена. Attention нового токена — это один query против закэшированных ключей. Инференс падает с `O(N²)` до `O(N)` на шаг генерации.
2. **Flash Attention.** Режем вычисление attention на тайлы так, чтобы полная матрица N×N вообще не попадала в HBM. Весь softmax и матричные умножения происходят в SRAM. Ускорение по часам в 2–4 раза на A100; в 5–10 раз на H100 с FP8.

К 2026 году обе техники стали всеобщими. Любой продакшен-стек инференса (vLLM, TensorRT-LLM, SGLang, llama.cpp) их предполагает. Любая фронтирная модель едет с включённым Flash Attention.

> 🎒 **На пальцах.** Откуда 16 миллионов: 4096 токенов, и на шаге номер `i` модель смотрит на `i` предыдущих. Сумма 1+2+...+4096 ≈ 8.4 млн пар, то есть порядка 16 млн операций — и почти всё это пересчёт вчерашних новостей. Представьте, что вы дописываете письмо и перед каждым новым словом перечитываете письмо с начала.

### KV cache math

На слой декодера, на токен — просуммировав по всем KV-головам:

```
bytes_per_token_per_layer = 2 * n_kv_heads * d_head * dtype_size
                          ^
                          K and V
```

`n_kv_heads` — это число *различных* KV-голов: при MHA оно равно числу query-голов, при GQA меньше, при MQA равно единице.

Для модели на 7B с 32 слоями, 32 головами (обычная MHA, то есть `n_kv_heads = 32`), d_head=128, fp16:

```
per token per layer = 2 * 32 * 128 * 2 = 16384 bytes (16 KB)
per token (32 layers) = 512 KB
per 32K context = 16 GiB
```

> 🎒 **На пальцах.** Пройдите арифметику пальцем и не потеряйте головы — самая частая ошибка именно здесь. 2 (это K и V) × 32 KV-головы × 128 чисел в голове × 2 байта на fp16 = 16384 байта, то есть 16 КБ на токен на слой. Слоёв 32, значит 512 КБ на один токен. Контекст 32K токенов — 16 ГиБ. То есть один длинный диалог съедает больше видеопамяти, чем весит вся модель в fp16 (14 ГБ), а про батч из десяти таких диалогов можно даже не начинать. Если у вас получилось 512 байт на слой, вы посчитали одну голову вместо тридцати двух и занизили ответ в 32 раза.

Для Llama 3 70B (80 слоёв, d_head=128, GQA с 8 KV-головами):

```
per token per layer = 2 * 8 * 128 * 2 = 4096 bytes (4 KB)
per token (80 layers) = 320 KiB
per 32K context = 10 GiB (10.7 GB в десятичных единицах)
```

Эти 10 ГиБ и объясняют, почему Llama 3 70B на контексте 128K занимает почти всю 40-гигабайтную A100 одним лишь KV-кэшем при батче единица.

**GQA is the KV-cache win.** Та же 80-слойная модель на обычной MHA с 64 головами дала бы в 8 раз больше — 80 ГиБ на контексте 32K, то есть больше одной H100. MLA сжимает ещё сильнее.

> 🎒 **На пальцах.** Смотрите, где именно GQA экономит: в формуле выше стоит множитель 8 (KV-голов), а было бы 64. Получается 4 КБ на токен на слой вместо 32 КБ — ровно в восемь раз меньше, и те самые 10 ГиБ превратились бы в 80 ГиБ. Голов для query по-прежнему много, просто восемь query-голов делят один комплект ключей и значений. Это как 64 читателя на 8 экземпляров книги вместо 64 экземпляров.

### Flash Attention — the tiling trick

Стандартный attention:

```
S = Q @ K^T          (HBM read, N×N, HBM write)
P = softmax(S)       (HBM read, HBM write)
O = P @ V            (HBM read, HBM write)
```

Три похода в HBM туда-обратно. На H100 пропускная способность HBM — 3 ТБ/с; у SRAM — 30 ТБ/с. Каждый поход в HBM — это замедление в десять раз против «держим всё на чипе».

Flash Attention:

```
for each block of Q (tile size ~128 × 128):
    load Q_tile into SRAM
    for each block of K, V:
        load K_tile, V_tile into SRAM
        compute S_tile = Q_tile @ K_tile^T     (SRAM)
        running softmax aggregation             (SRAM)
        accumulate into O_tile                  (SRAM)
    write O_tile to HBM
```

Один поход в HBM на тайл. Общий объём занятой памяти падает с `O(N²)` до `O(N)`. Обратный проход пересчитывает часть значений прямого прохода вместо того, чтобы их хранить — ещё одна экономия памяти.

> 🎒 **На пальцах.** Аналогия со стройкой: HBM — склад на другом конце участка, SRAM — ящик с инструментом под рукой, и он в десять раз ближе. Наивный attention трижды гоняет всю матрицу N×N на склад и обратно. Flash берёт кусок 128×128, доводит его до готовности в ящике и относит на склад только результат. Матрица N×N целиком не существует ни одной секунды.

**Numerical trick.** Бегущий softmax тащит через тайлы пару `(max, sum)`, поэтому итоговая нормализация точна. Это не приближение — Flash Attention даёт побитово тот же выход, что и стандартный attention (с точностью до неассоциативности fp16).

> 🎒 **На пальцах.** Проблема в том, что softmax надо делить на сумму всех экспонент, а вы видите только один тайл за раз. Решение бухгалтерское: держим текущий максимум и текущую сумму, и когда в новом тайле встречается число больше прежнего максимума, старую сумму домножаем на `exp(старый_max - новый_max)`. Ровно эти две строчки вы увидите в коде ниже — `exp_old` и `s = s * exp_old + ...`.

**Version evolution:**

| Version | Year | Key change | Speedup on reference hardware |
|---------|------|-----------|-------------------------------|
| Flash 1 | 2022 | Tiled SRAM kernel | 2× on A100 |
| Flash 2 | 2023 | Better parallelism, causal-first ordering | 3× on A100 |
| Flash 3 | 2024 | Hopper asynchrony, FP8 | 1.5–2× on H100 (~740 TFLOPs FP16) |
| Flash 4 | 2026 | Blackwell 5-stage pipeline, software exp2 | Inference-first (forward only initially) |

Flash 4 на старте умеет только прямой проход. Обучение по-прежнему идёт на Flash 3. Поддержка GQA и varlen в Flash 4 ещё в работе (середина 2026).

> 🎒 **На пальцах.** Практический вывод из таблицы простой: сначала посмотрите, какая у вас карта, и только потом выбирайте версию. Flash 3 требует Hopper (H100), Flash 4 — Blackwell. На A100 максимум, что вам светит, — Flash 2 и его 3×. И не ставьте Flash 4 под обучение: без обратного прохода обучать нечем.

### Speculative decoding — the other latency win

Дешёвая модель предлагает N токенов. Большая модель проверяет все N параллельно. Если проверка приняла k токенов, вы заплатили один прямой проход большой модели за k сгенерированных токенов. Типичное k=3–5 на коде и прозе.

Дефолты 2026 года:
- **EAGLE 2 / Medusa.** Встроенные draft-головы, которые пользуются скрытыми состояниями проверяющей модели. Ускорение в 2–3 раза без потери качества.
- **Speculative decoding with draft model.** Ускорение в 2–4 раза на потребительском железе.
- **Lookahead decoding.** Итерация Якоби; draft-модель не нужна. Нишевая штука, но бесплатная.

> 🎒 **На пальцах.** Работает это потому, что проверить 5 токенов разом стоит почти столько же, сколько сгенерировать 1: узкое место — не арифметика, а прокачка весов модели через память. Аналогия — стажёр пишет черновик абзаца, а начальник читает его целиком за один заход и вычёркивает с первой ошибки. Приняли 4 слова из 5 — получили четырёхкратную скорость на одну зарплату начальника.

### Continuous batching

Классический батчевый инференс: ждём, пока закончится самая медленная последовательность, потом стартуем новый батч. GPU простаивает, когда короткие ответы завершаются раньше.

Continuous batching (впервые появился в Orca, теперь есть в vLLM, TensorRT-LLM, SGLang): подсовываем новые запросы в батч, как только старые заканчиваются. Прирост пропускной способности в 5–10 раз на типичных чат-нагрузках.

> 🎒 **На пальцах.** Батч из 8 запросов, где семь ответов по 50 токенов, а один — на 2000. При классической схеме семь слотов из восьми простаивают 1950 шагов подряд. Continuous batching сразу заводит на освободившееся место новый запрос — как касса в супермаркете, которая не ждёт, пока вся очередь рассосётся, чтобы начать обслуживать следующего.

### PagedAttention — KV cache as virtual memory

Главная фича vLLM. KV-кэш выделяется блоками по 16 токенов; таблица страниц отображает логические позиции в физические блоки. Это позволяет делить KV между параллельными сэмплами (beam search, параллельная генерация), горячо подменять префиксы для кэширования промптов и дефрагментировать память. Прирост пропускной способности в 4 раза против наивного непрерывного выделения.

> 🎒 **На пальцах.** Наивный подход резервирует память под максимальную длину сразу: ответ вышел на 100 токенов вместо забронированных 4096 — 97% выделенного пропало зря. PagedAttention выдаёт кусочки по 16 токенов по мере надобности, поэтому перерасход не больше 15 токенов на запрос. Это ровно та же идея, что виртуальная память в операционной системе, только вместо страниц по 4 КБ — блоки по 16 токенов.

## Build It

Смотрите `code/main.py`. Мы реализуем:

1. Наивный инкрементальный декодер на `O(N²)`.
2. Декодер с KV-кэшем на `O(N)`.
3. Тайловый softmax, повторяющий алгоритм бегущего максимума из Flash Attention.

### Step 1: KV cache

```python
class KVCache:
    def __init__(self, n_layers, n_heads, d_head):
        self.K = [[[] for _ in range(n_heads)] for _ in range(n_layers)]
        self.V = [[[] for _ in range(n_heads)] for _ in range(n_layers)]

    def append(self, layer, head, k, v):
        self.K[layer][head].append(k)
        self.V[layer][head].append(v)

    def read(self, layer, head):
        return self.K[layer][head], self.V[layer][head]
```

Всё просто: наращиваем потокенные векторы K и V в списках по слоям и головам.

> 🎒 **На пальцах.** Кэш здесь — обычный список списков, никакой магии. Сгенерировали 100 токенов на модели с 32 слоями и 32 головами — в `self.K` лежит 32 × 32 × 100 векторов. Метод `append` вызывается один раз на токен, `read` возвращает всё, что накопилось. Именно эта структура и превращает `O(N²)` в `O(N)`.

### Step 2: tiled softmax

```python
def tiled_softmax_dot(q, K, V, tile=4):
    """Flash-attention-style softmax(qK^T)V with running max/sum."""
    m = float("-inf")
    s = 0.0
    out = [0.0] * len(V[0])
    for start in range(0, len(K), tile):
        k_block = K[start:start + tile]
        v_block = V[start:start + tile]
        scores = [sum(qi * ki for qi, ki in zip(q, k)) for k in k_block]
        new_m = max(m, *scores)
        exp_old = math.exp(m - new_m) if m != float("-inf") else 0.0
        exp_new = [math.exp(sc - new_m) for sc in scores]
        s = s * exp_old + sum(exp_new)
        for j in range(len(out)):
            out[j] = out[j] * exp_old + sum(e * v[j] for e, v in zip(exp_new, v_block))
        m = new_m
    return [o / s for o in out]
```

Побитово тот же выход, что у `softmax(qK) V` в один заход, но в каждый момент рабочий набор — это блок `tile × d_head`, а не полный `N × d_head`.

> 🎒 **На пальцах.** Возьмите N=1000 и tile=4: вместо тысячи оценок в памяти живут четыре, то есть рабочий набор меньше в 250 раз. Строка `out[j] = out[j] * exp_old + ...` — это «пересчёт старого итога в новый масштаб»: если максимум подрос, всё накопленное раньше уменьшают на нужный множитель, и результат остаётся честным. Так же вы пересчитывали бы среднюю оценку, узнав, что часть работ оценивали по другой шкале.

### Step 3: compare naive vs cached decoding on 100-token generation

Считаем K/V-проекции — именно ту работу, которую кэш реально убирает. Без кэша каждый шаг заново выводит K и V для всего префикса: `1 + 2 + ... + 100` = `O(N²)` = 5050. С кэшем каждый шаг проецирует ровно один новый токен: `O(N)` = 100. Код печатает оба числа, плюс проверку, что оба декодера выдают идентичный выход.

(Работа по подсчёту *оценок* не меняется — query всё равно смотрит на весь префикс в обоих случаях. Кэш покупает вам K, V префикса и скрытые состояния за ними, а не сам attention.)

> 🎒 **На пальцах.** 5050 — это сумма 1+2+...+100, то есть точно `100 × 101 / 2`. Выигрыш в 50.5 раза, и он растёт с длиной: на 1000 токенах будет 500500 против 1000, то есть уже в 500 раз. Правило простое — экономия примерно равна половине длины ответа. Важно понимать, за что именно платят: attention на последнем шаге всё равно перебирает все 100 ключей — и с кэшем, и без. Разница в том, что без кэша эти 100 ключей приходится каждый раз заново *считать*, прогоняя весь префикс через слои модели, а с кэшем они просто лежат готовые. Скрипт печатает `naive 5050 / cached 100 / 50.5x`.

## Use It

```python
# HuggingFace transformers auto-enables KV cache on decoder-only generate().
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.2-3B",
    attn_implementation="flash_attention_2",  # use FA3 if Hopper
    torch_dtype="bfloat16",
)
# generate() uses KV cache automatically
```

Продакшен на vLLM:

```bash
pip install vllm
vllm serve meta-llama/Llama-3.1-70B-Instruct \
    --tensor-parallel-size 4 \
    --max-model-len 32768 \
    --enable-prefix-caching \
    --kv-cache-dtype fp8
```

Кэширование префиксов между запросами — большая победа 2026 года: один и тот же системный промпт, few-shot примеры или длинный документ переиспользуют KV между вызовами. Для агентных нагрузок с повторяющимися промптами инструментов кэширование префиксов регулярно даёт пятикратный рост пропускной способности.

> 🎒 **На пальцах.** Считаем на агенте: системный промпт с описанием инструментов на 3000 токенов, пользовательский вопрос на 50. Без кэша каждый вызов прогоняет 3050 токенов, с кэшем — 50, потому что KV для трёх тысяч уже лежит готовым. Флаг `--enable-prefix-caching` в команде выше включает ровно это. Флаг `--kv-cache-dtype fp8` рядом урезает сам кэш вдвое: 1 байт на число вместо 2.

Скопируйте (или пометьте только на чтение) состояние кэша после прохода по P, иначе первое же продолжение допишет свои токены в общий список, и второе стартует с загрязнённым префиксом. Ускорение считайте так: было `n × len(P)` проходов, стало `len(P)` — при пяти продолжениях и промпте на 500 токенов это 2500 против 500.

## Key Terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| KV cache | «Трюк, который ускоряет декодирование» | Сохранённые K и V всех префиксных токенов; новые query обращаются к ним вместо пересчёта. |
| HBM | «Основная память GPU» | High Bandwidth Memory; 80 ГБ на H100, 192 ГБ на B200. Пропускная способность около 3 ТБ/с. |
| SRAM | «Память на чипе» | Быстрая память внутри SM, около 256 КБ на SM у H100. Пропускная способность около 30 ТБ/с. |
| Flash Attention | «Тайловое ядро attention» | Считает attention, не материализуя матрицу N×N в HBM. |
| Continuous batching | «Батчинг без ожидания» | Завершённые последовательности уходят из батча, новые заходят, батч не осушается. |
| PagedAttention | «Главная фича vLLM» | KV-кэш выделяется блоками фиксированного размера с таблицей страниц; убирает фрагментацию. |
| Prefix caching | «Переиспользовать длинные промпты» | Кэшируем KV общего префикса между запросами; серьёзное удешевление для агентов. |
| Speculative decoding | «Черновик плюс проверка» | Дешёвая draft-модель предлагает токены; большая модель проверяет k штук за один проход. |
